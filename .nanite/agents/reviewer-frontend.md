# Reviewer Context — Nanite Frontend

> Loaded by `nanite-reviewer-frontend`. Project-specific priorities for deep code review of the Nanite React/TypeScript SPA. Pair with `~/.nanite/skills/deep-review.md` for the review procedure and the severity rubric.
>
> **Release context:** Nanite is preparing its first beta for developer friends. The frontend should feel stable, accessible, and fast in a developer's first 15 minutes. Prioritize **ship blockers and high-impact UX issues** over style nits. Biome and TypeScript's strict mode already handle most style concerns — don't re-flag what the tooling catches.
>
> **Companion docs** (read before reviewing):
> - `.nanite/agents/frontend.md` — general frontend context, stack, component inventory, antipatterns found, known gaps
> - `docs/frontend-punchlist.md` — ~60 post-beta UI polish items (DO NOT re-flag as findings; they're already tracked)
> - `docs/beta-known-issues.md` — canonical beta blocker list (backend-centric but check anyway)

## Stack snapshot

- **Framework:** React 19.2.0 + TypeScript ~5.9.3 (strict)
- **Build:** Vite 7.3.1 (dev port 5176, proxies `/api` → `localhost:8090`)
- **Styling:** Tailwind CSS 4.2.1 (dark zinc palette)
- **State:** Zustand 5.0.11 (4 stores) + React Query 5.90.21 (server state)
- **Editor:** TipTap 3.20.1 (rich text + slash commands)
- **Icons:** Lucide React
- **Linter:** Biome 2.4.7 (primary), ESLint (secondary)
- **Runtime embedding:** Go backend embeds built UI via `//go:embed` in `internal/server/ui_dist/`

## High-priority review targets

### 1. Chat transcript & SSE streaming

**Path:** `ui/src/hooks/useChat.ts`, `ui/src/components/chat/`

**Why it matters:**
- Core user-facing surface. Any regression breaks the product.
- SSE streaming + circuit breaker + session takeover + reconnection logic concentrate most of the complexity.
- Recent fixes (2026-04-10): `sendMessage` dep array reduced to 2 deps; Map mutations converted to immutable copies; jump-to-message plumbing added.

**Look hard at:**
- `useChat.ts` — SSE event handling, cleanup, race conditions in async effects. Look for stale closures in `useEffect`. Verify every `EventSource` has a cleanup in the effect's return function.
- `pendingJump` reactive effect — separate from the load-messages effect. Verify the races documented in `frontend.md` §Known Gaps are still properly handled (cross-session jump lands after messages-around fetch commits).
- `ChatTranscript.tsx` — `scrollToMessageId` with `requestAnimationFrame` retry loop (max 1s deadline). Check the deadline logic; an unbounded retry loop is a High finding.
- `ChatComposer.tsx` — TipTap slash commands. Check input sanitization for pasted HTML, drag-and-drop file handling, keyboard shortcut conflicts.
- `MessageContent.tsx` — markdown rendering + envelope dispatch. If `dangerouslySetInnerHTML` is used anywhere, it's a Critical unless the source is proven trusted.
- `ArtifactChip.tsx` — `[name](artifact:name)` markdown links. Verify the scheme handler can't be abused (`javascript:`, `data:`, etc.).

### 2. Envelope system & plugin rendering

**Path:** `ui/src/components/chat/envelopes/`, `ui/src/generated/plugin-envelopes.ts`, `ui/src/lib/plugin-slot-lookup.ts`

**Why it matters:**
- 25+ envelope card components. Plugin envelopes lazy-loaded via generated registry.
- `EnvelopeRenderer` dispatches by `envelope.type`. Unregistered types currently render via a catch-all — verify graceful fallback, not crash.
- Plugin slot resolution is INCOMPLETE per `frontend.md` §Known Gaps. No plugin registers a React component via `registerSlotComponent()`. Real plugins bypass with hardcoded AppShell mappings.

**Look hard at:**
- Every envelope card's prop validation — what happens with malformed `envelope.data`? Runtime validation (zod or handwritten guards) should exist at the API boundary; if it doesn't, flag as High.
- Lazy imports — each plugin envelope is code-split. Suspense boundaries and error boundaries must wrap them.
- `generated/plugin-envelopes.ts` — auto-generated by `scripts/generate-plugin-imports.mjs`. CI check is `node scripts/generate-plugin-imports.mjs --check`. Verify the pre-commit/pre-build hook is wired.
- `plugin-slot-lookup.ts` — 4-line shim that delegates to runtime `getDynamicSlotComponent()`. Today it always returns undefined (no runtime registrations exist). Verify all 3 call sites (`AppShell.tsx`, `RightRail.tsx`, `SettingsPage.tsx`) handle undefined gracefully. This is already documented as working; don't re-flag the gap itself.

### 3. State stores (Zustand)

**Path:** `ui/src/stores/`

**Why it matters:**
- `useChatStore`, `useAppStore`, `useLayoutStore`, `useSprintPlanningStore`. `useChatStore` is the most complex — Maps for presence, circuit breaker state, streaming content.
- Recent fix: Maps now create immutable `new Map()` copies for mutations. Any new `.set()` without a new Map is a regression.

**Look hard at:**
- Map mutation pattern — every `set((state) => …)` that touches `activeStreams`, `pendingTools`, `cliActiveSessions` must create a new Map. A direct `state.activeStreams.set(…)` return is a Medium finding (stale references for consumers).
- `useLayoutStore` persistence — `nanite-layout` key in localStorage. Backward compatibility if the shape changes.
- Store hydration order — does any component read store state before the store has loaded from localStorage?
- Selector granularity — any component using `useChatStore()` without a selector re-renders on every store change. Hot components should use fine-grained selectors.

### 4. API client & data fetching

**Path:** `ui/src/lib/api.ts`, `ui/src/lib/types.ts`

**Why it matters:**
- 50+ endpoints. Fetch-based REST client. Type definitions shared across the app.
- 500+ lines of TypeScript interfaces. Drift between backend and frontend types is a real risk.

**Look hard at:**
- `any` usage — every occurrence is a finding. `as Foo` assertions without validation are findings.
- Error handling pattern: the `!res.ok` block is consistent; verify no endpoint bypasses it.
- Request body typing — anonymous inline types vs. named interfaces. Named interfaces in `types.ts` are preferred.
- Response parsing — any endpoint that doesn't validate its response shape against TypeScript types is silently trusting the backend. Runtime validation at API boundaries (zod or similar) is preferred for anything user-facing.
- Dead endpoints — recent fix removed `listAgentProfiles()`. Look for other unused exports.

### 5. Plugin settings & dynamic forms

**Path:** `ui/src/components/settings/PluginConfigPanel.tsx`, `ui/src/components/settings/PluginManager.tsx`, `ui/src/components/settings/WidgetManager.tsx`

**Why it matters:**
- Plugin config forms render from backend-provided schemas. 5 field types: string, bool, int, select, secret.
- Override components are gated behind `developer_mode`; `recover_mode` strips plugin rendering entirely.
- `secret` field type needs extra care — values must never appear in logs, error messages, or DOM attributes.

**Look hard at:**
- `secret` field rendering — masked input? Memory clearing on unmount? No `console.log` of values. No DOM attributes exposing them.
- Developer mode / recover mode toggles — verify the gating actually blocks what it claims to block. PluginConfigPanel must skip component overrides in recover mode; EnvelopeRenderer must use core-only registry; PluginWidgets must hide.
- Dynamic component resolution — `generated/plugin-config-components.ts` registry. Lazy imports with Suspense.
- Widget drag-drop — `@dnd-kit`. Accessibility: keyboard reorder support is non-obvious; check it works.

### 6. Observability & process health

**Path:** `ui/src/components/settings/observability/`, `ui/src/components/settings/ToolDashboard.tsx`

**Why it matters:**
- Surfaces stale CLI processes, utility call logs, execution stats. "Kill Stale" button is a privileged action.

**Look hard at:**
- `ProcessHealthPanel.tsx` — `POST /api/processes/kill-stale`. Confirmation dialog? Idempotent retry? Error feedback?
- `UtilityLogTable.tsx` — table pagination, sort, filter. Large logs should not block the render thread.
- Chart.js integration — lazy-loaded? Bundle size impact?

### 7. Settings & provider management

**Path:** `ui/src/components/settings/SettingsPage.tsx`, `ProviderManager.tsx`, `PreferencesPanel.tsx`

**Why it matters:**
- API keys stored in OS keychain. CLI paths user-editable. Toggle locked until requirements met.
- `secret` fields across settings — same concerns as plugin config.

**Look hard at:**
- API key inputs — masked, not logged, not in React DevTools with readable values.
- CLI path validation — path traversal via manual override? Race between detection and save?
- Provider toggle lock — verify the requirements check is sound; a user shouldn't be able to enable a provider without valid credentials.

### 8. Keyboard shortcuts & accessibility

**Path:** `ui/src/hooks/useKeyboardShortcuts.ts`, `ui/src/components/modals/`, `ui/src/components/drawers/`

**Why it matters:**
- 9+ keyboard shortcuts documented. Plugin-registered bindings merged in.
- Modals and drawers need focus management, Esc to close, Tab trap.

**Look hard at:**
- Focus trap in modals — when a modal opens, focus goes in; when it closes, focus returns to the trigger.
- `Esc` key handling — consistent across drawers, modals, popovers.
- `Cmd+K` / `Cmd+B` / etc. — no conflicts with browser defaults for non-macOS users. Stretch: are these also bound with `Ctrl+` for Windows/Linux users running the SPA in a browser?
- ARIA labels on icon-only buttons — Lucide icon buttons without text need `aria-label`.
- Tab order in `SettingsPage.tsx` — multi-tab settings need logical Tab order.
- Color contrast — zinc palette dark theme. WCAG AA for body text. `text-zinc-500` on `bg-zinc-950` is borderline.

## Trust boundaries — enumerate for any security pass

1. **User input in composer** — free-form text. Any unvalidated echo into markdown/HTML is an XSS risk.
2. **Backend API responses** — TypeScript types are not runtime validation. A compromised backend (or a type drift) can inject bad data into the DOM.
3. **Plugin envelope data** — backend forwards plugin-generated content. Same concern: any `dangerouslySetInnerHTML` path fed from envelope data is Critical unless the upstream is proven trusted.
4. **Artifact URLs** — `[name](artifact:name)` scheme. Custom schemes in markdown links need sanitization.
5. **localStorage persistence** — `nanite-layout`, `nanite:toolCallDisplayMode`. Do NOT persist tokens, API keys, or user PII here.
6. **Clipboard / drag-and-drop** — pasted HTML into TipTap editor, dropped files in composer. Pasted rich content should be sanitized.
7. **Embedded markdown / code blocks** — highlight.js for syntax highlighting. Verify it uses safe rendering (no eval of language strings).

## Nanite-specific patterns to protect

These are already established and working. Don't regress them. Don't propose replacing them unless the scope is "architecture review" and you have strong justification.

- **React Query with 1min staleTime, 1 retry** — consistent across all useQuery calls.
- **Immutable Zustand Map mutations** — new Map per set.
- **Centralized SSE event name constants** in `lib/sse-events.ts` — do NOT reintroduce magic strings.
- **CVA-based Button variants** — match the existing pattern for any new variant-bearing component.
- **Tailwind utility classes, no inline CSS, no CSS modules, no styled-components.**
- **`cn()` utility** from `lib/utils.ts` for conditional classes.
- **Path alias `@/`** maps to `src/`. Use it.
- **Zustand for client state, React Query for server state** — don't mix.

## How to run this review

When `nanite-reviewer-frontend` is booted with a scope:

1. Read this file. Note the high-priority targets and the no-flag list.
2. Read `.nanite/agents/frontend.md` for stack details, component inventory, established patterns, and known gaps.
3. Invoke the `deep-review` skill with the scope.
4. Collect tooling evidence:
   - `npm run lint` (Biome check) — always
   - `tsc -b --noEmit` — type check
   - `npm audit` — for the security category
   - `npm run build` — verify it still builds (the go:embed step depends on this)
   - Manual traversal with browser DevTools for performance / a11y claims
5. Write findings to `docs/audits/<date>-<slug>/` per the skill's output contract.
6. Return the one-line confirmation. Do NOT dump findings into the chat.

## Reviewer guardrails

- **Do not fix code.** Review only.
- **Do not re-flag the frontend punchlist.** It's ~60 polish items and they're already tracked.
- **Do not re-flag the known gaps.** They need a design decision, not a review finding.
- **Release context is "first beta for developer friends."** Focus on crashes, data loss, confusing errors, broken flows. Cosmetic nits are Low or Info.
- **Accessibility matters.** A modal without focus management is High, not Low, because it breaks keyboard users entirely.
- **Performance claims need profiler evidence.** Don't flag "unnecessary re-render" without a React DevTools Profiler trace. "Looks suspicious" is not a finding.
- **Type safety regressions are High.** Every new `any` or `as` is a step back.
