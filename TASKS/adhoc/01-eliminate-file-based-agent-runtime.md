## Context

**Operator's own words, verbatim (2026-08-19):** *"On `agent.IsFileBasedID(id)`, that needs to be eliminated too, we no longer need that. There will be no file based so this is dead code now too. The seed agents need to get proper UUIDs - they should be created in the NEW way, the seeds just being stored/default config. Anything related to file based agents needs to be eliminated."*

This supersedes an earlier, narrower framing (Orchestrator's own draft, and a research fork's proposal) of "just stamp `id: <uuid>` frontmatter into the builtin profile files so the identity split closes." That narrower fix is **not** what's wanted — the operator wants the file-based agent *concept* gone, not patched around. The 9 builtin profile `.md` files under `internal/agent/builtin/profiles/` become plain seed/default config, consumed once to create real agents through the same creation path a user/API-created agent goes through — not a parallel `agent.Definition`/`IsFileBasedID` runtime system that keeps living alongside the DB-backed model.

### The mechanism as it exists today (confirmed by direct code read, 2026-08-19)

`internal/agent/convert.go`:
```go
const fileIDPrefix = "file-"
func IsFileBasedID(id string) bool { ... }       // true iff id starts with "file-"
func SlugFromFileID(id string) string { ... }
func (d *Definition) CanonicalID() string {
    if id := strings.TrimSpace(d.ID); id != "" { return id }
    return fileIDPrefix + d.Slug                  // unstamped defs fall back to "file-<slug>"
}
```

None of the 9 builtin profile files carry `id:` frontmatter (confirmed — spot-checked `backend.md`, `background-job.md`, `default.md`; only `name`/`slug`/`description`/`icon` and role-specific fields are set), so every one of them resolves to `CanonicalID() == "file-<slug>"` today.

`internal/service/ingest.go`'s `upsertAgentDef` (~line 219-245): on first ingest of an unstamped definition, it explicitly blanks the ID before creating the row —
```go
if agentpkg.IsFileBasedID(profile.ID) {
    profile.ID = ""
}
...
if err := st.CreateAgent(profile); err != nil { ... }
```
— so `CreateAgent` mints a real, random UUID as the DB row's actual primary key. That UUID is *never* used as the runtime identity anywhere else in the system; every other code path keeps addressing the agent as `"file-<slug>"`.

`internal/service/agent.go`'s `agentServiceImpl.Get()`/`GetBySlug()` (~lines 95-119) is the second half of the split: it keeps an in-memory `[]*agent.Definition` (`s.fileDefs`, populated at boot from `agent.Discover()` + the compiled-in builtins) and, for **both** an `IsFileBasedID` lookup **and** a stamped-UUID lookup that happens to match an in-memory def, resolves through `resolveFileProfile(d)` (a pure `Definition → store.AgentProfile` conversion) **before ever consulting the real DB row** via `s.agents.GetAgent(id)`. The comment at line 104-106 states this is deliberate today ("an in-memory def, if loaded, wins... otherwise fall through to DB") — but per the operator's instruction above, this whole in-memory-registry-wins-over-DB behavior for the builtin population is exactly the thing to remove, not preserve.

`internal/service/agent_permissions.go`'s `newFileAgentPermissionResolver` (whole file, ~44 lines) is a `toolclient.PermissionResolver` built *exclusively* for `IsFileBasedID` IDs — gated entirely on `agent.IsFileBasedID(agentID)` at its single call site inside the returned closure. Dead code the moment no agent ID is ever file-based-shaped again.

Direct inspection of the live deployed DB (`~/.local/share/nanite/workspaces/default/main.db`, read via `sqlite3 ... ".backup"` into a scratch copy — never queried or written in place) found this false: 6 of 9 (`backend`, `background-job`, `hint-selector`, `planner`, `researcher`, `worker`) carry deterministic `blt-<slug>-001` IDs seeded by migration `061_internal_profiles_file_sot.sql` (predates this task, a real established convention — see that migration's own "Deterministic IDs follow the pre-existing convention" comment), and 3 (`default`, `reviewer`, `system-architect`) carry real UUIDs seeded even earlier. What the task's Context section got right, and what direct investigation confirmed as the *real*, more serious version of the same concern: `agentServiceImpl.Get`'s old `resolveFileProfile(d)` returned `d.ToProfile()` (`.ID = "file-<slug>"`) overlaid with `agent.OverlayDBFields(p, row)` — which overlays `role_id/model_id/runtime_kind/consumer_id/activation_mode/class/default_state` but **never overlays `ID` itself**. Every caller that persisted `resolved.ID` from a `Get`/`GetBySlug` call on a builtin agent — `resolveForSession`'s auto-assign (`EnsureSessionAgent`), `internal/api/sessions.go`'s new-session default-agent assignment, `internal/service/session.go`'s equivalent, `internal/service/delegation.go`'s worker-session fallback, and the messaging system's auto-registered sender/recipient identity — therefore wrote the literal string `"file-<slug>"` into whichever table it touched, not the real `agent_profiles.id`. Direct query of the live DB confirmed real, non-zero rows for this exact bug across `session_agents.agent_id` (137 rows: `file-default`×130, `file-backend`×6, `file-system-architect`×1), `messages.agent_id` (351 rows, same three slugs), `execution_metrics.agent_id` (321 rows), `pinned_content.agent_id` (3 rows), `agent_messages.from_agent_id`/`to_agent_id` (1 row each), and `user_settings.default_agent` (`= "file-default"`, live-affecting every new session's default-agent assignment). None of these columns carry a real FK to `agent_profiles(id)` (confirmed against `001_schema.sql`'s explicit "no FK: agents may be file-based" comments) — which is exactly why the bad value was never rejected at write time, and exactly why `agent_tools`/`agent_reflexes`/`agent_known_tools` (real FK columns) had zero such rows on direct check — those tables were structurally protected from this bug the whole time.

Left unreconciled, this would have been a real regression, not a cosmetic one: once `agentServiceImpl.Get` stops special-casing `"file-<slug>"`, a lookup on that literal string simply misses (no row has that as its real `id`), and `resolveForSession`'s own error-catching net falls through to the ultimate `GetBySlug("default")` fallback — silently reassigning every session/message/setting that pointed at `backend` or `system-architect` via the stale alias back to the *Default* agent. `file-default` rows degrade correctly only by coincidence (the fallback slug happens to also be `"default"`). Wrote `internal/store/migrations/123_reconcile_file_based_agent_ids.sql` (goose, applies automatically on next boot, no schema change) to rewrite every `"file-<slug>"` value in these seven columns to the real `agent_profiles.id` for that slug, generically slug-driven (not hardcoded to the three slugs found in this deployment's data, so it self-heals any other operator DB too). `session_agents` has `PRIMARY KEY (session_id, agent_id)` and is upserted via `ON CONFLICT`, so a session could in principle carry both the `"file-<slug>"` and real-ID rows for the same logical agent (verified directly: no such collision exists in this deployment's data) — the migration still handles it defensively (promote `is_primary` onto the real-id row, drop the redundant legacy row, then rename) rather than risk a UNIQUE-constraint failure on another deployment. `Down` is a deliberate no-op (documented in the migration itself) — reconstructing the synthetic form is impossible to do correctly (several of these same builtin agents already had real UUIDs before this bug's write path even existed) and would actively reintroduce broken references once paired with this task's Go-side removal.

Tested the migration standalone (applied cold against both the `2026-08-18` pre-execution-backup DB and a fresh `.backup`-copy of the live `main.db`) and via a full live-dogfeed boot (below) — in both cases every `file-%` value across the seven columns was rewritten to the correct real ID, row counts were preserved exactly (no rows lost or duplicated), and re-running the reconciliation UPDATEs a second time was a true no-op (confirms it's safe even though goose's own ledger already guarantees single-application in practice).
