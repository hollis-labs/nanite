# Move self-tool definitions and dispatch to `internal/selftools`

**Phase:** 1 — Core mechanism (`TASKS/harness-reactive-self-tools`)
**Status:** implemented
**Depends on:** none
**Touches:** `internal/mcp/self_tools_transport.go` and the 15 sibling `internal/mcp/self_tools_*.go` files that add methods to `SelfToolsTransport` (full move to a new `internal/selftools` package, including their `_test.go` counterparts); `cmd/nanite/main.go` (`initMCP`'s `mcp.NewSelfToolsTransport(s)` call and every `selfTools.<Field> = ...` wiring line, ~30 lines around `main.go:889-914`); `internal/mcp/naming.go` (only if `IsReservedSelfToolName` or similar needs to move — investigate first, see step 3); `docs/tool-naming-convention.md` (its "Do not add MCP-origin tools to this namespace... add it to `internal/mcp/self_tools.go`" line, `docs/tool-naming-convention.md:103`, names a file that doesn't exist under that name today and won't exist under `internal/mcp` at all after this move).

## Context

`docs/engineering/architecture/11-harness-reactive-self-tools.md`'s "Where it lives: `internal/selftools`" section is the design. Confirmed directly against this checkout (not assumed) before writing this task:

- `SelfToolsTransport` (`internal/mcp/self_tools_transport.go:90`) is a single struct with `ListTools` (`:390`) and `CallTool` (`:404`) methods satisfying whatever `Transport` shape `mcp.Manager.AddBuiltinServer` expects. 16 files in `internal/mcp` currently add methods to it or declare the struct itself: `self_tools_transport.go`, `self_tools_agent_source.go`, `self_tools_chat_search.go`, `self_tools_describe.go`, `self_tools_dispatch_executor.go`, `self_tools_dispatch.go`, `self_tools_handoff.go`, `self_tools_list.go`, `self_tools_panels.go`, `self_tools_procedure.go`, `self_tools_remember.go`, `self_tools_reminders_pins.go`, `self_tools_validate.go`, `self_tools_whoami.go`, `self_tools_workflow_run.go`, `self_tools_workflow.go` (`grep -l "func (st \*SelfToolsTransport)\|type SelfToolsTransport struct" internal/mcp/*.go`) — re-run that grep before starting, since more may have landed since this task was authored, and cross-check against each file's own `_test.go` counterpart (e.g. `self_tools_dispatch_audit_test.go`, `self_tools_dispatch_cooldown_test.go`, `self_tools_dispatch_executor_test.go`, `self_tools_dispatch_multi_candidate_canary_test.go`, `self_tools_dispatch_test_helpers_test.go`, `self_tools_handoff_test.go`, `self_tools_list_test.go`, `self_tools_panels_test.go`, `self_tools_procedure_test.go`, `self_tools_agent_editable_test.go`, `self_tools_agent_source_test.go`, `self_tools_chat_get_test.go`, `self_tools_chat_search_test.go`, `self_tools_describe_test.go`, `self_tools_describer_test.go`) which also move.
- `SelfToolsTransport`'s own field list (`internal/mcp/self_tools_transport.go:90` onward) already imports `internal/messaging`, `internal/subagent`, `internal/background`, `internal/dispatch` (the `dispatch.Spawner`/`dispatch.EnvelopeWrapper`/`dispatch.WorkflowLauncher` types, not to be confused with this design's own `internal/selftools/reactions` engine — different `dispatch` package, don't conflate the two), `internal/broker`, `internal/agentworkflow`, `internal/builders`, `internal/executor/envelope_render`, and `internal/store`. None of these import `internal/chat` or `internal/service` — confirmed directly, matching the design doc's claim that the constrained side of the import graph (`internal/mcp`/`internal/selftools` can't import `internal/chat`/`internal/service`, because both already import `internal/mcp`) isn't violated by this move.
- The wire-level `Tool`/`ToolResult` types live in `internal/mcp/http_transport.go:38` and `:45` — general MCP transport types, not self-tools-specific. These **stay in `internal/mcp`**; `internal/selftools` imports them from there. This is the one real new import edge this move introduces: `internal/selftools` → `internal/mcp`. Confirmed one-directional and safe — `internal/mcp` (the package, not `main.go`) never needs to import `internal/selftools` back. The actual registration call, `mcpManager.AddBuiltinServer(mcp.SelfServerName, selfTools)` (`cmd/nanite/main.go:914`), lives in `main.go`, which already imports both packages — `internal/mcp` itself has no `internal/selftools` import to add.
- `docs/tool-naming-convention.md:95-103` ("The `nanite_*` reserved namespace") already treats self-tools as their own concept distinct from MCP, and already (inaccurately, as of this task's authoring) points at a nonexistent `internal/mcp/self_tools.go`. Update this pointer to `internal/selftools` as part of this move — a one-line doc fix, in scope since this task is exactly what makes that line accurate for the first time.

## What to do

1. Create the new top-level package `internal/selftools`. Move the 16 non-test files enumerated above (re-verify the list first) and their `_test.go` counterparts into it, updating each file's `package mcp` declaration to `package selftools`.
2. Fix every resulting compile break from the package rename:
   - Files remaining in `internal/mcp` that referenced `SelfToolsTransport`-adjacent symbols now moved out (e.g. `naming.go`'s reserved-namespace check, if it referenced anything self-tools-specific beyond a plain string constant — investigate; if it only ever compared against a literal `"nanite_"` prefix string, it needs no change and stays in `internal/mcp`, since reserved-namespace defense is a Manager/registration-layer concern, not a self-tools-package concern).
   - `internal/selftools`'s new files referencing `mcp.Tool`, `mcp.ToolResult`, `mcp.SelfServerName`, or any other type/constant that legitimately stays in `internal/mcp` — add the `internal/mcp` import and qualify (`mcp.Tool` etc.).
   - `cmd/nanite/main.go`: `mcp.NewSelfToolsTransport(s)` (`:889`) becomes `selftools.NewSelfToolsTransport(s)` (new import), and the resulting value's type at every `selfTools.<Field> = ...` wiring line (`:907-590`+) is now `*selftools.SelfToolsTransport` — Go's type inference handles most of this transparently via the local `selfTools` variable, but double-check any place elsewhere in the codebase that declares a variable of type `*mcp.SelfToolsTransport` explicitly (grep for it) rather than relying on inference.
3. Any other real caller of `mcp.SelfToolsTransport`/`mcp.NewSelfToolsTransport` outside `main.go` (grep the whole tree, including tests) — update the same way. Do not assume `main.go` is the only call site without checking.
4. Update `docs/tool-naming-convention.md:103`'s "add it to `internal/mcp/self_tools.go`" line to point at `internal/selftools` instead.
5. This is a pure move — **no behavior change**. Do not refactor, rename methods, reorganize the file split, or change any tool's `Name`/`Description`/`InputSchema` while moving it. If you spot something worth cleaning up along the way, note it in this file's Work Log as a follow-up candidate rather than doing it inline (matches this project's `EXECUTION-PROCESS.md` fix-as-new-worker-task discipline for anything beyond this task's own scope).

## Work log

**Re-verification of the file inventory (step 0, before touching anything).** Re-ran `grep -l "func (st \*SelfToolsTransport)\|type SelfToolsTransport struct" internal/mcp/*.go` — confirmed the same 16 files the task names. But that grep pattern only catches files declaring the struct or adding *methods* to it; it does not catch files that are just as much "self-tools" by content and by filename convention but only contain free functions or type/const declarations. Cross-checking every `internal/mcp/self_tools_*.go` file (not just the ones matching that grep) turned up three more non-test files the task's own inventory missed:

- `internal/mcp/self_tools.go` (1206 lines) — the actual static tool-definition slice (`selfToolDefinitions()`, `SelfToolProviderDefinitions()`) the design doc's own "large static Go slice" language refers to. `self_tools_list.go`, `self_tools_describe.go`, and `self_tools_transport.go` (all three in the original 16) call `selfToolDefinitions()` unqualified — since it's unexported, leaving this file behind would have made the move not compile at all, not just be incomplete.
- `internal/mcp/self_tools_describer.go` — `RegisterSelfToolDescribers`, the per-call description-render hook for `task_execute`/`tool_list`/`skill_list`. Self-tools-specific; called from `cmd/nanite/main.go` and `internal/service/tool_parent_dispatch_allowlist_test.go`.
- `internal/mcp/self_tools_python.go` — `RunPythonSandbox` and `naniteRunPythonToolDefinition()`, the `python_run` self-tool's sandbox implementation. Self-contained (only `self_tools_transport.go` calls into it).

And a fourth, more surprising one: `internal/mcp/elicitation_pilot_test.go` — filename doesn't match the `self_tools_*` pattern at all, but its entire content (`TestPilotTool_DirectiveRequiresElicitation` etc.) drives `SelfToolsTransport.CallTool("message_send", ...)` end-to-end through `newSelfTools(t)`. This one only surfaced as a `go vet` "undefined: newTestStore" failure after the main move compiled — grep alone wouldn't have found it since it names neither `SelfToolsTransport` as a type nor adds a method to it.

Also moved: `internal/mcp/examples/` (68 golden-example JSON files), embedded via `self_tools_describe.go`'s `//go:embed examples/*.json` — a relative-to-file-location embed directive, so it silently breaks (`go build` error: "pattern examples/*.json: no matching files found") if the code moves without the directory. Confirmed via `grep` that nothing outside `self_tools_describe.go` references this directory, so the whole thing moved with the code, no split needed.

Net effect: **47 files** in `internal/selftools` (19 non-test + 28 test, vs. the task's estimated 16+15), plus the `examples/` directory — all still a pure move; the extra files are corrections to an undercounted inventory, not scope creep.

Stayed in `internal/mcp`.

**Mechanical exports required in `internal/mcp` to keep the split compiling (necessary consequence of the move, not a refactor of behavior):** several `internal/mcp` helpers the self-tools files called unqualified (legal when same-package, impossible once split) were unexported and had no other legitimate home — they're genuinely general MCP-transport infrastructure (used by `dev_tools.go`/`code_exec_tools.go`/`general_tools.go` too, or, for the elicitation ones, by both self-tools and remote-MCP-server elicitation), so they stay in `internal/mcp` and get exported rather than duplicated:
- `errorResult`→`ErrorResult`, `textResult`→`TextResult`, `intArg`→`IntArg` (`internal/mcp/dev_tools.go`) — shared by every in-process builtin transport, self included.
- `elicitUserInput`→`ElicitUserInput`, `elicitationCreateParams`→`ElicitationCreateParams`, `elicitationRequestedSchema`→`ElicitationRequestedSchema` (`internal/mcp/elicitation.go`) — `message_send kind=directive`'s elicitation gate is self-tools' only caller of the server-side half of this file; the client-side half (remote-MCP-server elicitation) stays used only within `internal/mcp`.
- `tool_ctx.go`'s `WithSessionID`/`SessionIDFromContext`/`WithCallerProfile`/`CallerProfileFromContext`/`WithTurnToolUseIDs`/`TurnToolUseIDsFromContext`/`WithTurnToolNames`/`TurnToolNamesFromContext` were already exported and stayed in `internal/mcp` unchanged — confirmed this file is genuinely general (its own doc comment: "the mcp package... avoids a circular import while... the service layer stamp[s] the ctx... before handing off to tool execution"; `internal/service/chat_tool_executor.go` calls `mcp.WithTurnToolUseIDs` directly, independent of self-tools). Self-tools files now reference these as `mcp.WithTurnToolUseIDs(...)` etc.

All ~470 resulting `mcp.`-qualification call sites across the moved files were done via a small AST-adjacent script (not a blind find/replace) that tracks Go string/rune/raw-string/comment spans char-by-char and only rewrites identifier occurrences outside those spans, with an additional negative-lookbehind excluding anything preceded by `.` (to leave real selector expressions like `req.Tool` — an `agentworkflow.ToolStepRequest` field, unrelated to `mcp.Tool` — untouched). Verified by hand against the two highest-risk cases found in `self_tools_workflow.go`: three `"description": "Tool name to call."`-style string literals (self-tool input-schema prose) and the one `req.Tool` selector both survived byte-for-byte unmodified; a blind regex would have corrupted the former.

Gave the moved file its own minimal copy (elicit-only; the original's unused-here `respondFn`/`RespondFromEnvelopeData` branches were dropped as dead weight for this file, not carried over as unused code) rather than exporting the original for a single external caller.

**`internal/selftools` needed its own `TestMain`.** `internal/mcp/main_test.go`'s `TestMain` (`envelope.SetupForTesting()` + `goleak.VerifyTestMain`) covered the self-tools tests for free when they were still part of the same package/test-binary; splitting the package means splitting the test binary too.
