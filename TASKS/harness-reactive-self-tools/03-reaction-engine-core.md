# Reaction engine core — `internal/selftools/reactions.Fire`

**Phase:** 1 — Core mechanism (`TASKS/harness-reactive-self-tools`)
**Status:** implemented
**Depends on:** `01-move-self-tools-to-internal-selftools.md` (the `internal/selftools` package must exist to host this sub-package), `02-reactive-layer-schema.md` (needs `ListEnabledSelftoolReactions` and the two new tables).
**Touches:** new package `internal/selftools/reactions` (new files — a `Fire` entry point, an `internal_api_call` executor, a `render_card` resolver stub wired to `04`), `internal/store/selftool_reactions.go` (read-only consumer, no changes expected beyond what `02` already built).

## Context

`docs/engineering/architecture/11-harness-reactive-self-tools.md`'s "Where it lives" and "The import-cycle constraint" sections are the design. This is the task that actually builds `internal/selftools/reactions` — read both sections in full before starting, plus `TASKS/reflex-taxonomy/07-harness-reactive-self-tools-design-session.md`'s decision 4 (naming: `reactions`, not `react`/`action`) and decision 5/6 (why the four reaction kinds split into two structurally different execution shapes).

**Package naming, already decided, do not revisit:** `internal/selftools/reactions`, not `internal/selftools/react` or `internal/selftools/action`. `action` is already heavily claimed one level over by `internal/agent/reflexes` (`action_kind`, `execute_action`, `Executor.Apply`) — reusing it here reintroduces the exact vocabulary collision `docs/engineering/GLOSSARY.md`'s "Self-tool reaction" entry exists to prevent.

**The execution-shape split, confirmed against the real import graph (re-verify, don't assume it's still true if significant time has passed since this task was authored):**

- `internal_api_call` needs no live UI delivery — it executes fully synchronously inside `internal/selftools/reactions` via a plain HTTP client call. No cycle problem: `net/http` has no opinion about `internal/chat`/`internal/service`.
- `external_api_call` and `callback` are seeded (`02`) but **not executable in this batch** (`implemented=false`) — this task's `Fire()` must recognize them, skip execution, and emit a clear log/telemetry signal that a configured-but-unimplemented reaction kind was found enabled (should not normally happen, since nothing seeds them as enabled in this batch, but `Fire()` must not silently pretend they fired if a future operator enables one by hand before the execution code exists).
- `render_card` **cannot execute inside this engine** — it needs to reach the SSE/streaming layer, which sits above `internal/selftools`. `internal/mcp`/`internal/selftools` cannot import `internal/chat` or `internal/service` (both already import `internal/mcp` — confirmed directly against the import graph by the design session, re-confirm via `go list -deps` or equivalent if in doubt). `Fire()`'s job for this kind is to **resolve** the envelope payload (JSON) and return it in its result, not to deliver it — delivery (building the actual `<!--ENVELOPE_DATA:...-->` marker string and embedding it in the tool's `ToolResult`) is `04-render-card-construction.md`'s job, done by the calling self-tool handler, which already sits in `internal/selftools` (same package as every other self-tool handler) and already returns `*mcp.ToolResult` today.

**Halt precedent, already independently re-verified by the design session (`TASKS/reflex-taxonomy/07-harness-reactive-self-tools-design-session.md` decision 6) — do not re-litigate, just apply the shape:** the constrained engine does only what it can reach (here: `internal/store` reads/writes plus outbound HTTP for `internal_api_call`); the actual "reach the live UI" side effect happens one layer up, in a caller with an unconstrained view. `internal/agent/reflexes/resolve.go`'s `Resolve()` → `chat_generate.go`'s halt-abort is the precedent this design explicitly follows.

## What to do

1. **`Fire(ctx context.Context, toolName string, payload map[string]any) (Result, error)`** — the entry point every harness-reactive self-tool handler calls after doing its own (thin) work. Looks up `store.ListEnabledSelftoolReactions(ctx, toolName)`, and for each enabled row:
   - Looks up the row's `reaction_kind_id` against `selftool_reaction_kinds` to get `category`/`implemented`.
   - If `implemented=false`: skip execution, record it in the result as skipped (do not error the whole `Fire()` call — one misconfigured/future-kind reaction shouldn't block the others).
   - If kind is `internal_api_call`: execute it (step 2).
   - If kind is `render_card`: resolve it (step 3) and include the resolved payload in the returned `Result`, do not attempt delivery.
   - If kind is `external_api_call` or `callback`: per the `implemented=false` seed from `02`, these should never reach this branch in practice — but code the branch defensively (log + skip, matching the general `implemented=false` handling) rather than assuming it's unreachable.
   - Every attempted-and-implemented reaction (success or failure) needs a trace record — but **do not build the telemetry write in this task**; that's `05-selftool-reaction-telemetry.md`, sequenced right after this one specifically so `Fire()`'s return shape (`Result`) carries everything `05` needs (tool name, reaction kind, config used, success/error) without `05` having to change `Fire()`'s signature. Design `Result` with that consumer in mind now.
2. **`internal_api_call` execution** — a minimal, illustrative implementation matching the worked example's own illustrative config shape (`docs/engineering/architecture/11-harness-reactive-self-tools.md`'s worked-example section: `{endpoint, method, body_template}`). Build the request body by substituting `payload`'s fields into `body_template` (simple `{{key}}` string substitution is sufficient — this is explicitly not asked to handle nested templating, auth, retries, or idempotency; see this folder's README, "What this batch does NOT do"). Issue the HTTP call against `endpoint` (same-process, so a plain `http://localhost:<port>` or an internal handler call — pick whichever is simpler given how this service's own HTTP server is wired, and document the choice). Treat a non-2xx response as a failed (not fatal) reaction — logged, included as an error in the per-reaction result, doesn't stop other reactions from firing.
3. **`render_card` resolution** — given the row's `config` (`{envelope_type, template}` per the worked example) and the caller's `payload`, substitute `payload`'s fields into `template` the same way as step 2, marshal to JSON, and return it in the `Result` (do not build the `<!--ENVELOPE_DATA:...-->` marker string here — that's `04`'s job, in the calling self-tool handler, not this engine). Keep this function's signature narrow and pure (config + payload in, JSON out, no side effects) so `04` can call it directly without needing anything else from this package.
4. Wire `Fire()`'s `TraceStore`-shaped dependency (the narrow store interface it actually needs — `ListEnabledSelftoolReactions` plus whatever `05` will need) the same way `internal/agent/reflexes/telemetry.go`'s `TraceStore` interface narrows its own dependency surface (`internal/agent/reflexes/telemetry.go:56-60`) — don't take a full `*store.Store` parameter if a two-or-three-method interface is sufficient; keeps this package's dependency surface exactly what it needs, matching the precedent this design explicitly follows.

## Done means

- `internal/selftools/reactions.Fire` exists, handles all four reaction kinds per the branching above (two executed, two defensively skipped), and returns a `Result` shape `05` can consume without changing `Fire()`'s signature.
- A regression test proves: a tool with one enabled `render_card` reaction and one enabled `internal_api_call` reaction firing together both resolve/execute independently (the "both" case the design doc's own framing promises, not just one kind at a time) — use a fake/injected HTTP target for the `internal_api_call` test (e.g. `httptest.NewServer`), don't require a real running service.
- A regression test proves an `implemented=false` reaction (seed one synthetically as `enabled=true` for the test, since nothing in this batch enables one by default) is skipped, not executed, and does not error the whole `Fire()` call.
- A regression test proves `internal_api_call`'s non-2xx response is recorded as a per-reaction failure without stopping a sibling reaction from firing.
- `go build ./cmd/nanite/`, `go vet ./...`, `go test ./...` pass.
- Your `internal_api_call` request-issuing mechanism (same-process HTTP client vs. an internal handler call — step 2's open question) is documented in this file's Work Log with your reasoning.

Built `internal/selftools/reactions` as five new files:

- `engine.go` — `Store` interface (`ListEnabledSelftoolReactions`/`GetSelftoolReactionKind`, satisfied directly by `*store.Store`), the four `Kind*` slug constants, `Engine`/`NewEngine(st Store, httpClient *http.Client, logger *slog.Logger) *Engine`, and `(*Engine).Fire(ctx, toolName, payload) (Result, error)`. Chose the `Engine`-with-constructor shape (mirroring `internal/agent/reflexes/engine.go`'s own `Engine`/`NewEngine` exactly, one level over in the sibling package this design explicitly follows) rather than a bare package-level `Fire` func, since `Fire` needs a store handle and an HTTP client and the task's own item 4 explicitly asks for a narrowed, injected dependency surface rather than either a global or a widened `Fire` signature. `Fire`'s own visible signature (`ctx, toolName, payload) (Result, error)`) matches the task's item-1 listing exactly; the receiver carries the injected dependencies.
- `result.go` — `Outcome` (`success`/`error`/`skipped_not_implemented`, matching `05`'s own Context verbatim), `FiredReaction` (`ReactionID`, `Kind`, `Category`, `Config`, `Outcome`, `Error`, `Payload json.RawMessage`), `Result` (`ToolName`, `Reactions []FiredReaction`), and a `Result.RenderCardPayload()` convenience accessor returning the first successfully-resolved `render_card` payload — the accessor `04`'s marker-embedding helper is expected to call instead of hand-scanning `Reactions`.
- `template.go` — unexported `substituteTemplate(v any, payload map[string]any) any`, a `{{key}}`-regex substitution shared by both `render_card`'s `template` and `internal_api_call`'s `body_template` (recurses through `map[string]any`/`[]any`, replaces in `string` leaves via `fmt.Sprint(payload[key])`). A missing payload key is left as the literal `{{key}}` text rather than silently blanked — a deliberate, documented choice (visible-not-silent on a misconfigured/missing field), not spec'd explicitly by the task so called out here for review.
- `render_card.go` — `ResolveRenderCard(configJSON string, payload map[string]any) (json.RawMessage, error)`: parses `{envelope_type, template}`, substitutes, and marshals into the real envelope wire shape (`{"kind":"envelope","version":1,"type":...,"data":...}` — matching `internal/selftools/self_tools_transport.go`'s `buildShowEnvelope`/`callShowCard` byte-for-byte, confirmed by reading that function directly, and matching `GLOSSARY.md`'s "Envelope" entry's own `(kind, version, type, data)` shape) rather than a bespoke shape — this is what should let `04`'s marker-embedding helper hand the payload straight to the three existing marker consumers with zero changes to any of them, per that task's own Context. Pure function, no `Engine` receiver, no store/HTTP dependency, per the task's item 3.
- `internal_api_call.go` — `(*Engine).executeInternalAPICall(ctx, configJSON, payload) error`: parses `{endpoint, method, body_template}`, substitutes, marshals to a JSON body, issues the request via `e.httpClient`, and returns an error (not fatal, caught by `Fire`) for a transport failure or a non-2xx status (with a 512-byte-bounded response-body snippet folded into the error message).

**`internal_api_call`'s request-issuing mechanism (documented per the Done-means requirement):** a plain same-process `*http.Client.Do` call against `endpoint` exactly as configured — not an in-process handler/`ServeMux` invocation. Reasoning: this codebase already has an established, repeated precedent for "point a same-process consumer at this live harness" — `cmd/nanite/main.go`'s own `apiBaseURL := fmt.Sprintf("http://127.0.0.1:%d", *port)` is threaded, already fully resolved, into `service.NewContainer`, `WorkflowContextAssembler`, `ExternalWorkflowEngineConfig.APIBaseURL`, and `service.NewAgentCardGenerator` — none of those consumers independently discover the port or join a base+path themselves; they're just handed a ready-to-use URL string. `internal_api_call`'s `endpoint` config field is designed to work the same way: the seeding caller (illustrated by `07`'s worked example, not built in this task) is expected to populate `endpoint` with a fully-qualified `http://127.0.0.1:<port>/...` URL, and this package's executor treats it as an opaque string handed to `http.NewRequestWithContext` — it never resolves a base URL or port itself. I considered and rejected calling the target handler in-process (bypassing the network stack) — it would require this package to import `internal/server`'s routing internals (or thread a `http.Handler`/`*http.ServeMux` reference through `NewEngine`), adding real coupling for a same-process loopback call whose network-hop cost is already negligible in this service's own design (the codebase's own `apiBaseURL` precedent already accepts that cost everywhere else this pattern is used). A plain `http.Client` requires zero import-graph consideration (`net/http` has no opinion about `internal/chat`/`internal/service`) and keeps `internal_api_call.go`'s only dependency on the rest of the codebase at `internal/store`'s config-shape convention, nothing more. Added a `defaultHTTPTimeout` (10s, used only when the caller passes a nil `*http.Client` to `NewEngine`) as baseline hygiene against a hung same-process endpoint — not retries/auth/idempotency, which stay explicitly out of scope per the README.

**`Result`'s shape, designed for `05`'s consumption per the task's own instruction:** every `FiredReaction` already carries tool-adjacent-but-not-tool-name fields `05` needs verbatim — `Kind` (event_type), `Category`, `Config` (the config used), `Outcome`/`Error` (success/error) — plus `Payload` for `render_card`'s resolved JSON. `05`'s own task file confirms this shape is sufficient ("Design `reactions.Result`... with enough per-reaction detail that this task's wrapper doesn't need anything beyond it plus a `tool_call_id` string passed in by the caller") — `Result` was built to satisfy exactly that without `05` needing a second store read or a changed `Fire` signature.

**Kind branching, per the task's step-by-step:** `!kind.Implemented` is checked generically first (covers any future/unknown kind marked not-implemented). The kind-specific `switch` that follows explicitly enumerates `KindExternalAPICall`/`KindCallback` as their own defensive skip case (not merged into `default`) — this is intentionally redundant with the generic `implemented=false` check given migration `126`'s actual seed data (both are seeded `implemented=0` today, so this branch is unreachable in practice right now), but per the task's own instruction ("code the branch defensively... rather than assuming it's unreachable") it guards against a future operator hand-flipping `implemented=true` on either kind in the DB before real executor code exists for them — the switch's `default:` case (a genuinely unrecognized kind slug, not one of the four known ones) is a distinct, separately-logged scenario from this explicit case.
