## Context

Architecture doc `docs/engineering/architecture/05-storage-and-migrations.md`, "Migrations: adopting a real ledger":

> There is currently no `schema_migrations` table — every migration file re-runs in full on every boot, idempotency achieved by swallowing specific SQL errors. This already caused one real production crash-loop... **Decision: adopt `pressly/goose`** rather than build custom migration infrastructure. Real version tracking, supports embedded SQL files, SQLite support, up/down rollback. This is a well-solved problem in the Go ecosystem — not a gap worth filling with bespoke tooling.

Decision log `docs/architecture-decision-log-2026-08-17.md` §13 ("Migration mechanism — adopt goose, don't build custom"):

> No `schema_migrations` ledger exists today — all 93 migration files re-run in full on every boot, idempotency achieved by swallowing specific SQL errors. This already caused one production crash-loop (`e2273f8`) and the fix (`migrate:skip-if-column-exists`) was applied only to the three migrations involved in that incident — the identical structural pattern in `043`/`089` remains unguarded, so the same failure class is still live. **Decision: adopt `pressly/goose`**... If there's still appetite to publish something OSS, a thin wrapper tuned to patterns actually hit here (the CHECK-widening rename-recreate-copy dance) is a more realistic target than a full migration engine.

### The crash-loop incident — verified against real commit history

Both commits the decision log references are real and in this repo's history (contrary to the possibility flagged in the drafting brief that `e2273f8` might not exist — it does):

- `e2273f8` ("fix: crash-loop from subagent_runs migrations recreating a stale schema", 2026-08-17): `nanite-api-service` crash-looped in production (250 restart attempts) on `CHECK constraint failed: status IN (...)`. Root cause: migrations `019`/`065`/`067` each recreate `subagent_runs` from scratch (SQLite can't `ALTER` a `CHECK` constraint), but each only knows its OWN historical column/CHECK set — no ledger means every file re-runs every boot, so migration `019`'s rebuild (using its original 7-value CHECK, predating `'stalled'`/`'over_budget'` which `065` added later) tried to copy a real row that already had status `'stalled'` and failed outright.
- `61a5514` (PR #261, merging `e2273f8` + a Copilot-review fix `b5d5c13` quoting the table identifier in `columnExists`): the actual fix — a `migrate:skip-if-column-exists <table> <column>` directive, added ONLY to migrations `019`, `065`, `067` (the three involved in the incident). Verified against a real copy of the crashed production database per the commit message; the fix is real and landed.

**This means the decision log's warning that "the identical structural pattern in `043`/`089` remains unguarded" is not hypothetical — verified directly**: both `internal/store/migrations/043_scope_project_reminders_pins_todos.sql` and `internal/store/migrations/089_agent_messages_subagent_result_kind.sql` use the exact same `RENAME → CREATE TABLE IF NOT EXISTS → INSERT OR IGNORE` rebuild pattern (required because SQLite can't `ALTER` a `CHECK` constraint in place) — the same shape that crash-looped in `subagent_runs` — and neither carries the `migrate:skip-if-column-exists` guard. `043` produces `todos_legacy_d1`; `089` produces `agent_messages_legacy_089` as the renamed-away original table (both intentionally left undropped today, per their own comments, specifically so the rename-swallow + `INSERT OR IGNORE` no-op path stays safe on every re-run — this is the exact mechanism a real ledger replaces).

### The current mechanism, verified against `internal/store/store.go`

- **94 migration files** in `internal/store/migrations/` (numbered `001`-`093`; two files share the `051` prefix, hence 94 files for 93 numbers — check both when doing the goose conversion, their ordering relative to each other currently depends on full filename alphabetical sort, not just the numeric prefix).
- **No `schema_migrations` table anywhere.** `Store.migrate()` (`store.go:67-169`) reads every `.sql` file under the embedded `migrations/` dir, sorts alphabetically, and executes every statement in every file **on every single process boot**, unconditionally.
- **Idempotency today is achieved two ways**, both need to be understood (and effectively replaced) before converting to goose:
  1. **Swallowed SQL errors** (`store.go:132-164`): `"duplicate column"` (ADD COLUMN re-run), `"no such column"` gated to DDL-only statements (DROP COLUMN / CREATE INDEX re-run), and `ALTER TABLE ... RENAME TO` failures matching `"no such table"` or `"already another table"` (rename re-run). This is real, load-bearing logic — a straight lift to goose without preserving equivalent idempotency (or, better, making it unnecessary because goose only runs each migration once) will break existing deployments' upgrade path unless handled carefully.
  2. **The `migrate:skip-if-column-exists <table> <column>` directive** (`store.go:171-217`, `migrationSkipIfColumnDirective`/`columnExists`): an opt-in marker (first line of a migration file) used today by exactly 3 files — `019_subagent_approval.sql`, `065_subagent_run_status_taxonomy.sql`, `067_subagent_run_retry_lifecycle.sql`. This is the exact mechanism a real `schema_migrations` ledger makes structurally unnecessary (goose's ledger means a migration runs exactly once, ever — no need to detect "have I already run" via a marker column on every boot). Once goose tracks applied migrations, this directive and its parsing code become dead weight to remove, not something to port forward.

## Work log

**Dependency.** Added `github.com/pressly/goose/v3` (`v3.27.3`) via `go get` + `go mod tidy`. This transitively bumped `modernc.org/sqlite` `v1.49.1 → v1.54.0` (goose's own `go.mod` directly requires the newer version, and Go's MVS picks the max across the module graph) plus a cluster of otel/grpc/`golang.org/x/*` transitive versions. Unavoidable side effect of adding a real dependency, not something worth pinning around — verified safe via the full `go test ./...` pass at the end.

**goose's actual conventions — researched, not guessed** (per the task's own instruction): inspected the vendored module source directly (`$(go env GOMODCACHE)/github.com/pressly/goose/v3@v3.27.3`) plus goose's public docs site/GitHub, since the task explicitly warned not to invent a convention.
- Version = the digits before the first `_` in the filename, parsed as `int64` (`NumericComponent`), and **must be unique across the whole migration set** — this is what made the duplicate `051` prefix a hard blocker, not just cosmetic.
- SQL files need `-- +goose Up` / `-- +goose Down` annotations. `-- +goose NO TRANSACTION` opts a migration out of goose's default per-migration `sql.Tx` wrapping. `-- +goose StatementBegin` / `StatementEnd` brackets a multi-statement block (e.g. a trigger body) that goose's parser would otherwise split incorrectly — goose's SQL parser is a simple per-line "does this line end in `;`" scanner (`internal/sqlparser`), not something that understands `BEGIN...END` semantically.
- Programmatic API used: `goose.NewProvider(goose.DialectSQLite3, db, fsys, opts...)` + `provider.Up(ctx)`. `fsys` is `fs.Sub(migrationsFS, "migrations")` so goose sees the 94 files at its FS root (matches how `fs.Glob` looks for `*.sql`).
- **No first-class "adopt goose against an existing database" mechanism exists** — checked goose's docs site (`pressly.github.io/goose`) and its bundled README; confirmed via web search there's no baseline/adopt command, and the standard community workaround is exactly what this task's own Context section suggested as option (a): seed the ledger table directly. Implemented via goose's own public `database.NewStore(database.DialectSQLite3, goose.DefaultTablename)` → `CreateVersionTable` + `Insert` (rather than hand-rolling the `goose_db_version` schema), so the seeded ledger has exactly the shape goose itself would produce.

**Duplicate `051` prefix — resolved by renumbering.** Two files shared the `051` prefix (`051_agent_workflows.sql`, `051_chat_harness_slim_prompt.sql`); their existing execution order came from the OLD runner's full-filename alphabetical sort (`agent_workflows` < `chat_harness_slim_prompt`), which does NOT match goose's version-number-only ordering. Fixed by renumbering **all 94 files sequentially 001–094**, in their original alphabetical order (so relative execution order is byte-for-byte preserved), via a scripted two-phase `git mv` (temp-suffix pass, then final-name pass, to avoid collisions mid-rename). `051_agent_workflows.sql` kept `051`; everything from `051_chat_harness_slim_prompt.sql` onward shifted up by one, ending at `094_playbook_match_log_raw_sent_text.sql`. Verified programmatically: 94 unique version numbers, exactly `1..94`, no gaps.

**Goose-format conversion, all 94 files:**
- Prepended `-- +goose Up` (+ `-- +goose NO TRANSACTION` for the 16 files that manage their own literal `BEGIN;`/`COMMIT;`/`END;` transaction — new numbers `008, 019, 020, 027, 029, 030, 061, 062, 063, 066, 068, 074, 075, 082, 083, 092`). These needed NO TRANSACTION because goose's default behavior wraps a migration in its own `sql.Tx`, and a literal `BEGIN;` statement inside an already-open `sql.Tx` fails ("cannot start a transaction within a transaction") — confirmed this is safe under Nanite's single-connection pool (`sqlitekit.OpenSingle` forces `MaxOpenConns=1`), so `db.ExecContext` calls in goose's NO-TRANSACTION path always hit the same underlying SQLite connection, preserving the exact transaction semantics these files were originally written for (PRAGMA `foreign_keys=OFF` outside the txn, explicit `BEGIN`/`END` around the recreate-table dance).
- Appended a documented, deliberately empty `-- +goose Down` to all 94 (see "Down migrations" below).
- Bracketed the two files with real multi-statement `CREATE TRIGGER ... BEGIN ... END;` bodies (`003_todos_and_plans.sql`, `043_scope_project_reminders_pins_todos.sql`) with `-- +goose StatementBegin`/`StatementEnd` — without this, goose's line-based parser would have split each trigger into invalid fragments (verified this would fail: a bare `CREATE TRIGGER ... BEGIN` line has no trailing `;`, so goose keeps buffering into the next `UPDATE ...;` line, flushes an incomplete statement missing its `END;`, then treats the following standalone `END;` as its own invalid statement).
- Removed the retired `-- migrate:skip-if-column-exists` directive line from the three files that carried it (new numbers `019`, `066`, `068`) and rewrote their header comments to describe goose's ledger as the mechanism that now prevents the crash-loop's structural cause, instead of leaving stale prose describing deleted machinery.

**`store.go` rewrite.** Removed `migrationSkipIfColumnDirective`, `columnExists`, `quoteIdentifier`, `splitSQL`, and all three swallowed-SQL-error branches (`duplicate column`; `no such column`/`no such table` gated to DDL; `ALTER TABLE ... RENAME TO` failures) — confirmed via repo-wide grep these had zero other call sites. New `migrate()` builds a `*goose.Provider` over the embedded `migrations/` dir and calls `Up(ctx)`. Cutover for pre-existing databases: `isPreGooseDatabase` checks for the `sessions` table (created by migration 1, never dropped/renamed by anything later — a reliable "this DB already ran the old mechanism to completion" signal) with no `goose_db_version` table yet; if true, `seedLegacyLedger` marks versions `0..legacyMigrationCutoverVersion` (94, a fixed constant, deliberately NOT "however many files exist now" — future migrations just get real numbers above it) as already-applied before `Up()` runs, so goose never re-executes their SQL against data that already has their effects. A genuinely fresh database (no `sessions` table) skips seeding and runs all 94 for real, from version 1.

**Six real, pre-existing bugs found and fixed** — all invisible under the old mechanism specifically because it unconditionally swallowed the exact SQL errors these would have raised, and all now impossible to leave in place because goose does not swallow anything:
1. Five migrations (new numbers `070, 072, 073, 076, 077`) had their *final* statement missing a trailing `;` (e.g. `070`: `ALTER TABLE agent_profiles ADD COLUMN role_tools TEXT NOT NULL DEFAULT '[]'` with no terminator). The old naive `splitSQL` tolerated this via its EOF-flush of the trailing buffer; goose's per-line parser doesn't, and fails with "unexpected unfinished SQL query" the moment it hits the `-- +goose Down` annotation with an unterminated statement still buffered. Fixed by adding the missing `;` — pure syntax, zero semantic change, verified by re-running the fresh-DB boot after each fix.
2. Migration `082` (new numbering, `082_durable_agent_launch_policy.sql`) contained `ALTER TABLE durable_agent_instances ADD COLUMN current_session_id ...` / `ADD COLUMN failure_reason ...`, but the immediately-preceding migration `081`'s `CREATE TABLE` **already declares both columns directly** (confirmed by inspecting `081_durable_agent_instances.sql`). This means these two ALTERs have failed with "duplicate column" on literally *every* boot since whenever `081` was edited to include those columns — including a genuinely fresh install — and were invisible only because the old runner swallowed "duplicate column" everywhere, unconditionally. Fixed by deleting the two dead ALTER lines (the `CREATE TABLE ... _new` rebuild later in the same file already declares both columns, so the end-state schema is unchanged either way) and documenting why in the migration file itself.

Both fixes were mechanical, zero-semantic-change corrections needed to make the *already-decided* goose conversion actually boot — not new architecture decisions, so not escalated. Per `EXECUTION-PROCESS.md` worker step 7 this is "verifying how big the job is," not "verifying whether to still do it."
