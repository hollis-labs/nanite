### Verified against real code (2026-08-18) — the "zero functional effect" claim is TRUE for prompt assembly, but the mechanism is bigger than the docs describe

**Confirmed true: nothing in the chat/prompt-assembly pipeline reads `agent_known_skills`.** Grepped every call site of `ListAgentKnownSkills`/`GetAgentKnownSkill` across the repo — the only callers are the REST API handlers in `internal/api/agent_capabilities.go` themselves. No consumer in `internal/service/chat*.go`, `internal/context/*`, `internal/skillbroker/*`, or anywhere in the turn loop reads this table to build a system prompt, filter tools, or influence behavior in any way. This matches the decision log's "confirmed zero functional effect on prompt assembly" claim exactly.

**But the docs' framing ("removing the frontmatter parsing and seeding code creates no functional gap") undersells how much real, reachable surface sits on top of this table.** Verified:

1. **`internal/service/ingest.go:299-313`** (`seedRoleSkills`) is the file-based path: when a `.md` agent file's `roleSkills:` YAML frontmatter is ingested, it calls `InsertAgentKnownSkill` for each slug with `Pinned: true, Reason: "role_seed"`. This is the path TASKS.md item 17 is actually asking to cut — genuinely dead-end, zero downstream consumer.

2. **`ui/src/components/settings/agents/AgentBuilderWizard.tsx`** has its own, independent, GUI-driven seeding path: a `role_skills` form field (~line 787, 934) and, on wizard submit, a loop (~lines 1771-1775) that calls `api.createAgentKnownSkill(agentId, {...})` for every declared role skill — writing straight to `agent_known_skills` via the REST API, bypassing `ingest.go` entirely.

3. **`ui/src/components/settings/agents/AgentCapabilitiesPanel.tsx`** is a full standalone CRUD editor for `agent_known_skills` — list/create/update/delete via React Query mutations against `api.listAgentKnownSkills`/`createAgentKnownSkill`/`updateAgentKnownSkill`/`deleteAgentKnownSkill` (all confirmed live in `ui/src/lib/api.ts`).

4. **`internal/api/agent_builder.go`** has its own `RoleSkills` handling on `store.AgentProfile` (merge/normalize logic at ~lines 59, 334, 365, 430-431, 476, and a builder-completeness warning at ~658-659 checking whether `role_tools`/`role_skills` are still empty) — this is the Builder Wizard's server-side counterpart to (2), independent of the `.md`-file frontmatter path.

**This means "cut `agent_known_skills`-as-currently-used" reads two different ways depending on how literally you take it**, and the two readings have very different blast radii:
- **Narrow reading** (what TASKS.md's own justification text actually supports — "zero functional effect on prompt assembly," "frontmatter parsing and seeding code"): cut only `roleSkills:` frontmatter parsing + `ingest.go`'s `seedRoleSkills`. This is what this task file scopes to.
- **Broad reading** (implied by the task's title, "agent_known_skills-as-currently-used" as a whole): would also mean removing the REST CRUD API, the store layer, the Builder Wizard's `role_skills` field and seeding loop, and the Agent Capabilities settings panel — i.e., removing a currently-reachable, currently-functional (if low-value) GUI feature, not just dead code.

**Flagging this prominently per the instruction to report real doc/reality mismatches rather than guess**: this task file takes the narrow reading, because that's the one the decision log's own stated justification ("zero functional effect on prompt assembly," "no functional gap") actually supports. Removing the GUI/API/store layer would be a real, user-visible feature removal that deserves its own explicit decision (and its own task, sized correctly), not something to fold into a "confirmed dead code, no functional gap" cut.
