## Context

TASKS.md Phase 0 item 20: "Retire the in-app `workspaces` table and the filesystem-level `NANITE_WORKSPACE` multi-instance mechanism (keep `NANITE_DB_PATH`)." Decision log §15 ("Two 'workspace' concepts — both retired, for different reasons"), architecture doc `05-storage-and-migrations.md`'s "'Workspace' — both concepts retired" section, and `GLOSSARY.md`'s **Instance**/**"Workspace"** entries all describe the same two-concept split. **This task required real disambiguation work before writing "What to do" — the naive reading of decision log §15 ("`projects` (nested under it) goes with it") is wrong and would break a real, kept mechanism if followed literally. Read this section in full before touching anything.**

### Concept 1 — the in-app `workspaces` table (UI session-grouping): real, 1 row, safe to retire — but `projects` does NOT go with it

`workspaces` is defined in `internal/store/migrations/001_schema.sql`. Confirmed 1 real row in practice (migration `087_consolidate_personal_workspace.sql`'s own commit message: consolidated a second "personal" workspace down to the sole "default" one, with 22 real sessions migrated, zero projects/workflows at that workspace). `internal/store/workspaces.go` has full `Workspace` CRUD (`ListWorkspaces`/`GetWorkspace`/`CreateWorkspace`/`UpdateWorkspace`/`DeleteWorkspace`/`ResolveWorkspaceID`), exposed via `internal/api/workspaces.go` + 5 real REST routes, with a real, mounted settings-page component (`ui/src/components/settings/WorkspaceProjectManager.tsx`). This part is a clean, low-risk cut.

**However — decision log §15 says "`projects` (nested under it) goes with it," and this is where the task prompt's disambiguation warning turns out to be load-bearing.** Verified directly against the schema (`internal/store/migrations/001_schema.sql`):

```sql
CREATE TABLE projects (
    id TEXT PRIMARY KEY,
    workspace_id TEXT NOT NULL REFERENCES workspaces(id),
    ...
);

CREATE TABLE agent_projects (
    agent_id TEXT NOT NULL,
    project_id TEXT NOT NULL REFERENCES projects(id),
    ...
);
```

**There is exactly one `projects` table in this schema — not two.** It is simultaneously:
1. The UI-grouping table nested under `workspaces` (`internal/store/workspaces.go`'s `Project`/`ListProjects(workspaceID)`/`CreateProject`/etc., exposed via `/api/workspaces/{wid}/projects` in `internal/api/workspaces.go`), **and**
2. The FK target of `agent_projects` — the real, live Agent Construction scope-reference mechanism architecture doc `01-agent-construction.md` explicitly describes as kept: *"`agent_projects` (already real, already FK'd once fixed) is the existing precedent [for scope]."* Confirmed live: `internal/store/agent_projects.go` (`ListAgentProjects`/`ListProjectAgents`/`AddAgentProject`/`RemoveAgentProject`, all joining directly against `projects`), exposed via real REST routes in `internal/api/agents.go` + `internal/api/api.go` (`GET/POST /api/agents/{id}/projects`, `DELETE /api/agents/{id}/projects/{projectId}`, `GET /api/projects/{id}/agents`).

**These are not two different `projects` concepts that happen to share a name — they are the literal same table serving both roles.** Decision log §15's "`projects` goes with it" is talking about the UI-grouping *role* of this table, but taking it literally (`DROP TABLE projects`) would delete the FK target `agent_projects` depends on and break the kept Agent Construction scope mechanism outright. **This is the real finding this task's disambiguation instruction was pointing at.**

**Resolution used for this task file** (a design call within what the docs already settled, not a new architecture decision — flag to the Orchestrator if this reasoning doesn't hold up under implementation): keep the `projects` table and `agent_projects` fully intact; only remove the `workspace_id NOT NULL REFERENCES workspaces(id)` column/FK from `projects` (drop the column, since there's no more `workspaces` table for it to reference) and the workspace-nested REST surface (`/api/workspaces/{wid}/projects/*`) — NOT the project-CRUD logic itself, which likely needs to be re-exposed as flat `/api/projects` routes (or reuse the `/api/agents/{id}/projects` + a still-needed `GET/POST/PUT/DELETE /api/projects` for the settings-page project manager, which the frontend `WorkspaceProjectManager.tsx`/sidebar project UI still needs — verify what the sidebar `ScopeSelector.tsx`/`NewProjectDialog.tsx` actually call before removing any project-CRUD route). **If this restructuring isn't mechanically obvious once you're in the code, escalate — don't guess past it; this is exactly the kind of design call `EXECUTION-PROCESS.md` wants surfaced, not silently resolved differently by two different workers.**

### Concept 1b — `workspace_role_trust`: a third, real, live consumer of `workspace_id` the decision log never mentions

Verified while tracing `workspace_id` usage: `workspace_role_trust` (`internal/store/migrations/035_role_trust_model.sql`, seeded by `036_role_trust_seed_dogfood.sql`) is a **live trust-tier gating mechanism** — `internal/store/trust.go`'s `ResolveTrust(ctx, workspaceID, agentProfileID)` is called from `internal/subagent/service.go:772` (real subagent-dispatch approval-bypass gating) and `internal/mcp/self_tools_panels.go:168`. `internal/dispatch/trust.go`'s `TrustResolver` interface doc comment: *"resolves the effective trust tier for a (workspace, agent) pair."* REST surface: `GET/POST/DELETE /api/workspaces/{workspace_id}/roles/{agent_profile_id}/trust` in `internal/api/trust.go`, with a real settings panel (`ui/src/components/settings/RoleTrustPanel.tsx`).

**Neither decision log §15 nor TASKS.md item 20 mentions `workspace_role_trust`** — flagged to the operator during planning as needing an explicit call. **Operator decision, 2026-08-18 — final: full removal, not a collapse-to-global.** Drop the `workspace_role_trust` table entirely, remove the `ResolveTrust` call sites at `internal/subagent/service.go:772` and `internal/mcp/self_tools_panels.go:168` (along with the override-layer logic in `internal/store/trust.go` they call into), remove the `/api/workspaces/{workspace_id}/roles/{agent_profile_id}/trust` REST surface (`internal/api/trust.go`), and delete `RoleTrustPanel.tsx`. Trust resolution reverts to unconditional base-tier resolution with no override layer — whatever `ResolveTrust` fell back to when no override row existed becomes the only behavior, not a workspace-scoped or global-scoped override table.

### Concept 2 — filesystem-level `NANITE_WORKSPACE`: lives in an external, separate repo — not directly cuttable from within `apps/nanite`

Grepped the entire repo for `NANITE_WORKSPACE`: it appears **only in doc comments** (`cmd/nanite/serve_autostart.go:190`, `cmd/nanite/path.go:23`, `internal/config/layout.go:20`, `cmd/nanite/plugin_cmd.go:155`) — **Nanite's own Go code never reads this env var directly.** It's honored implicitly by `github.com/hollis-labs/go-apppaths` (`paths.Resolve(brand.ID, ...)` in `internal/config/layout.go`), which derives `<APPNAME>_WORKSPACE` from the app's brand prefix as part of its own path-resolution API. **`go-apppaths` lives in a separate git repository** (`/Users/chrispian/dev/hollis-labs/libs/go-apppaths`, confirmed via `git rev-parse --show-toplevel` — it is not a subdirectory of this repo, it's a versioned Go module dependency, `github.com/hollis-labs/go-apppaths v0.1.0` in `go.mod`), **shared across Nanite, Tesseract, and (per `path.go`'s own comment) Torque**. The workspace-selection API (`Layout.SelectWorkspace`/`ResolveWorkspace`/`Workspaces()`, backed by an `active_workspace` pointer file under `StateDir`) is defined entirely in that external module's `paths/workspace.go`.

**Confirmed Nanite-side usage is zero**: `grep -rn "SelectWorkspace\|ResolveWorkspace\|\.Workspaces()\|WithWorkspace"` across the whole `apps/nanite` tree returns nothing — Nanite never calls any of go-apppaths' workspace-switching API. It only passively inherits the env-var-driven path resolution because that's how `paths.Resolve` works. **This means there is no Nanite-side code to delete for "the mechanism" itself — it was never built here.** What *is* real and in-scope for this repo: the doc comments in the 4 files above describe `NANITE_WORKSPACE` as if it's a supported, notable Nanite feature (e.g. `path.go`'s doc comment for the `nanite path` CLI subcommand: *"Resolution honors every override the running daemon would see — the NANITE_DB_PATH / NANITE_WORKSPACE env vars..."*). That's accurate today (the env var genuinely does still work, inherited from go-apppaths) but should be reworded to stop presenting it as a first-class Nanite feature, since Nanite is retiring its conceptual support for multi-instance switching.

**Confirmed decision log's claim of "zero automated usage in the test suite"**: `grep -rn "NANITE_WORKSPACE" --include="*_test.go" .` returns zero matches.

**Scope boundary for this task** (flag prominently when reporting): actually removing `<APPNAME>_WORKSPACE` support from `go-apppaths` would be a cross-repo change affecting Tesseract and Torque too — clearly out of scope for a Nanite-only Phase-0 task and not something this task file can direct a worker to do. If the operator wants the library-level capability gone too, that's a separate, cross-portfolio decision to raise explicitly — this task only covers what's actually addressable inside `apps/nanite`: doc-comment cleanup (stop describing it as a supported mechanism) and confirming (already done, above) that nothing here builds on top of it.

### A third, unrelated "workspace" — do NOT touch

While tracing `workspace` mentions, found a **third, distinct** usage that must be left alone: `WorkspacesRoot` (`internal/runtime/agent/deps.go`, `internal/service/agent_deps.go`, `internal/launcher/launcher.go`) is the on-disk root (`~/.nanite/workspaces/`, the pre-XDG dotdir convention, separate from go-apppaths' `~/.local/share/nanite/workspaces/default/`) where **CLI-launched agent subprocess boot directories get materialized** — completely unrelated to both the DB `workspaces` table and the `NANITE_WORKSPACE` env var. `GLOSSARY.md` and the decision log only document two "workspace" collisions (Instance vs. in-app table); this is a third one this task's investigation surfaced independently. Do not remove or rename `WorkspacesRoot` as part of this task — it's live, unrelated infrastructure for agent boot-dir materialization.

## What to do

1. **In-app `workspaces` table**: new migration dropping `workspaces`. Remove `Workspace`-only CRUD from `internal/store/workspaces.go` (keep `Project`/`ListProjects`/etc., see step 2) and `ResolveWorkspaceID`. Leave `agent_projects`, `internal/store/agent_projects.go`, and the `/api/agents/{id}/projects`/`/api/projects/{id}/agents` routes completely untouched.
3. **`workspace_role_trust`**: drop the table entirely (new migration). Remove the `ResolveTrust` call sites (`internal/subagent/service.go:772`, `internal/mcp/self_tools_panels.go:168`) and the override-layer logic in `internal/store/trust.go` they call into. Remove the REST surface in `internal/api/trust.go`. Trust resolution reverts to unconditional base-tier resolution — confirm what that base-tier fallback actually is (read `ResolveTrust`'s current implementation for what it returns when no override row exists) and make that the permanent, only behavior. 4. **Frontend**: remove/trim `WorkspaceProjectManager.tsx` per step 2's resolution (it may become a project-only manager rather than being deleted outright — check what it actually renders first). Delete `RoleTrustPanel.tsx` entirely — with `workspace_role_trust` fully removed, there's nothing left for this panel to manage. 5. **`NANITE_WORKSPACE` doc comments**: reword the 4 comment sites (`cmd/nanite/serve_autostart.go:190`, `cmd/nanite/path.go:23`, `internal/config/layout.go:20`, `cmd/nanite/plugin_cmd.go:155`) to stop presenting `NANITE_WORKSPACE` as a supported Nanite feature, while staying factually accurate that go-apppaths still honors it underneath (don't claim it no longer works — it does, Nanite just isn't building anything on top of it).
