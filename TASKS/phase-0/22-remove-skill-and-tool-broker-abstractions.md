## Context

TASKS.md Phase 0 item 22: "Skill broker / tool broker formal-abstraction removal — delete the rule-matching wrapper (`go-toolbroker`/`NaniteDefaultRules`, `internal/skillbroker`), call the existing filter/selection logic directly. Mechanical, but touches a currently-live, actively-exercised path — tag for real testing, unlike the pure-dead-code cuts above."

Decision log §11 ("Steering — skill broker and tool broker retired as abstractions; catalogs stay") and `docs/engineering/architecture/03-steering.md` are the governing sources:

> "Both the skill broker and the tool broker (the formal 'broker' abstraction layers) are retired. The broker pattern served a real purpose early ... but isn't earning its complexity anymore. What stays: the underlying catalogs (skills table, tool catalog) and the actual selection/filter logic that does real work (permissions, allowlist, chat-surface exclusion, progressive discovery). What goes: the formal rule-matching 'broker' wrapper around them (`go-toolbroker`/`NaniteDefaultRules`, `internal/skillbroker`)."

**Naming trap, read before touching anything**: this codebase has THREE distinct systems that all use the word "broker," and only two of them are in scope for this task:

1. **Tool Broker** (`go-toolbroker` module, `internal/toolclient`) — in scope, cut.
2. **Skill Broker** (`internal/skillbroker`) — in scope, cut.
3. **Agent Broker** (`github.com/hollis-labs/agentkit/broker`, wired in `internal/service/chat_broker_dispatch.go`/`container.go`/`cmd/nanite/main.go` as `agentBrokerInstance`) — **NOT in scope.** This is decision log §10's separate steering system ("Agent broker + `promptrouter` — proposed to consolidate into `internal/agent/reflexes`... Agreed in principle; concrete design still to be worked out"). It decides which subagent profile a turn dispatches to (worker/planner/chat), is gated partly by Modes' `mode=work`/`mode=plan` signals (TASKS.md item 21's coupled-stub requirement references this — "the agent broker's mode-dependent rules... must be stubbed out"), and is scheduled for Phase 3 consolidation into the `dispatch_to_agent` reflex action kind, not a Phase 0 cut. Verified live and actively firing on every chat turn (`chat_broker_dispatch.go`'s own header comment: "the seam where chat_generate.go consults `broker.Decide()` BEFORE the chat-loop entry"). **Do not touch `agentbroker`/`AgentBroker`/`chat_broker_dispatch.go` in this task** — conflating it with the Tool/Skill Broker is exactly the kind of naming collision `GLOSSARY.md` exists to prevent.

### What the Tool Broker actually does today (verified)

`internal/toolclient.ToolClient` wraps `github.com/hollis-labs/go-toolbroker/broker.LocalBroker`. The rule-matching layer is functionally a no-op today: `internal/toolclient/config.go`'s `NaniteDefaultRules()` returns exactly one rule — `{Name: "nanite-catalog", Intent: "*", Match: {Patterns: ["*"]}, Action: {Type: "include"}}` — a catch-all that matches every intent and includes every tool. Its own doc comment explains why: the go-toolbroker library's bundled example rules (`hadron_*`/`volon_*`/`cortex_*` name patterns, a fixed intent vocabulary) never matched any of Nanite's real tools, so every real selection previously fell through to the library's implicit "no rules matched; returning all tools" fallback (flagged as a real gap by ADR-001/CW-20260815-0011) — `NaniteDefaultRules` was written specifically to make that fallback an explicit, always-applicable rule instead of an implicit one. **Net effect: `LocalBroker.SelectTools`'s rule-matching pass currently always returns the entire registered tool catalog, unranked** — it does no real filtering. The real narrowing happens entirely downstream, in code that already lives outside the broker: `ToolClient.CheckPermission`/`GetPermissions` (permissions), `service/tool.go`'s `filterToolsByAllowlist` (schema-v2 tools allowlist) and `applyChatSurfaceFilter` (chat-role surface exclusion, `internal/dispatch/chat_surface.go`), the `developer_mode` dev-tool gate, and progressive discovery (`request_tools`/`ProgressiveDiscoveryThreshold`) — this is exactly the "actual selection/filter logic that does real work" the decision log says stays.

Nanite's own keyword-relevance scoring (`internal/toolclient/intent.go`'s `SelectByIntent`/`scoreToolAgainstIntent`) is **not** part of go-toolbroker — it's Nanite-authored substring/keyword scoring used by the reasoning-augmented selection path (`SelectWithSignals`/`RankTools` in `ranking.go`). This stays; only its use of `broker.ToolDefinition` as the shared currency type needs to be re-pointed at a non-go-toolbroker type once the dependency is removed (see What to do).

**A second, currently-dead copy of the same broker pattern exists in `internal/mcp/manager.go`**: `Manager.Broker *broker.LocalBroker` (line 57) is populated at boot (`cmd/nanite/main.go:962`: `mcpManager.Broker = broker.NewLocalBroker(nil, toolCfg.Rules)`) and receives every discovered tool via `RegisterTools` on every `DiscoverTools` pass (lines ~415-428) — real CPU/allocation work happens here. But `Manager.GetTools()`/`GetToolsForIntent()` (lines ~440-465), the only methods that read from `m.Broker`, have **zero callers anywhere in the codebase** (verified: `grep -rn "\.GetTools()\|\.GetToolsForIntent(" --include="*.go" .` matches only the internal `GetTools()` → `GetToolsForIntent()` self-call, no external caller). The real tool-listing path (`toolclient.ToolClient.ListTools()` → `tb.MCPManager.GetAllTools()`) goes through a completely separate, broker-free method (`GetAllTools`, line ~481) that was already bypassing the Manager's broker. `Manager.Broker` and its `RegisterTools` wiring are dead weight tied to this same abstraction — remove them alongside the `toolclient` broker, not left behind as an orphan.

### What the Skill Broker actually does today (verified)

`internal/skillbroker.SelectSkills` (called from `internal/chat/context.go`'s `buildSkillListForSessionWithIntent`, which is called by `internal/chat/context_client.go:194`) is a deterministic keyword/agent-tag/mode-bonus scoring function over an agent's assigned-skill candidate set (already mode-filtered upstream by `filterAgentSkillsByMode`, which is **not** part of `internal/skillbroker` and stays). Per decision log §11: "Skills: clean slate, not a revival. Never actually exercised in practice ... `agent_skills` has zero rows workspace-wide." Verified: `buildSkillListForSessionWithIntent` calls `s.ListAgentSkills(agentID)` first — with zero `agent_skills` rows in any real environment, `candidates` is always empty and `SelectSkills` short-circuits (`if len(candidates) == 0 { return nil }`) before any of its scoring logic runs. The package is call-reachable but functionally inert today for lack of data, not for lack of a live call site — same "wired but starved of input" shape as several other Phase 0 cut targets. Decision log §11 explicitly names `internal/skillbroker` (not just go-toolbroker) as a target: "Follows the same model as tools: FK-based assignment through the role/scope/agent composition model, **no separate ranking abstraction**." There is no "existing filter/selection logic" inside skillbroker analogous to the tool broker's permissions/allowlist stack to preserve — the only real upstream logic is the mode filter, which already lives outside the package.

### Override-block / `tool_enrichments` — resolved, cut entirely, no port-forward

`internal/toolclient/enricher.go`'s `storeEnricher` (a `broker.Enricher` implementation reading the `tool_enrichments` table) and `broker.go`'s `WithEnricher(enr)` wiring compose a markdown "Tool Overrides" block (`SelectResult.OverrideBlock`) that is threaded all the way to the system prompt (`internal/service/chat_generate.go`, `selection.OverrideBlock` → `composeExtraSystemPrefix`, ~line 456-464). This was flagged during planning as an open design call (port forward vs. cut) since it isn't one of the four things decision log §11 explicitly lists as staying.

**Operator decision, 2026-08-18 — final: cut entirely, do not port forward.** `18a-cut-dead-storage-and-config.md` already confirmed `tool_enrichments`'s write path (`UpsertToolEnrichment`/`DeleteToolEnrichment`/`ListToolEnrichments`) is dead — zero callers anywhere. With no write path, the override-block's read side (`GetToolEnrichment`) is structurally inert: it can only ever read rows that nothing in the codebase can write. Cutting it alongside the broker removal produces zero behavior change in practice, and the intended replacement mechanism is already scheduled — `FilterToolSelection` (Phase 3, per `docs/engineering/architecture/09-plugin-system.md`'s plugin-system gap and the Steering phase's tool-selection filter stack) is the forward-looking seam for this kind of tool-selection augmentation, not a go-toolbroker-specific mechanism worth preserving in the interim.

Confirm `18a`'s `tool_enrichments` write-path cut has landed (or land it as part of this task if sequencing puts this task first — check `TASKS/INDEX.md` for the actual wave order) before removing the override-block/enricher code, so the "already structurally inert" reasoning is verifiably true at the time this task executes, not just true in the planning snapshot.

- The override-block/`tool_enrichments` read path (`enricher.go`/`WithEnricher`) is removed in full — no port-forward, per the operator's resolution in Context.
