**This task's dependency claim in TASKS.md does not match the actual codebase — verified directly, not assumed. Read this whole section before writing the export/drop migration.**

Grepped every real writer (`INSERT INTO broker_decisions`, `INSERT INTO agent_broker_decisions`, `INSERT INTO strategy_decisions`) and traced each back to its owning system:

1. **`strategy_decisions`** — written by `internal/store/strategy_log.go`. This is the strategy planner's own decision log. Removed cleanly by `11-cut-strategy-planner` (decision log §10: "Strategy planner — full cut, not partial. Both outputs are gone."). **Confirmed dependency: `11-cut-strategy-planner`.**

2. **`broker_decisions`** — written by `internal/store/broker.go`'s `LogBrokerDecision`/`LogBrokerDecisionEx`, called from `internal/service/tool.go`'s `toolServiceImpl.logDecision`/`logDecisionWithSignals` inside `SelectForAgent` — the **Tool Broker's** own decision log (the system `22-remove-skill-and-tool-broker-abstractions` cuts). `internal/store/broker.go`'s own type doc comment confirms this: `BrokerDecision` "records a tool broker selection event." **Confirmed dependency: `22-remove-skill-and-tool-broker-abstractions`.**

3. **`agent_broker_decisions`** — written by `internal/store/broker_decisions.go`'s `InsertAgentBrokerDecision`, called from `internal/service/chat_broker_dispatch.go` (line ~469). This file's own header comment states its origin precisely: "CW-20260509-0046: agent-broker call-site wiring upstream of chat-harness prompt assembly. This file owns the seam where `chat_generate.go` consults `broker.Decide()` BEFORE the chat-loop entry to decide whether the turn dispatches to a worker/planner subagent." It imports `agentbroker "github.com/hollis-labs/agentkit/broker"` — this is the **Agent Broker** (decision log §10), a *different system* from both the strategy planner and the Tool/Skill Broker pair `22-remove-skill-and-tool-broker-abstractions` covers. `internal/store/broker_decisions.go`'s own doc comment spells out the naming history explicitly: "The tool broker ... owns the table `broker_decisions` ... The agent broker ... owns the table `agent_broker_decisions` ... That name was already taken upstream by the tool broker, so the implementation lands under `agent_broker_decisions`."

   **The Agent Broker is not removed by any currently-scheduled Phase 0 task.** Decision log §10 describes it as "proposed to consolidate into `internal/agent/reflexes`... Agreed in principle; concrete design still to be worked out" — this is Phase 3 steering-redesign work (the `dispatch_to_agent` reflex action kind, per `docs/engineering/architecture/03-steering.md`), not a Phase 0 item. TASKS.md item 21 ("Modes, in full") requires the Agent Broker's *mode-dependent rules* to be stubbed out in the same change ("the agent broker's mode-dependent rules (2–4, the `mode=work`/`mode=plan` thresholds) must be stubbed out ... or the broker breaks referencing a deleted signal") — but stubbing a subset of the broker's *rules* is not removing the broker itself, and `chat_broker_dispatch.go`'s call to `InsertAgentBrokerDecision` is unconditional on every consultation, not gated by which rule fired. Verified: the Agent Broker keeps running and keeps writing `agent_broker_decisions` after item 21 lands. Neither item 11 (strategy planner) nor item 22 (Tool/Skill Broker) touches `agentkit/broker` or `chat_broker_dispatch.go` at all.

   **Conclusion: dropping `agent_broker_decisions` in this task would break a live INSERT on every chat turn that consults the Agent Broker — its writer is not scheduled for removal anywhere in the current Phase 0 plan.** This is a genuine doc/reality mismatch (TASKS.md's dependency note "#11, #21, and #22... removes their writers" is incorrect for this specific table), not a judgment call — escalating rather than guessing past it, per `EXECUTION-PROCESS.md`'s "if reality doesn't match what the docs/decision-log claim — stop, don't guess" instruction. **`agent_broker_decisions` is out of scope for this task.** It should be revisited as part of (or immediately after) whatever Phase 3 task retires the Agent Broker into reflexes — flag that follow-up explicitly when this task completes; do not create a new task file for it now (no Phase 3 task file exists yet to attach it to).

**Separately, note the item-numbering confusion in the original task description this task was scoped from is itself imprecise**: it's not that TASKS.md "reuses '21' for two different items" — item 21 ("Modes, in full") appears exactly once. The real numbering collision in TASKS.md's Phase 0 section is between the **Cuts** list's items 25-27 (`sessions.status` CHECK cleanup / `sessions.compaction_summary` / P7) and the **Renames** list's items 25-27 (PTY naming scrub / `internal/recovery/*` namespace / "Volon" eradicated) — six distinct items sharing three numbers across the two lists. This doesn't change this task's conclusion (`agent_broker_decisions`'s writer genuinely isn't removed by 11/21/22 regardless of which numbering description is used), but the numbering claim as stated doesn't hold up against the actual document — worth the Orchestrator knowing precisely which collision is real.

**`event_log` confirmed as the correct export/future-capture target**: schema verified in `internal/store/migrations/001_schema.sql`: `event_log(id, session_id, event_type, category, detail, metadata, created_at)` — exactly the "`event_type`/`category` discriminator + flexible `metadata` JSON blob" shape decision log §14 describes.
