## Context

TASKS.md Phase 0 Cuts, item 27: "**P7** (the scratchpad→`handoff_stashes` compaction-time snapshot) — cut the extraction step only; the scratchpad tool and Glass-4 both stay untouched." Decision log §22: "P7 (compaction-time scratchpad snapshot into `handoff_stashes`) — cut. Distinct from the scratchpad tool itself (kept, §21). P7 is the mechanism that extracts a snapshot of the scratchpad into `handoff_stashes` at compaction time for continuity purposes — but it's write-only and never read back for anything except Glass-4/long-running sessions, and the scratchpad was never meant to reliably hold the structured continuity fields P7 extracts in the first place. Dead weight regardless of the scratchpad's own value. Cut the extraction step; the scratchpad tool stays." `docs/engineering/architecture/06-session-lifecycle-and-recovery.md`'s "Handoffs, scratchpad, and Glass-4" section: "P7 ... cut. Write-only, never read back for the vast majority of sessions, and the scratchpad was never meant to reliably hold the structured fields P7 extracted anyway."

**Verified exact extraction step**: `internal/context/compaction.go`, `runStages` (lines 121-133) — guarded by `if p.StashWriter != nil && p.SessionID != ""`, it generates a UUID, calls `BuildPayloadFromScratchpad(p.ScratchpadSnapshot)` (`internal/context/handoff_stash.go:62-70`, pulling well-known string-slice keys — `decisions_locked`, `open_questions`, `active_file_refs`, `active_ticket_ids`, `should_reread` — out of the raw scratchpad map), and writes it via `p.StashWriter.WriteHandoffStash`. This is the whole mechanism to remove.

**Verified `handoff_stashes` is a shared table — P7 and Glass-4 both write rows into it, distinguished by a schema discriminator, and only the table itself must survive.** `internal/context/handoff_envelope.go`'s own comments make this explicit: "`HandoffEnvelope` wraps a `HandoffPayload` with a schema discriminator so the reader can distinguish Glass-4 self-authored handoffs from legacy P7 stashes in the same `handoff_stashes` table" (line 17-19). Glass-4 writes envelope-wrapped rows via `MarshalHandoffEnvelope`/`ctxpkg.HandoffEnvelopeSchemaGlass4` (`schema: "glass-4"`); P7 writes bare `HandoffStashPayload` JSON with no schema field. `ParseHandoffEnvelope` (`internal/context/handoff_envelope.go:51-79`) explicitly detects and rejects legacy-shaped rows (`ErrHandoffEnvelopeWrongSchema`), and the `handoff_pointers_expand` self-tool (`internal/mcp/self_tools_handoff.go:179-207`) falls back to returning the raw payload for rows that don't parse as a Glass-4 envelope — "covers legacy P7 rows the agent might reference for some reason." **Cutting P7's write step does not require touching the table, the store methods (`UpsertHandoffStash`/`GetHandoffStash`/`GetLatestStashForSession`), or any of this schema-discrimination code — all of that keeps working for Glass-4-only traffic once P7 stops writing.**

**Verified the P7/Glass-4 coexistence logic already in the two live compaction call sites** — this is the trickiest part of the removal, read carefully. `internal/service/chat_generate.go` has two places that construct a `ctxpkg.CompactionPipeline{}` (the recovery path `recoverFromContextOverflow`, ~line 2372, and the pre-loop budget gate `enforceBudgetOrCompact`, ~line 2636). Both currently do:
```go
sess, _ := s.store.GetSession(sessionID)
longRunning := IsLongRunning(sess)
if longRunning {
    // Glass-4 fallback handoff write — KEEP, unrelated to P7
    s.ensureGlass4HandoffPreCompact(ctx, sess, chatMessages, ch)
}
pipeline := &ctxpkg.CompactionPipeline{ ..., ScratchpadSnapshot: <snapshot> }
if !longRunning {
    pipeline.StashWriter = storeStashWriter{s: s.store}  // P7 — REMOVE
}
```
The `!longRunning` guard exists so P7 doesn't clobber Glass-4's own "latest stash is the self-authored envelope" invariant for long-running sessions — non-long-running sessions still got the legacy P7 write. **This task removes the P7 write unconditionally (for every session, not just long-running ones)** — after this change, `pipeline.StashWriter`/`ScratchpadSnapshot` no longer exist as fields at all, so both `if !longRunning { pipeline.StashWriter = ... }` blocks disappear along with the field they set. The `longRunning`/`IsLongRunning` variable and the `ensureGlass4HandoffPreCompact`/`InjectGlass4HandoffSlot` calls around it are **Glass-4 logic and stay exactly as they are** — they belong to `28-cut-session-intent-classifier` (a different, not-yet-drafted Phase 0 task per TASKS.md item 28 — "making Glass-4 universal, remove the `IsLongRunning` gate"), not this one. Don't touch the `longRunning` gate itself; only remove the P7-specific field assignments nested inside it.

**Verified `scratchpadSnapshot()` (`internal/service/chat_loop_state.go:705-714`) is P7-only, not shared scratchpad-tool infrastructure.** Its own doc comment says so explicitly: "returns a shallow copy of the scratchpad for use in compaction handoff stash payloads (P7, CW-20260420-0024)." It has exactly two call sites (`internal/service/chat_generate.go:1137` and `:1445`), both solely to populate the now-dead `ScratchpadSnapshot` pipeline field via the `recoverFromContextOverflow(... scratchSnap)`/`(... midSnap)` parameter. It reads `ls.scratchpad` (the real underlying map the scratchpad tool's read/write/clear methods operate on) but does not mutate it and is not itself part of the tool surface — removing it does not touch `ls.scratchpad` or any of the tool's own methods. Once this method and its two call sites are removed, `recoverFromContextOverflow`'s `scratchpadSnapshot map[string]any` parameter (line ~2335) becomes dead — remove the parameter and update its two call sites accordingly (don't leave an always-empty/always-nil parameter as vestigial noise).

**Verified `internal/api/sessions.go`'s manual `/compact` endpoint (`handleCompactSession`) is a third, unconditional P7 call site** — unlike the two chat_generate.go sites, it has no `longRunning` gate at all: `StashWriter: service.NewStashWriter(a.Services.Store), ScratchpadSnapshot: map[string]any{}` (lines 679-680), with the comment "P7 HandoffStash: no loopState in HTTP path; empty scratchpad snapshot" (line 677). Since the HTTP path never had a real scratchpad snapshot to give it anyway (always `map[string]any{}`), removing this is strictly simpler than the chat_generate.go sites — no gating logic to preserve, just delete the two field lines and the stale comment.

**Note on `CompactionResult.HandoffStashID`** (`internal/context/compaction.go:35`): this field is only ever populated by the P7 write block (`result.HandoffStashID = stashID`, line 129) and only ever read to populate `CompactionEvent.HandoffStashID` for the (currently-unwired, Phase 5) `compaction_events` postmortem record (lines 167-169: `if result.HandoffStashID != "" { evt.HandoffStashID = &result.HandoffStashID }`). Once P7's write is removed, this field is permanently empty — remove the field and the two read sites along with it. Do **not** remove `store.CompactionEvent.HandoffStashID` (the DB-facing struct in `internal/store/compaction_events.go`) or the `compaction_events.handoff_stash_id` column — those belong to the separate, still-pending `compaction_events` wiring task (decision log §20, Phase 5) and may get a real writer again later (e.g. sourced from Glass-4's stash instead); cutting that column is out of scope here and not something TASKS.md item 27 asks for.
