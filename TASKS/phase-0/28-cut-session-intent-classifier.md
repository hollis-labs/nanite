## Context

TASKS.md Phase 0 item 28: "`ClassifySessionIntent`/`ScoreIntent`/`sessions.intent`, alongside making Glass-4 universal (remove the `IsLongRunning` gate so every session gets it, then delete the now-unused classifier)."

Decision log §23 ("Glass-4 handoff — made universal; the intent classifier is cut entirely") and `docs/engineering/architecture/06-session-lifecycle-and-recovery.md`'s "Handoffs, scratchpad, and Glass-4" section are the governing sources:

> "Glass-4 ... becomes universal — every session gets it, not just ones that scored above a threshold. Motivation: not an observed context-size problem (none seen in practice), but general, low-cost value regardless of session type. **The entire session-intent classification mechanism is cut alongside this** (`ClassifySessionIntent`/`ScoreIntent`, `internal/service/session_intent.go`, the `sessions.intent` column, `IsLongRunning`). Verified it has exactly one real consumer — gating Glass-4 — which is now moot. Reinforcing evidence this was the right call, not just a simplification: two of the classifier's weighted signals (`HasSessionMode`, `HasWorkspace`) already depend on mechanisms cut earlier in this same review (modes; the in-app `workspaces` concept), so the classifier would have silently degraded regardless."

**Verified end-to-end, matches the decision log exactly:**

- `internal/service/session_intent.go` defines `IntentSignals` (with `HasSessionMode`/`SessionModeSlug` populated from a `*store.Mode`, and `HasWorkspace` populated from `sess.WorkspaceID != ""`), `ScoreIntent` (additive weighted scorer — `+3` for `HasSessionMode` when the mode slug is one of `work`/`plan`/`planning`/`research`/`build`/`code`; `+1` for `HasWorkspace`), `ClassifySessionIntent` (buckets the score into `long-running`/`per-turn`/`ephemeral`), and `SignalsFromSession` (the assembler, taking `*store.Mode` as a parameter).
- **Exactly one real caller**: `internal/api/sessions.go`'s session-creation handler (~lines 86-103) — `service.SignalsFromSession(sess, agent, sessionMode)` → `service.ClassifySessionIntent(...)` → `a.Services.Store.SetSessionIntent(sess.ID, intent)`. No other call site anywhere in the codebase (verified via grep for `ClassifySessionIntent`/`ScoreIntent` — only `session_intent.go` itself, `session_intent_test.go`, and this one handler).
- **`IsLongRunning`** (`internal/service/handoff_glass4.go` ~line 161): `func IsLongRunning(sess *store.Session) bool { if sess == nil || sess.Intent == nil { return false }; return *sess.Intent == store.SessionIntentLongRunning }`. Its own doc comment: "Used as the gate for both the proactive Glass-4 stash hook and the post-compaction inject — per-turn / ephemeral / unclassified sessions never carry a Glass-4 handoff."
- **Exactly two call sites, both in `internal/service/chat_generate.go`**, each gating two things:
  - `longRunning := IsLongRunning(sess)` gates a call to `s.ensureGlass4HandoffPreCompact(ctx, sess, chatMessages, ch)` (the proactive stash write) in both `recoverFromContextOverflow`-shaped code (~line 2363) and `enforceBudgetOrCompact` (~line 2627).
  - The same `longRunning` var also gates `InjectGlass4HandoffSlot(s.store, result.Window, sessionID, ch)` (the post-compaction inject) a few lines later in each function (~2428 and ~2672).
  - **Note**: in the first of these two functions, `longRunning` (via `!longRunning`) *also* currently gates whether the legacy P7 stash writer (`pipeline.StashWriter = storeStashWriter{s: s.store}`) is wired — but P7 itself is being cut entirely by a separate task (TASKS.md item 27, decision log §22: "cut the extraction step only; the scratchpad tool and Glass-4 both stay untouched"). Once P7's extraction step is gone, this `if !longRunning { pipeline.StashWriter = ... }` line disappears on its own — don't treat it as this task's problem to solve if `27-cut-p7-handoff-stash-snapshot` (or equivalent) lands first; if it hasn't landed yet when this task runs, removing the `IsLongRunning` gate here means `pipeline.StashWriter` would need to be set unconditionally-false (never wired) rather than conditionally, since after this task every session is "long-running" in Glass-4 terms. Coordinate or escalate if both tasks are in flight on this file simultaneously.
- **`sessions.intent` column**: added by `internal/store/migrations/052_session_intent.sql` — `ALTER TABLE sessions ADD COLUMN intent TEXT NULL CHECK (intent IS NULL OR intent IN ('long-running', 'per-turn', 'ephemeral'))`. A `CHECK`-constrained column requires the same SQLite rename-recreate-copy dance (or a goose equivalent, if `09-adopt-goose-migrations` has landed) as other constrained-column removals in this codebase — this is not a plain `DROP COLUMN`.
- **No frontend surface**: checked `ui/src/lib/types.ts` and related components — the only `intent` fields exposed to the UI are `BrokerDecision.intent`/`InspectorBrokerDecision.intent` (the **Tool Broker**'s per-selection intent string, an unrelated system — see `22-remove-skill-and-tool-broker-abstractions`'s Context section for the same naming trap). `sessions.intent` is never rendered or read by the frontend. No frontend changes needed.
- **Naming trap to flag for the worker**: `internal/context/handoff.go`'s `HandoffPayload.SessionIntent` (a free-text narrative field inside the Glass-4 self-authored payload, e.g. `"long-running session; deterministic handoff fallback..."` in `handoff_glass4_fallback.go`) is a **completely different field** from `store.Session.Intent`/`sessions.intent` — same word, unrelated system (one is a classifier enum on the session row, the other is prose content inside a handoff envelope). Do not touch `HandoffPayload.SessionIntent` or its call sites; it stays as-is.

### Dependency reasoning on `21-cut-modes` / `20-retire-workspaces-and-instance-mechanism` (explicitly asked for)

This task **does not need** `21-cut-modes` or `20-retire-workspaces-and-instance-mechanism` to land first. The reinforcing argument in decision log §23 (`HasSessionMode`/`HasWorkspace` "already depend on mechanisms cut earlier in this same review") is *supporting evidence the cut is correct*, not a technical prerequisite — this task deletes `session_intent.go` wholesale, so it doesn't matter whether `store.Mode`/workspace fields still resolve correctly by the time this lands; the whole scoring mechanism that reads them is going away regardless, not being preserved in degraded form.

**However, there is a real file-overlap risk worth flagging, not a dependency**: `internal/api/sessions.go`'s session-creation handler (the block this task removes) currently calls `a.Services.Store.GetSessionMode(sess.ID)` to obtain the `*store.Mode` passed into `SignalsFromSession`. If `21-cut-modes` lands *first* and removes `store.Mode`/`GetSessionMode` from the codebase before this task starts, `internal/api/sessions.go` will already fail to compile at that call site — which is fine, because this task's own worker will be removing that exact block anyway (verify it's already broken/removed rather than re-introducing it). If this task lands *first*, the classify-and-set block (including the `GetSessionMode` call) disappears entirely, and `21-cut-modes`'s worker won't find anything session-intent-related left to touch in this file. **Both tasks touch the same ~20-line region of `internal/api/sessions.go`.** Per `EXECUTION-PROCESS.md`'s parallelization-safety check ("For every pair of tasks you're considering running in parallel, explicitly check they don't touch overlapping files... If there's any doubt, serialize them"), **this task and `21-cut-modes` must not run in parallel** — the Orchestrator should serialize them (order doesn't matter, but not simultaneously) to avoid a merge collision on the same lines.
