### Reality check #1 — the mechanism is materially bigger and more live than "barely adopted" suggests. Report this prominently.

`prompt_templates`/`agent_prompt_templates` is not just a compaction-disclosure content store. `ComposePromptForAgent` (`internal/store/prompt_templates.go:255-305`) is the **live system-prompt assembly path for the canonical `file-default` chat agent** — called from `internal/chat/context_client.go:620` inside `assembleAgentSlotContent`, which every system-prompt assembly path passes through. Migration `027_chat_role_harness_prompt.sql` is the **only** `INSERT INTO agent_prompt_templates` row across all 93 migrations (`grep -n "INSERT.*agent_prompt_templates\|AssignPromptTemplateToAgent" internal/store/migrations/*.sql` confirms this — TASKS.md's "one real assignment ever" claim is accurate on this specific point) — it assigns `blt-chat-harness-001` (the actual "You are a helpful AI assistant embedded in the Nanite chat harness..." identity prompt) to `agent_id = 'file-default'`. That one assignment is what puts real, load-bearing content in front of every `file-default` chat turn today.

There is also a real, wired frontend surface beyond that one seeded row: the Agent Builder Wizard (`ui/src/components/settings/agents/AgentBuilderWizard.tsx`) lets an operator select prompt templates when creating/editing any agent, and on save loops `for (const templateId of capabilities.prompt_template_ids ?? []) { await api.assignTemplateToAgent(agentId, { template_id: templateId }); }` (line 1757-1759) — a real call into `POST /api/agents/{id}/prompt-templates`. So while only one assignment has ever been *seeded*, the wizard makes it possible for an operator to have created more at runtime; this cut removes a working (if lightly-used) feature, not just an inert seed row. Full CRUD REST surface confirmed at `internal/api/api.go:344-351` (list/create/get/update/delete templates, plus list/assign/remove per-agent).

**Why the cut is still safe** (verified, not assumed): `assembleAgentSlotContent` already has a fallback for every agent *without* a template assignment — `if composed == "" { ...use agent.SystemPrompt... }` (`internal/chat/context_client.go:625-634`). Every agent except `file-default` already goes through this fallback today (zero other assignments exist). `file-default`'s own `agent_profiles.system_prompt` is kept in lockstep with the exact same canonical content the `chat-role-harness` template serves, via the file-source-of-truth boot sync documented in `internal/agent/builtin/profiles/default.md`'s frontmatter (PROMPT-SYNC comment: "`internal/agent/builtin/profiles/*.md` [is] the file source-of-truth for ALL internal agents — boot-time sync replaces the `source='internal'` agent_profiles row body with this file's contents on every Nanite start"). Migration `058_universal_rules_extract.sql`'s own comment confirms the same demoted body is maintained in both places by hand ("`internal/agent/builtin/profiles/default.md` is the canonical markdown source and has been demoted in parallel ... When the demoted body changes, edit `default.md` AND the SQL strings below in lockstep"). So removing `ComposePromptForAgent` and always taking the `agent.SystemPrompt` path should be functionally equivalent for `file-default` — **but this is a claim to verify against the live DB, not just trust from the comments** (see What to do, step 1).

### Reality check #2 — "since modes are being cut" is an imprecise citation; the actual dependency reasoning is independent of `21-cut-modes`

TASKS.md's rationale conflates two unrelated "mode" concepts that happen to share vocabulary. The 4 disclosure variants (`compaction-disclosure-general`/`-code`/`-plan`/`-research`, seeded by `internal/store/migrations/030_compaction_disclosure_prompts.sql`) are selected by `disclosureSlugForMode(evt.SummaryMode)` (`internal/chat/context.go:100-111`), where `SummaryMode` comes from `CompactionEvent.SummaryMode`, which is populated from `CompactionPipeline.Mode`, which is set by `classifyModeFromAgentTags(agent)`/`ClassifyCompactionMode` (`internal/service/chat_generate.go:2814-2886`) — **a heuristic that inspects `agent.Tags` for substrings like "code"/"engineer"/"plan"/"research"**. This is a completely different mechanism from the Session Mode system `21-cut-modes` removes (the `modes` table, `sessions.current_mode_id`, slash commands, `ClassifyMode`). `classifyModeFromAgentTags`/`CompactionMode` is not part of that cut at all — it continues to exist after `21-cut-modes` lands, and it's still actively used elsewhere: `p.Mode` also selects the summarizer's system prompt during real compaction (`summarySystemPrompt(p.Mode)`, `internal/context/compaction.go:271`) — **this task does not touch that**, only the disclosure-template lookup.

Given that, the actual reasoning for collapsing 4 disclosure variants into 1 doesn't route through `21-cut-modes` at all — it's simply: the 4 texts share ~90% identical structure (Compaction Notice → Preserved/Lost → Recovery: handoff stash id, `chat_search`, summary metadata) and differ mainly in which nouns get preserved/lost per domain; collapsing them into one unified message that doesn't need a mode lookup is a reasonable simplification on its own merits, independent of any other Phase 0 item. **Depends on: none** — do not block this task on `21-cut-modes`.

### Verified: the compaction-disclosure mechanism is currently unreachable in practice (separate finding, not a reason to skip step 1)

`renderCompactionDisclosure` (`internal/chat/context.go:43-69`) starts with `evt, err := s.GetLatestCompactionEvent(ctx, sessionID)`. Per decision log §20, `compaction_events` has no writer wired at either production call site yet (Phase 5 work) — meaning `evt` is `nil` today and the disclosure never actually injects in a live session. This doesn't change what to do here (the relocation should still happen so the feature is correct once §20's wiring lands), but it does mean there's no way to manually dogfeed-verify the *disclosure rendering itself* end-to-end before `compaction_events` is wired — verify it by direct unit test against a synthetic `CompactionEvent`, not by triggering a real compaction and expecting to see it in a chat session.
