**Verified: this is a genuine three-generation naming fossil, exactly as decision log §33 and `docs/system-audit/2026-08-17/code-architecture/15-envelope-system.md` describe** (Fragments Engine → Volon → Nanite is the brand-name lineage; each rename left its fence tag recognized somewhere for backward compatibility with already-persisted messages):

### Backend fence-tag parsing — one location
`internal/chat/envelope.go:222-223`:
```go
// envelopePattern matches fenced code blocks with volon-envelope or nanite-envelope language tags.
var envelopePattern = regexp.MustCompile("(?s)```(?:volon-envelope|nanite-envelope)\\s*\n(.*?)```")
```
This is the **only** backend fence-tag parser (`ParseEnvelopes`, called from wherever assistant message content needs envelope extraction). It already does NOT recognize `fragments-envelope` — confirms the system-audit doc's finding. `internal/chat/envelope_test.go` has 4 literal `"volon-envelope"` occurrences (lines 17, 45, 89, 92) exercising this regex — these need to change from "assert volon-envelope IS parsed" to "assert volon-envelope is NOT parsed" (or be removed if that's redundant with a positive `nanite-envelope`-only test), not just find-and-replaced to `nanite-envelope` (which would silently stop testing the drop).

### Frontend fence-tag parsing — two independent locations (confirmed the doc's claim of a real backend/frontend inconsistency)
- `ui/src/components/chat/ChatMessage.tsx:269` (live-streaming path, before `message.envelope` is populated): `` /```(?:volon-envelope|nanite-envelope|fragments-envelope)\s*\n([\s\S]*?)```/g ``
- `ui/src/components/chat/MessageContent.tsx:224` (strip-fences-from-display-text) and `:229` (detect-open/incomplete-fence for the streaming placeholder) — same three-alternative pattern, duplicated.

Both frontend locations currently recognize all three tags (`nanite-envelope`, `volon-envelope`, `fragments-envelope`); the backend recognizes two (`nanite-envelope`, `volon-envelope`). **All three call sites need to end up with the same single alternative: `nanite-envelope` only.**

### Confirmed: zero live backend emission path writes anything but `nanite-envelope` today
Checked every place the backend constructs an envelope-fenced block: `internal/chat/commands.go:388`, `internal/chat/errors.go:113`, `internal/runtime/agent/sandbox_content_claude.go:45`, `internal/runtime/agent/sandbox_content_envelope.go:12`, `internal/mcp/self_tools.go:409`, `internal/service/chat_generate.go:1801`, `internal/mcpserver/handlers.go:45` — every one already emits `` ```nanite-envelope ``. **`volon-envelope`/`fragments-envelope` parsing exists purely as backward compatibility for already-persisted historical messages** (chat history written back when the app was still called Volon, or before that, Fragments Engine) — there is no live code path that could regress by dropping them. This matches decision log §33's "no need to preserve" framing for `fragments-envelope` and extends the same reasoning to `volon-envelope`.

**Real, concrete consequence of dropping this parsing you should know going in (not a reason to not do it — decision log is explicit this is wanted — just don't be surprised by it):** any already-persisted assistant message in the DB whose content still contains a literal `` ```volon-envelope `` or `` ```fragments-envelope `` fence (from before the `nanite-envelope` rename) will, after this change, render as a raw unparsed code block/JSON blob on reload instead of a rendered Card, for both the backend `ParseEnvelopes` path and the frontend re-parse path. Given "No agents run in production during this work" and the standing aggressive dead-code policy (decision log §8), this is accepted, not a regression to work around — but confirm this in your Work Log rather than assuming.
