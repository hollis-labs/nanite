# Add `known_tools` catalog, `agent_tools` join, `agent_dispatch_allowlist` — replace free-text tool assignment

**Phase:** 1
**Status:** implemented
**Depends on:** none functionally, but land before or alongside `08-kill-file-reingest-on-boot-pattern.md` (that task's `seedRoleToolsFromIngest` cleanup references this table)
**Touches:** new migration (`known_tools`, `agent_tools`, `agent_dispatch_allowlist` tables), `agent_profiles.tools`/`tool_permissions`/`role_tools` columns (deprecate, do not drop yet — see Context), `agent_profiles.parent_dispatch_allowlist` (**naming-collision risk with the new `agent_dispatch_allowlist` table — read Context before naming anything**), `internal/service/tool.go` (`SelectForAgent` — eventual real consumer, wiring itself may be a follow-up task, see What to do), `internal/service/ingest.go` (`seedRoleToolsFromIngest`)

## Context

Architecture doc `01-agent-construction.md`: *"`known_tools` — live-synced catalog. status=unavailable, not deleted, when a server disconnects. `agent_tools` — join, replaces `tools:`/`toolPermissions:`/`roleTools:` entirely... `agent_dispatch_allowlist` — separate concept from `agent_tools`: which tools this agent may authorize a subagent it dispatches to use."*

### Today's mechanism, verified — no separate YAML frontmatter field, three JSON-blob columns instead

There is no standalone `toolPermissions:`/`roleTools:` frontmatter field as such. `agent_profiles.tools`/`tool_permissions`/`mcp_servers` are plain JSON-TEXT columns, populated both from `.md` frontmatter (`internal/agent/parser.go`) and directly via the REST API (`internal/builders/agent_builder.go`). `agent_profiles.role_tools` (migration `070`) is the closest existing thing to a seed-the-roster mechanism: `internal/api/agents.go`'s boot-time hook parses `role_tools` JSON and inserts one `agent_known_tools` row per entry (`pinned=1, reason='role_seed'`) — but migration `070`'s own comment is explicit this is "NOT a contract the runtime enforces," a best-effort enrichment, not the real selection path. `known_tools`/`agent_tools` formalizes this into a real FK-based contract.

### `known_tools` (new) vs. `agent_known_tools` (existing, live, do not confuse)

`agent_known_tools` (`internal/store/migrations/069_per_agent_state.sql:22-32`) is a **live, currently-used** per-agent roster table: `agent_id` (real FK to `agent_profiles`), `tool_name TEXT` (bare string, no catalog to reference — this is exactly the gap `known_tools` closes), `pinned`, `activation_count`, `ttl_seconds`. It has a real REST CRUD API (`internal/api/agent_capabilities.go`) and a live GUI (`AgentCapabilitiesPanel.tsx`). **`known_tools` (this task's new table) is a different thing: a global tool catalog** (one row per real tool that exists in the system, live-synced against builtins + MCP discovery), not a per-agent roster. `agent_tools` (also new, this task) is the join between `agent_profiles` and `known_tools` — the actual replacement for `tools:`/`toolPermissions:`/`roleTools:`. **Do not merge or rename `agent_known_tools` as part of this task** — it stays as the per-agent pin/activation-tracking table; `agent_tools` is the new FK-based grant table sitting alongside it. Flag this distinction explicitly in code comments given the codebase's documented history of exactly this kind of naming collision (`GLOSSARY.md`'s stated reason for existing).

### `agent_dispatch_allowlist` (new) vs. `agent_profiles.parent_dispatch_allowlist` (existing) — likely different concepts, verify before naming

`agent_profiles.parent_dispatch_allowlist` (migration `060_agent_parent_dispatch_allowlist.sql:48`) already exists today: a JSON array of **role slugs** (e.g. `["researcher","planner","worker"]`) a parent agent may dispatch to, read by the Tool Broker Describe hook. The architecture doc's new `agent_dispatch_allowlist` is described as "which **tools** this agent may authorize a subagent it dispatches to use" — a different axis (tools, not target roles). **Before creating a table named `agent_dispatch_allowlist`, confirm with a direct read of the architecture doc's intent and a `GLOSSARY.md` check whether these are deliberately two different mechanisms that happen to share a near-identical name, or whether the new table is meant to supersede/absorb the existing column.** If both are real and distinct, rename one to avoid the collision (e.g. `agent_dispatch_tool_allowlist` for the new one, keeping `parent_dispatch_allowlist`'s existing name) rather than shipping two "dispatch allowlist" concepts with confusingly similar names — this is exactly the class of naming risk `GLOSSARY.md` exists to catch before it ships, not after.

## What to do

1. Create `known_tools`: `id`, `name` (unique), `source` (builtin/mcp/plugin), `status` (`available`/`unavailable` — not deleted on disconnect, per architecture doc), `description`, `concurrency_safe` (placeholder for `06-tool-concurrency-safety-classification.md`'s Phase 3 work — coordinate naming, don't duplicate the column), `created_at`/`updated_at`. Live-sync against builtins + current MCP discovery at startup (mirroring how `agent_known_tools.tool_name` values are populated today, but as a global catalog, not per-agent).
2. Create `agent_tools`: `agent_id FK -> agent_profiles`, `tool_id FK -> known_tools`, replacing `tools:`/`tool_permissions:`/`role_tools:`'s selection semantics. Mark a subset of `known_tools` rows as always-included defaults (per architecture doc: *"so a new agent can't accidentally ship without the tool-discovery escape hatch — `request_tools`/`tool_list`/`tool_describe`... a flag on `known_tools`... not a per-creation-flow default that can be silently dropped"*).
3. Resolve the `agent_dispatch_allowlist` naming question above before creating any new table/column; implement per that resolution.
4. Deprecate (do not drop) `agent_profiles.tools`/`tool_permissions`/`role_tools` — mark clearly as legacy, migrate their current values into `agent_tools` for every existing agent as part of this task (not deferred to `10`, since `10`'s scope is the `.nanite/agents/*.md` → `roles`/`agents` migration specifically, not the tool-assignment migration). Actually wiring `internal/service/tool.go`'s `SelectForAgent` to read `agent_tools` instead of the legacy columns may be substantial enough to warrant its own follow-up task if it grows beyond a straightforward read-path swap — assess during implementation and escalate/split if so, rather than silently under-scoping this task.
5. Update `internal/service/ingest.go`'s `seedRoleToolsFromIngest` to write into `agent_tools` (or confirm it should be retired entirely once `known_tools`/`agent_tools` is the real contract, superseding the "best-effort enrichment" it currently provides) — coordinate with `08`'s reingest cleanup so this isn't done twice.

**Schema (migration `110_known_tools_and_agent_tools.sql`, next number after `109` — verified via `ls internal/store/migrations/` at start, since other Phase 1 workers are landing migrations in parallel).**
- `known_tools`: `id`, `name` (unique), `source`, `status` (`available`/`unavailable`, never deleted), `description`, `concurrency_safe` (nullable placeholder for Phase 3 item `06`, confirmed that task expects this exact column name/table), `always_included`, timestamps. Seeded with `request_tools`/`tool_list`/`tool_describe` as `always_included=TRUE` placeholder rows (`INSERT OR IGNORE`) so the escape-hatch flag exists from migration time, not just after the first `SyncKnownTools` boot pass.
- `agent_tools`: `(agent_id, tool_id)` composite PK, real `ON DELETE CASCADE` FKs to `agent_profiles`/`known_tools` (brand-new table, no rebuild-dance needed unlike `107`'s retrofit), plus a `granted_via` provenance column (`explicit`/`role_seed`/`legacy_backfill`) mirroring `agent_known_tools.reason`'s established precedent.
- `agent_dispatch_tool_allowlist`: same shape as `agent_tools`, no `granted_via` (nothing seeds it yet — see Deviations).
- `agent_tools_legacy_backfill`: a small marker table (`agent_id` PK) — **not in the original plan**, added after a real bug found during testing (see Deviations).

**Go layer.**
- `internal/store/known_tools.go`: `KnownTool` struct + `ListKnownTools`/`ListAvailableKnownTools`/`ListAlwaysIncludedKnownTools`/`GetKnownToolByName`/`UpsertKnownTool` (upsert-by-name, deliberately never touches `always_included`/`concurrency_safe` on conflict)/`MarkKnownToolsUnavailableExcept`.

- `internal/service/known_tools_sync.go`: `SyncKnownTools(ctx, st, catalog, isBuiltin)` — upserts one row per currently-registered tool (source classified `builtin` vs `mcp` via `ToolClient.IsBuiltinTool`; see Deviations on the `plugin` sub-classification), then marks anything not in the current catalog `unavailable` (never deleted).
- `internal/service/known_tools_backfill.go`: `BackfillAgentToolsFromLegacyColumns(ctx, st)` — the one-time-per-agent carry-over of `agent_profiles.tools`/`role_tools` (unioned as patterns, glob-matched via `toolclient.MatchPattern` against the live catalog) filtered through `toolclient.ParsePermissions(agent.ToolPermissions).CheckPermission` — i.e. it replays today's real two-stage selection filter against the live catalog once, so the backfilled grants match today's actual effective selection, not an approximation. `role_tools` entries are deliberately included as real grant candidates (upgrading them from their current zero-effect-on-selection status) per the architecture doc's framing that `agent_tools` replaces `roleTools:` "entirely" — this is a documented behavior upgrade, not a parity bug, and has zero live effect until the follow-up (`11`) wires the read path.
- `internal/service/ingest.go`'s `seedRoleToolsFromIngest`: unchanged behavior for `agent_known_tools`; added a second write into `agent_tools` (`granted_via='role_seed'`) per name that resolves against `known_tools`, matching the backfill's upgrade. Names not yet in the catalog are skipped for `agent_tools` without failing ingestion (still recorded in `agent_known_tools` as before).
- `internal/service/container.go`: wired `SyncKnownTools` right after the existing `catalog := cfg.ToolClient.ListTools()` block (before `AutoIngestAgents`, since `seedRoleToolsFromIngest` needs `known_tools` rows to already exist), and `BackfillAgentToolsFromLegacyColumns` right after `AutoIngestAgents` (so brand-new agents ingested on the same boot are covered by the backfill too).
- `internal/store/agents.go`: added `agent_tools`/`agent_dispatch_tool_allowlist`/`agent_tools_legacy_backfill` to `DeleteAgent`'s explicit per-agent cleanup list (belt-and-suspenders alongside the real `ON DELETE CASCADE` FKs, matching this list's existing style for `agent_skills`/`agent_projects`). Added `DEPRECATED` doc comments to `AgentProfile.Tools`/`.ToolPermissions`/`.RoleTools` pointing at `agent_tools` and this task/its follow-up — columns are **not dropped**, per the task's own instruction, and are still the live read path until `11` lands.

**`SelectForAgent` wiring — deferred to a new follow-up, not silently under-scoped.** Verified directly against `internal/service/tool.go` and `internal/toolclient/permissions.go`: `agent_profiles.tool_permissions` is glob-capable `allow_list`/`deny_list` with deny-wins-over-allow semantics (`toolclient.ToolPermissions.CheckPermission`), and `ToolClient.SelectToolsAsProvider` itself also calls `CheckPermission` internally before tools ever reach `service/tool.go`. `agent_tools` (per the architecture doc's own stated shape) is a plain positive-grant join with no deny/glob-exclusion concept — there is no "grant everything except a glob" shape available. Rewiring the live selection path therefore requires a real design decision (how deny-glob semantics carry forward, whether the inner `toolclient` permission pass also gets rewired) that the architecture doc does not answer, not a mechanical read-path swap. Filed `TASKS/phase-1/11-wire-select-for-agent-to-read-agent-tools.md` per this task's own instruction to split rather than under-scope; the one-time backfill above already resolves "what should the *data* look like today" by replaying `CheckPermission` at backfill time, so `11` starts from data that already matches live behavior.

**Deviations from the original plan.**
1. **Added `agent_tools_legacy_backfill` (not in the architecture doc or original plan).** First implementation used `agent_tools` rows tagged `granted_via='legacy_backfill'` as the one-time-per-agent guard. Testing (`TestBackfillAgentToolsFromLegacyColumns_RunsOncePerAgent`) caught a real bug: if an operator later revokes the *only* such row for an agent, the guard disappears along with it, and the next boot silently re-derives and re-grants the very tool the operator revoked — exactly the "reingest overwrites a GUI customization" anti-pattern the architecture doc's "What's cut" section names as a real, already-fixed bug for agent profile files. Fixed by adding a small, independent marker table instead of reusing the grant rows as their own guard. `agent_tools` itself is unchanged from the architecture doc's stated `(agent_id, tool_id)` shape.
2. **`known_tools.source` only ever writes `builtin`/`mcp` at sync time, not `plugin`.** The task spec lists `builtin/mcp/plugin` as the enum. Verified there is no existing per-tool-name → owning-MCP-server → trust-tier lookup exposed by `internal/mcp.Manager` (only a per-*server*-name `tierForLocked`, not surfaced by name for an arbitrary tool) — building one is a small but real addition to a different package, out of scope for this ticket's FK-join replacement. `source` remains a free-text column so a future sync can start writing `plugin` without a schema change; noted as a known simplification rather than silently doing nothing.
3. Added test coverage beyond what was strictly asked (`internal/store/known_tools_test.go`, `agent_tools_test.go`, `internal/service/known_tools_sync_test.go`, `known_tools_backfill_test.go`) covering upsert/status-lifecycle, grant/revoke round trips, the `DeleteAgent` cascade, the always-included-survives-zero-grants Done-means bullet directly, and the one-time-guard behavior (including the regression case that caught deviation #1 above).
