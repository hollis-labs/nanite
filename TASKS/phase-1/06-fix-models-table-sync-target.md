# Fix the `models` table's `models.dev` sync target (currently writes to an in-memory overlay, not the DB)

**Phase:** 1
**Status:** implemented
**Depends on:** none, but `02-add-agents-composition-columns.md`'s `model_id` FK is only meaningful once this lands — land this first or in the same change
**Touches:** `internal/service/container.go` (`syncCatalogToRegistry`, the `modelsdev.WithOnRefresh` wiring), `pkg/models/registry.go` (`SyncFromCatalog` — the in-memory overlay this currently feeds), `internal/store/models.go` or equivalent (new DB-write path), `internal/store/seed.go` (the current one-time seed `INSERT`, confirm relationship to the new sync path)

## Context

Architecture doc `01-agent-construction.md`: *"`models` — real schema (`provider_id` FK, `context_window`, pricing, `is_enabled`) — its `models.dev` refresh target needs fixing (currently feeds an in-memory overlay, not this table)."* Decision log §4: *"`models` table already exists with a real schema and a live `models.dev` refresher, but the refresher currently feeds an in-memory overlay (`pkg/models`), not the DB table — needs reconciling before `agents.model_id` can FK against it meaningfully."*

### Exact current gap, verified

`models` table schema (`internal/store/migrations/001_schema.sql:185-198`) is real and complete: `id`, `provider_id FK -> providers(id)`, `model_id`, `display_name`, `context_window`, `max_output`, `supports_tools`, `supports_vision`, `pricing` (JSON), `is_enabled`, `sort_order`. All fields the decision log names are present — the schema isn't the gap.

The sync chain: `internal/service/container.go:885` wires `modelsdev.New(modelsdev.WithOnRefresh(syncCatalogToRegistry))`; `syncCatalogToRegistry` (`container.go:1543`) builds a `modelsdev.CatalogInput` and calls `models.SyncFromCatalog(input)` (`pkg/models/registry.go`), which "atomically replaces the catalog overlay" — an in-memory `map[string]Model` guarded by `sync.RWMutex` (`pkg/models/registry.go:~275`), **not the DB table**. **The only DB write into `models` anywhere in the repo is `internal/store/seed.go:68`'s one-time seed `INSERT`** — confirmed by grep, no `UPDATE models`/ongoing `INSERT INTO models` exists anywhere.

## What to do

1. Decide the target shape: does `syncCatalogToRegistry` get redirected to write the DB table directly (replacing the in-memory overlay), or does it write both (DB as source of truth, in-memory overlay kept as a fast-read cache layered on top)? Per the "database is the source of truth" principle, prefer DB-authoritative — but confirm no other code path depends on `pkg/models`' in-memory overlay's specific read characteristics (latency, no-DB-roundtrip) before removing it outright; if a real reason to keep it as a cache exists, keep it as a cache that's kept in sync with the DB, not as the sole store.
2. Implement the real DB-write sync path: on `models.dev` refresh, upsert `models` rows (matching by `provider_id` + `model_id`), setting `context_window`/`max_output`/`supports_tools`/`supports_vision`/`pricing`/`is_enabled` from the fetched catalog data.
3. Reconcile with `internal/store/seed.go:68`'s one-time seed — confirm the ongoing sync path correctly upserts over the seeded rows rather than conflicting with them (same `id`/`provider_id`+`model_id` matching key).
4. If the in-memory overlay (`pkg/models.Model`) is kept as a cache, confirm every current reader of it (grep `pkg/models` call sites) still gets correct data once the DB is the authoritative write target — don't leave two divergent sources of truth.

## Done means

- `models.dev` refresh cycles write real, verifiable rows into the `models` DB table (confirmed via a real refresh cycle in a dev session, not just a unit test against a fixture).
- `agents.model_id` (added by `02`) can FK against a `models` row and get real, current metadata — verified end to end (an agent composition with a `model_id` set, resolved through the cascade, produces the correct provider/model string for a real turn).
- No divergence between the DB `models` table and any retained in-memory overlay (if kept).
- `go build ./cmd/nanite/`, `go vet ./...`, `go test ./...` pass.

**Correction to the record (per EXECUTION-PROCESS.md worker step 7 — decision stands, rationale corrected).** The task context claims "the only DB write into `models` anywhere in the repo is `internal/store/seed.go:68`'s one-time seed INSERT." That's incomplete: `internal/store/seed.go`'s `SeedProviders()` also writes into `models` (via `INSERT OR IGNORE`) and runs on **every boot** (`cmd/nanite/main.go:186`, before `NewContainer`/the catalog wiring) — not one-time. It reads from `pkg/models.AllSeeded()` (the static compiled-in list), not from the models.dev catalog overlay, and `INSERT OR IGNORE` never updates a row that already exists — so the actual gap is the same as stated (no ongoing `UPDATE`/upsert path exists anywhere, confirmed via grep for `UPDATE models`/`INSERT.*INTO models` — zero hits outside `seed.go`), just for a slightly different reason than "one-time seed" implies. This doesn't change the task; noting it because it matters for how the new sync path had to reconcile with existing writes (see below).

**Step 1 — design decision: DB-authoritative write, in-memory overlay kept as a synced cache (not dropped).**
Grepped every real call site of `pkg/models`' registry functions (`ByModelID`, `Pricing`, `MaxOutputFor`, `ContextWindowFor`, `ProviderFor`, `AllSeeded`) across the repo. Four real (non-comment) call sites:
- `internal/truncate/truncate.go:65` — `ContextWindowFor` in the per-turn context-budget calculation.
- `internal/chat/engine.go:328` — `ProviderFor` in per-turn model→provider routing.
- `internal/store/usage.go:14` — `Pricing` in per-turn usage/cost recording.
- `internal/store/seed.go:66,234` — `ByModelID`/`AllSeeded` at seed time only.

Three of four are per-turn, latency-sensitive, in-process lookups with no tolerance for a DB round-trip. Per the task's own instruction ("confirm no other code path depends on the overlay's specific read characteristics... if a real reason to keep it as a cache exists, keep it as a cache that's kept in sync with the DB, not as the sole store"), this is exactly that case. Decision: keep `pkg/models`' overlay as the in-process read cache; make the `models` DB table the durable, authoritative write target, fed from the **same** merge output as the overlay (not a second, independent merge) so the two structurally cannot diverge.

**Steps 2–3 — implementation.**
- `internal/store/models.go` (new): `Store.SyncModelsFromRegistry()`. Iterates `models.AllSeeded()` (the same curated set `Seed()`/`SeedProviders()` already write — deliberately **not** every model models.dev returns for a known provider; see the real-catalog finding below for why that would have been actively harmful) and re-resolves each through `models.ByModelID()`, which checks the overlay first. Writes are **UPDATE-by-`id` first, INSERT-with-`ON CONFLICT(provider_id, model_id)` fallback** — not a single `ON CONFLICT(provider_id, model_id)` upsert as the task's wording suggested, because verifying against a real production DB backup copy (see below) surfaced a real case the natural-key-only approach misses.
- `internal/service/container.go`: `syncCatalogToRegistry` now takes `*store.Store` (threaded via a closure at the `WithOnRefresh` registration and at the warm-cache-path manual call) and, after `models.SyncFromCatalog(input)`, calls `st.SyncModelsFromRegistry()`.

**Real-DB verification (task's Done-means criterion, not skipped for a fixture).** Copied `~/.local/share/nanite/workspaces/default/backups/main.db.pre-execution-backup-20260818-132726` to a scratch path and ran the real sync path (`SeedProviders()` → build `CatalogInput` from a real `modelsdev.Client` pointed at the real, previously-fetched `~/Library/Caches/go-modelsdev/catalog.json` → `models.SyncFromCatalog` → `SyncModelsFromRegistry`) against it via a throwaway `cmd/verify06` program (built, run, and deleted before commit — not part of the shipped diff). Two real, concrete findings from this, both fixed before landing:

1. **Stale/rotated model_id, exactly the scenario step 3 asked to check for.** The real backup's `models` row `id='claude-sonnet'` had `model_id='claude-sonnet-4-20250514'` — the model `pkg/models/registry.go`'s own comment says was retired and replaced by `claude-sonnet-4-5-20250929`. `Seed()` ran once, long ago, under whatever the static registry said at the time; `SeedProviders()`'s `INSERT OR IGNORE` never updates it. A naive `ON CONFLICT(provider_id, model_id) DO UPDATE` upsert does **not** catch this: the stale row's `(provider_id, model_id)` pair no longer matches the refreshed value, so the real collision is on the `id` PRIMARY KEY, which that conflict target doesn't cover — it would have inserted a **second**, duplicate row instead of correcting the first. Fixed by matching on `id` first (the field `pkg/models.Model` keeps stable specifically so wire IDs can rotate under it), falling back to the natural-key upsert only when no row with that `id` exists yet. Verified against the real backup: the stale row is corrected in place (same `id`, `model_id` now `claude-sonnet-4-5-20250929`, `display_name`/`context_window`/`max_output`/`pricing`/`supports_vision` all refreshed to current values), no duplicate created. Added `TestSyncModelsFromRegistry_ReconcilesRotatedModelID` (`internal/store/models_test.go`) as a permanent regression test reproducing this exact fixture.
2. **Pre-existing cross-provider collision in the overlay merge itself (ADR-001), unrelated to this task's stated scope but directly threatening its Done-means criterion ("get real, current metadata").** The real models.dev disk cache (190 providers) has multiple reseller/gateway providers (`qihang-ai`, `302ai`, `jiekou`, `nano-gpt`, `helicone`, `llmgateway`, `abacus`) that list `claude-sonnet-4-5-20250929` verbatim at different pricing/context values than Anthropic's own listing. `modelsdev.CatalogInput`'s maps are keyed by bare model ID with **no provider dimension** (ADR-001 calls this "provider-agnostic" by design) — so without scoping, `qihang-ai`'s discounted numbers (0.43/2.14 per-M, 200K context) silently overwrote Anthropic's real ones (3/15 per-M, 1M context) in the overlay, and — because this task wires the DB write through that same overlay — would have landed those wrong numbers in the `models` table too. This is a real, already-live bug in the already-merged overlay design, not something introduced by this task, and touching `syncCatalogToRegistry`/the `modelsdev.WithOnRefresh` wiring is explicitly in this task's own touch-list, so fixed it there rather than filing a separate escalation for a bug that would otherwise poison this task's own output: added `modelsDevProviderAllowlist` (`anthropic`, `openai` — the providers Nanite's adapters actually call) and filter `c.List()` refs against it before building `CatalogInput`. Re-verified against the same real backup + real disk cache: `claude-sonnet-4-5-20250929` now correctly shows context_window=1,000,000, max_output=64,000, pricing 3/15 (Anthropic's real listing). Documented as a correction to ADR-001's "Limitations" section (`docs/decisions/ADR-001-models-catalog-sync.md`) — Option C (the overlay pattern itself) is not reopened, only the provider scoping of what feeds the merge.

**Step 4 — no divergence.** `SyncModelsFromRegistry` reads exclusively through `models.ByModelID()` (overlay-then-static) — there is exactly one merge (`models.SyncFromCatalog`), and the DB row is a direct materialization of whatever that merge currently returns for each seeded model. No second, independent merge algorithm exists. Verified this explicitly in `TestSyncModelsFromRegistry_UpsertsRealRows` (asserts DB `context_window`/`max_output` equal `models.ByModelID(...)`'s live overlay values after a simulated catalog refresh) and empirically against the real backup DB (context_window/max_output/pricing in the DB after sync matched `models.dev`'s real, current listing exactly).

**Scope discipline.** Deliberately did **not** write DB rows for every model models.dev returns for a matching provider (e.g. Anthropic alone lists 13 models in the real catalog, OpenAI 47 — vs. the ~7 curated chat models Nanite actually seeds). `SyncModelsFromRegistry` stays scoped to `models.AllSeeded()`'s curated set, matching exactly what `Seed()`/`SeedProviders()` already write. Importing models.dev's full long-tail catalog into `models` would flood `GET /api/models`'s composer dropdown with rows the runtime doesn't otherwise know how to route — a real UX regression the task didn't ask for and "Done means" doesn't require.
