## Context

Architecture doc `02-agent-launching.md`: *"`agents.runtime_kind` (`cli` | `api`) replaces a fragile four-site string-prefix convention... that has caused real historical misrouting bugs. One typed field, checked once, not a string pattern matched in four places expected to stay in sync by convention."*

### The four sites, exact and self-documented in the code itself

`internal/chat/engine.go:283-291`'s own doc comment on `NormalizeCLIProvider` names all four explicitly as "the single source of truth consulted by": (1) `chat_generate.go`'s CLI bypass when the registry returns `prov == nil`, (2) `runtime/agent/bootdir.go`'s layout dispatch, (3) `runtime/agent/factory.go`'s `shouldUsePTY` check, (4) `service/agent_deps.go`'s `stripRegistryPrefix` (which delegates to `NormalizeCLIProvider` rather than re-implementing prefix logic itself — already partially consolidated, but still a fifth call site consuming the string-prefix convention rather than a typed field).

`IsCLIProvider` (`engine.go:256-258`): `name == "pty" || strings.HasPrefix(name, "pty-") || strings.HasPrefix(name, "sub-")`. `IsPTYProvider` (`:261-263`): narrower, PTY-only variant. `NormalizeCLIProvider` (`:292-303`): strips `pty-`/`sub-` prefixes, maps legacy bare `"pty"` → `"claude"`.

**A fifth, distinct site**: the boot-profile catalog has its *own* parallel `pty-claude`/`pty-codex`/`pty-opencode` handling in `internal/bootprofile/compiler.go` (confirmed via its test fixtures using exactly these provider-alias strings) — this is the "boot-profile catalog's own layered `pty-` prefix convention" architecture doc `02` names separately from the four `engine.go`-documented sites. This task does not need to fix the boot-profile catalog's version (`02-retire-boot-profile-catalog.md` removes the whole mechanism), but must confirm it isn't left as a still-live, un-migrated sixth routing decision once this task's four/five sites are converted — i.e. sequence such that nothing routes through the old convention by the time both this task and `02` are done.

### `resolveProvider` is a separate, adjacent mechanism — not one of the four, but reads `IsCLIProvider`

`internal/service/chat.go:1141-1195`'s `resolveProvider` calls `chat.IsCLIProvider(runtimeProvider)` at line 1157 as one step in its own fallback chain (session → agent → user-default → fallback-chain → inferred). This task's job is the four/five string-prefix sites; `resolveProvider`'s own chain collapsing into the construction cascade is `05-collapse-resolveprovider-into-cascade.md`'s job — but that task's replacement logic will itself need `runtime_kind`, so land this task first or in the same batch.

### Design decision: OR runtime_kind with the legacy check, don't replace it outright (documented in code, not silent)

`classifyNilProvider`'s gate is `runtimeKind != "cli" && !chat.IsCLIProvider(providerName)` — an OR, not a straight replacement — for two concrete, still-live reasons, both called out in the function's own doc comment and in `IsCLIProvider`'s doc comment in `engine.go`:

1. A file-discovered agent profile with no `agent_profiles` DB row yet has `RuntimeKind == ""` (`Definition.ToProfile()` has no frontmatter representation for it at all — see `agent.OverlayDBFields`'s doc comment, confirmed by reading `internal/agent/convert.go`).
2. The boot-profile catalog (`internal/service/chat_bootprofile_resolve.go`'s `cliRoutableProvider`) **is still live** and synthesizes a `"pty-<adapter>"` alias to force CLI routing *independent of whichever agent happens to be bound to the session* — this is exactly the "boot-profile catalog's own layered pty- prefix convention" this task's coordination note flags as a parallel routing mechanism not to break. It is retired in full by `TASKS/phase-2/04-retire-boot-profile-catalog.md`, not this task; until that lands, a pure `runtime_kind`-only gate would break every currently-working boot-profile-driven CLI session.

**This was validated against real production data, not just theory.** I copied a real backup (`~/.local/share/nanite/workspaces/default/backups/main.db.pre-execution-backup-20260818-132726`) into an isolated scratchpad location (never the live tracked DB), opened it through the real `store.New` (which runs the full goose migration chain including migration 117) via a temporary throwaway `_test.go` file in `internal/store/` that was deleted immediately after use (confirmed via `git status --short` before and after — clean both times, no accidental writes to any tracked file), and queried `agent_profiles`. **Every one of the 28 real agent rows has `default_provider = ''` and a backfilled `runtime_kind = 'api'`** — none of this project's `.nanite/agents/*.md` files declare a `model:`/`provider:` frontmatter field at all (confirmed via grep across the fleet). This means: in the *current* real deployment, every CLI session that has ever run did so entirely via a session-level provider override (the composer dropdown / boot-profile catalog), never via any agent's own `runtime_kind`/`default_provider`. A pure `runtime_kind`-only conversion (no OR fallback) would have silently broken **every** currently-working CLI session in this deployment — this is exactly the kind of "verify every existing CLI and API agent still launches correctly... zero intended behavior change" regression the task explicitly warns against, and the OR design is what prevents it while still making `runtime_kind` authoritative for any *newly* CLI-configured agent (validated by `TestClassifyNilProvider_RuntimeKindCLI_Authoritative`). The OR's legacy-fallback branch is explicitly flagged in three places (`IsCLIProvider`'s doc comment, `classifyNilProvider`'s doc comment, `cliRoutableProvider`'s doc comment) as dead code to delete once `TASKS/phase-2/04-retire-boot-profile-catalog.md` lands, so it doesn't become a silent, permanent second decision input.
