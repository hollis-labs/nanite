# Collapse `resolveProvider`'s fallback chain into the construction cascade; fold in `MessageWakePolicy`'s equivalent collapse

**Phase:** 3
**Status:** implemented
**Depends on:** Phase 1's `agents.model_id` (`TASKS/phase-1/02-add-agents-composition-columns.md`) resolved through a real cascade (`TASKS/phase-1/01-add-roles-table-and-cascade-resolution.md`); `TASKS/phase-2/01-wire-runtime-kind-routing.md` (this task's replacement logic needs `runtime_kind` already wired)
**Touches:** `internal/service/chat.go` (`resolveProvider`, `tryProviderCandidate`), `internal/chat/engine.go` (`InferProvider`), `internal/service/messaging_reactor.go` (`resolveMessageWakePolicy` — folded into this task, see Context)

## Context

Architecture doc `02-agent-launching.md`: *"`resolveProvider`'s bespoke fallback chain collapses into the construction-model cascade... Once an `agents` row has a real, cascade-resolved `model_id`, provider/model resolution is 'read the already-resolved value,' not a second independent walk."*

### `resolveProvider`'s exact current chain, verified

`internal/service/chat.go:1141-1195`: (1) `sessionProvider` (if set, checked against `s.providers`/CLI-provider check), (2) `agentProvider` via `tryProviderCandidate`, (3) `user_settings.default_provider`, (4) `user_settings.ProviderFallbackChain` (iterated), (5) `chat.InferProvider(model)` as the final floor. Five independent steps, none of which read a cascade-resolved value — each one is its own bespoke lookup.

### Real, confirmed bug this task must fix: `resolveProvider` can silently override an explicitly-set `runtime_kind='cli'`

Found and empirically confirmed twice independently during Phase 2's close-out (Orchestrator's live dogfeed validation against the running `nanite-api-service`, and the fresh Phase 2 Reviewer's own throwaway probe test against the real `resolveProvider` method — both 2026-08-19; see `TASKS/ESCALATIONS.md`'s matching 2026-08-19 entries for the fuller trail). `01-wire-runtime-kind-routing.md` correctly wired `agent.RuntimeKind` into `classifyNilProvider` — but `classifyNilProvider` is only ever reached when `resolveProvider` (this task's own target, still untouched) returns a **nil** `llmcontracts.Provider`. `resolveProvider`'s existing five-step chain (session → agent → `user_settings.default_provider` → fallback-chain → `chat.InferProvider(model)`) has zero awareness of `runtime_kind` and returns early with a real, non-nil provider the moment *any* step resolves to a registered HTTP provider — which is the normal case for `user_settings.default_provider`/`InferProvider(model)` in any installation with at least one HTTP provider configured (nearly all of them). Concretely: an agent configured the "obvious" way post-Phase-2 — `runtime_kind='cli'`, a bare `default_provider` (e.g. `"claude"`, not the legacy `"pty-claude"`/`"sub-claude"` alias shape) — never reaches `classifyNilProvider` at all; `resolveProvider` silently resolves it to a real HTTP provider instead, and the turn routes through the API path with **no error, no warning distinguishing this from correct routing**. Doesn't regress any currently-live agent (confirmed: all 28 real rows in the production DB backup have `default_provider=""` and `runtime_kind` backfilled to `'api'`), but it's a live landmine for the very first agent configured with `runtime_kind='cli'` going forward — exactly the "silent fail-open" pattern `standards/code-quality.md` flags as this codebase's most-repeated real defect class.

**This task's rewrite (item 1 below) must close this specific gap as part of "read the cascade-resolved value as the primary path"** — the rewritten `resolveProvider` must consult `runtime_kind` before (or as part of) walking any fallback step that could resolve to a real HTTP provider, so a `runtime_kind='cli'` agent can never silently end up on the HTTP path regardless of what `default_provider`/`user_settings.default_provider`/the fallback chain would otherwise resolve to. Add explicit test coverage for exactly this case (a `runtime_kind='cli'` agent with a bare, non-prefixed `default_provider`, alongside a registered HTTP provider and a populated `user_settings.default_provider` — confirm the turn still routes CLI, not HTTP) — this is the literal reproduction the Reviewer used to confirm the bug and is not covered by any existing test in `chat_generate_cli_bypass_test.go` today.

### `MessageWakePolicy`'s resolution — same shape, folded into this task rather than a standalone Phase 5 task

Verified during Phase 5 planning research: `internal/service/messaging_reactor.go:87-121`'s `resolveMessageWakePolicy` is a three-step chain — `session.Metadata`'s `message_wake_policy` JSON key → `agent.Constraints` (`chat.ParseAgentConstraints`, resolved via `ResolveForSessionReadOnly`) → hardcoded `chat.SubagentPolicyAutoSummarize` fallback. Decision log §29 explicitly calls this "the same shape as `resolveProvider`'s already-flagged bespoke fallback chain... a fourth independent manual resolution walk in the codebase. Collapses into the role→agent→task cascade already locked for construction rather than staying its own separate mechanism." Since this mechanism depends on the same cascade-resolution infrastructure as `resolveProvider` (not on anything messaging-specific), and TASKS.md's own Phase 5 text has no explicit bullet covering it, this task absorbs it as a second, smaller instance of the identical pattern rather than leaving Phase 5 to invent a standalone "Messaging" task for one adjacent-shaped fix.

## What to do

1. Once an `agents` row has a real, cascade-resolved `model_id` (Phase 1) and `runtime_kind` (`01`), rewrite `resolveProvider` to read the already-resolved composition value as its primary path, falling back to `chat.InferProvider(model)` only for the genuine edge case of an agent with no resolvable composition (should become rare-to-nonexistent post-Phase-1, but keep the floor for safety rather than assuming it's dead).
2. Confirm `user_settings.default_provider`/`ProviderFallbackChain` either fold into the cascade as a genuine "role-level default" concept, or are confirmed superseded entirely by per-role/per-agent `model_id` assignment — a real design decision, document which was chosen and why in this file's Work Log.
3. Rewrite `resolveMessageWakePolicy` the same way: read the cascade-resolved value from the agent's composition (a `message_wake_policy` field belongs at whichever cascade tier makes sense — likely role-level default, agent-level override, task-level override for a specific dispatch) instead of its current three-step bespoke walk.
4. Preserve exact current behavior for every existing agent/session during the rewrite — this is a resolution-mechanism swap, not a policy change; a session that resolved to a particular provider/model or wake policy before this task must resolve to the same one after, unless the operator has explicitly reconfigured something via the new cascade.

## Done means

- `resolveProvider` reads the cascade-resolved value as its primary path; the bespoke five-step chain is gone or reduced to a documented, narrow fallback.
- A `runtime_kind='cli'` agent with a bare (non-`pty-`/`sub-`-prefixed) `default_provider` routes to the CLI runtime even when a real HTTP provider is registered and `user_settings.default_provider`/the fallback chain would otherwise resolve one — verified by a new test reproducing the exact scenario in the Context finding above, not just by inspection.
- `resolveMessageWakePolicy` is similarly collapsed into the cascade.
- No behavior change for any existing agent/session's resolved provider, model, or wake policy — verified by comparing resolution output before/after for a real sample of existing sessions.
- `go build ./cmd/nanite/`, `go vet ./...`, `go test ./...` pass.

### 1. `resolveProvider` rewrite + the real bug fix

`resolveProvider` gained a fifth parameter, `runtimeKind string`, threaded from `chat_generate.go`'s call site as `agent.RuntimeKind` (the value already produced by `s.agents.ResolveForSession`'s cascade-application step, `applyScalarCascade`). `cliRuntime := runtimeKind == "cli"` is now checked at two points in the walk:

- **Step 1 (session-level):** a non-CLI-shaped explicit `sessionProvider` no longer probes the HTTP registry when `cliRuntime` is true — it warns and falls through to the agent tier instead of returning a real provider.
- **Step 2 (agent-level, the actual bug):** a non-CLI-shaped `agentProvider` (the cascade-resolved `agent.DefaultProvider`) returns `(agentProvider, nil)` immediately when `cliRuntime` is true, instead of calling `tryProviderCandidate` (which is exactly the call that silently resolved a real HTTP provider pre-fix).
- **New commit point after step 2:** if `cliRuntime` is still true after both steps above (e.g. `agentProvider == ""`), the function returns `(name, nil)` using whatever name is available (`agentProvider`, falling back to `sessionProvider`) and **never reaches** steps 3/4/5 (`user_settings.default_provider`, `ProviderFallbackChain`, `chat.InferProvider(model)`) — all three of which can only ever resolve to a registered HTTP provider name, so they are structurally unreachable once `runtimeKind=='cli'` is established. This directly closes the gap described in the task's Context section and in `TASKS/ESCALATIONS.md`'s matching 2026-08-19 entry.

When `cliRuntime` is false (every currently-real agent — see below), the control flow is byte-for-byte equivalent to the pre-fix algorithm (same conditions, same order, just restructured with early returns replaced by if/else-if/else where the new branch needed to interject) — no behavior change for any existing installation.

**Required new test** (Context's explicit acceptance criterion): `TestResolveProvider_CLIRuntimeKind_BareDefaultProvider_NeverRoutesHTTP` in `chat_resolve_provider_test.go` reproduces the exact scenario from the Reviewer's probe test — `runtime_kind='cli'`, bare `default_provider="claude"`, a registered HTTP `"anthropic"` provider present, and `user_settings.default_provider="anthropic"` populated. Asserts `resolveProvider` returns `("claude", nil)`, confirmed against `classifyNilProvider`'s own existing `TestClassifyNilProvider_RuntimeKindCLI_Authoritative` coverage (in `chat_generate_cli_bypass_test.go`, unmodified) that `("claude", nil)` is exactly the shape that completes CLI routing end-to-end via `driveBootSession` when an adapter is registered. Two companion tests added alongside it: `TestResolveProvider_CLIRuntimeKind_NoAgentProviderAtAll_StillCLI` (no agent/session provider name at all — still never falls through to `user_settings`) and `TestResolveProvider_APIRuntimeKind_BareDefaultProvider_StillResolvesHTTP` (no-regression companion: the exact same bare-provider shape on a `runtime_kind='api'` agent still resolves to the registered HTTP provider, unchanged). All 12 tests in `chat_resolve_provider_test.go` (9 pre-existing + 3 new) pass; pre-existing tests were updated only to add the new 5th parameter (`"api"` for every one, since none of them exercise CLI-runtime behavior).

### 2. Design decision (item 2 of "What to do"): `user_settings.default_provider`/`ProviderFallbackChain` are kept as a real, narrow operator-level fallback tier — NOT declared dead

Checked the real production DB backup (`~/.local/share/nanite/workspaces/default/backups/main.db.pre-execution-backup-20260818-132726`, copied to an isolated scratch path before any query — never touched the tracked backup file itself): all 28 real `agent_profiles` rows have `default_provider=""`, confirming the task's own Context claim. That means **step 2 (the cascade-resolved `agentProvider`) is a no-op for every single existing agent today** — none of them have a role/model_id/default_provider populated yet. Given that, `user_settings.default_provider` (which the real `user_settings` row has set to `"anthropic"`) is the tier that actually resolves the large majority of real sessions with no explicit `session.Provider` today (confirmed: ~69 of 343 real session rows have `provider=""`/NULL and would resolve via this tier). Declaring steps 3/4 dead and removing them, as the architecture doc's aspirational framing might suggest, would be a real behavior change for every one of those sessions — directly forbidden by this task's own "preserve exact current behavior" constraint. **Decision:** kept steps 3/4 as a documented, narrow, operator-level installation-wide floor, explicitly NOT part of the role→agent→task composition cascade (there's no role/agent-level equivalent of "one global provider preference" — it's a genuinely different kind of value), rather than declaring the doc's stated end-state already true. Documented in `resolveProvider`'s doc comment and inline at the steps 3/4 block itself.

### 3. `resolveMessageWakePolicy` collapse

Rewrote to reuse `internal/agent/override`'s shared merge engine (the same `override.Resolve(base, project, session)` `internal/service/role_cascade.go`'s `ResolveAgentCascade` is built on) instead of its own three-step bespoke if/else walk. Added a `MessageWakePolicy string` scalar field to `override.OverrideConfig` (`merge.go`), following the exact same "no live role-level source column yet, but wire the seam" precedent already established for `ModelID` in that same file — `roles` has no `message_wake_policy`-equivalent column, so the role tier is deliberately the zero value in every call; only the agent tier (`agent_profiles.constraints` via `chat.AgentConstraints.MessageWakePolicy`) and the task/session tier (`sessions.metadata["message_wake_policy"]`) ever populate a layer today. `override.Resolve(override.OverrideConfig{}, &agentLayer, taskLayer)` applies role→agent→task with the session/task layer winning, matching the prior precedence exactly (session override wins, agent default is the fallback, `auto_summarize` is the final global default). Each tier's typo-safety (`chat.IsValidSubagentCompletionPolicy`) is preserved — an invalid value at either tier is warned-and-ignored (left out of its layer) so the merge falls through to the next tier, identical to the pre-fix behavior. All 6 pre-existing tests in `messaging_reactor_test.go` pass unmodified (no signature change on `resolveMessageWakePolicy` itself — only its internals changed).

**Deliberately not touched:** `internal/service/agent.go`'s `applyScalarCascade`/`ResolveForSession(ReadOnly)` — considered writing the merged value back onto `agent.Constraints` (so `resolveMessageWakePolicy` could read a single already-cascaded field, mirroring `resolveProvider`'s `agent.DefaultProvider` pattern exactly), but rejected: `agent.Constraints` is read by many other call sites (e.g. `chat_generate.go`'s `HardCeiling`/`ConsecutiveFailCap`/`RunawayFailCap`/`IdleTimeoutSeconds` turn-loop enforcement), and round-tripping the whole JSON blob through `chat.ParseAgentConstraints`/`json.Marshal` on every `ResolveForSession` call — even though provably value-preserving on inspection — was a larger, unnecessary blast radius for a role tier that contributes nothing today. Kept the cascade merge local and self-contained to `messaging_reactor.go` instead, at the cost of `resolveMessageWakePolicy` still doing its own two lookups (`ResolveForSessionReadOnly` + `s.sessions.Get`) rather than one.
