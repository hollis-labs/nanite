### Rule 1's current feed is `promptrouter`, not `internal/agent/reflexes` — a real coupling this task must resolve

`buildBrokerInput` (`chat_broker_dispatch.go:400`) calls `promptrouter.Match(userContent, tier, pattern, promptrouter.BuiltinReflexes())` and projects the result into `in.ReflexMatchID`/`in.ReflexAgentSlug`/`in.ReflexConfidence` (confidence = `match.Reflex.Priority / 100.0`). **Today's Rule 1 *is* the promptrouter integration** — there is no existing `internal/agent/reflexes`-table-backed feed into the broker at all. This task must explicitly decide (and document the decision in this file's Work Log): does the new reflex-table-backed matcher become Rule 1's replacement feed directly, or does the `dispatch_to_agent` action kind's own predicate/trigger evaluation subsume Rule 1 entirely (i.e., a `dispatch_to_agent` reflex fires on its own trigger, no separate "broker" concept survives at all)? The latter is more consistent with "reflexes are the single steering primitive" (architecture doc 03) — prefer it unless a concrete blocker surfaces; if choosing the former, document why.

### A second, deliberately-independent consumer exists — do not collapse it

`internal/mcp/self_tools_dispatch.go`'s `callExecuteTask` (~lines 116-154) runs its *own* separate reflex match (`st.ReflexSet` — a different reflex set than `promptrouter.BuiltinReflexes()`, may include user overrides loaded via `promptrouter`'s `LoadUserReflexes()`) to populate `dispatch.ReflexHints` for the `task_execute` self-tool's own dispatch call — independent of the upstream agent-broker's decision. `chat_broker_dispatch.go`'s own header comment (lines 7-17) documents this as two deliberately separate layers: *"Both layers run. ## Work log

### Design decision 1 — `dispatch_to_agent` config shape

`internal/store/agent_reflexes.go`'s new `ReflexActionDispatchToAgent = "dispatch_to_agent"` constant, with `action_spec` JSON shape:

```json
{"agent_slug": "planner", "confidence": 0.75, "reason": "human-readable why"}
```

- `agent_slug` (string, **required**) — the target agent profile's slug/role (matches the codebase's existing `AgentSlug` vocabulary used by `dispatch.RoleAssignment`/`dispatch.ReflexHints`/`promptrouter`'s `ResolvesTo.Profile`). `internal/api/reflexes.go`'s `validateReflexDefinition` rejects a `dispatch_to_agent` row whose `action_spec` omits or empties this field.
- `confidence` (number, optional, `[0,1]`) — carried into the `event_log` metadata and the in-memory outcome; not enforced/gated anywhere (same as the retired broker's `Decision.Confidence`, which was audit-only).
- `reason` (string, optional) — defaults to `"reflex:" + reflex.Name` at the executor call site when omitted. This is the decision log §14 write-site-discipline field.

The action kind was added to `internal/agent/reflexes` (executor case — staged-only, no live hook, same pattern as `inject_reminder`/`force_tool_choice`), to `internal/store/migrations/119_agent_reflex_dispatch_to_agent.sql` (CHECK-constraint table rebuild, tested against a real backup — see Verification below), and to the CRUD/validation surface (`internal/api/reflexes.go`).

Two new predicate node kinds were added to the evaluator (`internal/agent/reflexes/evaluator.go`) to make the trigger side possible at all: `scope_tier` and `execution_pattern` — string-equality compares (`op` ∈ `{=, !=}`) against two new `reflexes.State` fields, `ScopeTier`/`ExecutionPattern`. These are populated from the **current turn's already-computed** `classify.ScopeTier`/`classify.ExecutionPattern` (via `ls.Classification()`), not from `StateCollector` (which only knows about already-persisted history) — see design note 3 in `chat_reflex_dispatch.go`'s header comment. `State` also gets a synthetic single-element `UserMessages` entry holding the raw in-flight `userContent` (not a DB read), so a `window=1` `user_regex_window`/`text_regex_window` predicate already works against the live turn text without any further plumbing — this is the substrate `02-migrate-promptrouter-to-reflexes.md` (Rule 1's phrase-match migration) will need.

### Design decision 2 — Rule-1-feed question: **subsumed, not fed directly**

Per architecture doc `03-steering.md` ("reflexes are the single steering primitive"), **no separate "broker" abstraction survives this task.** The `dispatch_to_agent` action kind's own trigger evaluation (`internal/service/chat_reflex_dispatch.go`'s new `attemptReflexDispatch`) *is* the replacement for Rules 1/5/6 — it lists active `agent_reflexes` rows filtered to `action_kind='dispatch_to_agent'` (via the existing `Store.ListAgentReflexesForAgent`, already ordered `priority DESC, created_at ASC`), evaluates each trigger with `reflexes.EvaluateTrigger` (the same exported primitive `Engine.EvaluateState` uses internally), and the first one to fire wins. "No dispatch" (former Rule 6) is simply the case where nothing fires — no explicit reflex row represents "do nothing," matching the task's own step 4 guidance.

**This is the answer `02-migrate-promptrouter-to-reflexes.md` needs:** Rule 1's promptrouter phrase-match migration should become its own `dispatch_to_agent` reflex rows (higher `priority` than the seeded `dispatch_to_agent_open_subagent` fallback below, so a specific phrase match wins over the general tier/pattern rule — mirroring the old priority-ordered rule list where Rule 1 was checked before Rule 5), using `text_regex_window`/`user_regex_window` (`scope=user`, `window=1`) predicates against the synthetic `UserMessages[0]` entry described above. No new trigger-kind plumbing should be needed for that migration; only new seed rows (or a migration mapping promptrouter's catalog into `agent_reflexes` rows).

A second, closely related but distinct design note (not one of the two required decisions, but load-bearing for anyone reading this later): **dispatch_to_agent is deliberately evaluated on its own path, not through `reflexes.Engine.EvaluateState`** (the pipeline `chat_reflexes.go`'s `evaluateAndInjectReflexes` uses for `inject_reminder`/`halt_session`/etc.). That pipeline suppresses a reflex from re-firing for 15 minutes (`Engine.recentlyFired`) — correct for a nudge, wrong for a routing decision that the retired broker re-evaluated fresh on every single turn with no cooldown. `attemptReflexDispatch` calls `reflexEngine.Executor.Apply` directly (to get the parsed `action_spec` back as an `AppliedAction`, not through the debounced per-turn pass) and bumps `fired_count` itself, without the debounce gate.

### A finding worth recording: the retired broker never actually enforced its own routing decision

`attemptBrokerDispatch`'s synthesized `task_execute` call **never threaded `decision.AgentProfile` into the call's args.** `task_execute`'s own internal `dispatch.AssignRole(tier, pattern)` independently re-derives Worker-vs-Planner from the *same* `classify.Classify` output, so the broker's decision and `AssignRole`'s decision agreed by construction for `TierOpen`+`PatternSubagent` turns — but the broker's own decision value was never actually enforced anywhere. `attemptReflexDispatch` preserves this exact behavior (synthesizes the same unmodified `task_execute` call; `AssignRole` still resolves the real target downstream) rather than adding a new hard-override mechanism, because the only place that could thread such an override (`self_tools_dispatch.go`'s `callExecuteTask`) is the file this task's brief explicitly says to leave alone. The fired reflex's `agent_slug` is therefore **declared intent + event_log telemetry, not an enforced override**, for this migration — flagged explicitly for whoever picks up promptrouter's Rule 1 migration or any future work wiring a real role-override arg into `task_execute` (would require touching `self_tools_dispatch.go`, out of scope here).

### `event_log` capture (decision log §14)

Every `dispatch_to_agent` firing writes a `dispatch_to_agent` / category `reflex` event_log row with metadata: `reflex_id`, `reflex_name`, `agent_slug`, `confidence`, `reason`, `scope_tier`, `execution_pattern`, and `alternatives_considered` (every other `dispatch_to_agent` candidate evaluated that turn, with whether it fired) — real structured reasoning, not a bare event name. A non-firing turn writes **no** event_log row (deliberate — matches every other action kind's behavior: an `inject_reminder` reflex that doesn't fire doesn't log anything either). This is a real behavior difference from the retired broker, which logged a telemetry row (`agent_broker_decisions` + `agent_broker_decision` event_log entry) on *every* consultation including chat-direct misses, plus an `agent_broker_decision` SSE wire event on every consultation. Neither the `agent_broker_decisions` table/store method/admin CLI (`cmd/nanite/admin_cmd.go`, `admin_export_decisions.go` — a real, still-useful historical-audit consumer, confirmed via grep) nor the SSE wire event type had a living FE consumer (the file's own old comment: "the FE inspector card itself is intentionally a follow-up" and was never built) — left untouched/retired respectively, not escalated, since dropping an unconsumed telemetry event alongside the call site that produced it is within this task's "full retirement of this file's broker call site" instruction.
