## Context

TASKS.md Phase 4 item 2: *"Unify the three run-another-agent surfaces into one shared request/result type."* Architecture doc `04-harness.md`: *"REST delegation, LLM-triggered subagent dispatch, and durable-agent wake all converge on the same `generateResponse` execution, but each currently has its own request/result type, draining logic, and completion-signaling mechanism. Collapsing to one shared shape is real, scoped work — keeping the genuinely different entry semantics... while unifying what's underneath them."*

### Confirmed: all three do converge on one execution path

Verified directly: all three ultimately call `Dispatcher.Run` (`internal/dispatcher/dispatcher.go:169-201`), which validates `CallerType`, stamps it on `ctx` via `WithCallerType`, and calls `d.runner.Invoke(...)` → `chatServiceImpl.generateResponse`. This is the real convergence point, not just a doc claim.

### The three surfaces, as they exist today

**A. REST delegation** — `internal/api/messages.go:75-137` (`POST /api/sessions/{id}/delegate`, `/delegate-aggregate`) → `chatServiceImpl.DelegateTask` (`internal/service/delegation.go:24-238`). Type: `chat.DelegationRequest`/`chat.DelegationResult` (`internal/chat/delegate.go:8-26`). **Synchronous drain**: a `for { select { case evt := <-ch: ...; case <-time.After(5*time.Minute): ...; case <-ctx.Done(): ...} }` loop (`delegation.go:169-237`) accumulating `delta` content directly in the calling goroutine, blocking the HTTP handler until completion, timeout, or cancellation. Completion signal: channel close.

**B. LLM-triggered subagent dispatch** — an MCP self-tool call → `subagent.Service.Spawn(ctx, subagent.SpawnRequest{...})` (`internal/subagent/service.go:597`, request type `internal/subagent/types.go:175-223`) → a persisted `subagent.Run` row → async `svc.execute`/`executeWithSlot` → `ChatRunner.Run(ctx, run *subagent.Run) (*subagent.Result, error)` (`internal/service/subagent_runner.go:530`, result type `subagent.Result{Summary, ResultJSON}`, `types.go:286-289`). Draining: async goroutine + capture channel (`drainCapture`, `subagent_runner.go:632`), gated by two detectors **unique to this surface and safety-critical, not incidental plumbing**:
- **Fabrication-suspected detection** (`errSubagentFabricationSuspected`, `detectFabrication`, `subagent_runner.go:63-74,664-691`) — tool called, no successful `tool_result`, yet non-empty assistant text.
- **Zero-output detection** (`errZeroOutput`, ~line 693+) — clean drain but nothing produced, routed to `StatusStalled`.

Completion signal: capture-channel close, classified through `classifyRunOutcome` into `subagent_runs.status`.

**C. Durable-agent wake** — `durableWakeService.Wake(ctx, instanceID, DurableAgentWakeRequest)` (`internal/service/durable_wake.go:195-250`) → `DurableAgentService.Start`/`Resume` (`internal/service/durable_agents.go:332-467`, types at lines 54-66) → `deliverWakePrompt` (`durable_agents.go:476-494`) → `DurableAgentRuntimeController.SendMessage` → `chatDurableAgentRuntimeController.SendMessage` (`internal/service/durable_agent_runtime_controller.go:57-63`) → **`ChatService.HandleMessage`** — the same entry point real user chat messages use, and the odd one out: `HandleMessage` fires `launchGeneration` in a goroutine and returns immediately (`chat.go:775`); the wake call **completes as soon as the message is queued, not when the agent finishes**. Completion tracking is instead a **lifecycle state machine**: `durable_agent_instances.status` transitions plus `durable_agent_events` rows (`recordWakeEvent`, `durable_wake.go:229-230,383-391`).

**A real, documented gap in this surface, confirmed in the code's own comments** (`durable_wake.go:307-324`): nothing ever transitions an instance's status back out of `Active` once a turn completes — for a process-class instance this is by design (Fresh-Per-Wake session policy makes "active" inert), but it means this surface's "lifecycle state machine" doesn't actually observe turn completion the way the other two surfaces' drains do. This is a real asymmetry to be honest about in the unified design, not something to paper over.

### `CallerType` doesn't map 1:1 onto the three surfaces today — this is why the dependency on Phase 0 #3 matters

The three `CallerType` values (`CallerChat`/`CallerSubagent`/`CallerBackground`, `dispatcher.go:49-68`) do **not** correspond 1:1 to surfaces A/B/C. REST delegation (A) and LLM-triggered subagent dispatch (B) both stamp `CallerSubagent`. Durable-agent wake (C) currently mis-stamps `CallerChat` instead of the intended `CallerBackground` — this exact bug is `TASKS/phase-0/03-fix-callertype-mistagging.md` (status not-started as of this planning pass). **If this task's unified request/result type keys any behavior off `CallerType` (a natural design choice, since it's already the one real discriminator all three pass through `Dispatcher.Run`), it must be built against the *fixed* three-way mapping, not the current two-value-in-practice one** — hence the hard dependency on Phase 0 #3 landing first, not just a nice-to-have ordering.

### Shared type design

New file `internal/dispatcher/agent_run.go` — a **strict superset**, additive normalization layer, not a replacement of any surface's existing wire/persisted result type:

- `CompletionMode` (`sync_drain` / `async_capture` / `queued`) — names each surface's genuinely different completion contract instead of collapsing them.
- `RunStatus` (`completed` / `failed` / `timed_out` / `cancelled` / `stalled` / `over_budget` / `fabrication_suspected` / `queued` / `skipped`) — a superset union of delegation's Success/Error pair, subagent_runs' CW-20260519-0074 taxonomy (plus a `fabrication_suspected` refinement that taxonomy doesn't expose as its own persisted value — see below), and durable wake's lifecycle-event vocabulary.
- `AgentRunRequest{CallerType, Completion, TargetSessionID, Prompt, Timeout}` — built by each of the three call sites before deriving the narrower `dispatcher.Request` `Dispatcher.Run` actually consumes.
- `AgentRunResult{CallerType, Completion, TargetSessionID, Status, Content, Envelope, TokensUsed, Err, ToolCalls, ToolResultsSuccess, ToolResultsError}` — built by each surface from values its own (unmodified) drain/classification logic already computed.
- `LogOutcome(AgentRunResult)` — one shared, structured `"agent-run: outcome"` slog line with consistent field names across all three surfaces (the concrete, real "consumer" of the shared result type — see design rationale below).

**Where the shared type is constructed/consumed, per surface:**
- **A — REST delegation** (`internal/service/delegation.go`, `DelegateTask`): builds `runReq` before dispatch (5-minute timeout now has one source of truth — `runReq.Timeout` — instead of a re-hardcoded literal at the select loop). At each of the three completion branches (channel close, `time.After` timeout, `ctx.Done()`), derives an `AgentRunResult` **from the already-finalized `result` fields** (never the other way — see "derive, never drive" below) and calls `LogOutcome`.
- **B — LLM-triggered subagent dispatch** (`internal/service/subagent_runner.go`, `ChatRunner.Run`): builds `runReq` before invoking; at each of the 4 existing return points (drainCapture error / fabrication-suspected / zero-output / success) derives an `AgentRunResult` from `drainCapture`'s already-computed tuple (`summary, envelope, counts`) and calls `LogOutcome`.
- **C — durable-agent wake** (`internal/service/durable_wake.go`, `Wake` + the `RunDue` pre-computed-skip branch): builds `runReq` with `Completion: CompletionQueued`; reports `RunStatusSkipped` / `RunStatusFailed` / `RunStatusQueued` (never a synchronous-completion status — this surface genuinely cannot know completion synchronously).

### Design rationale / deviations from the literal task wording

1. **`Dispatcher.Run`'s signature is unchanged; the shared type is not "what `Dispatcher.Run` returns."** Traced the real call chain for all three surfaces (`delegation.go`, `subagent_runner.go`'s `invokeChat`, and `chat.go`'s `launchGeneration`→`runGeneration`, which is what durable wake's `HandleMessage` path ultimately hits). In every case, `Dispatcher.Run` is invoked in a goroutine and returns only a validation `error`; the actual turn's content/outcome has always been drained by the *caller's own* logic (delegation's select loop, `drainCapture`, or — for durable wake — nobody drains it at all, since `HandleMessage` returns as soon as the message is queued). `Dispatcher.Run`'s own doc comment additionally states it is deliberately the "narrow boundary... not a place to grow per-caller fields," with a signature that "MUST match `chatServiceImpl.generateResponse` byte-for-byte." Changing that signature to return the shared type would (a) contradict that documented invariant, (b) not actually be possible for durable wake (which has no result to return synchronously), and (c) risk becoming exactly the "lowest-common-denominator" shape the task explicitly forbids. The shared type is therefore constructed one layer up, by each surface's own existing completion-observation code — which is where the real completion signal has always lived. This is a correction of the task's framing against what the code's call graph actually does, not a reopening of the decision to unify — the decision (one shared type, used by all three call sites) stands and is implemented.

2. **"Derive, never drive."** For surfaces A and B, the `AgentRunResult` is *always* built from values the pre-existing (byte-for-byte unmodified) drain/classification logic already computed — `drainCapture`, `detectFabrication`, `zeroOutputRun`, `partialResult`, and delegation's select-loop event switch are untouched. This was a deliberate, load-bearing implementation choice after finding a subtlety in delegation's existing logic: an early "error" stream event can set `result.Success=false`/`result.Error` mid-loop, and the *later* channel-close branch's "worker produced no output" check only fires when content is still empty — meaning an existing (if arguably quirky) precedence between "mid-stream error" and "empty-content fallback" had to be preserved exactly rather than recomputed from a generic status. Building `AgentRunResult` from the finalized values (after the untouched logic ran) rather than trying to have it *drive* those fields avoids silently changing this behavior.

3. **Subagent dispatch's shared-type construction lives in `internal/service/subagent_runner.go` (`ChatRunner.Run`), not in `internal/subagent/service.go`'s `execute()`.** Two independent reasons converged on this: (a) `execute()`'s `classifyRunOutcome` is the only place with full post-attempt classification, but the fabrication-suspected sentinel (`errSubagentFabricationSuspected`) is unexported and private to `internal/service` — `execute()` (in `internal/subagent`) has no way to distinguish "fabrication suspected" from a generic failure without either a fragile string-match or exporting a new cross-package sentinel (out of scope: this task is shape unification, not touching the fabrication detector's contract); (b) `internal/subagent` cannot import `internal/dispatcher` at all — `internal/chat` imports `internal/subagent` (`envelope_response_subagent.go`), and `internal/dispatcher` imports `internal/chat`, so `subagent → dispatcher → chat → subagent` would be a real import cycle. `internal/service` already imports all three packages with no cycle, and is the only layer with direct, unstring-matched visibility into both `drainCapture`'s tuple and the fabrication/zero-output verdicts. Consequence: the shared type's `RunStatusOverBudget` value is real (part of subagent_runs' taxonomy, reachable via `classifyRunOutcome` after `ChatRunner.Run` returns) but is never emitted by my `LogOutcome` call sites — documented in the type's doc comment rather than silently dropped from the enum, since dropping it would violate "strict superset."
   Verified this doesn't change what actually gets persisted: `subagent_runs.status` for a real, live fabrication-suspected run (real-session verification below) still recorded `"failed"` — exactly as before. `AgentRunResult.Status = RunStatusFabricationSuspected` is strictly additional signal (visible via `LogOutcome`'s log line), not a replacement of `classifyRunOutcome`'s output.

4. **None of the four existing wire-facing/persisted result types were replaced or reshaped** (`chat.DelegationResult`, `subagent.Result`, `service.DurableAgentWakeResult`, `service.DurableAgentLaunchResult`). ### Durable-wake completion-tracking gap — disposition

The task's step 4 instruction: address the gap "only to the extent needed to give the unified result type an honest, non-misleading status... do not attempt a full redesign... escalate if it is [bigger]."

Resolved within scope, no escalation needed: `Wake`'s `AgentRunResult` always reports `Completion: CompletionQueued` and `Status: RunStatusQueued` (or `RunStatusSkipped`/`RunStatusFailed`) — it never claims synchronous completion. This is inherently honest given what's actually knowable at `Wake`'s return point (the turn hasn't run yet — `HandleMessage` queues it and returns immediately). The underlying gap `durable_wake.go`'s own doc comments describe (nothing transitions `durable_agent_instances.status` back out of `Active` once a turn completes, for `fresh-per-wake`/`concurrent` compositions where that would matter) is a **lifecycle state-machine completion-tracking mechanism** — building that would mean wiring a completion hook from `chat.go`'s async `launchGeneration` back into `durable_agent_instances`, which is exactly the "full redesign... beyond shape unification" the task says not to absorb here. Confirmed via real-session verification (below) that this residual ambiguity is unchanged and confined to the *existing*, untouched wire response (`DurableAgentLaunchResult.Instance.Status`) — my new `LogOutcome` line gives an operator reading logs an honest, non-misleading signal (`status=queued`) alongside it, without touching that pre-existing field's meaning or requiring the redesign.
