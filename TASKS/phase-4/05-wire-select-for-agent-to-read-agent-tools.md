## Context

Found during `04`'s implementation (2026-08-18), per that task's own explicit instruction: *"Actually wiring `internal/service/tool.go`'s `SelectForAgent` to read `agent_tools` instead of the legacy columns may be substantial enough to warrant its own follow-up task if it grows beyond a straightforward read-path swap — assess during implementation and escalate/split if so, rather than silently under-scoping this task."* It did grow beyond a mechanical swap, for a specific, verified reason below — this task is that follow-up, not a re-litigation of `04`'s decision to defer it.

`agent_profiles.tools` (schema-v2 allowlist) and `agent_profiles.tool_permissions` (`toolclient.ToolPermissions` — `allow_list`/`deny_list`, both **glob-capable** via `toolclient.MatchPattern`, deny-wins-over-allow) are two independently-applied filters `SelectForAgent` runs in sequence today (`filterToolsByAllowlist` then `filterToolsByPermissions`/`CheckPermission`). `agent_tools` (04's new table) is a **plain positive-grant join** — `(agent_id, tool_id)` rows, no glob, no deny concept. Replacing the first two with a read from the third is not a mechanical swap because:

- A `deny_list` glob (e.g. `"dev_*"` denied while everything else is allowed) has no representation in a positive-grant-only join — there is no "everything except X" shape in `agent_tools` as specified by `01-agent-construction.md`. Modeling deny semantics on top of `agent_tools` (a parallel deny-join? a policy-expression column? leaving `tool_permissions` alive as a second, still-enforced layer indefinitely?) is a real design decision the architecture doc does not answer — it only says `agent_tools` "replaces `tools:`/`toolPermissions:`/`roleTools:` entirely," not how deny-glob semantics carry over.
- `04`'s one-time backfill (`internal/service/known_tools_backfill.go`) already resolved this ambiguity **for the data**, by replaying `ToolPermissions.CheckPermission` against the live catalog at backfill time and only granting what survives — i.e., the backfilled `agent_tools` rows already reflect each agent's current *effective* selection (allow ∩ NOT deny), snapshotted once. That resolves "what should today's data look like" but not "what should the live enforcement mechanism be going forward" once an operator starts editing `agent_tools` directly (e.g. via `TASKS/phase-5/01-build-assignment-api.md`'s grant/revoke endpoints) independently of the frozen legacy columns.
- `ToolClient.SelectToolsAsProvider`'s own internal permission pass (`toolclient/broker.go`) also calls `CheckPermission` before tools ever reach `service/tool.go` — a full swap has to decide whether that inner layer also gets rewired, or stays as a defense-in-depth backstop reading the (deprecated but still populated) legacy column indefinitely.

## What to do

1. Decide the deny-semantics question above: either (a) design a real deny/exclusion mechanism that sits alongside `agent_tools` (name it distinctly — check `GLOSSARY.md` first, same discipline `04` applied), or (b) make a deliberate, documented call that `agent_tools` membership is allow-only going forward and `tool_permissions.deny_list` is retired in effect (not just deprecated in name) once an agent has real `agent_tools` rows, with a clear migration story for agents that still rely on deny-glob behavior. Don't silently pick one without recording the reasoning.
2. Rewire `SelectForAgent` (`internal/service/tool.go`) to read granted tool names via `agent_tools` (through `known_tools`) as the primary selection filter, replacing `filterToolsByAllowlist(allTools, agent.Tools)`. Decide whether `filterToolsByPermissions`/`CheckPermission` stays as a second pass per (1)'s answer.
3. Decide whether `ToolClient.SelectToolsAsProvider`'s own internal `CheckPermission` call (`toolclient/broker.go`) needs to change too, or can remain reading the legacy column as a defense-in-depth backstop indefinitely (call out the resulting "two systems of record" tradeoff explicitly if so).
4. Handle the "empty `agent_tools`" case correctly: per `04`'s backfill, an agent with no legacy restriction was backfilled with a grant row for every tool available *at backfill time* — decide whether the live read path should also auto-grant newly-added catalog tools to such an agent going forward (matching today's "no restriction" live behavior) or requires an explicit re-sync/re-grant step (a real behavior change from today, which must be flagged if chosen).
5. Always include `known_tools.always_included=true` rows regardless of `agent_tools` membership (the `request_tools`/`tool_list`/`tool_describe` escape hatch) — `04` created the flag and the column; this task is what actually has to honor it in the live selection path.
6. Update/extend `TASKS/phase-5/01-build-assignment-api.md`'s grant/revoke expectations if this task's answer to (1)/(4) changes what "revoking a tool" or "an agent with zero explicit grants" means for an operator using that API.

### Item 1 — deny-semantics decision (the required real design call)

**Decision: a precisely-scoped version of (b), not (a).** No parallel deny/glob mechanism was built alongside `agent_tools` — it stays a plain positive-grant join, per the architecture doc's own stated shape. But "retire `tool_permissions.deny_list` in effect" turned out to need real scoping once I traced every place `tool_permissions`/`CheckPermission` actually runs, because a blanket retirement would have broken two things the architecture doc doesn't mention and that a naive read of "replaces `tools:`/`toolPermissions:`/`roleTools:` entirely" would have silently broken:

1. **File-based agents structurally cannot have `agent_tools` rows.** `agent_tools.agent_id` is a real FK to `agent_profiles`. A file-based agent dispatched under its runtime `"file-<slug>"` alias (`internal/service/agent_permissions.go`, `internal/agent/convert.go`'s `IsFileBasedID`) is resolved by `SelectForAgent`'s own `s.agents.GetAgent(agentID)` call using that literal alias string, which does **not** match the DB row's real UUID PK (confirmed by tracing `upsertAgentDef`/`AutoIngestAgents` in `internal/service/ingest.go`: a real `agent_profiles` row does get minted for every file-based definition at boot, but under its own UUID, not the `"file-<slug>"` runtime identity `SelectForAgent` is actually called with). So `s.agents.GetAgent("file-<slug>")` genuinely misses today, exactly as it did before this task — `agent_tools` is unreachable for this population, full stop, not a scoping choice I invented.
2. **`tool_permissions` already carries a distinct, separately-shipped, already-tested defense-in-depth responsibility** (CW-20260512-0117 / SP-20260512-0010, `internal/service/tool_permissions_render_test.go`) closing a real gap: tools that reach `allTools` via the `discoverAgentMCPTools` direct-MCP fallback bypass `SelectToolsAsProvider`'s own gate entirely. That's a different concern from "what does this agent's roster name," and this task's mandate (replace the roster-definition source) doesn't extend to dismantling it.

Given that, the actual, implemented decision is: **`agent_tools` (+ the `known_tools.always_included` escape hatch) is the *sole* selection-time gate, at the `SelectForAgent` surface, for any agent that resolves to a real `agent_profiles` row.** `tool_permissions`'s `allow_list`/`deny_list` is *not* consulted a second time at that surface for this population — `filterToolsByAllowlist` (the old schema-v2-allowlist reader) is deleted outright, and the old `filterToolsByPermissions` call that used to run unconditionally now only runs for agents that do **not** resolve to a real `agent_profiles` row (structurally, today, only file-based agents). `ToolClient.SelectToolsAsProvider`'s own internal `CheckPermission` call, `CallTool`'s execution-time backstop, and `HandleRequestToolsForAgent`'s gate are all left **completely unchanged** — deliberately, per item 3's own explicitly-offered "leave as defense-in-depth backstop indefinitely" option (see item 3 below for the resulting tradeoff, which is real and is flagged for Phase 5).

Verified this doesn't regress `tool_permissions_render_test.go`'s existing acceptance coverage: `SelectToolsAsProvider`'s inner `CheckPermission` gate runs *before* my new agent_tools filter even sees the tool list, so for every existing test that exercises a broker-registered tool set (not the `discoverAgentMCPTools` fallback), the permission narrowing already happened at that first gate — removing the second, redundant `service/tool.go`-level call changes nothing observable for those tests. Confirmed by running the full existing suite unchanged apart from `tool.go`/`tool_test.go` itself — every test in `tool_permissions_render_test.go`, `tool_chat_surface_test.go`, and `tool_parent_dispatch_allowlist_test.go` passes with zero modifications.

### Item 2 — `SelectForAgent` rewired

`filterToolsByAllowlist(allTools, agent.Tools)` deleted outright (dead after this change) and replaced with a new `filterToolsByAgentTools(ctx, *store.Store, agentID, tools)` — reads `ListAgentToolNames` (added by `04`, `internal/store/agent_tools.go`) through the FK join to `known_tools`, applied only when `SelectForAgent` resolved a real `agent_profiles` row for `agentID` this call. `filterToolsByPermissions` is kept (not deleted) but its call site is now scoped to the `else` branch (no real `agent_profiles` row resolved) — see item 1.

### Item 3 — `ToolClient.SelectToolsAsProvider`'s inner `CheckPermission`

**Left unchanged**, reading `agent_profiles.tool_permissions`/`PermissionResolver` indefinitely, as explicitly offered by this task's own item 3. Reasons: it's the load-bearing execution-time backstop (`CallTool`'s own doc comment already calls it that, pre-dating this task) and it's the only mechanism file-based agents have. **The resulting "two systems of record" tradeoff, named explicitly**: because this inner gate runs *before* `service/tool.go` ever sees the tool list, a DB-backed agent's still-populated (deprecated-but-not-dropped) `tool_permissions.deny_list` can silently veto a tool at that first gate — before my new `agent_tools` filter ever gets a chance to reconsider it. Concretely: an operator who later grants a tool via `agent_tools` (Phase 5's not-yet-built assignment API) that the agent's *stale* legacy `deny_list` still denies will find the grant silently ineffective — the tool never reaches `allTools` in the first place. **This is not a live bug today**: `04`'s backfill computed every existing agent's `agent_tools` grants by replaying `CheckPermission` against the live catalog at backfill time, so today's grants are already a subset of what `tool_permissions` independently allows — zero observable day-one behavior change. It becomes live the first time Phase 5's grant endpoint creates a genuinely new grant. Flagged as a required item in `TASKS/phase-5/01-build-assignment-api.md` (see below).

### Item 4 — the "empty case" decision

**Decision: (b), no live auto-grant of newly-added catalog tools.** `agent_tools` is the literal, static source of truth for roster membership going forward. An agent that looks "unrestricted" today (its `agent_tools` grants happen to cover the *entire* catalog, because `04`'s backfill snapshotted it that way) does **not** automatically gain visibility into a tool added to `known_tools` after this task lands — that requires an explicit (re-)grant, either via a future assignment-API convenience action or an equivalent re-sync pass. **This is a real, flagged behavior change** from pre-`04` live behavior (where an empty `agent.Tools` column meant "no restriction," dynamically, forever). Rationale: there is no "unrestricted" flag anywhere in the `04` schema (`agent_tools` is a plain `(agent_id, tool_id)` join, nothing else) — inventing one to preserve the old dynamic-no-restriction semantics would be new, out-of-scope schema/design work, and would silently resurrect the exact "implicit magic silently overriding an explicit operator action" anti-pattern `04`'s own `agent_tools_legacy_backfill` deviation was built specifically to avoid (a later boot re-deriving "should still be unrestricted" from a stale signal, overriding whatever an operator explicitly did via `agent_tools` in the meantime). Flagged explicitly in `TASKS/phase-5/01-build-assignment-api.md`.

### Item 5 — `always_included` escape hatch

Implemented as `resolveAlwaysIncludedTools` + `unionToolsByName`, folded into `allTools` *after* the `FinalizeToolSelection` cap/token-budget prune (so the escape hatch survives a truncation-heavy session) but *before* being handed to the chat-surface filter's own deliberate B4 exclusion of `tool_describe`(applied by re-filtering the escape-hatch set itself through `applyChatSurfaceFilter` for the chat-role agent, so the always-included union can never re-add back a tool that filter intentionally strips). Also folded into the progressive-discovery branch's `builtinTools` construction, since that branch returns a different, truncated tool list and would otherwise miss the guarantee.

**Real bug found and fixed as a direct consequence of implementing this item**: `request_tools` has no registration anywhere in the normal builtin/MCP catalog (`ToolClient.ListTools()`) — it's synthesized ad hoc only inside the progressive-discovery branch via `toolclient.RequestToolsMetaTool()`. `container.go`'s real `SyncKnownTools` call site builds its catalog from `cfg.ToolClient.ListTools()`, which never includes `request_tools` — meaning `SyncKnownTools`' `MarkKnownToolsUnavailableExcept` pass would have marked the migration-seeded `request_tools` row `unavailable` on the very first real boot after `04`'s migration, permanently excluding it from the escape hatch (my `resolveAlwaysIncludedTools` correctly skips non-`available` rows). Caught by my own new acceptance test (`TestSelectForAgent_AlwaysIncludedSurvivesZeroGrants`), not by inspection. Fixed at the root cause in `internal/service/container.go`: the catalog passed to `SyncKnownTools` now has `toolclient.RequestToolsMetaTool()` appended before syncing, so `request_tools` is tracked as a real, permanently-available catalog entry like every other tool, instead of a status-blind special case in the read path. `tool_list`/`tool_describe` didn't need the same fix — they ship via the self MCP server and are already present in `ListTools()`.
