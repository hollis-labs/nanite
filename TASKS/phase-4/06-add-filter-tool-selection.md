**Phase:** 4
**Status:** implemented
**Depends on:** Phase 0 #22 (`22-remove-skill-and-tool-broker-abstractions.md`) should already be landed — this task is that removal's explicitly named forward-looking replacement mechanism for the go-toolbroker enricher's cut `OverrideBlock` feature, not a mechanism that needs to coexist with it.
**Touches:** `internal/plugin/filter.go` (new `FilterToolSelection` constant, alongside the existing 8), `internal/service/tool.go` (`toolServiceImpl` struct and `SelectForAgent` — needs a design decision on where the filter applies, see Context), `internal/service/chat_generate.go` (likely insertion point, see Context), `internal/service/container.go` (wiring if `toolServiceImpl` gains a `pluginHost` field).

## Context

TASKS.md Phase 3 (final item): *"Add `FilterToolSelection`."* Architecture doc `09-plugin-system.md`: *"a filter exists for tool *results* (post-execution) but not tool *selection* — a plugin can't currently add, remove, or reshape which tools get offered to the model for a turn, only react after the fact. Add `FilterToolSelection` alongside the tool-selection filter stack."* This closes the one real gap the plugin-system review found in an otherwise "close to comprehensive" filter/hook chain.

### The existing filter chain, verified

`internal/plugin/filter.go:199-212` — 8 named filter points: `FilterSystemPrompt`, `FilterUserMessage`, `FilterToolResult`, `FilterAssistantResponse`, `FilterContextWindow`, `FilterEnvelopeData`, `FilterReflexState`, `FilterReflexAction`. No `FilterToolSelection` exists. The registry (`FilterRegistry.Register`/`RegisterWithView`/`Apply`, same file, lines 86-168) is generic — adding a new named filter point requires no registry changes, only a new constant plus a real call site.

Existing call sites, all `s.pluginHost.ApplyFilter(pluginpkg.Filter<X>, data, fctx)`: `FilterSystemPrompt` (`chat_generate.go:475`), `FilterUserMessage` (`:484`), `FilterContextWindow` (`:986`, on `[]llmtypes.ChatMessage`), `FilterAssistantResponse` (`:1791`), `FilterEnvelopeData` (`:1872`); `FilterToolResult` lives separately in `internal/service/chat_tool_executor.go:523`.

### The insertion-point decision this task must make explicit

Tool selection happens in `toolServiceImpl.SelectForAgent` (`internal/service/tool.go:219-...`), called from `chat_generate.go:357`, returning `*ToolSelection{Tools []llmtypes.ToolDefinition, Catalog string, Progressive bool, OverrideBlock string}` (`tool.go:32-37`). The function internally runs: broker selection → permission filter (`filterToolsByPermissions`, `:277`) → allowlist + chat-surface filter (`:299-302`) → `FinalizeToolSelection` cap (`:311`) → description rendering (`:328`) → progressive-discovery repackaging (`:342+`).

**`toolServiceImpl` has no `pluginHost` field today** (struct at `tool.go:109-125`), unlike `chatServiceImpl` (`chat.go:277`, has `pluginHost PluginEventSink`). So applying `FilterToolSelection` *inside* `SelectForAgent` requires first wiring plugin-host access into `toolServiceImpl` (new constructor param/setter + `container.go` update). The lower-friction alternative is applying the filter in `chat_generate.go` immediately after `SelectForAgent` returns (`:357`), operating on `selection.Tools` — `chatServiceImpl` already has `s.pluginHost` in scope there, matching the exact pattern the other five `chat_generate.go`-resident filters already use. **Pick one and document why in this file's Work Log** — don't leave it as an implementation-time coin flip; the two options have different implications for whether a plugin can see (and override) the pre-cap, pre-allowlist tool set or only the fully-resolved final list.

Also confirm before starting: `ToolSelection.OverrideBlock` (`tool.go:36`, the go-toolbroker enricher's markdown block) should already be gone by the time this task runs, since Phase 0 #22 cuts it and explicitly names `FilterToolSelection` as its replacement, not something meant to coexist with it. If `OverrideBlock` is still present, that's a signal Phase 0 #22 hasn't actually landed — flag it rather than building around a field that's supposed to already be dead.

### Insertion-point decision (required by this task, documented per its own instruction)

**Decision: post-call in `chat_generate.go`, operating on `selection.Tools` immediately after `SelectForAgent` returns — NOT inside `toolServiceImpl.SelectForAgent` with new `pluginHost` wiring.**

Reasoning:
1. **Matches the established pattern exactly.** All five existing `chat_generate.go`-resident filters (`system_prompt`, `user_message`, `context_window`, `assistant_response`, `envelope_data`) operate on the *value about to be used* at the point it's about to be used — not on some earlier system's internal intermediate state. `selection.Tools` post-`SelectForAgent` is exactly that value for tool selection: it's what gets normalized (`normalizeToolInputSchemas`), what determines the no-tools warning (`hasUsableTools`), what gets partitioned for lazy-load, and what's ultimately threaded into `assembleTurnContext` → the LLM payload. Filtering it here is consistent with "plugins filter the thing that's about to happen," the same design principle every other filter in this file already follows.
2. **Lower friction, zero new plumbing.** `toolServiceImpl` has no `pluginHost` field today (confirmed — `tool.go:93-108`'s struct has no such field). Wiring one in would require a new constructor param, a `container.go` wiring change, and — critically — `toolServiceImpl` has no natural session/agent `FilterContext` at every one of its several internal call sites (`SelectForAgent` is called from `chat_generate.go` but also, per its interface doc, is meant to be reusable); `chatServiceImpl` already has `s.pluginHost` in scope exactly once, at exactly the right point, with `fctx` cheaply constructible from parameters already in hand (`sessionID`, `agentID`).
3. **The tradeoff, made explicit (per this task's own instruction to document it):** because this filter runs *after* `SelectForAgent` returns, a plugin sees the **fully-resolved final tool list** — post `agent_tools` grant filter (05's new roster-membership gate), post the chat-surface filter's B4 exclusions, post `FinalizeToolSelection`'s cap/token-budget prune, post the `always_included` escape-hatch union, and post progressive-discovery's builtin-only repackaging when that branch is active. A plugin CANNOT see or override the broker's raw pre-filter output, and cannot distinguish "a tool was excluded by the agent's own grants" from "a tool was excluded by the token-budget cap" — it only sees the end result. This is the intentional tradeoff of the lower-friction option this task's own Context section named as available, and it mirrors exactly how `FilterToolResult` only sees the final tool-execution output, not intermediate transport-layer state. If a future need arises for a plugin to see/override the broker's pre-cap output specifically, that requires wiring `pluginHost` into `toolServiceImpl` as a separate, additive change — not something this task's scope required, and not something I built preemptively (no unrequested plumbing).
4. **Progressive discovery is a non-issue at this insertion point**, not something requiring special-case handling: whichever branch `SelectForAgent` took, `selection.Tools` is already the final list handed back (progressive discovery repackages `Tools` into the builtin-only surface *inside* `SelectForAgent`, before returning) — so a single filter application point in `chat_generate.go`, applied uniformly to `tools := selection.Tools`, correctly covers both cases without an `if selection.Progressive` branch.
5. **`selection.Tools` itself is never re-read after `chat_generate.go` line 348** (confirmed via `grep -n "selection\." chat_generate.go` — only `.Progressive` and `.Catalog` are read again later, never `.Tools`), so filtering the local `tools` variable (not mutating `selection.Tools` in place) is sufficient and correct — no second read site would see stale, unfiltered data.

### What was implemented

1. **`internal/plugin/filter.go`** — added `FilterToolSelection = "tool_selection"` to the standard filter-point constant block (now 9 named filter points, alongside the existing 8), with a doc comment explaining what it sees and pointing at this task file and at `FilterToolResult` as its post-execution counterpart. `gofmt`-realigned the whole const block after insertion (cosmetic only, no semantic change to the other 8 constants beyond alignment).
2. **`internal/service/chat_generate.go`**:
   - Moved the single `fctx := pluginpkg.FilterContext{SessionID: sessionID, AgentID: agentID}` declaration that used to live just before the `system_prompt` filter (around the old line 421) up to immediately after `tools := selection.Tools` (around the new line 348), and reused it at every later `ApplyFilter` call site in the function (all five pre-existing ones plus the new one) — one declaration, same scope throughout `generateResponse`, no shadowing, confirmed no intervening block/brace closes between the new declaration site and any of its uses.
   - Added the `FilterToolSelection` call, applied to the local `tools` variable, positioned **before** `normalizeToolInputSchemas(tools)` (so a plugin-added tool's schema gets normalized too) and therefore also before the tools-lazy-load essential/lazy partition and the no-tools warning check (both of which now correctly see the plugin-filtered list, not the pre-filter one).
   - Extracted the actual filter-application logic into a new standalone function, `applyToolSelectionFilter(pluginHost PluginEventSink, tools []llmtypes.ToolDefinition, fctx pluginpkg.FilterContext) []llmtypes.ToolDefinition`, placed next to `normalizeToolInputSchemas` — mirroring this file's own existing precedent (`composeExtraSystemPrefix`, `applyChatSurfaceFilter` in `tool.go`) of extracting filter/compose logic into an independently unit-testable pure(ish) function rather than leaving it inlined in the middle of the enormous `generateResponse` function body. `generateResponse` now just calls `tools = applyToolSelectionFilter(s.pluginHost, tools, fctx)`. Nil-safe: nil `pluginHost`, a filter error, or a filter returning a value that doesn't type-assert back to `[]llmtypes.ToolDefinition` all degrade to "return `tools` unchanged, log a warning" — a misbehaving plugin can never crash the turn or silently empty the tool surface.
   - **`internal/service/tool.go` and `internal/service/container.go` were deliberately left untouched** — a direct, correct consequence of the insertion-point decision above (no `pluginHost` field added to `toolServiceImpl`, so no constructor/wiring change needed). Both were listed as conditional in this task's own `Touches` line ("needs a design decision," "wiring if `toolServiceImpl` gains a `pluginHost` field") — the decision made means neither actually needed a change.
