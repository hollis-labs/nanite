# Reflex architecture review — precedence, ordering, and internal structure for six job-types

**Phase:** 4 (Steering & Reflex Migration)
**Status:** design complete, operator-signed-off (2026-08-19) — see `docs/engineering/architecture/10-reflex-action-taxonomy.md` for the full design. **Implementation is deferred and not yet filed as a follow-up task.** This file's own scope (design/discussion) is done; do not dispatch it as a routine batch item.
**Depends on:** none to start; informs (but does not block) any future runaway-detection work.
**Touches:** `internal/agent/reflexes/` (engine, action-kind dispatch, schema), `docs/engineering/architecture/03-steering.md` (the doc this task is meant to resolve the open watch-item in).

## Context

`docs/engineering/architecture/03-steering.md`'s own "Watch item" (still open, self-flagged when `dispatch_to_agent` was added as the sixth action kind): *"reflexes are now carrying six distinct jobs that used to be five separate systems. That consolidation was the right call case-by-case, but it will likely need real internal structure (a clear action-kind taxonomy, maybe priority tiers) to stay comprehensible once fully built — don't assume the current simple schema scales to six jobs as cleanly as it handled one."* The six current action kinds: `inject_reminder`, `force_tool_choice`, `send_message`, `halt_session`, `add_schedule`, `dispatch_to_agent` (the last one added by `TASKS/phase-4/02-dispatch-to-agent-reflex-action-kind-and-broker-migration.md`).

A separate architecture-review agent (2026-08-19, reviewing agent boots/reflexes/steering) raised this same gap independently, framed sharply: *"Give reflexes explicit precedence now, not after six job-types are all live... Runaway detection will almost certainly land as a reflex action (`halt_session` already exists) — so this design debt is now directly in the path of the work you said you're about to do, not a separate cleanup. Worth settling ordering/priority as part of building runaway detection, not after."* The operator agreed this is worth a dedicated architectural pass rather than deferring further, and will work it directly with an agent in its own session — this task exists so it has a place in the plan/sequence, not to be executed here.

### What's concretely unresolved

- **No declared precedence/ordering** when multiple reflexes match the same event/state in the same evaluation pass — current behavior (whatever it happens to be from evaluation order) is implicit, not designed.
- **No action-kind taxonomy** distinguishing, e.g., a reflex that should always win (a safety/halt action) from one that's advisory (a nudge/reminder) — all six kinds are currently peers in the schema.
- **No priority tiers** — nothing in the current schema expresses "this reflex should be evaluated/applied before that one" or "this action kind pre-empts that one if both fire."
- **Runaway detection is coming and will almost certainly be a `halt_session` reflex action** — if it lands before precedence is designed, the ordering question gets answered implicitly and accidentally by whatever the runaway-detection implementation happens to do, rather than deliberately.

## What to do

This is a design/discussion session, not a mechanical worker task — the operator will shape the actual approach live. At minimum, the session should produce:

1. A decision on whether reflexes need explicit priority tiers (and if so, how many, and what each tier means) or whether a simpler mechanism (e.g., action-kind-based pre-emption: safety actions like `halt_session` always win over advisory actions) is sufficient.
2. A decision on evaluation-pass ordering semantics when multiple reflexes match the same trigger: first-match-wins, all-fire-independently, priority-ordered, or something else — and whether this differs by action kind.
3. Explicit design for where runaway detection sits in this structure, since it's the concrete near-term consumer of whatever precedence model is chosen.
4. An updated `docs/engineering/architecture/03-steering.md`, replacing the open "Watch item" with the resolved design (or a concrete follow-up task file, if the design itself is decided but implementation is deferred).

- Any other reflex job (the five already-migrated ones) — this is about the *structure* holding all six together, not re-litigating any individual migration.

## Work log

**2026-08-19 — architecture/design session with operator, no code changed.** Full design recorded in `docs/engineering/architecture/10-reflex-action-taxonomy.md`; `docs/engineering/architecture/03-steering.md`'s open "Watch item" updated to point at it. Summary of decisions, in the order settled:

1. **Concrete problems confirmed against live code first**, not assumed: `priority` does two undeclared things depending on call site (evaluation-order only in the generic pass vs. first-match-wins selection in `dispatch_to_agent`'s own path); priority values are already inconsistent even within `halt_session` alone (100/90/10 across the three seeds); two `force_tool_choice` reflexes can co-fire with contradictory directives (both land in the same `<system-reminder>` block); `halt_session` doesn't preempt other actions in the same pass and doesn't stop the current turn (it only stamps `halted_at`, checked on a later request via `frontend_readiness.go`); and there are three reflex-evaluation call sites, not two — `internal/mcp/self_tools_dispatch.go:matchDispatchToAgentReflex` independently duplicates `internal/service/chat_reflex_dispatch.go:attemptReflexDispatch`'s selection loop, by necessity (`internal/mcp` can't import `internal/service`), not oversight.
2. **Four facets, decided in this order**, each mapped to real prior art rather than invented fresh: (a) **category** (`system_message` advisory vs `execute_action` deterministic) as an extensible lookup, not a two-value hardcode — deliberately *not* collapsed further, since the combining algorithm/provenance ceiling/recurrence default below all need real per-kind FK granularity, the same reasoning that killed a generic `callback` action kind (considered and rejected — see doc); (b) **combining algorithm per kind** — `deny_overrides`/`first_applicable`/`all_applicable`, modeled on XACML's policy-combining algorithms (AWS IAM's own evaluation is one instance of `deny_overrides`) — this is also what fixes the `force_tool_choice` contradiction (`first_applicable`) and the halt-preemption gap (`deny_overrides`); (c) **provenance/authority tier** (`system`/`operator`/`plugin`, real FK not free-text `created_by`) for a security purpose — gating which tiers may declare high-blast-radius kinds like `halt_session`/`dispatch_to_agent` — confirmed `agent_proposed` doesn't need to be a fourth live tier, since `store.ApprovePendingReflex` already collapses provenance to `"operator:" + reviewedBy` on approval, so "active ⇒ approved" is already true by construction; (d) **recurrence cascade** — system default → per-kind override → per-reflex override — which also removes the *behavioral* justification for `dispatch_to_agent`'s bespoke no-debounce code path (becomes a kind-level override instead), leaving only the import-cycle constraint as the reason multiple invocation points exist.
3. **One shared decision engine, not one call site.** The three call sites' *selection logic* (list → evaluate → combine) must unify into one exported primitive living in `internal/agent/reflexes` (the one package all three callers already import without a cycle) — but their *State-building* legitimately stays separate, since two of the three populate `ScopeTier`/`ExecutionPattern` from live in-flight classification data the DB-backed `StateCollector` can't see yet.
4. **Halt must actually halt** — two bundled fixes, both explicitly confirmed in scope by the operator: same-pass preemption (via `deny_overrides`) and turn-level synchronicity (the current turn must actually abort, not just flag the session for a later readiness check — today's gap is in `chat_generate.go` right after the `evaluateAndInjectReflexes` call).
5. **A fifth, adjacent mechanism got separated out during the discussion, not folded in**: an agent-initiated "declare a fact, harness reacts" pattern (e.g. `nanite_report_task_updated`) has no predicate/event/interval trigger, so it isn't a reflex action kind at all — resolved to implement as small `nanite_*` self-tools with their own harness-reactive category flag, named separately from reflex vocabulary on purpose (rejected reusing "event"/"notify" — both already mean something else in this codebase). Naming for this mechanism ("harness-reactive self-tools" leading) and its own design pass are explicitly deferred, not part of this task's output.
6. **Telemetry pass added at the operator's explicit request** ("make sure we have strong telemetry working for the reflex system... capture what we need for trace/debugging"), checked against live code rather than assumed: found the same three-call-site fragmentation from point 3 above already produces a telemetry gap, not just a decision-logic one — `dispatch_to_agent` firings land in `event_log` *or* `playbook_match_log` depending on which of the two duplicate call sites handled them (different schemas, never both); `fired_count`/`last_fired_at` is bumped by two of the three paths but never by `matchDispatchToAgentReflex` (`self_tools_dispatch.go`), so the operator UI can show a `dispatch_to_agent` reflex as never-fired while it's actively routing; and the `EmitReflexFired`/`EmitReflexActionStaged` plugin hooks only fire from inside `Engine.EvaluateState`, so any plugin instrumented against them is structurally blind to every `dispatch_to_agent` firing. Resolution: this isn't separate work from the shared-decision-engine fix in point 3 — once there's one `reflexes.Resolve(...)` entry point, telemetry emission belongs there too, closing all three gaps as one consolidation rather than three patches. Requirement locked (one consistent trace record, one sink, full plugin-hook coverage, `alternatives_considered`-style "why this one won" data generalized beyond `dispatch_to_agent`); the storage shape (widen `event_log` vs. a new dedicated table) is explicitly left open.
7. **What's still genuinely open** (see doc's own "What this session did not decide" section for the full list): exact DDL, the specific per-tier action-kind allow-list values, whether recurrence needs a third "fire once ever" mode, final self-tool-mechanism naming, the unified telemetry sink shape, and whether/when to build the plugin-registered-action-kind extension seam. Operator's explicit call on these: acceptable to leave open and let real usage over the next couple weeks inform the answer, rather than force a decision now.

**Not done in this session, by design:** no schema/migration, no code change, no follow-up implementation task filed yet (`docs/engineering/architecture/10-reflex-action-taxonomy.md`'s "Status" section is the source of truth on what remains).
