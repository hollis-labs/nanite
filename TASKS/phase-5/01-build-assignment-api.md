## Context — what already exists vs. what's actually missing (verified directly, not assumed)

- **`roles` REST CRUD already exists in full** (`internal/api/roles.go`, built by Phase 1 task `01`: `GET/POST /api/roles`, `GET/PUT/DELETE /api/roles/{id}`). Nothing to build here.
- **`agent_profiles.role_id`/`consumer_id`/`model_id` are NOT settable via the API today**, confirmed live during Phase 1's Wave 2 validation checkpoint: `CreateAgentRequest`/`UpdateAgentRequest` (`internal/api/types.go`) have no fields for any of the three. The columns exist (Phase 1 tasks `02`, `03`) and are correctly readable (once Phase 1 task `12` lands), but there's no write path via the API yet. This is real, missing work.
- **`consumers` has store-layer CRUD only, no REST** (`internal/store/consumers.go`, Phase 1 task `03`'s own Work Log explicitly deferred the REST layer to this task). Build `GET/POST /api/consumers`, `GET/PUT/DELETE /api/consumers/{id}`, matching the existing route-naming convention `roles.go` already established.
- **`agent_tools` has a list endpoint only** (`GET /api/agents/{id}/tools`, from Phase 1 task `04`). No grant/revoke (`POST`/`DELETE`) endpoints exist yet — an operator (or a future UI, whenever one gets built in some later, explicitly-scoped effort) needs a way to actually assign/remove a tool grant via the API, not just read the current set. `TASKS/phase-4/05-wire-select-for-agent-to-read-agent-tools.md` is the task that makes the live tool-selection path actually read from these grants — **read its Work Log before building this task's grant/revoke endpoints**, it changes what "grant" and "revoke" actually mean for an operator, in three concrete ways:
  1. **No live "unrestricted" bypass.** `SelectForAgent` now treats `agent_tools` as the literal, static roster for any agent with a real `agent_profiles` row — there is no "grant everything, including future catalog additions" flag anywhere in the schema. An agent that looks "unrestricted" today (e.g. `worker`/`backend`/`default`) only has that many grants because `04`'s backfill snapshotted the full catalog *at that point in time*. A tool added to `known_tools` after this task lands is invisible to every agent, including previously-"unrestricted" ones, until something explicitly grants it. This task's grant endpoint is that "something" — there is no other live mechanism. If the API design wants a real "grant everything currently available" convenience action (e.g. `POST /api/agents/{id}/tools/grant-all`), build it explicitly; do not assume a bare `agent_tools` row count of "the full catalog" means "stays unrestricted forever."
  2. **`tool_permissions.deny_list`/`allow_list` is retired *at the `SelectForAgent` surface* for any agent with a real `agent_profiles` row, but NOT retired at the deeper `ToolClient.SelectToolsAsProvider`/`CallTool` layer** (left there deliberately, as a defense-in-depth backstop — see `05`'s Work Log item 3). This means a stale, still-populated `agent_profiles.tool_permissions.deny_list` (deprecated, not dropped by `04`) can silently veto a brand-new `agent_tools` grant this task's `POST` endpoint creates — the tool would never reach the LLM's selection at all (the inner gate runs before `agent_tools` filtering even happens), even though the grant "succeeded" from the API's point of view. **This task's grant endpoint must not silently ship that footgun**: either (a) have the grant handler check the target agent's `tool_permissions.deny_list` for a pattern match against the tool being granted and reject the request with a clear error naming the conflicting legacy pattern, or (b) surface a warning in the response body, or (c) clear/neutralize the agent's `tool_permissions` column once it has any real `agent_tools` rows. Pick one and document the choice in this task's own Work Log — don't leave it a silent gap the way `05` explicitly declined to (that decision was deliberate and scoped to `05`; this task is where the consequence becomes operator-visible and needs a real answer).
  3. **A parallel, execution-time re-check (`internal/service/tool_execution_rules.go`'s `enforceExecutionRules`) still reads the legacy `agent_profiles.tools` JSON column, not `agent_tools`.** `05` deliberately left this file untouched (out of its stated `Touches`, and modifying `agentServiceImpl.Get`'s file-based-vs-DB-backed ID resolution semantics safely needed more investigation than that task's scope warranted) — but flagged that once this task's grant/revoke endpoints let `agent_tools` diverge from the now-frozen `agent_profiles.tools` column, a tool granted via `agent_tools` (and therefore visible in `SelectForAgent`'s output) can get rejected at execution time with `"tool not in agent's allowed tool set"`, because `enforceExecutionRules` is still checking the old column. **This task must close that gap** — update `enforceExecutionRules` to consult `agent_tools` (mirroring `05`'s `filterToolsByAgentTools` scoping: real `agent_profiles` row → `agent_tools` is authoritative; no real row → fall back to the legacy check) so a grant this task's own API creates is actually usable, not silently rejected one turn later.
- **`agent_dispatch_tool_allowlist`** (Phase 1 task `04`'s renamed table, resolving the `agent_dispatch_allowlist`/`parent_dispatch_allowlist` naming collision) — check whether anything currently needs a REST surface for it before building one; if nothing consumes it yet, note that in the Work Log and skip rather than building speculative CRUD.
