# Build a real installed/enabled state model for plugins (WordPress-style, DB-backed, builtin+subprocess uniform)

**Phase:** 5
**Status:** implemented
**Depends on:** none
**Touches:** `internal/plugin/manage.go` (`DisablePlugin`/`EnablePlugin`/`IsDisabled`/`PluginStatus` — replace the file-rename mechanism), new migration (`plugins` state table), `internal/plugin/registrations.go` (`applyManifestRegistrations` — the shared entrypoint where the new state model gates registration), `internal/plugin/builtin/*/plugin.yaml` (12 builtin manifests, read-only reference)

## Context

Architecture doc `09-plugin-system.md`: *"Builtin plugin enable/disable — needs a real installed/enabled state model, not the current file-rename mechanism... Explicitly modeled on WordPress's plugin state (code present = installed, a separate flag = active/enabled), working uniformly for both builtin and subprocess plugins via GUI/CLI/API — not the current subprocess-only, disk-manifest-rename approach that doesn't even apply to builtins... this state belongs in the DB, not encoded as a file's presence/absence."*

### Current mechanism, verified — file-rename, and a real nuance about builtins worth resolving before assuming it's a no-op for them

`internal/plugin/manage.go` — `DisablePlugin`/`EnablePlugin`/`IsDisabled`/`PluginStatus` all operate by renaming `plugin.yaml` ↔ `plugin.yaml.disabled` inside `pluginsDir`. **12 builtins confirmed, each with its own real on-disk `plugin.yaml`** (not just compiled Go — they genuinely have manifest files too): `adapter-claude`, `adapter-codex`, `adapter-gemini`, `adapter-nanite-native`, `adapter-opencode`, `agentwidgets`, `bookmarks`, `card-rules-demo`, `contextwidgets`, `debugwidgets`, `observabilitywidgets`, `sessionstats` — all under `internal/plugin/builtin/*/plugin.yaml`. No DB table exists for plugin state today — fully greenfield.

**A nuance a worker must resolve, not assume**: because builtins do have on-disk `plugin.yaml` files, the file-rename mechanic would technically *execute* against them — but disabling a builtin this way only removes its manifest from disk; the Go code is still compiled into the binary, and whether its `init()`/registration wiring still runs depends on the actual builtin-loading path (`LookupConstructor`). **Confirm this behavior directly during implementation** before assuming the current mechanism is a clean no-op for builtins — if it's actually silently broken (manifest gone, code still registers), that's a real bug this task's replacement should also fix, not just a "doesn't apply" framing to note and move past.

`applyManifestRegistrations` (`internal/plugin/registrations.go:220`) is the single shared registration entrypoint for both builtin and subprocess plugins — this is where the new DB-backed state model gates registration (skip calling it for a disabled plugin, builtin or subprocess alike, instead of the current disk-presence check).

## What to do

1. Create a `plugins` table: `id`/`slug`, `kind` (`builtin`/`subprocess`), `installed` (bool — code present, or manifest/package staged), `enabled` (bool — the WordPress-style active flag), timestamps.
2. Seed the table for all 12 current builtins as installed+enabled (matching today's default-on behavior) and for any currently-installed subprocess plugins per their current file-presence state.
3. Replace `DisablePlugin`/`EnablePlugin`/`IsDisabled`/`PluginStatus`'s file-rename implementation with DB reads/writes against the new table — same function signatures where possible, so GUI/CLI/API callers don't need to change beyond the implementation swap.
4. Gate `applyManifestRegistrations` (or its caller) on the new `enabled` flag, uniformly for builtin and subprocess — confirm this actually stops a disabled builtin's registration wiring from running (the real bug flagged in Context, if confirmed present).
5. Resolve the builtin-disable behavior nuance from Context as part of this task, not deferred — a disabled builtin must genuinely not register, not just lose its manifest file.

## Done means

- `plugins` table exists, correctly seeded for all current builtins and subprocess plugins.
- Disabling a plugin (builtin or subprocess) via GUI/CLI/API genuinely stops its registration wiring from running on the next reload/restart — verified for at least one builtin and one subprocess plugin.
- The file-rename mechanism is fully retired.
- `go build ./cmd/nanite/`, `go vet ./...`, `go test ./...` pass.

## Work log

### Builtin-disable nuance — resolved, and the real bug is confirmed present (in a narrower shape than Context assumed)

Traced the two loader paths (`internal/plugin/loader.go`) end to end before writing any code:

- `internal/plugin/manage.go`'s old `DisablePlugin`/`EnablePlugin`/`IsDisabled`/`PluginStatus` operated on `pluginsDir` — the **runtime** `./plugins/` directory (gitignored, populated only by the install API/CLI). The 12 (see count correction below) builtins' real `plugin.yaml` files live under `internal/plugin/builtin/*/plugin.yaml` — a **different** directory tree, `//go:embed`-compiled into the binary and read via each builtin's `Manifest()` method. In the **default** deployment (no operator ever ran `install-local` against a builtin's own source dir), `pluginsDir` holds no builtin manifests at all, so the old `DisablePlugin(pluginsDir, "bookmarks-widget")` would just error `"not installed (no plugin.yaml found)"` outright — a clean, honest failure, not a silent no-op. This is narrower than Context's framing ("the file-rename mechanic would technically execute against them").
- The **real, confirmed bug** is one level deeper, in `LoadRegisteredBuiltins` (`internal/plugin/loader.go`): it loads **every** constructor in the compiled-in registry (`GetRegistered()`) that isn't already present in `host.plugins`, **completely independent of any on-disk manifest state**. `cmd/nanite/main.go`'s `discoverAndLoadPlugins` calls `DiscoverPlugins`+`LoadDiscovered` first, then unconditionally calls `LoadRegisteredBuiltins` for anything not yet loaded. So in the one scenario where a builtin's manifest *does* get copied into `pluginsDir` (an operator installs a builtin's own source via `install-local`) and is then disabled via the old file-rename, `DiscoverPlugins` correctly skips that now-manifest-less directory — but `LoadRegisteredBuiltins` picks the builtin right back up via its constructor and loads it anyway, running `applyManifestRegistrations` for it in full. **Confirmed via a live server run** (see Verification below) that this same "load every registered constructor unconditionally" loop is what the new DB-backed gate needed to close, not just the `applyManifestRegistrations` call site alone.
- Corrected a second factual claim in Context/`09-plugin-system.md`: there are **11** real builtins under `internal/plugin/builtin/`, not 12 — `sessionstats` (named in Context's list) does not exist anywhere in this workspace; `internal/plugin/allplugins`'s import list has 11 entries and a live server run logs `"plugins: loaded builtins","count":11`. Doesn't change any implementation: the seeding logic below reads the live `GetRegistered()` registry rather than a hardcoded count, so it's correct regardless of how many builtins actually exist. Per `EXECUTION-PROCESS.md` worker step 7, noting the correction here rather than treating it as a blocker.

### What was built

1. **Migration** `internal/store/migrations/121_plugins_installed_enabled_state.sql` — `plugins` table: `plugin_id TEXT PRIMARY KEY` (canonical id — `manifest.Identifier()`/`p.ID()`, not necessarily the `pluginsDir` directory name, which can differ, e.g. dir `bookmarks` vs id `bookmarks-widget`), `kind` (`builtin`/`subprocess`, CHECK-constrained), `installed`, `enabled` (both INTEGER bool, default 1), `created_at`/`updated_at`. Verified against a real copy of the backed-up production DB (`~/.local/share/nanite/workspaces/default/backups/main.db.pre-execution-backup-20260818-132726`, copied to an isolated scratch path — never opened in place) via a throwaway `go run` harness: migration applied cleanly, `EnsurePluginSeeded`/`IsPluginEnabled`/`SetPluginEnabled`/`DeletePluginState` all round-tripped correctly against the real schema.
2. **Store layer** `internal/store/plugins.go` — `PluginState` struct + `GetPluginState`/`ListPluginStates`/`EnsurePluginSeeded` (first-sight-only seed, never overwrites an existing row — so a re-run never clobbers an operator's prior choice)/`SetPluginEnabled` (explicit upsert, used by disable/enable)/`IsPluginEnabled` (returns `(enabled, hasRow, err)` — `hasRow=false` fails open to `enabled=true`, matching today's implicit default-on behavior for anything never explicitly toggled)/`DeletePluginState`.
3. **`internal/plugin/manage.go`** — full rewrite. `DisablePlugin`/`EnablePlugin`/`IsDisabled`/`PluginStatus` keep their exact `(pluginsDir, name string)` signatures (per the task's own "GUI/CLI/API callers don't need to change beyond the implementation swap" — verified true: neither `internal/api/plugins.go` nor `cmd/nanite/plugin_cmd.go` needed any edit, and neither was touched, per the explicit parallel-worktree boundary with tasks 01/04). Internally: `resolvePluginIdentity` resolves the caller's `name` to a canonical `(slug, kind)` — first via an on-disk `pluginsDir/<name>/plugin.yaml` (or a legacy `plugin.yaml.disabled`, restored in place — see migration note below); if neither exists, falls back to treating `name` as the canonical id directly if it matches a registered constructor (the path that makes a **builtin with no on-disk `pluginsDir` copy** — the default case — genuinely disable-able for the first time). DB access goes through a package-level `pluginStateStore`, set once by `cmd/nanite/main.go`'s `serve` command (`plugin.SetPluginStateStore(s)`, right alongside the existing `pluginHost.SetStore(s)`) so the server and these functions share one store instance; a standalone CLI invocation (`nanite plugin disable/enable`, which never boots a server) lazily opens and caches its own connection via `config.ResolveLayout()` — the same default DB-path resolution `cmd/nanite`'s own `resolveDBPathWith("")` performs. Fixed a small latent bug while rewriting `PluginStatus`: the old constructor-lookup fallback ran for subprocess plugins too, which never have a compiled-in constructor, so every valid subprocess plugin was misreported `"no-binary"`; the rewrite skips that check for `kind == subprocess`.
4. **`internal/plugin/loader.go`** — not in the task's stated `Touches` list, but necessary: gating only inside `applyManifestRegistrations` would leave the file-rename retirement causing a real regression for subprocess plugins (their OS process would spawn even while disabled, since `SubprocessPlugin.Load()` — called by `host.LoadPlugin`, well before `applyManifestRegistrations` — is what actually execs the entrypoint) and wasn't the actual fix for the confirmed `LoadRegisteredBuiltins` bug above. Added: `DiscoveredPlugin.MigratedFromDisabled` (set by `DiscoverPlugins` when it finds and restores a legacy `plugin.yaml.disabled`, so the plugin's pre-migration disabled state can be preserved rather than silently defaulting to enabled); `DiscoverPlugins` itself now restores any legacy `.disabled` manifest it finds (pure filesystem, no DB access — keeps `DiscoverPlugins`'s signature and callers, including the untouchable `internal/api/plugins_registry_test.go`, unchanged); a new `seedAndCheckEnabled(host, pluginID, kind, defaultEnabled) bool` helper, used by both `LoadDiscovered` and `LoadRegisteredBuiltins`, that seeds the DB row on first sight and reports the enabled flag — reading `host.store` (nil-safe: **fails open** to `enabled=true` and touches no database when no store is configured, which is true of most existing unit tests that build a bare `Host`). `LoadDiscovered` now skips a disabled plugin entirely (never calls `host.LoadPlugin`, so `Load()`/process-spawn never runs); `LoadRegisteredBuiltins` does the same for builtins — this is the literal fix for the confirmed bug.
5. **`internal/plugin/registrations.go`** — added a second, defense-in-depth gate at the very top of `applyManifestRegistrations` (before `recordManifest`/`activePlugin` mutation), checking `host.store.IsPluginEnabled` and returning `nil` immediately (no error, no side effects) if disabled. Not redundant with the loader-level gate: since `applyManifestRegistrations` is the shared entrypoint the task itself names as the layering point for Phase 5 items `03` (`registers.agent_profiles`) and `05` (`registers.crud`), this check guarantees any future registration category added inside this function — or any future caller that reaches it without going through `loader.go` — automatically respects the enabled flag too, without every future task needing to remember to check it itself.
6. **`cmd/nanite/main.go`** — one-line addition: `plugin.SetPluginStateStore(s)` next to the existing `pluginHost.SetStore(s)`.

### Deviation: `internal/api/plugins.go` left with a known, documented follow-up gap (not fixed, per the explicit worktree boundary)

`handleListManaged` (`internal/api/plugins.go` ~line 170) has its own inline check: `if status == "disabled" { manifestPath = .../plugin.yaml.disabled }`. Under the new DB-backed model `plugin.yaml` is **never** renamed, so a plugin `PluginStatus` now reports `"disabled"` for will have this fallback point at a file that no longer exists, causing `ParseManifest` to fail and that plugin entry to be silently dropped from the managed list (display-only regression — it does not affect whether the plugin is actually loaded/registered, which is correct). Per the explicit dispatch instruction not to touch `internal/api/*` (task 01's declared territory, running concurrently in a separate worktree) and per this task's own `Touches` list (which does not include this file), this was left as-is and is documented here as a real, concrete follow-up: `internal/api/plugins.go`'s `handleListManaged` should drop that `.disabled`-path branch (always read `plugin.yaml`) the next time a task legitimately touches that file. Not escalated as a stop condition — it's a scoped, isolated display bug in a file outside this task's `Touches`, not a data-integrity or security concern, and doesn't block or contradict this task's own Done means.
