# Close the CLI-install-vs-hot-reload asymmetry

**Phase:** 5
**Status:** implemented
**Depends on:** none, but coordinate with `11-build-plugin-installed-enabled-state-model.md` if both touch plugin install/lifecycle code in the same window
**Touches:** `cmd/nanite/plugin_cmd.go` (`triggerRestart`, `pluginInstallLocal`/`pluginInstallRemote` and other lifecycle commands, the existing `--no-restart` flag), `internal/api/plugins.go` (`handleReload` — the existing hot-reload endpoint, unchanged, just called from a new place)

## Context

Architecture doc `09-plugin-system.md`: *"Hot-reload confirmed real (`POST /api/plugins/reload`, dev-mode `window.__nanite_reloadPlugin`) — genuinely avoids a restart... One real asymmetry to close: CLI-based plugin install still requires a manual restart while the API-driven install path and the reload endpoint both hot-load live — have the CLI call the reload endpoint automatically after a local install instead of leaving this inconsistent."*

### Exact current state, verified

`cmd/nanite/plugin_cmd.go:185-197`'s `triggerRestart()` shells out to `cerberus restart <service>` (or prints a manual-restart message if cerberus isn't available). Called at the end of `pluginInstallLocal` (`plugin_cmd.go:290`), `pluginInstallRemote` (`:316,360`), and other lifecycle commands (`:485,495,505`) — always a full process restart, never the hot-reload path. A `--no-restart` flag already exists (`:26-28,46-47`) to skip this, confirming restart-by-default is deliberate current behavior, not an oversight to be treated as a bug in itself.

The hot-reload path already exists and is CLI-reachable today, just not wired into `install`: `nanite plugin reload <name>` (`plugin_cmd.go:92-96` → `pluginReload`, `cmd/nanite/plugin_dev_cmd.go:53-70`) POSTs to `/api/plugins/reload` (`internal/api/plugins.go:124` → `handleReload`, full body at `:701-741`: unload-best-effort → `runPluginLoadIntoHost` → emit disabled+enabled event pair).

### A real constraint: this only applies to subprocess plugins

A builtin's Go code is compiled into the binary — installing/updating a builtin genuinely requires a rebuild+restart; hot-reload structurally cannot apply. **This task's fix must branch on plugin kind**, not universally skip `triggerRestart()` — applying the reload-instead-of-restart fix uniformly would silently break builtin installs.

## What to do

1. In `pluginInstallLocal`/`pluginInstallRemote` (and any other lifecycle command currently ending in `triggerRestart()`), branch on plugin kind: for a **subprocess** plugin, call the same reload path `pluginReload` already uses (`POST /api/plugins/reload`) instead of `triggerRestart()`; for a **builtin**, keep the restart requirement (a builtin install/update genuinely needs one).
2. Preserve the existing `--no-restart` flag's meaning — confirm it still does something sensible now that the default subprocess path no longer restarts at all (may become a no-op for subprocess plugins, should remain meaningful for builtins).
3. Verify end to end: a real local subprocess-plugin install via the CLI hot-loads without a restart; a builtin install/update still correctly prompts for or performs a restart.

## Done means

- A subprocess plugin installed via the CLI is live (hot-loaded) without requiring a manual restart.
- A builtin plugin install/update still correctly requires a restart (regression check — this task must not silently break builtin installs by applying the fix too broadly).
- `go build ./cmd/nanite/`, `go vet ./...`, `go test ./...` pass.
- Verified in a real local install of a real subprocess plugin.

## Work log

**Implementation.** Added three new functions to `cmd/nanite/plugin_cmd.go`:

- `activationMode(manifest *plugin.PluginManifest) string` — pure decision function, returns `"hot-reload"` for `manifest.Runtime == "subprocess"`, `"restart"` otherwise (builtin, empty/legacy manifest, or nil manifest when kind couldn't be determined — conservative default).
- `triggerHotReload(name string)` — POSTs to `/api/plugins/reload` (the exact same endpoint/body `pluginReload` in `plugin_dev_cmd.go` already uses). Unlike `pluginReload` (a direct CLI command that `os.Exit(1)`s on failure), this degrades softly on failure (unreachable service, 4xx/5xx) — prints a manual-reload hint and returns, mirroring `triggerRestart`'s existing soft-failure behavior when cerberus isn't available. This matters because by the time this runs, the install/update/enable already succeeded on disk; a hard exit here would be a regression from `triggerRestart`'s current behavior.
- `triggerActivation(name string, manifest *plugin.PluginManifest)` — the actual branch point: `activationMode == "hot-reload"` → `triggerHotReload`; otherwise → `triggerRestart()` (unchanged, still `--no-restart`-gated).

Rewired every call site that produces a fresh/updated `plugin.yaml` on disk to call `triggerActivation` instead of `triggerRestart()`:
- `pluginInstallLocal` (already had `manifest` parsed in scope).
- `pluginInstallRemote`, catalog-found branch — parses the manifest at the just-installed `final` dir (previously only `triggerRestart()` was called here with no manifest read at all).
- `pluginInstallRemote`, git-clone fallback branch — manifest was already parsed in scope.
- `pluginEnable` — parses `plugin.yaml` after `EnablePlugin` renames it back from `.disabled` (it exists again at that point), then branches. This one wasn't explicitly required by "Done means" but is called out by name in "What to do" step 1 and is functionally sound (see below), so it's included.
- `pluginUpdate` in `cmd/nanite/plugin_install_flow.go` — reuses the `newManifest` already parsed for the version-bump message; falls back to `nil` (→ restart) if that parse failed. Not named in the task's Context section (which only cites `plugin_cmd.go` line numbers) but it's a `triggerRestart()` call site doing a reinstall-from-catalog, i.e. functionally an install — in scope under "any other lifecycle command currently ending in `triggerRestart()`", and directly covered by the builtin "Done means" bullet's own wording ("A builtin plugin install/**update**...").

**Deviation: `pluginUninstall` and `pluginDisable` deliberately kept on unconditional `triggerRestart()`, both plugin kinds — not branched.** The task's "What to do" step 1 names "any other lifecycle command currently ending in `triggerRestart()`" as in scope, which literally includes these two (line 485 = uninstall, line 495 = disable, per the task's own citations). I evaluated wiring them to the same `/api/plugins/reload` call and found it doesn't work, functionally:
- `handleReload` (`internal/api/plugins.go`) requires `plugin.yaml` to exist at the target path — it does unload-best-effort *then load*, i.e. it always ends with the plugin loaded. That's the wrong end state for uninstall/disable (which want *not loaded*), and by the time `triggerRestart()` fires in both commands today, the manifest that `handleReload` needs is already gone: `pluginUninstall` has already `os.RemoveAll`'d the whole directory, and `pluginDisable` has already renamed `plugin.yaml` → `plugin.yaml.disabled` via `plugin.DisablePlugin`. Calling `/api/plugins/reload` at that point 404s ("plugin not installed or disabled") instead of unloading anything — the running host (subprocess process included) would keep serving the uninstalled/disabled plugin with zero signal that anything went wrong, which is worse than today's behavior (a full restart that guarantees clean state).
- There's no unload-only endpoint to call instead. The task's own `Touches` line scopes `internal/api/plugins.go` to "`handleReload` — the existing hot-reload endpoint, unchanged, just called from a new place" — i.e., this task reuses the existing endpoint as-is, it doesn't add a new one. Building a real hot-uninstall/hot-disable would need a genuinely new unload-only endpoint, which is out of this task's stated scope.
- I confirmed this isn't ambiguous about *what to do* (the instruction to branch is clear) but a straightforward functional-correctness call about *where the existing reload endpoint's semantics actually apply* — not a "stop and escalate" case per the process doc (no doc/architecture disagreement, no item-vs-item conflict), just an implementation judgment I'm logging per the "distinguish decision from rationale, note the correction, keep going" guidance.
- Both functions still have full explanatory comments at the `triggerRestart()` call site documenting this reasoning for the next reader/reviewer.
- The task's own "Done means" bullets only test install (`"A subprocess plugin installed via the CLI is live..."`, `"A builtin plugin install/update still correctly requires a restart"`) — uninstall/disable aren't part of the acceptance bar, which is consistent with this scoping decision.

**`--no-restart` semantics (What to do step 2).** Kept the flag's literal meaning intact rather than repurposing it: it still gates every restart path exactly as before (builtin install/update/enable, and uninstall/disable, both plugin kinds — `triggerRestart()` itself still does the `if noRestart { return }` check, unchanged). It has nothing to skip on the new subprocess hot-reload path — `triggerActivation` calls `triggerHotReload` unconditionally for a subprocess manifest, regardless of `noRestart`. Rationale: the flag's name and its existing doc comment are specifically about skipping a *restart*; a hot-reload is not a restart (it never shelled out to cerberus or touched the live process), so there's nothing for `--no-restart` to meaningfully skip there — this matches the task's own explicit allowance ("may become a no-op for subprocess plugins ... should remain meaningful for builtins"). Verified live: `nanite plugin install <subprocess-src> --no-restart` still prints "Hot-reloading..." / "is live — no restart needed" (no skip), while `nanite plugin install <builtin-src> --no-restart` prints neither "Restarting..." nor any cerberus shell-out attempt (flag correctly still gates the builtin path). Updated the `noRestart` var's doc comment and `triggerRestart`'s comment references (`buildInstaller` doc comment in `plugin_install_flow.go`) to describe the new semantics precisely, so this isn't silently surprising to a future reader.

**Pre-existing bug discovered during verification (out of scope, not introduced by this task, logged as a heads-up).** `internal/api/plugins.go`'s `unloadPluginFromHost` calls `pms.pluginHost.UnloadPlugin(manifest.Name)` (the manifest's display `name` field), while `runPluginLoadIntoHost`/the subprocess bridge key on `manifest.Identifier()` (`id` when set, v1 schema). For any v1-schema plugin where `id` and `name` differ (true of the actual scaffold template's own generated `plugin.yaml` — e.g. `id: demo-verify`, `name: Demo Verify`), a *second* call to `POST /api/plugins/reload` (or any load-after-a-prior-load, e.g. `enable` after the plugin was already loaded once) fails: unload misses (`plugin "Demo Verify" not found`) because it's keyed under `demo-verify` in the host registry, then load fails because `demo-verify` is already registered. Reproduced this with the **unmodified, pre-existing** `nanite plugin reload demo-verify` command (untouched by this diff, lives in `plugin_dev_cmd.go`) called a second time against an already-loaded plugin — confirming it predates this task and isn't something introduced by wiring the CLI to the same endpoint. This is inside `handleReload`'s own helper functions, which this task's `Touches` line explicitly scopes as "unchanged" — fixing it is out of this task's authorized scope. Flagging it here as a genuine, reproducible, worth-a-follow-up-task finding; it does not affect this task's Done-means criteria, since the first (fresh) hot-load of any given plugin id in a given host process always succeeds cleanly (verified twice above), which is exactly the CLI-install path this task is scoped to fix.
