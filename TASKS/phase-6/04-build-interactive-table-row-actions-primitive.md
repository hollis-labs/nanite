This reinforces the decision log's own instruction to design fresh — there is nothing to port even if porting were preferred.

### Base primitive and response-routing mechanism, both real and ready to extend

`table-card` (`ui/src/components/chat/envelopes/primitives/TableCard.tsx` — sortable columns, `data: {title?, columns: [{key,label,sortable?}], rows: Record<string,primitive>[], caption?}`) is the base to extend. Its schema (`libs/go-envelopes/manifest/schemas/table-card.schema.json`) is strict (`additionalProperties: false` on both root and column objects) — adding row/column actions requires a real schema change, not just new frontend rendering logic.

**Response-routing is already fully generic, not `approval-card`-specific** — confirmed: `POST /api/envelopes/{id}/respond` (`internal/api/api.go:498` → `handleEnvelopeRespond`, `internal/api/envelopes.go:27`) looks up the envelope instance by ID, validates the response `kind` matches the stored `envelope_type`, and dispatches via `chat.LookupResponseHandler(envelopeType)` — a plain `map[string]ResponseHandler` registry (`internal/chat/envelope_handler.go:36-68`) any envelope type can bind into via `chat.RegisterResponseHandler(type, handler)`. **This task needs no new transport mechanism** — just (a) a `ResponseHandler` registered for the new interactive-table type(s), and (b) `EnvelopeInstance` creation on emit (same as `subagent-spawn-approval`/`question-form` already do), so a response has an addressable `id`.

## What to do

1. Design the `actions` capability on `table-card`'s schema: per-row and/or per-column, schema-validated action definitions (an action ID, label, and confirmation requirement at minimum) — reference Adaptive Cards' `Action.*` element model as a design touchstone per the architecture doc, without copying it wholesale; fit it to this codebase's existing `props`/discriminator conventions.
2. Extend `table-card.schema.json` to allow the new `actions` field (root and/or column level, per the design in step 1) — this is a real, deliberate schema change to a currently-strict (`additionalProperties: false`) schema, not an additive no-op.
3. Extend `TableCard.tsx` to render row/column action buttons and POST a response via the existing `/api/envelopes/{id}/respond` mechanism.
4. Register a `ResponseHandler` for the new action-response shape, following the exact registration pattern `subagent-spawn-approval`'s handler already uses.
5. Wire `EnvelopeInstance` creation on emit for any plugin/backend code that wants to use this primitive, so responses have an addressable envelope ID.
6. Build a real, working example (a test plugin or a genuine first consumer, if one exists in this pass's scope) demonstrating a real row action round-trip.

**Backend**: `internal/chat/envelope_response_table.go` (new) — `TableCardActionHandler`, registered in `internal/service/container.go` via `chat.RegisterResponseHandler("table-card", chat.NewTableCardActionHandler())` immediately after the elicitation-prompt registration, mirroring the exact `subagent-spawn-approval` pattern. Unlike `subagent-spawn-approval` (which drives one specific backend side effect), `table-card` is a generic reusable primitive with no built-in business logic — the handler's job is defensive/generic: it re-parses the envelope's server-persisted `EnvelopeJSON` (never trusts the client-submitted `row`/`action` data), confirms the submitted `action_id` (+ `column_key` when column-scoped) actually names an action the table was emitted with, validates `row_index` bounds, and resolves the row content from the persisted rows before writing it into `HandlerResult.TranscriptData`. A plugin wanting real side effects for a specific table can register its own `table-card` handler, which overwrites this default per the registry's existing "later registration wins" semantics (documented in `envelope_handler.go`).

**Frontend**: `ui/src/components/chat/envelopes/primitives/TableCard.tsx` — added `onRespond?: EnvelopeResponder` prop (spread in unconditionally by `EnvelopeRenderer.tsx` whenever the envelope has an `id`, no manifest/registry change needed since table-card already uses the default `{ data }` prop shape, not a `props: "..."` discriminator). Renders a root-level "Actions" column (row actions) and inline per-column action buttons (column actions), preserves each row's *original* index across client-side sort so `row_index` in a submitted response always matches the server-persisted row order, supports `confirm`/`confirm_message` via `window.confirm` (existing codebase precedent, e.g. `AppearancePanel.tsx`), and degrades gracefully: when `onRespond` is absent (the existing passive `card_show` emission path, which deliberately does not create an addressable `EnvelopeInstance`), no action buttons render at all rather than rendering permanently-dead ones; once `data.prior_response` is present (post-reload hydration, via the same wrap-level-merge-into-`data` mechanism `EnvelopeRenderer.tsx` already uses for other `{ data }`-shaped cards), buttons stay visible but disabled with a small "already recorded" note.

**Emit-path / addressability**: confirmed the existing split — `card_show`'s marker-based emission (`internal/selftools/self_tools_transport.go`'s `callShowCard`) deliberately does **not** call `CreateEnvelopeInstance` (see `internal/service/chat_generate.go`'s own comment: "Persistence stays the responsibility of interactive paths... where the row ID is needed for response endpoints") — so a plain (non-interactive) `table-card` via `card_show` continues to work exactly as before, unaffected by this change. Any caller that wants an *interactive* table-card must emit it through the addressable persist+stream path (`ApprovalEmitterImpl.Emit` / the same mechanism `ElicitationEmitterImpl` already wraps for `elicitation-prompt`) so the envelope gets a real `EnvelopeInstance` row and `id`. No new production emitter was added in this pass (no existing plugin/self-tool in this repo currently wants to emit an *interactive* table — confirmed via grep, matching the task Context's "no prior implementation exists" finding); the schema, renderer, and response handler are all in place and are exercised end-to-end by the integration test below using `store.CreateEnvelopeInstance` directly (the same call `ApprovalEmitterImpl.Emit` makes), which is the smallest correct proof the plumbing works without inventing a new user-facing tool the task didn't ask for.
