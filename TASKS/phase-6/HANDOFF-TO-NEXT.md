# Phase 6 (Envelopes & Cards) — Handoff to the next Orchestrator

Written from what actually happened during Phase 6 execution, not from the original task-file plans. Source: each `TASKS/phase-6/0{1..6}-*.md` Work Log + Review notes, `TASKS/INDEX.md`'s Phase 6 section, `TASKS/ESCALATIONS.md`. All six task files are `reviewed` and closed as of 2026-08-21.

## What shipped

Six tasks, all `reviewed`, no fix-and-re-review cycle needed on any of them:

1. **`01` — `todo-list` retired, folded into `list-card`.** `list-card`'s schema (`libs/go-envelopes/manifest/schemas/list-card.schema.json`) grew an optional `data_source` object (`{kind, scope, scope_id}`) plus per-item `id`/`status`. The frontend `ListCard.tsx` gained a `data_source.kind === "todos"` branch (`LiveTodoList`) that re-fetches via the same `useTodos`/`useToggleTodo` hooks the old `TodoListCard.tsx` used — `TodoListCard.tsx` is deleted. The `todo_list` self-tool emitter (`internal/selftools/self_tools_transport.go`'s `callTodoList` — moved packages since the task was written, was `internal/mcp/self_tools_transport.go`) now emits `type:"list-card"` with `data_source:{kind:"todos",...}` instead of `type:"todo-list"`.

2. **`02` — `plan-review` retired, folded into `list-card` + `confirmation-card`.** `list-card.schema.json`'s `data_source.kind` grew a `"plans"` value (`plan_id`, plus `in_progress`/`skipped` statuses). `confirmation-card.schema.json` grew a parallel `data_source:{kind:"plan_approval", plan_id}` plus `request_changes_label`. Frontend: `ListCard.tsx` gained `PlanStepsListCard`/`PlanStepRow`; `ConfirmationCard.tsx` gained `PlanApprovalConfirmationCard` (using `useApprovePlan`/`useRejectPlan`) alongside the untouched `GenericConfirmationCard` path. `PlanReviewCard.tsx` is deleted.

3. **`03` — `subagent-spawn-approval` recomposed onto `ApprovalCard`.** The largest of the three retirements. `SubagentSpawnApprovalCard.tsx` is deleted; `ApprovalCard.tsx` is now a single component with two flavors discriminated by `envelope.type === 'subagent-spawn-approval'`, reproducing the risk badge, prompt truncation/collapse, "Advanced" section, reason textarea, and approve/reject buttons the old bespoke component had. The wire type string `subagent-spawn-approval` was kept unchanged (a real decision — see Deviations below); only the manifest's `component`/`export` fields were repointed at `ApprovalCard`. Zero backend Go changes — the emitter (`internal/subagent/service.go:848`), response handler (`internal/chat/envelope_response_subagent.go`), and the `sessions.go` recovery gate are byte-identical to `main`.

4. **`04` — new interactive-table-with-row-actions primitive.** `table-card.schema.json` grew a `$defs/action` definition and both root-level and column-level `actions` arrays (previously `additionalProperties:false` throughout — a real schema loosening, not additive-only). New backend: `internal/chat/envelope_response_table.go`'s `TableCardActionHandler`, registered in `internal/service/container.go` via `chat.RegisterResponseHandler("table-card", ...)` — validates `action_id`/`column_key`/`row_index` against the server-persisted envelope, never trusts client-submitted row data. `TableCard.tsx` renders row/column action buttons, preserves original row index across client-side sort, supports `confirm`/`confirm_message`, and degrades to no buttons when `onRespond` is absent (the passive `card_show` path) or to a disabled "already recorded" state once `prior_response` exists. **This primitive has zero real production emitter as of Phase 6 close** — fully wired and reachable, exercised only via two full-stack Go integration tests (`internal/api/envelopes_table_card_e2e_test.go`) that go through the real HTTP mux and the real `TableCardActionHandler`, not a literal browser click. Flagged by both review passes as a legitimate primitive-before-first-consumer situation, not a regression.

5. **`05` — Card data excluded from replayed conversation history.** Described in this phase's own task file as the single highest-leverage item, and the review pass agreed ("strongest piece of the phase"). Real fix site: `internal/chat/context_client.go`'s `AssembleSlotSources`, **not** `internal/context/compaction.go` (the architecture doc's phrasing implied compaction; the task's own traced pipeline confirmed compaction's four stages structurally never reach this data because it never has `ContentBlocks` populated). Added `replayContent(content string) string` in `internal/chat/structured.go`: unmarshals persisted `store.Message.Content` as `StructuredMessage` and returns only `.Text`, discarding `.Envelopes` (and `.ToolCalls`) for LLM-facing history replay, falling back to the raw string for non-JSON/legacy/`envelope_response` content. Only the read path changed — the emit/persist path (`chat_generate.go`'s `WrapResponse`/`MarshalContent`) still writes full envelope data every turn.

6. **`06` — CLI boot content now sources the Card type list dynamically.** Added `chat.RegisteredEnvelopeTypeNames()` (sorted, mutex-protected) to `internal/chat/envelope.go`. `envelopeSchemaContent` (`internal/runtime/agent/sandbox_content_envelope.go`) and `claudeMDBody` (`internal/runtime/agent/sandbox_content_claude.go`) both converted from hardcoded `const` strings to functions that build the "Registered Envelope Types" content from the live in-process registry at plant time. Fixed two nonexistent-path references (`config/envelopes.yaml`, `internal/envelope/schemas/*.schema.json`) and swept several doc-comment sites making the same stale claim. Also fixed a doc comment in `internal/plugin/builtin/adapter-claude/plugin.go` falsely claiming an exported `BuildEnvelopeSchema` symbol that never existed (confirmed via `git log -S`).

## What deviated from plan, and why

- **`02`'s real emitter is a prompt string, not Go code.** The task file's Context section pointed at `internal/subagent/service.go` (based on comments there describing the `plan-review` wire shape) as the likely emitter. Verified false during implementation: those comments are inside the fully type-agnostic envelope-lifting plumbing (`liftResultEnvelopes`/`extractLiftableEnvelopes`), which never constructs any specific envelope type. The real construction site is `internal/selftools/self_tools.go`'s `plan_create` tool's `Description` string (~lines 395-397) — a natural-language instruction telling the LLM to write the fenced `nanite-envelope` JSON block itself. There is no Go call site to mechanically update; the fix was rewriting the prompt copy. Both the implementing worker and the independent fresh reviewer traced and confirmed this directly by grep, not by trusting the task file's assumption.

- **`03`'s wire-type-string question was resolved as "keep it."** The task file explicitly left open whether `subagent-spawn-approval` should keep its manifest type string or be renamed. The worker chose to keep it, reasoning: renaming would require migrating a real, non-empty production table (5 real `subagent_envelope_instances`-adjacent rows in the live DB at the time, 3 already responded) and touching every literal-string call site for no behavioral gain, since `approval-card` itself has no live backend response-handler registration of its own to converge onto. Only the manifest's `component`/`export` fields moved. This is a legitimate implementation decision, not an escalation — flagged here so the next Orchestrator doesn't assume the wire type changed.

- **Stale line references caught and corrected during implementation, not treated as blocking mismatches**, per the sharpened escalation rule already in effect for this project: task 03's cited `sessions.go:~818` recovery gate is actually at line 609; task 06's cited `internal/plugin/builtin/adapter-claude/plugin.go:168` planting call site turned out to be inside the unrelated `SyncProjectRoot` function — the real, live planting call site is `internal/runtime/agent/bootdir_plant.go`'s `sandboxFiles()` (`PopulateSandbox`, the function the task file assumed was live, has been a documented no-op since Phase 4c.6). Both were independently re-confirmed by the fresh reviewer.

- **Every worker in the `01`–`05` batch initially left its work uncommitted in its own worktree rather than committing to its branch.** Per `TASKS/INDEX.md`'s merge notes: "All five workers left their changes uncommitted... Each was asked to commit before merge; verified via `git log <branch> --oneline`... before every merge." This echoes a prior instance already logged against Phase 5 task 12's Work Log — worth treating as a standing pattern rather than a one-off: expect an explicit "commit to your branch before reporting done" step to be needed in dispatch instructions for future phases, or budget for the extra round-trip it otherwise costs at merge time. (Task 06's own Work Log doesn't explicitly record its commit status one way or the other — don't assume it followed the same pattern without checking `git log` directly if it matters to you.)

## Gotchas discovered mid-phase

- **`libs/go-envelopes/manifest/` is one shared, non-worktree-isolated physical checkout**, reached from every worktree via a `go.mod` local `replace` directive (through a `.claude/libs/go-envelopes` symlink). This was already a known, logged hazard (`TASKS/ESCALATIONS.md`, 2026-08-18, "shared `.claude/libs/go-envelopes` replace-target") predating Phase 6, and Phase 6 hit it exactly as documented: tasks `01`/`02`/`03` all edited the same `envelopes.yaml` file concurrently (each removing/replacing a different standalone entry), and `04` touched `table-card.schema.json` in the same directory. Workers coordinated by keeping each own diff narrow and re-checking the file mid-task for sibling edits rather than reverting anything — no conflicts occurred inside the manifest itself. **This hazard is now closed for the go-envelopes-mirror mechanism specifically**: the combined `01`–`04` manifest/schema state (plus a shared test-fixture fix, see below) was landed as go-envelopes commit `7978078c` (`manifest/envelopes.yaml`, three schema files — `list-card`, `confirmation-card`, `table-card` — `CHANGELOG.md` backfill, `registry_test.go`, `validator_test.go`). Re-verified in this worktree post-commit: `go build`/`go vet`/`go test ./...` clean, frontend build + `generate-plugin-imports.mjs --check` + `vitest run` (187/187) all clean against the final committed manifest state. If a future phase needs to touch this shared manifest again, expect the same coordination need to recur (nothing about the mechanism itself changed, only this phase's specific edits landed).

- **A real manual merge conflict, not just sequential coordination, hit `ui/src/components/chat/envelopes/primitives/ListCard.tsx`.** Tasks `01` and `02` both independently added a `data_source`-driven live-rendering branch to the same file (`01`'s `LiveTodoList`/`ListRow` for `data_source.kind:"todos"`, `02`'s `PlanStepsListCard`/`PlanStepRow` for `data_source.kind:"plans"`). The Orchestrator resolved this by hand, keeping both as distinct, intentional components side by side rather than force-unifying them, then re-verified via a full frontend build (`tsc -b && vite build`, clean) and `vitest run` (187/187) — not just absence of conflict markers. `self_tools.go` (also touched by both `01` and `02`) auto-merged cleanly with no manual intervention needed.

- **The `registry_test.go`/`validator_test.go` shared-library test-fixture break.** Both tests hardcoded `"todo-list"` as their fixture for "a core type with no schema file." Before Phase 6, `todo-list` and `plan-review` were the *only* two schema-less core types; once both `01` and `02` land, zero core types remain schema-less, breaking both tests regardless of which task's edit landed first. The prescribed substitute fixture (`session-task`) turned out to already have a real schema too — empirical audit found no real core type remains schema-less after this phase's removals at all. Fixed as a synthetic-fixture rewrite via `registry.go`'s existing `WithManifestFS` test hook (registers an ad-hoc schema-less type at test time) rather than coupling either test to real, live manifest content. Landed as part of the `7978078c` checkpoint commit above.

- **A worker legitimately declined mid-task, and was replaced, not pressed.** The worker assigned task `03` initially attempted the go-envelopes checkpoint commit across a chain of escalating requests, then raised a legitimate scope-authorization concern (being asked to vouch for four tasks' — `01` through `04` — combined correctness, not just its own) partway through, and declined further action. The Orchestrator treated this as a reasonable call, not a failure, and re-routed the checkpoint-commit work to a fresh agent rather than pressing the original worker. This was an Orchestrator-level process correction, not an operator escalation — see `TASKS/INDEX.md`'s Phase 6 "Shared `libs/go-envelopes` mirror" note for the full account.

## Things discovered mid-phase worth knowing, not in the original plan

- **`table-card`'s new interactive primitive has no real emitter yet.** It's fully wired (schema, renderer, response handler, addressable-envelope-instance path) but nothing in this repo currently emits an *interactive* table-card in production — only the passive, non-addressable `card_show` path exists today. If a future phase wants to build the first real consumer, the plumbing is ready; don't assume "table-card" already has live usage just because its primitive shipped.
- **`docs/engineering/architecture/08-cards.md`'s "known live bug" section is now stale.** It documents the CLI boot-content staleness that task `06` fixed. Both review passes (06's own, and the earlier combined 01-05 pass) logged this as a non-blocking observation, not fixed as part of this phase (no task in this batch owned doc maintenance). Whoever next touches that doc should update or remove that section.
- **`internal/api/envelopes.go`'s `handleEnvelopeRespond` sets `responded_at` before invoking the `ResponseHandler`**, so a handler rejection has no retry path. This is pre-existing, generic framework behavior shared by every response handler (not introduced by task `04`), but flagged by the reviewer because table-card's click-driven UX makes it more reachable day-to-day than the prior LLM-authored-JSON-only interactive cards.
- **A stale `"type": "nanite"` example survives in `envelopeSchemaContent`'s static header/examples section** (the "Interactive envelopes" `kind: question|action|approval` pattern) — `"nanite"` is not itself a registered envelope type anywhere and would be rejected as `unregistered_type` if actually validated. Task `06` deliberately left this untouched (out of its stated scope: the type-list table + the two nonexistent-path pointers, not the static wire-format examples) — flagged by its worker and independently confirmed by the reviewer, not fixed.
