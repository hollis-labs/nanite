## Context

`docs/engineering/architecture/10-reflex-action-taxonomy.md`, "Harness-reactive self-tools (adjacent mechanism, deliberately not part of this taxonomy)": distinguished during the 2026-08-19 architecture-review session as a **sibling** mechanism to reflexes, not a reflex action kind. An agent-initiated "declare a fact, let the harness react" pattern (e.g. `nanite_report_task_updated(id, msg)` — the harness decides whether/how to react: a card, an internal API call, both, neither). It has no predicate/event/interval trigger — the agent's own tool call *is* the trigger — so it structurally can't be an `action_kind` row.

**Resolved shape, not yet built:** small, purpose-built `nanite_*` self-tools (the namespace already reserved for first-party tools per `docs/tool-naming-convention.md`, already outside the general MCP trust-tier/result-cache apparatus meant for arbitrary external reach — see `docs/mcp-trust-model.md`). Each self-tool's own definition should carry a category/kind field marking it harness-reactive — preferred over a bare boolean, for the same extensibility reason as Facet 1's category table in the main taxonomy doc (room to add more reaction shapes later without a schema change).

**Naming is not finalized.** Leading candidate: "harness-reactive self-tools." "Report tools" and "declare tools" were considered and explicitly rejected as *final* only in the sense that neither is locked yet — not rejected outright. Whatever name is chosen, **avoid "event" and "notify"** — both already carry distinct meaning elsewhere in this codebase's vocabulary (`trigger_kind='event'`, the `event_log` table; `notify_external`, a candidate deferred deterministic reflex kind) and reusing either would reintroduce the exact naming confusion the whole taxonomy session was trying to eliminate. Check `GLOSSARY.md` before locking any name, per `EXECUTION-PROCESS.md`'s standing instruction.

The design doc is explicit: *"This mechanism gets its own design pass when it's actually built — this doc captures the distinction and the naming constraint so the context isn't lost, not a full spec for it."* This task file exists for the same reason `TASKS/phase-4/10-reflex-architecture-review.md` existed — to hold a place in the tracker for a design session the operator will run directly, not to hand a worker a spec that doesn't exist yet.

## Work log

**2026-08-20 — architecture/design session with operator, no code changed.** Full design recorded in `docs/engineering/architecture/11-harness-reactive-self-tools.md`; `10-reflex-action-taxonomy.md`'s stub section and "What this session did not decide" list both updated to point at it. Summary of decisions, in the order settled:

1. **Package boundary: `internal/selftools`, not `internal/mcp` or `internal/agent/selftools`.** Self-tool definitions/dispatch move out of `internal/mcp` (their current home — a static Go slice plus a hardcoded dispatch `switch`) into a new top-level package, matching this repo's own flat-sibling convention under `internal/` rather than nesting under a shared umbrella noun. `internal/agent/selftools` was seriously considered and rejected on a direct `GLOSSARY.md` check: `internal/agent/` already carries two distinct, established meanings (Agent composition/steering vs. `internal/runtime/agent/`'s boot-process runtime) — self-tools are neither, and nesting there would make "agent" mean a third thing depending on subdirectory, the exact collision class `GLOSSARY.md` exists to prevent. Confirmed Go's `internal/` visibility rule doesn't reward the nesting anyway — the enforced boundary is set by the first `internal/` segment from repo root regardless of depth, so this was a pure semantic-organization choice, not a language-idiom one.
2. **DB scope: reactive layer only, not a full self-tool catalog migration.** New table(s) for category/kind + reaction config, keyed by tool name; the ~70 existing tool definitions and their dispatch stay in Go. Matches how `agent_reflexes`/`agent_context_resolvers` already layer DB config on top of otherwise-Go-executed behavior without migrating the thing being configured.
3. **Category/kind as an extensible lookup table**, mirroring the taxonomy doc's own Facet 1 reasoning exactly (room to add reaction shapes later without a schema rewrite) — illustrative shape: `selftool_reaction_kinds` (slug, category, `implemented` flag) + `selftool_reactions` (tool_name, reaction_kind_id, JSON config, enabled). Deliberately **no combining-algorithm column** — reflexes need one because multiple reflexes of the *same kind* can compete for one state; self-tool reactions don't have that shape (one tool call's own configured reactions all fire independently, matching the design doc's own "a card, an internal API call, both, neither" framing).
4. **Reaction engine: `internal/selftools/reactions`, not `react` or `action`.** `action` was seriously considered (operator's own instinct: "self-tools trigger an action") and rejected once checked against `internal/agent/reflexes`'s existing, heavy use of exactly that word (`action_kind`, `execute_action`, `AppliedAction`, `Executor.Apply`) — same collision class as `agent` above, just one level down. `react` was rejected as a bare-verb package name against this repo's own noun/gerund sibling convention (`reflexes`, `messaging`, `envelope`). Checked against `GLOSSARY.md`: no existing "react"/"reaction" entry to collide with.
5. **Reaction vehicle: a new shared engine, not the `ENVELOPE_DATA` marker as-is and not cards-only.** Investigated the marker mechanism `card_show`/`todo_list` already use directly: confirmed it's fragmented across three independent, hand-duplicated consumers (`internal/service/chat_tool_executor.go`+`chat_generate.go:captureEnvelopeData`, `internal/api/tools_call.go:extractEnvelopeMarker`, `internal/mcpserver/handlers.go:convertEnvelopeMarkers`) — the same "duplicated by necessity, not oversight" shape the taxonomy doc already diagnosed for `dispatch_to_agent`'s three call sites, and for the same reason (`internal/mcp`/`internal/selftools` can't import `internal/chat` or `internal/service` — confirmed directly against the import graph, not assumed). Resolved: multiple doors are fine (self-tool reactions genuinely need to reach card rendering from both the in-process chat loop and the CLI-agent proxy, which don't share a call stack) — what has to be shared is what happens *past* each door. The marker signal itself stays (it's the only viable channel out of `internal/selftools` for a live UI effect); its interpretation collapses from three independent implementations to one, driven by the DB-backed category/kind lookup instead of hand-authored per-tool construction.
6. **Independently re-verified the halt-turn-synchronicity fix (`03`/`04`) is real and still holds**, since it directly informed decision 5's execution-shape split and several agents had claimed it was done without the operator having independently confirmed it. Read `internal/service/chat_generate.go:538-557` directly (the `ReflexActionHaltSession` check + abort-before-LLM-call, sitting after the same-pass `deny_overrides` preemption in `resolve.go`) and ran `TestGenerateResponse_HaltSessionReflex_AbortsTurnBeforeLLMCall`/`TestGenerateResponse_NonHaltReflex_DoesNotAbortTurn` live against this checkout — both pass. Confirmed the pattern that fixed it (constrained `internal/store`-only engine does the DB write; an unconstrained caller one layer up acts on the live effect) is the same shape `render_card` needs, with the caveat that self-tool reactions have multiple structurally-necessary doors where halt only ever had one.
7. **Telemetry: reuse `event_log` as-is, full coverage required.** Checked directly against `internal/agent/reflexes/telemetry.go` (task `06`, already implemented/reviewed) and `internal/store/migrations/001_schema.sql:473`: `event_log`'s existing `(session_id, event_type, category, detail, metadata)` shape is already fully polymorphic — no schema change needed, so the operator's own fallback ("if it doesn't already support that, we'll take that as scope") doesn't trigger. New parallel thin wrapper in `internal/selftools/reactions` (not an extension of reflexes' own `EmitFirings` — scope fence held), one `event_log` row per fired reaction, `category = "selftool_reaction"` (new value, kept distinct from reflexes' existing `category = "reflex"`).
8. **Worked example: `task_update_report(id, msg)`**, renamed from the design doc's original `nanite_report_task_updated` to match the `<concept>_<verb>` convention every other self-tool already follows (none of the ~70 registered self-tools carry a `nanite_` prefix except `nanite_code_execute`). Kept illustrative rather than bound to a real consumer (matches decision 9). Designed with two reaction rows — `render_card` and `internal_api_call` — specifically to exercise both execution shapes from decision 5/6 (engine-resolves-caller-surfaces vs. engine-executes-directly) and to prove the "both" case, not just one kind.
9. **Decision on immediate-vs-deferred implementation: document now, wait for a concrete consumer.** Explicit operator call, not a default-to-inaction — this file's own scope stays design-only either way, matching how `TASKS/phase-4/10-reflex-architecture-review.md` itself closed out. No follow-up implementation task file filed by this session.
10. **What's still genuinely open** (see `11-harness-reactive-self-tools.md`'s own "What this session did not decide" section for the full list): exact table/column DDL, real execution semantics for `internal_api_call`/`external_api_call`/`callback` (auth, retries, idempotency), provenance/authority tiering for reaction registration, the concrete refactor shape for the three existing `ENVELOPE_DATA` consumers, and a flagged-but-out-of-scope follow-up on `docs/tool-naming-convention.md`'s own `nanite_*`-reservation wording.
