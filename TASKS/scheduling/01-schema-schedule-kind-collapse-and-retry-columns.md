**Go-level `next_run` backfill, not pure SQL — a real, documented deviation from a literal reading of "backfill it... as part of this migration."** The task's own wording ("compute via the same cron-parsing logic `go-scheduler.NextRun`/`robfig/cron` already provides") names real Go cron-parsing code, not a SQL reimplementation of cron semantics. Writing a hand-rolled SQL cron parser risked silent correctness bugs for a value whose entire purpose is "don't silently get this wrong," and the actual runtime consequence of an incorrect `next_run` isn't cosmetic: it changes *when* the real production `lint-and-export` schedule fires once the new engine takes over (an eager/immediate fire on cutover vs. the real next 3am occurrence). So migration 127's SQL leaves `next_run` `NULL` for every row (safe, matches go-scheduler's own "NULL/zero = unscheduled" convention as a transient state) and a new, idempotent Go function — `backfillScheduleNextRun` (`internal/store/agent_schedules.go`) — runs immediately after every `migrate()` call inside `Store.New()` (`internal/store/store.go`, the single entry point that opens this DB in this codebase — confirmed via grep, no other `goose`/`migrate()` call site exists). It queries for `status='active' AND next_run IS NULL AND schedule_kind IN ('cron','one_shot')`, computes `cron.ParseStandard(schedule_spec).Next(now)` for cron rows (identical parsing to what `go-scheduler.NextRun` itself wraps — deliberately not importing `go-scheduler` itself here, since that dependency is `02-store-adapter.md`'s to add) and `now` for one_shot rows, and is a provable no-op on every boot after the first (verified in `TestBackfillScheduleNextRun_Cron`'s second-call assertion).
