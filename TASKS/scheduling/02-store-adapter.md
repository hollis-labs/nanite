## Context

`docs/engineering/architecture/12-scheduling.md`'s "The Store adapter" section is the design — read it in full, plus `libs/go-scheduler/scheduler.go:44-64`'s exact `Store` interface (four methods: `ListDueSchedules`, `ClaimAndUpdateScheduleRun`, `SetScheduleNextRun`, `DisableSchedule`) and `libs/go-scheduler/scheduler.go:24-32`'s neutral `Schedule` type (`ID`, `CronExpr`, `LastRun`, `NextRun`, `Enabled`, `JobType`, `Payload []byte`) before starting.

**The safety argument, already established, do not re-derive it — apply it:** `internal/store/store.go`'s `New()` opens the database via `sqlitekit.OpenSingle` — a single-connection pool with WAL, `busy_timeout(5s)`, and `_txlock=immediate` on every connection (`internal/store/store.go:35-39`). A single writer connection makes `UPDATE agent_schedules SET last_run=?, next_run=? WHERE id=? AND next_run=?` checking `RowsAffected()==1` safe by construction, in-process and cross-process — this is the CAS claim `ClaimAndUpdateScheduleRun` needs, and no new write-serialization infrastructure is needed to get it.

**Template to follow, directly transferable, not hypothetical:** `/Users/chrispian/dev/hollis-labs/apps/hadron/internal/scheduler/adapter.go`'s `storeAdapter` — Hadron's own `persistence.Store` already implements `ClaimAndUpdateScheduleRun`/`SetScheduleNextRun`/`DisableSchedule` with matching signatures and promotes them directly via struct embedding (`type storeAdapter struct { *persistence.Store }`); only `ListDueSchedules` needs an explicit conversion wrapper (DB record → neutral `gosched.Schedule`, packing app-specific fields into the opaque `Payload`). Confirm whether Nanite's `*store.Store` can follow the same embedding shortcut (i.e., whether it's worth adding `ClaimAndUpdateScheduleRun`/`SetScheduleNextRun`/`DisableSchedule` methods directly onto `*store.Store` with matching signatures, so a thin adapter can embed it the same way) or whether a fully separate wrapper type is cleaner given `*store.Store`'s existing method surface — either is acceptable, document your call.

**Embedding vs. separate wrapper (Context's explicit ask):** did **not** follow Hadron's `type storeAdapter struct { *persistence.Store }` embedding shortcut, even though it's mechanically possible here too (the three matching-signature methods use only `time.Time`/`string`/`bool`/`error`, so `*store.Store` would need zero `gosched` import to host them). Two reasons, both documented in `internal/scheduler/store_adapter.go`'s package doc comment: (1) `internal/store/agent_schedules.go` already has a consistent Nanite-flavored naming convention for this table (`InsertAgentSchedule`, `GetAgentSchedule`, `ListAgentSchedules`, `UpdateAgentScheduleStatus`, `BumpAgentScheduleFireCount`) that bare gosched-interface-shaped names would break; (2) `runner_adapter.go` (03, same package) explicitly documents and follows a narrow-dependency-interface convention specifically to avoid exposing a wide concrete service type's full method surface — embedding all of `*store.Store` (a large, general-purpose type used across the whole app, not one designed around scheduling) through `StoreAdapter` would be the opposite of that convention. Instead: added three small, Nanite-convention-named low-level DB methods to `internal/store/agent_schedules.go` (`ListDueAgentSchedules`, `ClaimAgentScheduleRun`, `SetAgentScheduleNextRun`); `DisableSchedule` reuses the already-existing `UpdateAgentScheduleStatus` (mapped to `status='expired'`, matching `durable_wake.go`'s own existing "fired one-shot → expired" behavior — see below). `StoreAdapter` holds `*store.Store` as a plain named field, not narrowed to an interface (unlike `runner_adapter.go`'s dependencies) and not embedded, because the CAS claim's correctness argument is specifically tied to `*store.Store`'s own `sqlitekit.OpenSingle` single-writer-connection configuration — narrowing to an interface would blur that argument, and the task's own required regression test (a real, not in-memory-only, `*store.Store`) reflects the same reasoning.

**`durable_agent_wake` → `instance_id` resolution mechanism:** confirmed via `internal/service/durable_wake.go`'s `ListDue`/`ListSchedules`/`Wake` that `agent_schedules.agent_id` is, and has always been, an `agent_profiles.id` (called `ProfileID` on `durable_agent_instances`) — `ListDue` walks `ListDurableAgentInstances(false)` outer and calls `store.ListAgentSchedules(ctx, inst.ProfileID)` inner. No existing store method resolves the reverse direction (profile → instance), so `StoreAdapter.resolveDurableAgentInstanceID` reuses the same existing `store.ListDurableAgentInstances(false)` listing (not a new query) and filters for `inst.ProfileID == schedule.AgentID` in Go. Today's real data shape is 1:1 (confirmed by reading `managed_durable_configs.go`'s `syncManagedDurableAgentConfig`, which creates exactly one instance then exactly one profile-scoped schedule per managed YAML config, and independently re-confirmed by running this adapter against a scratch copy of the real backup DB — see "Real-data verification" below), but nothing in the schema enforces that going forward. Rather than guess which instance a schedule fires against if 2+ instances ever share a profile, `resolveDurableAgentInstanceID` treats 0-match and 2+-match both as a conversion failure — the row is skipped from `ListDueSchedules` with a logged warning (same "skip the unconvertible record, don't abort the tick" pattern Hadron's own `storeAdapter.ListDueSchedules`/`toSchedule` uses), rather than silently picking a possibly-wrong instance. `Reason`/`ProjectID` are deliberately left empty in the built payload rather than computed here: `DurableAgentWakeService.Wake` (called downstream by `03`'s `RunnerAdapter.enqueueDurableAgentWake`) already falls back to `wakeReasonForInstance(inst)`/`resolveWakeScope(inst).ProjectID` internally whenever the incoming request leaves them empty, so duplicating that fallback in this adapter would just be a second, driftable copy of logic `Wake` already owns.

**Reconciling step 2's `{"body": row.Body}` illustration with `03`'s real fixed contract:** the dispatching agent's brief already flagged this mismatch (the illustrative shape didn't anticipate `instance_id`). Resolved by marshaling the *actual* `DurableAgentWakePayload` struct `runner_adapter.go` already defines (same package, so this is literally the identical Go type on both sides, not a hand-matched JSON shape) with `InstanceID` set via the resolution above and `Prompt: row.Body` — matching `durable_wake.go`'s own `RunDue`, which forwards `item.Schedule.Body` as `WakePayload.Prompt` today (confirmed by reading that code, not assumed).

**Job-payload pass-through for the other three types (`agent_workflow_run`/`command_run`/`reflex_dispatch`):** pass-through-as-is, not parse-and-repack. `row.JobPayload` is validated with `json.Valid` (a corrupt row is skipped, logged, rather than handed to the Runner as garbage) and then cast directly to `[]byte` — no `json.Unmarshal`/`json.Marshal` round trip, since re-marshaling byte-identical JSON buys nothing and risks silently reordering or dropping fields the adapter's own structs don't know about.

**`next_run` computation for `cron`-kind schedules (step 5):** confirmed by reading `libs/go-scheduler/engine.go`'s `tick()` that the real engine already owns computing a cron schedule's next `next_run` (via its own call to the library's `NextRun`) and a one-time schedule's disable-after-fire placeholder, then hands the computed value to `ClaimAndUpdateScheduleRun` as an argument — the `Store` adapter never needs to independently compute a next occurrence in its own method bodies. This adapter therefore contains **zero** cron-math of its own (matching Hadron's own `adapter.go`, which also has none) — the strongest possible form of "don't hand-roll a second cron-math implementation," since there's no cron-math here to duplicate go-scheduler's own `NextRun` in the first place. `toSchedule` only maps `schedule_spec` → `CronExpr` for `cron`-kind rows (forced empty for `one_shot`, regardless of what `schedule_spec` holds, matching `backfillScheduleNextRun`'s own confirmed finding that a `one_shot` row has no independent target-time encoding). `TestStoreAdapter_NextRunRoundTrip_OneShotAndCron` proves the round trip by calling `gosched.NextRun` directly in the test to simulate exactly what the real engine does, per this task's Done-means bullet.

**`DisableSchedule` status mapping:** maps to `status='expired'` via the existing `UpdateAgentScheduleStatus`, matching `durable_wake.go`'s `RunDue` (`if ... ScheduleKindOneShot { UpdateAgentScheduleStatus(ctx, ..., ScheduleStatusExpired) }`) — the engine's only real call site for `DisableSchedule` today is immediately after a one-time schedule's successful dispatch, the exact event `RunDue` already handles this way. `'paused'` was considered and rejected: this repo's status vocabulary reserves `paused` for a reversible, operator-toggled-off state, which a fired one-shot is not.
