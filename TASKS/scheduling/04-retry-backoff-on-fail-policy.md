# Retry, backoff, and `on_fail` policy

**Phase:** 1 — Core engine (`TASKS/scheduling`)
**Status:** implemented
**Depends on:** `01-schema-schedule-kind-collapse-and-retry-columns.md` (`schedule_runs` table, `max_retries`/`on_fail` columns), `02-store-adapter.md` (`DisableSchedule`), `03-runner-adapter-and-job-taxonomy.md` (wraps its `Enqueue`).
**Touches:** the same package as `02`/`03` (wraps the Runner adapter's `Enqueue`, or is layered as a decorator around it — see step 1), `internal/store/` (new `schedule_runs` read/write helpers, if `01` didn't already build them — check `01`'s Work Log first).

## Context

`docs/engineering/architecture/12-scheduling.md`'s "Retry, backoff, and `on_fail` policy" section is the design, in full — read it before starting. The core problem it solves: `go-scheduler` itself only offers "retry the same firing every second, forever, uncounted" (confirmed directly by the design session against `engine.go`'s `SetScheduleNextRun` rollback-on-failure behavior) — real retry/backoff/failure policy has to live entirely in this layer, not the library.

**The mechanism, already decided — implement it, don't redesign it:**
- On `Enqueue` failure, check `schedule_runs` for the current firing (`job.RunID`): if `attempt_count < max_retries` (the schedule's own column, from `01`) and `next_attempt_at` hasn't elapsed yet, return the same error again immediately **without a real dispatch attempt** — cheap, so `go-scheduler`'s 1-second hammering costs only a `schedule_runs` lookup between real attempts, while the actual backoff cadence is owned by `next_attempt_at`, not the library's tick rate.
- Once `attempt_count >= max_retries`, apply the schedule's `on_fail` policy: `disable` calls `Store.DisableSchedule` directly; `notify` emits an event (this task emits the event — full observability coverage is `06-schedule-fire-telemetry.md`'s job, but this task's `notify` branch must call into whatever emission point `06` builds, or a placeholder this task documents clearly if `06` hasn't landed yet) without disabling. Then **return `nil`** — signaling success to `go-scheduler` purely to stop its retry loop, with the real outcome recorded in `schedule_runs`, not misrepresented to the engine as a successful dispatch. (`retry` is not a valid terminal `on_fail` value at exhaustion — by definition it's what already happened for `attempt_count` rounds; confirm `01`'s schema Work Log for how the `on_fail='retry'` default value is meant to behave at exhaustion, since a schedule configured `on_fail='retry'` still needs *some* terminal behavior once `max_retries` is hit — document your resolution if `01` didn't already pin this down.)

**The backoff curve itself is explicitly not decided by the design doc — this task decides it, documents it, doesn't treat it as free-form.** Pick a concrete curve (e.g. exponential with a cap, matching a common convention — or linear, your call) and document the exact formula and any cap in this file's Work Log. This is a real implementation decision this task file is deliberately deferring to you, not an oversight.

## What to do

1. Decide whether this is a decorator wrapping `03`'s `Runner` (implementing `gosched.Runner` itself, delegating to the inner Runner on the real dispatch attempt) or logic folded directly into `03`'s `Enqueue`. A decorator (`retryingRunner{inner gosched.Runner, store ScheduleRunStore}`) keeps `03`'s own per-job-type dispatch logic and this task's retry/backoff bookkeeping independently testable — recommended, but not mandatory; document your call.
2. On every `Enqueue(ctx, job)` call: look up (or create, if this is the firing's first attempt) the `schedule_runs` row keyed by `job.RunID`. If a backoff window is active (per the mechanism above), short-circuit without calling the inner Runner. Otherwise call the inner Runner, record the outcome (`attempt_count++`, `last_error`, `next_attempt_at` per your chosen curve, `status`) in `schedule_runs`.
3. On exhaustion (`attempt_count >= max_retries`), apply `on_fail` per the mechanism above and mark the `schedule_runs` row `status='exhausted'` (or your `01`-aligned vocabulary).
4. On success, mark the `schedule_runs` row `status='succeeded'` (or equivalent) — this is what lets `06-schedule-fire-telemetry.md` and any future operator-facing view distinguish a clean fire from a retried-then-succeeded one.
5. Translate `gosched.ErrDuplicateJob` (from the inner Runner, per `03`'s own translation) through unchanged — a duplicate-run race is not a retry-policy concern, don't let this layer's bookkeeping misinterpret it as a failed attempt.

**A real, verified-against-primary-source mismatch found and corrected: `Job.RunID` is NOT stable across retry attempts of the same firing in real `go-scheduler` usage — the "keyed by `job.RunID`" mechanism description (this task file, `01`'s migration doc comment, `03`'s own Work Log) is factually wrong about the library's actual behavior, confirmed by reading `libs/go-scheduler/engine.go`'s `tick()` directly, not assumed.** `Job.RunID = fmt.Sprintf("sched-%s-%d", sch.ID, now.Unix())` — computed fresh from the *current tick's* wall-clock time, not from the schedule's original due time. On a failed `Enqueue`, the engine calls `SetScheduleNextRun(ctx, sch.ID, expectedNext)`, rolling `next_run` back to the pre-claim value so the *schedule* becomes due again on the very next 1-second tick — but the *next* tick computes a brand-new `Job.RunID` from its own `now.Unix()`, which differs from the previous attempt's (ticks are ~1s apart). `Job.FiredAt` is the same `now` value, so it changes too. The only field that stays stable across retries of one logical firing, from the Runner's own vantage point, is `Job.ScheduleID`. Taking "keyed by `job.RunID`" literally would mean every real retry attempt in production creates a brand-new `schedule_runs` row with `attempt_count` reset to 0 — silently defeating `max_retries` entirely and reproducing the exact "retries forever, uncounted" problem this whole task exists to fix, while still passing a unit test that (necessarily, since it doesn't run the real `Engine`) reuses the same `Job` value across simulated retry calls.

This is corrected per `EXECUTION-PROCESS.md`'s "distinguish the decision from its rationality" framing applied to an *implementation-mechanism* description, not a `TASKS.md` cut/keep/build action: the task's instruction ("on `Enqueue` failure... check `schedule_runs` for the current firing... on exhaustion... mark the row `exhausted`... return `nil`") is followed in full; only the specific SQL/lookup *key* used to find "the current firing's row" is corrected from "`run_id`, literally" to "`schedule_id`, with an open (non-terminal) row = the current firing" — the only version of the mechanism that is actually correct against the real library's behavior. **Resolution implemented** (`internal/store/schedule_runs.go`'s `GetOpenScheduleRun`, `internal/scheduler/retrying_runner.go`'s `getOrCreateRun`, both with full doc-comment writeups of this finding):
- `GetOpenScheduleRun(ctx, scheduleID)` returns the most recent **non-terminal** (`pending`/`failed`) row for a schedule — this is the row for "whichever firing's retry sequence is currently in progress," found by `schedule_id`, not `run_id`. If found, it's reused across attempts regardless of the incoming `Job.RunID`; the row's own `run_id` column is never rewritten on retries (stays the first attempt's value, documented).
- If no open row exists, a genuinely new firing is the common case (create a fresh row, `run_id = job.RunID`, `attempt_count = 0`). The one edge case handled explicitly: a caller (a test harness simulating repeated ticking with an *unchanged* `Job` value, which real `go-scheduler` never does) calling `Enqueue` again after this layer already concluded that exact firing (`status` already `succeeded`/`exhausted`) — detected by the latest row's `run_id` matching `job.RunID` *and* being terminal — returns that terminal row with a `terminal=true` signal rather than creating a duplicate/reset-budget row (which would also collide with `schedule_runs`' own `UNIQUE INDEX (run_id)`).
- `Enqueue` short-circuits this case with a new sentinel, `ErrRunTerminal`, alongside the existing `ErrBackoffActive` short-circuit — no real dispatch attempt, no bookkeeping mutation.
- `TestRetryingRunner_RetriesAcrossVaryingRunID_StillCountsAsSameFiring` (`internal/scheduler/retrying_runner_test.go`) is the direct regression proof: two `Enqueue` calls for the same `ScheduleID` with two genuinely *different* `RunID`s (simulating real `go-scheduler` tick behavior) correctly accumulate against one `schedule_runs` row and correctly exhaust at `max_retries=2`. `TestRetryingRunner_NewFiringAfterExhaustion_GetsFreshBudget` proves the complementary case: a new `RunID` arriving *after* a prior firing already concluded gets its own fresh row/budget, not blocked as terminal.

**Backoff curve: exponential with a cap.** `delay(attempt) = min(BaseDelay * 2^(attempt-1), MaxDelay)`, `attempt` = the 1-indexed real-dispatch-attempt number that just failed (the delay computed is the wait before the *next* attempt). Defaults: `BaseDelay = 30s`, `MaxDelay = 5m` — attempt 1 → 30s, attempt 2 → 60s, attempt 3 → 120s, attempt 4 → 240s, attempt 5+ → capped at 300s. Both are exported fields on `RetryingRunner` (`BaseDelay`/`MaxDelay`), overridable per-instance; zero value falls back to these defaults. Rationale, documented in-code: real schedule firings are cron-driven (minutes-to-hours apart), so a sub-minute-to-a-few-minutes window between retries of one firing is proportionate — long enough that `go-scheduler`'s 1-second hammering costs only a cheap `schedule_runs` lookup between real attempts (the mechanism's own stated goal), short enough that a transient failure still gets retried within roughly the same cadence most cron schedules already operate at. `Now func() time.Time` is also an overridable field (defaults to `time.Now`) for future fake-clock injection, though this task's own tests collapse the window a different way — see below.

**`on_fail='retry'`-at-exhaustion resolution: restated from `01`, not re-derived.** `01`'s Work Log (`TASKS/scheduling/01-schema-schedule-kind-collapse-and-retry-columns.md`) already resolved this: at exhaustion, `on_fail='retry'` (the column's own default) behaves identically to `on_fail='notify'` — log/emit, do not disable, return `nil` to stop `go-scheduler`'s own retry loop, let the schedule continue naturally at its next scheduled fire. Implemented as a shared `default:` fall-through case in `RetryingRunner.applyOnFail` covering `ScheduleOnFailNotify`, `ScheduleOnFailRetry`, and (defensively) any unrecognized value — never an unhandled/error branch. `TestRetryingRunner_OnFailNotify_DoesNotDisable` is table-driven across both `notify` and `retry` to prove neither disables.
