## Context

`docs/engineering/architecture/12-scheduling.md`'s "Full replace, not dual-run" section is the design, and its framing is explicit: `go-scheduler`'s `Engine` **replaces** the existing mechanism in full — it does not run alongside it. Running both would mean two independent pollers racing the same `agent_schedules` rows with two different correctness models (one CAS-based, one lookback-window-based); there's no scenario where that's safer than one engine with one claim mechanism. This is the single highest-blast-radius task in this batch — it deletes the one live, production-exercised scheduling path Nanite has today and replaces it with a new one in the same change. Treat it accordingly: real live-verification before considering it done, not just green tests.

Confirmed directly against this checkout (not assumed) before writing this task:
- The ticker: `cmd/nanite/main.go:1070-1094`, `lc.Go("durable-agent-wake-tick", ...)` — a 2-minute `time.Ticker` calling `container.DurableWake.RunDue(ctx, service.DurableAgentWakeRunRequest{Now: time.Now()})`.
- `wakeScheduleDue` (`internal/service/durable_wake.go:435`) is the per-schedule due-check `RunDue` calls; the 15-minute lookback window (`:311-314,451-461`) is the fragility this replacement retires as a side effect, not a separately-patched bug.

### The `run-due` endpoint's disposition — kept, due-check repointed onto `next_run`, not repointed onto `Engine.TickNow`

Confirmed real and still used: `internal/api/durable_agent_wake.go`'s `handleRunDurableAgentDueWake`/`handleListDurableAgentDueWake` back a **live UI feature**, not a dead/undocumented surface — `ui/src/components/settings/DurableAgentAdminPanel.tsx`'s "Run due wake pass" button (`runDurableAgentDueWake`) and "Due wake queue" card (`listDurableAgentDueWake`), both exercised by `ui/src/__tests__/phase-13-durable-agent-admin.test.tsx`. Per the CLAUDE.md system-prompt guidance about scope corrections ("a live UI attached to what sounded like a dead table, say — do the full job"), I treated this as real, load-bearing scope, not an incidental detail to wave through.

Three options were on the table (per the task's own step-4 framing: "real and still needed... repointed at the new Engine... or removed"). Chose **kept, due-check repointed onto `next_run`** (the same field the Engine's Store adapter now owns), explicitly rejecting a full repoint onto `Engine.TickNow(ctx)`:
- `Engine.TickNow` runs a real synchronous tick using the exact CAS claim path — the "purest" single-source-of-truth option — but its signature (`error`, no per-item detail) can't reproduce `RunDue`'s existing `DurableAgentWakeRunResult{Results []DurableAgentWakeResult}` shape (`InstanceID`/`ScheduleID`/`WakeReason`/`Skipped`/`SkipReason`/`LaunchResult`/`FailureReason` per item) or its `DryRun` mode — both real, tested, UI-relevant features I'd be silently dropping.
- Kept `RunDue`'s own per-item walk-and-`Wake` loop untouched, only swapping its due-check (via `ListDue`) from `wakeScheduleDue`'s recompute-with-lookback to `scheduleDueByNextRun` — a straight read of the same `next_run` column the Engine's `StoreAdapter`/`ClaimAgentScheduleRun` now maintains. This is not a second independent due-computation (the architecture doc's actual "full replace, not dual-run" concern) — it's the same single source of truth, just also read by a second, manual, low-frequency, operator-triggered consumer.
- Documented, in both `durable_wake.go`'s new `RunDue` doc comment and this Work Log, the one real accepted consequence: a manual `RunDue` fire doesn't go through the Engine's CAS claim, so it doesn't itself advance `next_run`. In practice this means a manually-fired **cron** schedule will very likely also get claimed by the Engine's own next 1-second tick moments later — not a new correctness gap (the pre-Engine codebase already had this exact "ticker and manual endpoint both call `Wake` directly, no coordination, `wakeSkipReason`'s per-instance already-active check is the only guard" shape for years), just a smaller and more visible race window now that the automatic side ticks every 1s instead of every 2min. **A one_shot schedule cannot double-fire this way**: `RunDue`'s existing success path sets `status=expired` directly, which drops the row out of the Engine's own `ListDueSchedules` `WHERE status='active'` filter immediately, independent of `next_run`.

### A real, load-bearing bug found and fixed while wiring the Engine: `managed_durable_configs.go`'s schedule re-sync was silently wiping `next_run` on every boot

Not something the task file's own Context anticipated — found by tracing the actual boot order before trusting `01`'s `backfillScheduleNextRun` to be sufficient on its own, then confirmed directly in the live dogfeed (see below). `Store.New()` runs `backfillScheduleNextRun` exactly once per process, immediately after migrations. `SyncManagedDurableAgentConfigs` (`container.go:1212`, called from `service.NewContainer`, itself called *after* `store.New()` returns in `main.go`) upserts the one real production schedule (Loom Curator's `lint-and-export`) via `syncManagedDurableAgentSchedule` → `InsertAgentSchedule` (`INSERT OR REPLACE`) on **every single boot**, per that function's own pre-existing doc comment. Before this task, `syncManagedDurableAgentSchedule`'s existing-row branch only preserved `FiredCount`/`LastFiredAt`/`CreatedAt`/`Status` from the prior row — `next_run` (and `max_retries`/`on_fail`/`job_type`/`job_payload`) fell through to `InsertAgentSchedule`'s zero-value defaulting on every re-sync, i.e. every restart after the first. Net effect: the one real production schedule's `next_run` would have been silently reset to `NULL` on every single boot after the migration-127 backfill's first pass — permanently invisible to `go-scheduler.Engine` (`NULL`/zero `NextRun` = "unscheduled, skipped", by the library's own documented convention) on every subsequent restart, forever. This would have made the entire migration a silent, restart-triggered regression for the one schedule Nanite actually runs in production today — exactly the kind of failure this task's elevated-risk framing exists to catch before merge, not after.

Fixed in `internal/service/managed_durable_configs.go`'s `syncManagedDurableAgentSchedule`: the existing-row branch now also preserves `next_run`/`max_retries`/`on_fail`/`job_type`/`job_payload` (with a defensive fresh-computation fallback if an existing row somehow still has no `next_run`), and the first-sync (brand-new row) branch computes a real `next_run` immediately via a new exported helper, `store.ComputeAgentScheduleNextRun(kind, spec, now)` (refactored out of `01`'s `backfillScheduleNextRun`, in `internal/store/agent_schedules.go`) — rather than leaving a freshly-synced schedule unscheduled until the *next* process restart's backfill pass. Verified directly in the live dogfeed below (`TestLoomCuratorScheduleSeededFromDurableConfigDrop` also updated to assert `sched.NextRun` is real and non-empty, not just infer it from `ListDue`'s result — see Tests section).

### Lifecycle wiring — where and how

- **Store adapter**: `02`'s `internal/scheduler.StoreAdapter{Store: s, Logger: slog.Default()}`.
- **Runner**: `04`'s `internal/scheduler.RetryingRunner{Inner: <03's RunnerAdapter>, Runs: s, Schedules: s, Disabler: <the same StoreAdapter instance>, Logger: slog.Default()}` — read `retrying_runner.go`'s real struct definition directly before wiring (per dispatch note), confirmed exact exported field names `Inner`/`Runs`/`Schedules`/`Disabler`/`Logger`/`Now`/`BaseDelay`/`MaxDelay`. **The bare `RunnerAdapter` is never handed to `gosched.New` directly** — only `RetryingRunner` is, satisfying the dispatch note's explicit warning.
- `03`'s `RunnerAdapter{Wake: container.DurableWake, Workflows: workflowLauncher, Commands: container.Tools}` — `Wake`/`Commands` come straight off the already-built `*service.Container`; `Workflows` is `main.go`'s own local `workflowLauncher` (`*service.WorkflowLauncher`, built at `main.go`'s existing pre-task line ~489), since it isn't (and per its own construction-order dependency on `container.DurableAgents`, can't be) built inside `service.NewContainer` itself. `ReflexLookup`/`ReflexExecutor` (the `reflex_dispatch` job type) deliberately left nil/unconfigured: `reflexes.Executor` isn't exposed anywhere on `*service.Container` today (only reachable internally via `chat.Config`, inside `NewContainer`), and nothing in this codebase produces a `job_type=reflex_dispatch` row yet (`07-wire-add-schedule-reflex.md`, not built). `RunnerAdapter` itself treats a nil `ReflexExecutor` as a clear per-firing "not configured" error, not a panic, so this is a documented, safe gap for `07`/`09` to close, not a silent one — logged here rather than expanding this task's own scope to also thread `reflexes.Executor` through `Container`.
- **Construction point**: `cmd/nanite/main.go`, immediately after `container.TaskManager` is built (~line 495 pre-edit / the block right after the existing `workflowLauncher`/`TaskManager` wiring) — the earliest point in `main.go`'s own boot sequence where `workflowLauncher` (needed for `RunnerAdapter.Workflows`) exists. Result assigned to a new, exported `service.Container.Engine *gosched.Engine` field (see below for why the field is typed against the external `go-scheduler` package directly, not `internal/scheduler`).
- **Start()**: inside `startBackgroundWorkers` (`main.go`), at the exact point the old ticker used to live — `if container.Engine != nil { container.Engine.Start() }`. Not wrapped in `lc.Go`: `Engine.Start()` spawns and owns its own internal goroutine/lifecycle (`go-scheduler`'s own `Start`/`Stop` contract), it isn't a `context.Done()`-driven loop the way every other daemon in that function is — wrapping it in `lc.Go` would just be a second, redundant lifecycle wrapper around a type that already manages its own.
- **Stop()**: `internal/service/container.go`'s `Container.Shutdown()`, called early — alongside (immediately before) the existing `stopSubagentReaper`/`runtimeReaper.Stop()` block, on the same "stop the thing that can dispatch new work before the subsystems it dispatches into start closing" principle that block's own comment already documents. `Engine.Stop()` blocks until go-scheduler's tick loop has actually exited (its own documented contract), so no in-flight tick can call into `DurableWake`/`WorkflowLauncher`/`ToolService` after they begin closing.

**Import-cycle finding, real, not hypothetical**: `internal/scheduler` (task `03`'s package) already imports `internal/service` (for `service.DurableAgentWakeRequest`/`WorkflowLaunchRequest`/`ToolResult`). A `Container.Engine` field typed `*internal/scheduler.Engine` would therefore create `service → scheduler → service`, an import cycle. Resolved by typing the field `*gosched.Engine` — the **external** `github.com/hollis-labs/go-scheduler` module directly (already a real, direct `go.mod` dependency since `03`), which has zero dependency on anything in this repo. `main.go` still goes through `internal/scheduler.StoreAdapter`/`RunnerAdapter`/`RetryingRunner` to build the two arguments `gosched.New` needs; only the `Engine` value itself is typed against the neutral external package on the `Container` struct.

**`Engine.Status()` reachability (task step 5)**: `container.Engine.Status()` is now a plain field access from anywhere holding a `*service.Container` — no unexported `main.go` local, no extra wiring needed for `09-operator-http-api.md` to reach it later. `Container.Engine` is nil on any `Container` built via `service.NewContainer` directly without `main.go`'s own post-hoc wiring (matching `AgentCardGenerator`/`TaskManager`'s existing pattern on this same struct) — expected and correct for the many tests that construct a bare `Container`.
