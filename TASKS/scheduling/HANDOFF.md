## What shipped, concretely

- **`go-scheduler`'s `Engine` fully replaces the old mechanism, in full — not a dual-run.** The 2-minute `time.Ticker` (`"durable-agent-wake-tick"`, formerly `cmd/nanite/main.go`) and `durable_wake.go`'s `wakeScheduleDue`/15-minute-lookback due-check are both deleted from the codebase, not deprecated-in-place — confirmed directly: `grep -rn wakeScheduleDue internal/` and `grep -rn "durable-agent-wake-tick" cmd/ internal/` both return only historical doc-comment references now (five and three hits respectively, all explaining what used to be there and what replaced it — zero live code). `go-scheduler.Engine` (constructed in `cmd/nanite/main.go`, wired to `service.Container.Engine *gosched.Engine`) is now the one live claim mechanism for `agent_schedules`, ticking every 1 second against a CAS (`UPDATE ... WHERE next_run=?`, `RowsAffected()==1`) that's safe by construction because `internal/store/store.go` opens the DB via `sqlitekit.OpenSingle` — a genuine single-writer-connection pool, not an assumption. `POST /api/durable-agent-wake/run-due` (the manual admin-panel "run due wake pass" button) was kept, not removed — its due-check was repointed onto the same `next_run` column the Engine reads (not a second independent due-computation), with one documented, accepted consequence: a manual fire doesn't itself advance `next_run`, so the Engine's own next tick will very likely also claim the same cron schedule moments later (a smaller, more visible version of a race that already existed pre-Engine, per task `05`'s Work Log).
- **`schedule_kind` collapsed from five values to two** (`cron`, `one_shot` only — `every_n_ticks`/`on_tick`/`on_event` dropped from the CHECK entirely, no live rows lost). **Four-job-type taxonomy** added: `durable_agent_wake` (the only type in live production use today, replacing `RunDue`'s old per-schedule dispatch), `agent_workflow_run`, `command_run` (dispatches through `service.ToolService.Execute`, the codebase's one existing generic "run a named tool with args" entry point — no separate sandboxed executor was built; `12-scheduling.md`'s own scope fence left that open), and `reflex_dispatch` (interim call directly into `reflexes.Executor.Apply`, bypassing `Resolve()`, since `Resolve()`'s shared decision engine wasn't built at the time this batch ran — documented as interim, not final, per the design doc's own open question). `agent_schedules` gained `max_retries`, `on_fail` (`retry`/`disable`/`notify`), `next_run`, `job_type`, `job_payload`. New `schedule_runs` table tracks per-firing attempt state.
- **Runner-owned retry/backoff/`on_fail` policy**, entirely outside `go-scheduler` itself (the library only offers "retry every 1s tick, forever, uncounted" — real policy has to live in the consuming app). `internal/scheduler.RetryingRunner` decorates the inner `RunnerAdapter`, tracks attempts in `schedule_runs`, and is the **only** thing ever handed to `gosched.New()` in production — `cmd/nanite/main.go` never hands the bare `RunnerAdapter` to the engine directly. Backoff curve: exponential with a cap, `delay(attempt) = min(30s * 2^(attempt-1), 5m)` — a real, documented implementation decision task `04` made (the design doc explicitly left the curve open; this is not a deferred item, it's a decided one, see "Deviations" below for why this is called out specifically). `on_fail='retry'` at exhaustion resolves identically to `'notify'` (log/emit, don't disable, let the schedule continue at its next natural fire) — also task `01`/`04`'s own resolved call, since the design doc didn't pin down what a still-`'retry'`-configured schedule should do once its own retry budget is exhausted.
- **Four producers**, all real and independently verified live against the actual `go-scheduler` engine (not just unit-tested in isolation):
  1. **Boot-time YAML sync** — `internal/service/managed_durable_configs.go`'s pre-existing `syncManagedDurableAgentSchedule`, which upserts the one real production schedule (Loom Curator's `lint-and-export`) on every boot. **Fixed as part of task `05`** — see Deviations below, this was silently broken by the schema change until caught.
  2. **`add_schedule` reflex wiring** — `reflexEngine.Executor.Schedule` assigned in `internal/service/container.go` (mirrors the pre-existing `Executor.Halt` wiring pattern), backed by `internal/service/reflex_schedule_hook.go`'s `NewReflexScheduleHook`/`buildReflexAgentSchedule`. This closes `CW-20260819-0006`'s loop — `add_schedule` was schema-legal and seeded but had no wired hook before this batch.
  3. **`schedule_create` self-tool** — `internal/selftools/self_tools_schedule_create.go`. Deliberately narrowed to `durable_agent_wake` only (no `job_type` input field at all) and enforces agent-self-scoping structurally (no `agent_id` input field either — the calling agent's id is resolved from trusted `ctx` values only, never from the tool's own `args` map, confirmed by the reviewer to have no path for a spoofed `agent_id` to matter).
  4. **`/api/schedules` operator HTTP API** — `internal/api/schedules.go`, full CRUD plus `GET /api/schedules/status` (exposes `Engine.Status()`). Standard operator auth (the existing uniform middleware chain every other `/api/*` route already rides) — no new gate, no new gap, a documented, non-final call per the design doc's own open question.
- **`schedule_fire` telemetry**, reusing the reflex `event_log` pattern exactly as `TASKS/harness-reactive-self-tools/05` did for self-tool reactions: `internal/scheduler/telemetry.go`'s `EmitScheduleFireTrace`, new `event_log` category `"schedule_fire"` (confirmed non-colliding with `"reflex"`/`"selftool_reaction"`), one row per real dispatch outcome (success/retry/exhausted) — backoff-window short-circuits and duplicate-job pass-throughs deliberately get no row (nothing in `schedule_runs` to correlate against either).

## What deviated from the original task files, and why

- **Migration renumbering, `126` → `127`.** Task `01`'s own file provisionally claimed `126_schedule_runs_and_retry_policy.sql` against the same `125_reflex_action_kind_provenance_allow.sql` baseline `TASKS/harness-reactive-self-tools/02-reactive-layer-schema.md` also claimed. `harness-reactive-self-tools` landed first (`126_selftool_reactions.sql`); `01` was dispatched with, and landed, `127_schedule_runs_and_retry_policy.sql` instead — exactly per its own task file's stated collision-handling instruction, not an ad hoc call. Confirmed on disk: `internal/store/migrations/` currently ends `125_reflex_action_kind_provenance_allow.sql`, `126_selftool_reactions.sql`, `127_schedule_runs_and_retry_policy.sql`.
- **`Job.RunID`-instability finding (task `04`) — a real correction to how this batch's own earlier task files (`01`, `03`) described the mechanism, not a design change.** `01`'s schema doc comment and `03`'s Runner design both assumed `schedule_runs` rows correlate to a firing by `go-scheduler.Job.RunID`. Task `04`'s worker read `libs/go-scheduler/engine.go`'s real `tick()` directly and found `Job.RunID = fmt.Sprintf("sched-%s-%d", sch.ID, now.Unix())` — computed fresh from the **current tick's own wall-clock time**, not stable across retries of the same logical firing (ticks are ~1s apart, so a retried firing gets a brand-new `RunID` on every attempt). Taking "keyed by `run_id`" literally would have silently defeated `max_retries` entirely in production (every retry creating a fresh `attempt_count=0` row) — the exact bug this whole task exists to prevent. Corrected mechanism, implemented and independently re-verified twice (by the Orchestrator, then by the fresh Reviewer, both reading `engine.go` directly): correlate by `ScheduleID` + "most recent non-terminal (`pending`/`failed`) row = the current firing in progress," never by `RunID` alone. Confirmed live during task `05`'s own dogfeed: one real schedule fired three separate times pre-restart, each producing a genuinely different `run_id` on the same `schedule_id` row lineage — direct, not simulated, confirmation of the finding.
- **A real, load-bearing bug found and fixed in task `05`: `managed_durable_configs.go` was silently wiping `next_run`/`max_retries`/`on_fail`/`job_type`/`job_payload` on every single boot.** Not anticipated by any task file's own Context — found by the `05` worker tracing the real boot order before trusting `01`'s once-per-process backfill to be sufficient on its own. `SyncManagedDurableAgentConfigs` re-upserts the one real production schedule on every boot (a pre-existing, intentional behavior); before this fix, its existing-row branch only preserved `FiredCount`/`LastFiredAt`/`CreatedAt`/`Status` from the prior row, so the new retry-policy columns fell through to `InsertAgentSchedule`'s zero-value defaults on every restart after the first. Net effect, had this shipped unfixed: the one schedule Nanite actually runs in production today would have had its `next_run` silently reset to `NULL` (`go-scheduler`'s own "unscheduled, skipped" convention) on every restart, forever — a permanent, restart-triggered regression of the entire migration for the only real workload it serves. Fixed in the same task, before merge: the existing-row branch now preserves all five new columns, and the first-sync branch computes a real `next_run` immediately via a new exported `store.ComputeAgentScheduleNextRun` helper rather than leaving a freshly-synced schedule unscheduled until the next restart's backfill pass.
- **A real bug found in Phase 2 review and fixed via the standard fix-then-re-review discipline: task `07`'s missing cron-syntax pre-check.** `buildReflexAgentSchedule` (the `add_schedule` reflex hook) never validated cron syntax for a non-empty `schedule_spec`, relying on `ComputeAgentScheduleNextRun`'s documented "fall back to due-now" behavior. The fresh Phase 2 Reviewer proved this was worse than a one-off "off-schedule immediate fire": `go-scheduler`'s own `tick()` computes `NextRun` **before** the CAS claim and silently skips a row on a parse error, forever — the row never reaches `ClaimAndUpdateScheduleRun` at all, with only a coarse `WorkerErrors` counter as any operator-visible signal. Reproduced against the real production pipeline (a real `StoreAdapter` + a real `gosched.Engine`, not a mock), not just asserted from reading code. Fixed with a `cron.ParseStandard` pre-check mirroring `08`/`09`'s already-existing pattern (both of those producers validated this correctly from the start — `07` was the one that skipped the front-door check), plus a regression test covering exactly this input shape. Independently re-reviewed by a **second**, dedicated fresh reviewer (no shared context with the fix worker or the original reviewer) — confirmed PASS: the pre-check genuinely runs before `next_run` is ever computed and before any row is built, no regression for valid specs, diff scoped to exactly the fix.

## Still-outstanding, non-blocking follow-up candidates (all logged in `TASKS/ESCALATIONS.md`, 2026-08-20 entries)

None of these block anything currently built or planned; recommend bundling into one small future cleanup task rather than dispatching four separate ones:

1. **`Container.Engine` → `Container.ScheduleEngine` naming rename.** `service.Container.Engine *gosched.Engine` sits next to `Permissions *permission.Engine`/`ReminderEngine *reminders.Engine` — a bare `Engine` is ambiguous against that precedent; `ScheduleEngine` would match. Two use sites to update if this is picked up (`cmd/nanite/main.go`'s construction, `internal/api/schedules.go`'s status handler).
2. **`ComputeAgentScheduleNextRun`'s duplicated cron-math vs. `gosched.NextRun`.** `internal/store/agent_schedules.go`'s `ComputeAgentScheduleNextRun` hand-rolls `cron.ParseStandard(spec).Next(now)` rather than calling `go-scheduler`'s own exported `NextRun` (`libs/go-scheduler/scheduler.go:85-92`), which does the identical thing. Pre-dates this batch (inherited from task `01`'s original `backfillScheduleNextRun`), but task `05` extended the duplication to a second call site (`managed_durable_configs.go`'s new-row branch) instead of consolidating — notably cutting against `02`'s own explicitly-documented "no cron-math duplication" principle, one file over in the same batch. Not a correctness bug today (identical logic, no behavioral divergence), purely a DRY debt.
3. **`managed_durable_configs.go` has the same missing-cron-validation gap `07` had, still unfixed.** The boot-time YAML-sync producer (`:281,295`) calls `ComputeAgentScheduleNextRun` directly with no `cron.ParseStandard` pre-check — the identical bug class task `07`'s fix just closed for the reflex-hook producer. A malformed cron expression in a `.nanite/durable-agents/*.yaml` file would silently fall back to "due now" and then be skipped forever by the engine, same failure mode. Lower risk than `07`'s case (operator/YAML-authored, human-reviewed before landing on disk, versus reflex/LLM-authored with no review step) — explicitly why this wasn't folded into `07`'s own fix scope.
4. **Task `08`'s minor `MaxRetries=3` hardcoded-literal nit.** `internal/selftools/self_tools_schedule_create.go`'s `scheduleCreateMaxRetries = 3` duplicates `InsertAgentSchedule`'s own column default (also 3) as a second hardcoded literal — task `07`'s hook avoids this by leaving `MaxRetries` unset and letting the store-level default apply. If the store default ever changes, this tool's rows would silently stop tracking it. Low severity.

**One more, separate from the "bundle" list above, worth independent awareness rather than bundling in:** `RetryingRunner`'s three `RecordScheduleRunAttempt` call sites (`internal/scheduler/retrying_runner.go`) only `slog.Error` on a `schedule_runs` bookkeeping-write failure and otherwise proceed as if the write succeeded — a narrow, currently-unobserved edge case where a write failure right at the exhaustion boundary could let a later tick grant more than `max_retries` real attempts. Flagged by the Phase 1 reviewer as a heads-up for whoever next touches this area (it was already visible-enough that `06`'s telemetry work folded a `bookkeeping_error` field into the trace-row metadata as partial mitigation, without changing the underlying log-and-continue control flow). Not a bundle candidate the way the four above are — it's an observability/robustness decision, not a naming/DRY cleanup.

## What this batch deliberately did NOT do

Per `docs/engineering/architecture/12-scheduling.md`'s own "What this session did not decide" list — do not assume any of the below is settled just because the batch is complete:

- **The retry backoff curve's specific numeric values are, in fact, now decided** — this is worth flagging explicitly because the design doc's own list names the curve as undecided, but task `04` made a real, documented implementation call (exponential, `30s` base / `5m` cap) rather than leaving it open. If you're reading the design doc and expecting an open question here, it's closed — check `04`'s Work Log or `internal/scheduler/retrying_runner.go`'s exported `BaseDelay`/`MaxDelay` fields for the actual values, not the design doc.
- **The `/api/schedules` auth/permission model's final shape is not locked.** Task `09` made a concrete, documented call (standard operator auth, riding the existing uniform middleware chain, no provenance-tier-style gating) — explicitly not a final security decision, matching the same "acceptable to leave open, let real usage inform it" precedent `reflex-taxonomy/05` used for the analogous reflex question.
- **Whether `reflex_dispatch` job firings should call into the shared reflex `Resolve()` decision engine (`10-reflex-action-taxonomy.md`) remains open.** Task `03` built an interim, documented call directly into `reflexes.Executor.Apply`, bypassing `Resolve()` — because `Resolve()` didn't exist as a concrete implementation at the time this batch ran. If `Resolve()` has since landed, whoever next touches `reflex_dispatch` should treat this as a real open decision, not settled.
- **`command_run`'s sandboxing/permission scoping beyond what normal self-tool execution already provides is not built.** It dispatches through `ToolService.Execute`, the same permission/registry checks any other tool call gets — nothing extra.
- **`CW-20260819-0005`'s two specific audit-agent definitions remain genuinely open.** This batch unblocks them (via `command_run` or `durable_agent_wake` as the trigger mechanism, resolving the "deferred pending 0004's trigger mechanism" blocker the original Torque task named) but does not scope or build either agent.
