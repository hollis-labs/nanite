# TeamRun launch surface — launch by name, with invocation-time overrides

**Phase:** 4 — Definition & launch API surface (`TASKS/teams`)
**Status:** reviewed
**Depends on:** `08`, `10`
**Touches:** `internal/api/teams.go` or a new `internal/api/team_runs.go` — exact file is this task's own research call, see below.

## Context

`docs/engineering/architecture/15-teams.md`'s "Runtime overrides follow the existing cascade" section states the requirement directly: *"A caller (Loom, or any Nanite consumer) should be able to launch against a saved Team by name with invocation-time overrides (`engineers.max: 3`) without creating a new persistent Team definition per call, matching how `WorkflowLaunchRequest.Params` already works today."*

**This planning session's research did not conclusively establish how the existing `WorkflowLauncher`/`WorkflowLaunchRequest` mechanism is actually invoked end-to-end today** (a REST route, a self-tool, an MCP-only surface for external consumers like Loom, or some combination) — confirmed real and reusable is the Go-level `WorkflowLaunchRequest` struct and `WorkflowLauncher` itself (`internal/service/workflow_launch.go`), but not the calling convention above it. **Before building anything, grep for the real existing entry point(s)** (`WorkflowLaunchRequest{` construction sites, any `/api/workflows`-shaped route, any self-tool that constructs one) and match whatever precedent already exists — do not invent a new pattern if one already exists for launching a plain (non-Team) workflow. If genuinely nothing external-facing exists yet for launching a workflow directly, treat that as a real finding worth flagging rather than silently working around it, and build the most consistent-with-this-codebase surface (a REST route, following `10`'s CRUD-endpoint conventions, is the safe default absent contrary evidence).

**Required prerequisite, found by task `08`'s own fresh reviewer (2026-08-20), not optional polish — read before building anything:** task `08`'s `internal/agentworkflow/registry.go`'s `Registry.Register` has no corresponding `Unregister`/eviction. `LaunchTeamRun` registers a permanently-unique-named compiled `WorkflowDefinition` (`team-run:<team-name>:<ulid>`) on every call and never removes it. This is not just an in-memory leak: `cmd/nanite/main.go` wires the *same* shared `*Registry` instance into `AgentCardGenerator`, whose `Generate()` (`internal/service/a2a_agent_card.go`) iterates `registry.Names()` and emits one `a2a.Skill` per entry into the **public** `/.well-known/agent-card.json` A2A discovery response. The moment this task wires `LaunchTeamRun` into real, callable traffic, **every single TeamRun launch — not eventually, from the first one — permanently pollutes an externally-visible discovery API with a stale one-off skill entry**, in addition to the unbounded memory growth. This task must not ship without addressing it: either (a) an eviction/TTL mechanism on `Registry` so a completed/stale TeamRun's compiled definition is removed after some bound, or (b) excluding per-launch-compiled TeamRun definitions from `AgentCardGenerator`'s skill enumeration (e.g. a naming-convention or explicit-flag filter). Pick one, implement it, document your reasoning — this is now a required "Done means" item for this task, not a follow-up to defer further.

## Work log

**Step 1 — existing-entry-point research (required finding, documented as instructed).** Grepped every `WorkflowLaunchRequest{` construction site and every `/api/workflows`-shaped route before building anything. Found three real call sites, not one, and none is a bare general-purpose REST route for the `agentworkflow`/`WorkflowLaunchRequest` mechanism:

1. `internal/api/workflows.go`'s `POST /api/workflows/runs` is a **red herring** — despite the matching route prefix, it drives an entirely different execution engine (`internal/workflow`'s YAML-pipeline `Executor`/`RunStore`/`Broadcaster`), never touching `agentworkflow.WorkflowDefinition`/`WorkflowLaunchRequest`/`WorkflowLauncher` at all. Confirmed by reading the handler body, not assumed from the route name.
2. `internal/selftools/self_tools_workflow_run.go`'s `workflow_run` self-tool is the real, working "launch a named `agentworkflow` definition with params" entry point — but it's reachable only from inside an already-running agent's own MCP tool-calling loop (a live chat turn, or a CLI-launched subprocess proxying back through `POST /api/tools/call`, which `internal/api/tools_call.go`'s own doc comment confirms is loopback-only). Not something an external HTTP consumer like Loom can hit directly without an agent/session already in the loop.
3. `internal/service/a2a_task_manager.go`'s `submitWorkflowTask` (A2A JSON-RPC task submission) is genuinely external-facing (GLOSSARY.md: A2A is "for callers with zero Nanite-specific knowledge") but only supports "launch an already-registered named workflow skill with one free-text message mapped to `{"prompt": ...}`" — no `TeamRunOverrides`-shaped body (per-slot counts, arbitrary `Params`, `ProjectID`/`ParentSessionID`/`TimeoutSeconds`/`AgentProfileID`), and a saved Team isn't itself a registered-by-name workflow skill today (only its per-launch compiled definition is, under a fresh-ulid name nobody could address ahead of time).

Net finding: **nothing genuinely external-facing today is both reachable without an agent/session/A2A-task already in flight AND shaped to accept `TeamRunOverrides`'s richer body.** Per the task file's own explicit fallback instruction, built `POST /api/teams/{id}/launch` in a new `internal/api/team_runs.go`, mirroring task 10's `internal/api/teams.go` CRUD conventions verbatim (same `decode`/`errorResp`/`jsonResp` helpers, same `errors.Is`-dispatched 404 handling, same uniform-middleware-chain auth posture, no narrower operator-only tier). Full reasoning is preserved as a package-level doc comment in `internal/api/team_runs.go` itself, not just here.

**Step 2 — registry-growth/agent-card-pollution prerequisite (required, not deferred).** Discovered while implementing that `internal/service/team_run_launcher.go`'s `TeamRunLauncher` (task 08) was never actually wired into `cmd/nanite/main.go`/`service.Container` at all — a real gap this task had to close regardless, since "wire `LaunchTeamRun` into real, callable traffic" is this task's own job. Added `Container.TeamRunLauncher` (set post-hoc from `main.go`, same pattern as `AgentCardGenerator`/`TaskManager`) and wired it from the same `workflowDefinitionsRegistry`/`workflowLauncher` pair those two already use — confirming directly against `main.go` that this is indeed the *same* shared `*Registry` instance `AgentCardGenerator` reads, exactly as the task file described.

Resolved the growth/pollution requirement with **two complementary pieces**, not just one, because the two "pick one" options in the task file address different halves of the problem:

- **Primary fix — (b), naming-convention exclusion, unconditional:** added `agentworkflow.TeamRunDefinitionNamePrefix` (`"team-run:"`, the exact literal prefix `LaunchTeamRun` already stamped) and `agentworkflow.IsTeamRunDefinitionName`, then filtered `AgentCardGenerator.Generate()`'s skill enumeration to skip any registry name matching it. `team_run_launcher.go` now builds its `wfName` from the shared constant instead of a duplicated literal, so producer and filter can't drift. This is the part that actually satisfies the task's literal complaint ("every TeamRun launch... permanently pollutes an externally-visible discovery API") — it holds **regardless of whether the underlying registry entry is still registered**, which matters because:
- **Secondary, partial fix — (a), terminal-status eviction:** added `agentworkflow.Registry.Unregister(name)` (nil-safe, idempotent) and call it from `LaunchTeamRun` immediately after a successful `Launch()` call when `launchResult.Status` is one of the real terminal states (`completed`/`failed`/`cancelled`). **Honest limitation, documented in code comments and here:** every Team's compiled phase sequence can only contain `flex`/`gate` step kinds (`CompileTeam` rejects anything else), and both kinds always return a *waiting* status on first entry — so for a well-formed Team (every illustrative example in `15-teams.md` opens on a flex step), this eviction path essentially never fires on the common path; it only helps the edge case where the engine's first `Run()` call reports an in-band `Failed`/`Cancelled` status synchronously (e.g. a runtime-only flex/gate setup failure) rather than needing external resolution. I chose to implement it anyway, on top of (b), because it's a real, low-risk, no-downside improvement for that edge case, and confirmed via `resumeWorkflowRun` (`a2a_task_manager.go`) that a still-waiting run's compiled definition genuinely must stay registered by name for a later `Resume()` call to find it — evicting eagerly for a waiting run would have silently broken Resume, so I did not attempt a broader TTL/sweep mechanism (no background goroutine, no `workflow_runs`-status sweep) given that added complexity/risk for a case the naming filter (b) already fully covers from the public-API-pollution angle. The one thing this pairing does **not** fully solve is unbounded in-process memory growth for long-lived/never-resumed waiting TeamRuns — flagged here explicitly as a known, narrower residual, not silently left undocumented.
