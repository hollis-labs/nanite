**Runtime engine (`internal/service/`, `internal/agentworkflow/`):**
- `workflow_engine_flex.go` — the flex-step executor (`parseFlexStepConfig`, `activeMembersForSlots`, `recheckFlexStep`, `evaluateFlexExit`, `standDownFlexMembers`). Wired into `BuiltinWorkflowEngine` via a post-construction `WithFlexSupport(store, stateCollector)` call (see `cmd/nanite/main.go`).
- `team_compiler.go` — `CompileTeam(name, phases, resolvedMembers) (agentworkflow.WorkflowDefinition, error)`. Pure function, no I/O. `Engine` is hard-coded to `EngineBuiltin` with no override path. `resolvedMembers` is accepted but deliberately unconsumed — flex `active_slots` in the compiled `Config` always holds slot *names*, re-resolved live at flex-step entry, never baked-in `(agent_id, session_id)` tuples.
- `team_run_launcher.go` — `TeamRunLauncher`, `LaunchTeamRun(ctx, teamID, TeamRunOverrides)`, `ResolveLazySlot(ctx, workflowRunID, teamID, slotName, overrides)`. Wired into `Container.TeamRunLauncher` / `cmd/nanite/main.go` by task `11` (it shipped unwired from task `08` itself).
- `team_routing.go` — `TeamRoutingService`, `SendToSlot` (explicit `@slot` addressing, broadcast-to-all-active default), `InstallTeamRunRouting(ctx, runID, teamID)` (semantic + coordinator-fallback routing, installs run-scoped `agent_reflexes` rows). **Audit remediation AD-08 closed the original wiring gap on 2026-08-23:** `cmd/nanite/main.go` constructs `Container.TeamRouting` beside `TeamRunLauncher`, and `handleLaunchTeam` calls `InstallTeamRunRouting` after `LaunchTeamRun` returns the real run id and member rows. Routing installation is required for the HTTP operation: an install failure returns a structured HTTP 500 containing the already-persisted `workflow_run_id`/status and explicit routing error; any returned partial reflex ids are cleaned up best-effort. The launch itself is not transactionally rolled back and the response says so, preventing a blind retry from silently duplicating a live run.
- `internal/agentworkflow/registry.go` — `Registry.Register`/`Unregister` (both added this batch; the registry had no mutation API before task `08`), `TeamRunDefinitionNamePrefix = "team-run:"`, `IsTeamRunDefinitionName`.

**API surface (`internal/api/`):**
- `teams.go` — `POST/GET /api/teams`, `GET/PATCH/DELETE /api/teams/{id}`. Standard uniform middleware chain, no new auth tier.
- `team_runs.go` — `POST /api/teams/{id}/launch`, accepting a `TeamRunOverrides`-shaped body, calling `LaunchTeamRun` and then the required `InstallTeamRunRouting`. A successful response includes `workflow_run_id`, `status`, and resolved `team_run_members` rows; a routing-install failure returns HTTP 500 with the persistent run id/status and routing error rather than claiming rollback.

## Five real load-bearing corrections found during planning (and why they mattered)

These are documented in `TASKS/INDEX.md`'s Teams section and each owning task's Context — restated here because a fresh session extending this code needs to know the design doc's own prose is not always literally accurate:

1. **`agent_parent_dispatch_allowlist`** (migration 060) is a JSON role-slug *column* on `agent_profiles`, not a table, and is advisory-only (rendered into an LLM-facing tool description, never enforced). The design doc proposed generalizing it for Team authority — task `04` deliberately did **not** copy this shape; `AuthorizedForVerb` is a real hard `if`-gate at the caller's own call site, modeled on `dispatch.TrustTier`/`ErrUntrustedRole` instead.
2. **`agent_profiles.durable`** is an unrelated eject-survival flag (migration 073, "exempt this profile from the reingest/eject predicate"), not a signal for whether a Team Slot should wake an existing durable identity. Task `08` treats `resolution: durable|fresh` as new Team-Slot-level launch config and never reads `agent_profiles.durable` anywhere in the resolution path.
3. **The real messaging self-tool is `message_send`, not `send_message`** — `send_message` is the name of the reflex `action_kind`, a related but distinct vocabulary item. Task `09` got this right; if you add a second explicit-addressing entry point, check this again.
4. **`workflow_run_steps.kind` has a hardcoded DB CHECK** (migration 051) that blocks inserting a `flex`-kind step without a real table-rebuild migration — task `03` exists specifically because of this, and task `06` found a second, unanticipated instance of the same problem (`waiting_on_flex` needed its own CHECK widening too, migration 133).
5. **"Slot" already has an established, unrelated, load-bearing meaning** in this codebase — `internal/context/slot.go`'s `SlotOrder`, one of six invariants in `internal/context/INVARIANTS.md` ("universal slot at position 0"). Every new identifier in this batch spells out "Team Slot," never a bare `Slot`. `docs/engineering/GLOSSARY.md` now has Team / Team Slot / TeamRun entries with this disambiguation spelled out explicitly — read it before adding a sixth loose use of "slot" anywhere near this code.

## The two required stress-test answers

The design doc's own "Validating this design" section named these "likely the messiest runtime edges of the whole design" and required concrete, tested answers, not a passing mention.

**Phase-closure race** (a flex step's exit trigger fires while other active members are still mid-turn) — owned by task `06`. **Chosen: fire immediately, with explicit stand-down.** The moment an authorized member's exit trigger fires, every currently-active member for that step's `active_slots` (including the one that fired it) is transitioned to `team_run_members.status = 'stopped'`. Anyone still mid-turn is not waited for and not specially notified — whatever their turn eventually produces is not this flex step's concern once it's closed. The worker chose this over "let others finish" or "closing flag + timeout" because those needed new schema/subsystem machinery the Guardrail diagram explicitly warns against inventing; "fire immediately" was directly implementable against what already existed (`team_run_members.status = 'stopped'` was seeded by task `02` with exactly this meaning, unused until task `06`). Covered by `TestBuiltinWorkflowEngine_FlexStepPhaseClosureRace_StandsDownStillActiveMember` in `internal/service/`.

**Routing-target resolution failure** (a message routes to an unavailable/failed slot member) — owned by task `09`. **Chosen: fail loudly, `ErrTeamRoutingTargetUnavailable`, no silent fallback.** If the target slot has members but none are `status='active'`, the send fails immediately with a typed error. If the target slot has zero members (a genuinely dormant lazy slot), exactly one lazy-resolution attempt is made via task `08`'s `ResolveLazySlot`; if that itself fails, same error, wrapping the cause. No automatic reroute to the coordinator fallback. Covered by `TestSendToSlot_TargetUnavailable_NoActiveMember_FailsLoudly` and `TestSendToSlot_TargetUnavailable_LazyResolutionFails`.

## Known limitations and deliberately-deferred scope

- **Unbounded registry memory growth for long-lived, never-resumed waiting TeamRuns.** Task `11`'s fix for the registry-growth/agent-card-pollution problem (below) has two parts: an unconditional naming-convention exclusion filter (`IsTeamRunDefinitionName`) that keeps every TeamRun's compiled definition out of the public `/.well-known/agent-card.json` regardless of registry state — this is the real, load-bearing fix — plus a narrower terminal-status eviction (`Registry.Unregister`, called when `Launch()` synchronously returns `completed`/`failed`/`cancelled`). Because every well-formed Team's compiled phase sequence opens on a flex or gate step, and both always return a *waiting* status on first entry, the eviction path essentially never fires on the common path in practice. **A TeamRun that reaches `waiting_on_flex`/`waiting_on_gate` and is never resumed keeps its compiled `WorkflowDefinition` in the shared `*agentworkflow.Registry` forever** — task `11`'s own Work Log documents this explicitly as a residual, not a silently-accepted gap. No TTL/sweep mechanism was built (deliberately — it would need to reason about `resumeWorkflowRun`'s requirement that a still-waiting run's definition stay registered, and the task judged that added complexity/risk wasn't justified once the public-API-pollution angle was fully closed by the naming filter). If you're building anything that launches many TeamRuns that might never resolve (a stress-test harness, a demo mode, etc.), know this before you're surprised by memory growth.
- **`authority_json`'s JSON-shape-only validation gap — no typed Go shape exists for this column at all.** Task `01` created `teams.authority_json` as a storage placeholder, explicitly leaving its real shape to task `04`. Task `04` then built a **separate normalized table** (`team_authority_grants`) instead of ever defining a typed Go struct for the JSON column. By the time task `10` built the CRUD API, `authority_json` had zero typed-decode callers anywhere in the codebase (confirmed via repo-wide grep) — so `internal/api/teams.go`'s write-time validation for this one field is JSON-shape-only (must decode as a well-formed JSON array), not the full typed validation every other sub-structure column (`slots_json`, `phases_json`, `routing_json`) gets. **Practical consequence: a caller can `POST`/`PATCH` a syntactically-valid-JSON-array `authority_json` value with any per-element shape at all — nothing rejects a malformed grant object inside it at write time.** The real, enforced mechanism is `team_authority_grants` (task `04`'s table, populated separately, not through this column) — `authority_json` on the `teams` row itself appears to be a genuinely dead/unused column at this point, not actively read by the compiler or launcher. Whoever picks this up next should decide: give it a real typed shape and validation, or retire the column since `team_authority_grants` already does the real job.
- **Two minor non-blocking findings from task 11's re-review**, neither touching the registry fix itself: (1) `IsTeamRunDefinitionName`'s `"team-run:"` prefix match has no enforcement anywhere preventing an operator-authored YAML workflow from accidentally starting with the same prefix — if that ever happened, that legitimate workflow would be silently excluded from the public agent card (a false exclusion, the mirror-image of the leak this task fixed). Currently inert, no such workflow exists today. (2) `internal/api/team_runs.go`'s doc comment states an empty request body is valid, but a genuinely zero-byte POST actually 400s (`io.EOF` before any field is read) — only a literal `{}` payload succeeds. Matches `teams.go`'s own pre-existing decode-error-to-400 convention, just a doc-comment overstatement.
- **`ResolveLazySlot`'s idempotency has a real check-then-act race under true concurrency** — flagged by task `08`'s own reviewer, and genuinely fixed at task `09`'s one real call site (`resolveActiveMembers` in `team_routing.go` uses a real double-checked-locking pattern, a `sync.Map`-backed per-`(workflow_run_id, slot_name)` mutex, tested under `-race` with 8 concurrent goroutines). **If you add a second concurrent-capable caller of `ResolveLazySlot` anywhere else, it does not get this protection for free** — `ResolveLazySlot` itself is still a plain read-then-write with no transaction or lock; the fix lives at task `09`'s call site, not inside `ResolveLazySlot`.

## Anything a future session should NOT assume is done

- **No self-tool or UI surface calls this API yet.** `POST /api/teams/{id}/launch` and the `teams` CRUD routes are real and tested via direct HTTP calls in this batch's own test suites, but nothing in the actual chat/agent runtime (no self-tool, no UI component, no reflex) invokes them. An agent cannot launch a Team on its own today.
- **`TeamRunOverrides` and routing defaults are "provisional v1," not locked.** The multi-member `@slot` addressing default (broadcast to every active member) is explicitly flagged in `team_routing.go`'s own package doc comment as provisional, per the design doc's own "no syntax or default is chosen here, deliberately" framing — real usage should inform the eventual default, not this batch's judgment call.
- **Mid-run elastic slot growth is not built.** `min`/`max` slots resolve `min` members (or an invocation-time override up to `max`) eagerly at launch only. There is a concrete, current blocker for the obvious alternative (`task_execute` is hard-capped at recursion depth 0, and a Team orchestrator slot triggering growth is itself typically a non-root dispatched session) — not just caution.
- **The final authority verb set is not locked.** Only `may_spawn`/`may_message`/`may_not_review` exist; the design doc's own suggested `may_delegate`/`may_approve`/`may_signal` are not built. The `verb` CHECK on `team_authority_grants` is a one-line widening away from adding one, by design.
- **`may_not_review` has no real call site anywhere in this batch.** Task `09` confirmed `AuthorizedForVerb`'s `to_slot='self'` sentinel is handled correctly at its one real call site (`may_message`), but nothing calls `AuthorizedForVerb` for `may_not_review` — there's no "review" operation in the runtime today to gate. Task `07` confirmed `approver_slot` (a gate step's compiled Config key, meant to eventually carry this) is not read or enforced by anything in the running engine either — it's forward-compatible metadata only.
- **The Team/Workflow definition split (one Team, multiple phase-sequence shapes) is not built.** Tasks `01`/`07` kept the phase sequence as its own addressable sub-structure (`Team.Phases()`/`SetPhases()`, a separate input to `CompileTeam`) specifically so this split is a future call-site change, not a rewrite — but the split itself doesn't exist.
- **A run-scoped Team Slot resolved lazily *after* `InstallTeamRunRouting` runs does not retroactively get its own asking-side semantic-routing rows.** Task `09`'s Work Log documents this as a known, flagged limitation of the per-`agent_id` reflex-row installation approach, not silently discovered later.

### AD-08 source correction: semantic routing vs. explicit Team-Slot messaging

The audit-remediation task's original Context conflated these two paths. The
run-scoped `dispatch_to_agent` reflexes installed by
`InstallTeamRunRouting` execute through `chat_reflex_dispatch`/`task_execute`;
they do **not** call `SendToSlot`. `SendToSlot` and `ResolveLazySlot` remain the
separate explicit `@Team Slot` messaging path, with no self-tool or UI caller
yet. AD-08 deliberately wired the architect-decided semantic/coordinator
routing installation from the HTTP launch handler; it did not invent a new
explicit-addressing surface. The lazy-after-install limitation above remains
unchanged and accepted.
