# Nanite Alignment Review — 2026-08-17

**Author's note on method:** This is an independent second opinion, not a continuation of the audit. I read all 23 audit documents (`docs/system-audit/2026-08-17/`) and `docs/release-vision.md` in full before forming any conclusion, then went back to the actual Go source for every claim this report's recommendations depend on — not just the audit's characterization of it. Specific things I verified directly against code rather than taking on the audit's word: whether an MCP control-plane surface already exists (it doesn't — checked `internal/mcp/self_tools*.go` and `internal/mcpserver/`), whether the pre-loop steering layers (agent broker, strategy planner, route dispatch) already skip for non-interactive callers (they don't — grepped for `CallerType` in all four call sites, zero hits), the actual code size of the steering/messaging subsystems, and the A2A TaskManager's routing design. Where a claim below rests on the audit alone, I say so.

---

## 0. Bottom line

**Ship the platform decision, but ship it smaller than the vision doc implies, and don't let "platform" become code for "build tenancy infrastructure."** The vision doc's core calls — CLI-wrapping primary, API-harness narrowed to durable agents, MCP as the external boundary — are all correct and each is *more* strongly supported by the evidence than the vision doc itself argues, once you actually check the code. But the vision doc under-estimates how much real subtraction "narrow the harness" requires (it isn't already partially true — I checked), and it leaves two decisions un-made that materially change scope: how much tenancy machinery "platform" actually requires before Loom is well-served (answer: almost none), and whether MCP genuinely needs a new mechanism for wake-and-track (answer: no — Nanite already built the exact pattern needed, for A2A, and it's sitting there unused with zero external callers).

The single highest-leverage move available right now is **not** wiring up MCP tools or cutting the broker layers — it's **finishing the reliability work already in flight on the durable-agent path**, because that path is the vision's stated core pillar and it is currently failing in ways serious enough to make "MCP is the front door" a bad idea until fixed. Six of seven durable-agent YAML files still pin a retired model ID as of the last DB snapshot in the audit (2026-08-17 17:59:54, *after* the fixing session), and the Recovery Broker has been structurally non-functional for the HTTP-provider chat path's entire life (46 of 50 permanent-outcome breadcrumbs). Opening an MCP front door onto a durable-agent runtime that still 404s on its own model config, on a session type whose crash-recovery path was never built for it, is building a platform on top of a foundation the audit itself shows is still settling.

Ranked, in the order I'd actually spend the next several weeks:

1. **Fix the durable-agent reliability floor** (model pinning, recovery broker's CLI-only assumption, subagent reply-delivery collision) — this is prerequisite to everything else, not parallel work.
2. **Build the MCP control-plane surface as a thin layer over the A2A TaskManager's existing routing logic**, not from scratch — reuse `SubmitTask`'s classify-and-route pattern, drop the JSON-RPC wire format, expose it as MCP tools (`wake_agent`, `get_agent_status`, `send_message`) with poll-based status (plain request/response — no subscription mechanism needed, see §Named risks/POV answers below).
3. **Retire A2A's wire protocol; keep its routing logic** as the seam behind the new MCP tools. Not "keep A2A" and not "delete everything A2A ever built" — combine.
4. **Cut the genuinely dead surface** (`gomsg`, `session_handoffs`, `agent_boot_plans`, `agent_cycles`, `ReviewMidExecution`, the known-tools reaper, `grounding_*` — all zero-caller, zero-row, or explicitly-gated-off) as a low-risk, high-clarity pass that doesn't touch anything load-bearing.
5. **Narrow the API-harness's pre-loop decision layers for durable-agent callers specifically** — not a rewrite, a `CallerType`-gated skip on the agent broker / strategy planner / route dispatch for `CallerDurableWake`, since a durable agent's "which agent, what approach" question is already answered at wake time and these three layers exist to solve a problem (ambiguous human input) durable agents don't have.
6. **Leave the context/slot system alone.** It's the one piece of the "general-purpose harness" that is both load-bearing for durable agents specifically (CLI-wrapped agents don't use it at all — see below) and genuinely well-built: six documented invariants, real tests, a clean separation of position vs. content. Don't let a "trim the harness" initiative accidentally sand down the one part of it doing its job well.

Everything below supports and qualifies this.

## 1. Vision-doc sanity check

The vision doc holds up well. It is unusually well-grounded for a strategy document — nearly every claim in it cites a specific audit finding, and I re-checked the load-bearing ones against source rather than trusting the citation. Three places where I think its own reasoning is weaker than it presents, and one place where it's stronger than it gives itself credit for:

**Weaker than presented: "platform vs. embedded" treats the two options as symmetric shapes when they aren't, yet.** The vision doc frames this as "platform's compounding-reliability-fixes advantage outweighs an embedded instance's simpler-boundary advantage," which is the right framing *for a system with real tenancy needs*. But Nanite today has exactly one external consumer (Loom), operated by the same person who operates Nanite, with no adversarial trust boundary between them. "Platform" is doing double duty in the vision doc: it means both "one config surface, not N" (which is just true, and doesn't require any new infrastructure — it's a property of Nanite already existing as a long-running service) and "a real tenancy primitive with ownership/access-control boundaries" (which is a genuine, multi-week build the vision doc itself flags as worth a gut-check in the very next paragraph). These are not the same decision. You get the config-surface win for free just by having Loom call Nanite's API instead of vendoring Nanite. You do not need per-consumer auth, agent-ownership ACLs, or "whose agent is this" GUI to get it. The vision doc's own corollary two paragraphs later ("namespace separation matters from day one") is the right-sized version of this — a clean self-tools/control-plane split — but the doc doesn't clearly separate that from the heavier tenancy-primitive framing above it, which reads as more architecture than what's actually being decided.

**Weaker than presented: "CLI-wrapping primary" and "durable agents core" is called a live tension needing reconciliation, but the evidence already resolves it.** Every durable-agent instance in the live DB is `runtime_kind: api` (0 overlap with `agent_runtime`, the PTY/subprocess table — confirmed independently in `09-durable-agents-runtime.md` §5 and `06-live-runtime-db.md`'s file-vs-DB section). I looked at why, not just that: a durable agent needs to sleep for hours to months and wake on an external signal with no human present. A PTY-backed CLI subprocess is a live OS process attached to a terminal-shaped I/O contract — keeping one alive indefinitely for an agent that wakes once a day is expensive and fragile (the audit's own orphan-reaper and crash-recovery docs show PTY session lifecycle is already a source of real incidents *for the sessions that exist today*, without adding month-long dormancy to the mix), and cold-booting a fresh subprocess per wake gets you no meaningful CLI-specific benefit over calling the HTTP API directly — the CLI's value-add (its own built-in tool execution, permission model, terminal UX) is specifically about *interactive* use. This isn't an open tension; it's two substrates that are already correctly specialized for two different problems, and the vision doc should say so directly rather than filing it as a question for the next planning pass.

**Stronger than presented: the vision doc under-claims how much work "narrow the API-harness's job" actually is.** It correctly identifies the target state (harness only needs to run durable agents well) but frames the current five-layer machinery as something that "was built... as if it needed to generally serve every kind of agent interaction" without establishing whether that generality is actually load-bearing today or just historical residue that would fall away naturally once the CLI path takes over interactive use. I checked: it's not residue. I grepped `chat_broker_dispatch.go`, `chat_strategy.go`, `chat_route_dispatch.go`, and `chat_reflexes.go` for any `CallerType`/`CallerDurable`/`CallerSubagent` branch — zero matches in all four. The agent broker, strategy planner, and route dispatch run bit-for-bit identically whether the turn originated from an interactive human message, a subagent dispatch, or a durable-agent wake with a pre-selected profile and a machine-authored prompt. This means "the API-harness's job narrows" is not a description of something already partially true that just needs cleanup — it's a real subtraction that has to be built, because there is currently no seam in the code where "this is a durable-agent wake, skip the reflex-catalog re-routing" could even hook in. The vision doc should be more assertive here, not less — this is good news for the plan (a durable agent's routing question is answered before the turn starts; skipping these layers for it is safe, not just tidy), but it's real engineering, not a formalization.

**One internal inconsistency worth naming:** the vision doc's "four usage modes" ranks CLI-wrapped interactive work as "the primary mode" and durable agents as "a core pillar, not a side experiment" in the same breath, without resolving which one actually gets more of the next planning pass's attention when they compete. Given the evidence (mode 1 is the one thing the audit consistently calls "architecturally sound" and "where Nanite adds value"; mode 4 is the one with nine root causes needed for a single successful run), I'd read "primary" and "core pillar" as *not* in tension — they're the two things worth protecting, and the case for aggressive cutting applies almost entirely to the machinery that serves neither directly (five decision layers, three messaging substrates, A2A). The vision doc gestures at this but doesn't say it as plainly as the evidence supports.

## 2. Prioritized alignment plan

Structured as cut / combine / streamline / leave alone, each ranked by actual impact on the vision's stated goals — not by how prominently the audit discussed it. I deliberately don't just enumerate the audit's findings back; several things the audit flagged (naming collisions in `mode`, `template`, `handoff`) I'm explicitly recommending you leave alone, and I say why.

### Cut (zero-caller, zero-row, or self-described-dead — low risk, do this first as a warm-up pass)

- **`internal/messaging/gomsg` (the `messaging_envelopes` table and Store).** Fully built, contract-tested, never constructed anywhere the process boots (`12-inter-agent-messaging.md` §3.5, confirmed by the audit's own grep). This is exactly the kind of speculative portfolio-interop layer that "no dependencies" argues against building ahead of need — delete it, and if federated agent-to-agent messaging becomes real later, build it against the MCP control-plane's actual shape, not a shape guessed at in advance.
- **`session_handoffs` and its full request/approval workflow.** Zero rows, zero store methods, one explanatory comment in `container.go`. This is unrelated to the actively-used `handoff_stashes`/Glass-4 continuity mechanism despite the name — don't confuse the two when cutting; only this one is dead.
- **`agent_boot_plans`.** Full CRUD + dry-run API, zero consumers anywhere in the boot path (`02-boot-process.md` §7). This looks like an earlier design for the same problem the boot-profile catalog now solves differently — cut it rather than maintaining two competing "plant content into a boot dir" mechanisms.
- **`agent_cycles`.** The type's own doc comment calls it "the durable unit of live-context continuity for durable agents," but has zero production callers and the one context-key helper that exists says outright "Nanite's current runtime does not yet consume the value" (`09-durable-agents-runtime.md` §8). If durable-agent continuity-summarization becomes a real need post-narrowing, redesign it against the narrowed harness's actual shape rather than resurrecting this.
- **`ReviewMidExecution`/`strategyClarifyingQuestion` (the budget-exhaustion review step).** Tested, never called. Given the strategy planner itself is being narrowed to near-nothing for durable-agent callers (see Streamline, below), don't invest in wiring this up first — it may not survive the narrowing anyway.
- **The known-tools/skills TTL reaper (`ReapExpiredAgentKnownTools`/`ReapExpiredAgentKnownSkills`).** Implemented, unit-tested, no ticker schedules it. Low-stakes; cut or wire it up in the same PR as whatever touches `agent_known_tools` next — don't let it linger as a third state.
- **`grounding_consultations`/`grounding_outcomes`.** Fully wired, gated off by an env var that's unset in production, zero rows ever. This is genuinely a "not sure if this is oversight or intent" case per the audit — but given the strategy planner it feeds is itself getting narrowed, resolve this by removing it rather than flipping the flag; if grounding-informed strategy planning matters later, it should be designed against the narrowed system, not bolted onto the one being cut down.
- **`tool_enrichments`.** Full read path, zero writers, the "admin tooling or probe agent" its migration comment anticipates doesn't exist (`07-tool-calling-mcp.md` §5). Cut the read path with it — don't leave a dead consumer pointed at nothing.

### Combine

- **A2A → the MCP control-plane's implementation seam, not a parallel system.** This is the single highest-value combine move and directly answers the vision doc's open question #2. Retire the A2A JSON-RPC wire protocol, the `/.well-known/agent-card.json` endpoint, `a2a_tasks`/`a2a_push_deliveries`, and the A2A wire types (`internal/a2a`, 401 lines — small, low-risk to remove). **Keep** `TaskManager`'s actual routing logic (`SubmitTask`'s classify-target-then-route-to-`WorkflowLauncher.Launch`-or-`DurableWake.Wake` pattern, and `GetTask`'s derive-state-from-the-real-execution-record-on-every-read approach) as the implementation behind new MCP tools. I read this code directly (`internal/service/a2a_task_manager.go`): its own doc comment already states the design principle the MCP surface needs — "does NOT create a third parallel execution substrate." This is not a rewrite; it's a re-skin from bespoke JSON-RPC methods to MCP tool definitions, and it retires a wire protocol that's self-described as unverified against its own spec with zero external callers, while preserving the one piece of real engineering it produced.
- **The agent broker's and strategy planner's redundant reflex-catalog consultation.** Both independently call `promptrouter.Match()` against the same `BuiltinReflexes()` catalog, at two separate call sites, weighting the result differently (agent broker: overriding; strategy planner: "(advisory)" commentary) — confirmed in `11-broker-strategy-steering.md` §3.1/§4.2. Once the durable-agent-caller skip lands (below), this collision only matters for interactive chat turns, where it's still worth fixing: compute the match once, pass it to both consumers, and make the two decision layers agree on whether a reflex match is binding or advisory — right now that's an accident of two independently-evolved rule sets, not a decision anyone made.
- **The two "which tools does this agent see" mechanisms — `roleTools:`/`role_tools` and `tools:`/`toolPermissions`.** Confirmed dead for 4 of 5 audited Agent Roles profiles (`chat-analysis/02`) and confirmed cosmetic for Curator's seeded patterns (`chat-analysis/02`, `3af1aa49`). Two "declare your agent's tools" surfaces exist; only one is real. Combine into one: either delete `roleTools:`/`role_tools` entirely (it currently only feeds a UI display table nothing else reads) or make it the actual mechanism and delete `tools:`. Given `tools:`/`toolPermissions` is the one that gates real behavior today, delete the other rather than trying to reconcile two competing sources of truth.

### Streamline (the harness narrowing itself — this is the real work)

- **Gate the agent broker, strategy planner, and route dispatch behind `CallerType != CallerDurableWake`.** This is the concrete version of the vision doc's "narrow the API-harness's job." A durable-agent wake already knows which agent profile is running (it woke a specific `durable_agent_instances` row pointing at a specific `agent_profiles` row) and typically delivers a machine-authored prompt (a schedule body or a webhook-rendered fragment identity), not ambiguous free-form human text. The agent broker's job — "which agent profile should handle this ambiguous message" — and the strategy planner's job — "direct_chain vs. subagent_delegation, based on intent tier" — are both questions a durable-agent wake has already had answered by the fact of being woken as a specific instance. Skipping them for durable-wake callers isn't a performance optimization, it's removing machinery that's structurally inapplicable to the caller. Interactive chat and subagent dispatch keep the full machinery unchanged.
- **Keep `chat_generate.go`'s core turn loop (context assembly → provider call → tool execution → termination bounds) as the shared execution path for both interactive and durable-agent turns.** This is the part of "the general-purpose harness" that's actually doing real, non-redundant work — six documented invariants in `internal/context/INVARIANTS.md`, a real test suite (`slot_invariants_test.go`), and it's the mechanism that makes durable agents' prompts consistent and cacheable turn over turn. Don't conflate "narrow the harness's *job*" with "shrink the harness's *turn loop*" — the loop is the thing durable agents specifically need to be great at; the pre-loop steering layers are the thing they don't need at all.
- **Fix the Recovery Broker's CLI-only assumption for the durable-agent (HTTP-provider) path, or scope it out explicitly.** `Broker.DispatchRetry` always calls the CLI/PTY `agent.Boot()` bootdir-setup path regardless of what kind of session failed (`13-session-lifecycle-recovery.md` §4.2, corroborated three independent ways in `chat-analysis/02`, `03`, `06`). This has been failing on 46 of 50 permanent-outcome breadcrumbs — i.e. it has effectively never worked for the exact session type (HTTP/API-provider) that durable agents run on. Given durable agents are the vision's core pillar and this is their primary crash-recovery mechanism, this is not optional polish — it's a correctness gap in the thing being declared load-bearing. Either build a real HTTP-provider recovery path (retry the API call directly, no bootdir involved) or explicitly document that HTTP-provider sessions rely on the (also real, also working) Orphan Sweep + cold-boot-with-recovery-pack path instead and stop invoking the broken broker path for them.
- **Consolidate the durable-agent config authoring surface.** Today, defining a durable agent requires two hand-authored artifacts (`agent_profiles` `.md` + `durable-agents/*.yaml`) kept in sync by convention (`09-durable-agents-runtime.md` §6), and Curator's real-world config sync required synchronized manual edits across at least three surfaces (`chat-analysis/03`). If MCP becomes the primary way external systems provision durable agents, this two-file convention is exactly the kind of manual-sync surface that will produce a repeat of the Curator incident for every future consumer. Not a rewrite — a single validation step at boot (or at `POST /api/durable-agents`) that checks profile/YAML consistency and fails loudly rather than silently drifting.

### Leave alone

- **The context/slot system (`internal/context`, `internal/contextbroker`).** Already covered above — this is well-built, invariant-protected, well-tested machinery that's genuinely load-bearing for the narrowed harness's actual job. Resist any temptation to fold this into a "general trim the harness" pass; it's not part of what's over-built.
- **`mode`, `template`, `handoff` naming collisions.** The audit correctly identifies these as real vocabulary collisions (`17-taxonomy-agent-types.md` §6), but none of them have caused a live incident the way `reflex` (two live renames) and the `dev`/`self` tool-namespace collision (a production incident, commit `5144590`) did. `agent_mode_assignments` and the legacy `agent_modes` table are both near-zero-row and effectively unused; `templates` vs. `prompt_templates` are used by genuinely different features that happen to share a word. Renaming these costs real effort (touching live code, migrations, docs) for a benefit that's purely cosmetic clarity. Fix the ones that bite; leave the ones that don't.
- **Mux/Agent-Mux as the optional MCP proxy.** The audit's tool-naming-collision incident (commit `5144590`) is correctly used in the vision doc as the sharpest illustration of "an optional convenience leaking failure modes into core reliability" — but the fix for that (the closed four-name `IsFirstPartyBuiltinServerName` reserved-namespace defense) is already in place and tested. The lesson to carry forward is architectural discipline (see Named risks, below, on why this needs hardening *before* opening the platform further), not "remove the Mux integration" — Mux genuinely is optional and Nanite genuinely does work with it absent, which is the property that matters.
- **The skills/knowledge auto-discovery pipeline (Pipeline 2, `mcp.Manager.AutoDiscover`).** 810 of 821 rows are mechanical 1-tool-to-1-skill wrappers, which reads as unimpressive until you notice its actual job — making every connected tool individually visible/assignable through the skill catalog and admin UI — is being done correctly. This isn't bloat; it's a working index. Leave it.

## 3. Sequencing

The vision doc asks specifically whether the MCP control-plane tool surface needs to exist before anything else, since external consumers will come to depend on it. **No — reliability work comes first, and I'd go further: standing up the MCP surface before the durable-agent path is trustworthy is actively counterproductive**, because it converts an internal reliability problem into an external-facing contract-breakage problem the moment Loom (or the next consumer) starts depending on it. The sequence:

1. **Durable-agent reliability floor** (the six-of-seven still-pinned model IDs, the Recovery Broker's CLI-only assumption, the subagent reply-delivery `FromAgentID` collision that's been silently failing since at least May). None of this requires the harness-narrowing work to land first — it's fixable against the system as it exists today, and it's the thing an external consumer will notice first and worst.
2. **Harness narrowing** (`CallerType`-gate the three pre-loop layers for durable-wake callers). This can happen in parallel with step 1 but should land before step 3, because the MCP control-plane's `wake_agent` tool is exactly the caller shape this gating targets — building the new external entry point on top of the un-narrowed harness just adds a fifth entry point into the same over-general machinery the vision doc wants narrowed.
3. **MCP control-plane surface**, built as the A2A-routing-logic re-skin described above. This is genuinely the right thing to build before other consumers arrive, but "before other consumers arrive" doesn't mean "before anything else" — it means before you let Torque or a third app start integrating the way Loom did.
4. **The cut/combine/dead-code pass.** Lowest risk, least urgent, best done last precisely because it's low-stakes cleanup that shouldn't compete for attention with the two things that actually gate whether the platform decision pays off.

The vision doc's own instinct here (MCP-first because externals will depend on it) is understandable but backwards under the evidence: the thing externals will actually depend on is durable-agent wakes *working*, and MCP is just the calling convention on top of that. Ship the calling convention onto a foundation that already 404s on model IDs and you've just made the failure externally visible sooner.

## 4. Named risks in the plan itself

- **The tool-naming collision defense is a closed, hand-maintained four-name list, and "platform" means more MCP servers, not fewer.** `IsFirstPartyBuiltinServerName` (`self`/`dev`/`code`/`general`) is exactly the mechanism that failed once already at small scale (commit `5144590`, a single Agent Mux upstream server literally named `nanite`). Opening Nanite up as a platform other portfolio apps build on top of means more MCP servers connecting over time, and the self-tools/control-plane namespace split the vision doc calls for (correctly) needs to be designed with this defense's actual shape in mind from day one — not bolted on after a second collision incident. I'd flag this as the single most concrete way the platform decision could "not survive contact with actually building it": a namespace collision between a control-plane tool name and something a future MCP server happens to expose isn't hypothetical, it already happened once with the self-tool surface.
- **The alphabetical-15-tool cap (`FinalizeToolSelection`) is still a live landmine for any new consumer's agent.** This directly caused Curator to never see its own tools once the catalog grew past ~300 (`chat-analysis/02`, `3af1aa49`) and was worked around per-agent (populating Curator's tool allowlist), not fixed generally. Every future MCP-platform consumer that connects a moderately-sized tool catalog is one alphabetically-unlucky tool name away from repeating this exact incident. This is a correctness bug hiding behind "tune it per agent," and the platform decision multiplies its blast radius.
- **"No dependencies" and "platform" are in mild tension that the vision doc doesn't fully resolve.** The doc is careful to say Nanite's own operation never needs to know a consumer exists — correct, and the right invariant. But once external systems depend on Nanite's MCP contract, Nanite's *release process* now has an external stability obligation it didn't have before (a breaking tool-schema change now breaks Loom, even though Loom isn't a runtime dependency of Nanite). This isn't a reason not to do it, but it's a real new constraint the vision doc frames purely as an architectural boundary question rather than also an operational/versioning one. Worth deciding explicitly — even informally, "MCP tool schemas are additive-only, breaking changes get a new tool name" — before the second consumer shows up, not after.
- **The "two ways to script a durable agent" (free-form steering vs. Agent Workflows) decision genuinely can't be made yet, and the plan shouldn't pretend otherwise.** One recorded execution in the entire database's history, and it failed on a config-resolution bug (`chat-analysis/07-synthesis.md` Pattern F, corroborated in `06-live-runtime-db.md` incident 7). Any part of this alignment plan that assumes Agent Workflows is a proven mechanism for durable-agent tasks is assuming something the evidence doesn't support yet. My read: leave Agent Workflows exactly where the vision doc leaves it — a genuinely open question — and don't let the MCP control-plane design implicitly pick a winner (e.g., don't design `wake_agent` in a way that only cleanly supports one of the two mechanisms).
- **Narrowing the pre-loop layers by `CallerType` risks silently breaking the one thing they do occasionally do right.** The agent broker's reflex-match rule and the strategy planner's background-dispatch rule aren't purely wasted motion — they're how a durable-agent's *own* mid-conversation dispatch decisions (e.g., an advisor-class instance's long-lived session choosing to delegate) currently get made, if that ever happens inside a durable session. Before gating these out wholesale for `CallerDurableWake`, confirm whether any live durable-agent class actually needs in-turn broker/strategy consultation (advisor/harness-class sessions, which persist and could plausibly want to delegate mid-conversation, are the ones to check) versus only the wake-turn's own top-level dispatch — the gating may need to be per-turn-type within a durable session, not a blanket skip on the whole lifecycle class.

## 5. The smallest, honest "v1 that reflects this vision"

Given no users and no monetization pressure, but a real goal of shipping something: the smallest defensible v1 is **CLI-wrapped interactive use (mode 1) kept exactly as-is, one durable-agent role (Curator, since it's the furthest along) running reliably end-to-end through a real MCP wake/status surface, and everything else either cut or explicitly deferred.** Concretely:

**In scope for v1:**
- Fix the durable-agent reliability floor (§3, step 1) — this alone would have prevented most of the nine-root-cause Loom pilot saga.
- The `CallerType`-gated harness narrowing for durable-wake callers.
- A small MCP tool surface (`wake_agent`, `get_agent_status`, `send_message_to_agent`) built on the A2A TaskManager's routing logic, with the self-tools/control-plane namespace split done from the start.
- The dead-code cut pass (low risk, real clarity win, good "portfolio piece" signal — a system with 27 of 79 tables at zero rows doesn't read as shipped, regardless of whether each is individually harmless).
- The two concrete correctness bugs most likely to bite a new MCP consumer immediately: the alphabetical-15-tool cap and the collision-defense namespace hardening.

**Explicitly deferred, not because they're unimportant but because they're not required to call this shipped:**
- Real tenancy/access-control primitives — build the lightweight version (a `consumer` tag in `durable_agent_instances.metadata_json`, already a JSON blob with room for it) and defer real ACLs until a second, less-trusted consumer actually shows up.
- Agent Workflows vs. steering resolution — genuinely not answerable yet, don't force it.
- The GUI-native interactive experience audit (see below) — worth doing, but it's evaluating an already-working mode, not blocking release of anything.
- The remaining naming-collision cleanup (`mode`, `template`, `handoff`) — cosmetic, do it opportunistically.
- gomsg/session_handoffs/agent_boot_plans etc. cuts can slip past v1 if time is short; they're pure subtraction and carry no urgency.

This is a real, opinionated cut: it explicitly does **not** wait for "the platform" in the fuller sense (multi-tenant, versioned-contract, N-consumer-ready) before calling something shippable. It ships one working consumer relationship (Loom via Curator) through the real intended interface (MCP), on a durable-agent runtime that's actually been made reliable first — which is a materially smaller, more honest v1 than "stand up the full MCP control plane and platform model," and it's demonstrable, documentable, and portfolio-worthy on its own.

## 6. Audit gaps

The audit is thorough and well-cited, but a few things it structurally couldn't see or under-weighted from what it worked from:

- **The GUI-native interactive experience — the audit names this gap itself, and it's real.** All chat-analysis evidence is either Claude Code dev-session transcripts (building Nanite) or direct DB queries; genuinely interactive, browser-open, human-typing-in-real-time usage of modes 1/2/3 isn't distinctly captured anywhere. Given mode 1 is being declared "the primary execution path going forward," this is the single biggest blind spot relative to what the vision doc is actually betting on. I'd prioritize this above nearly everything else in "what to look at next" — not because mode 1 is suspected broken (the audit's code-level read of the CLI/PTY bridge is genuinely positive), but because zero of the evidence base actually observes a human using it.
- **No denominator for the "silent fail-open" pattern's actual severity rate.** The audit correctly identifies dozens of instances of this pattern, but every source is either a dev session where something was actively being debugged (survivorship bias toward finding problems) or a DB snapshot of what happened, not what didn't. There's no way from this evidence base to distinguish "fail-open failures happen constantly and are usually invisible" from "these are the N failures out of M successful turns that got caught because someone was dogfooding hard." Both are true statements the audit can support; only one is alarming. Worth a dedicated pass that samples *successful*, unremarkable turns to get a real rate, not just incidents.
- **No security/auth-boundary review, and the MCP-as-primary decision changes what that gap costs.** This is fine under "no enterprise features" as a design choice, but the moment MCP becomes the primary external-system interface, "who can call `wake_agent`" becomes a real question even in a personal/portfolio context — Loom's existing webhook (`POST /api/loom/curator-wake`) has no auth mentioned anywhere in the nine-doc trail that covers it. Not urgent to solve, but worth explicitly deciding "yes, MCP calls are unauthenticated for v1, that's an accepted risk given the trust model" rather than leaving it unexamined.
- **No cost/token-economics view.** The audit surfaces one striking data point (a single 20-hour confused session cost $0.469/917K tokens, more than the next nine sessions combined) but doesn't build this into a broader picture of what "durable agents running unattended, potentially for months" costs at scale if a similar confusion loop recurs unattended rather than under a human's nose. Worth a dedicated look given mode 4 is specifically the unattended one.
- **Deployment/observability tooling (Cerberus) itself wasn't examined**, only the crash-loop bug that happened to surface through it. Given "no dependencies" explicitly frames Cerberus as a deployment convenience Nanite must be able to run without, it might be worth a short pass confirming that's actually true in practice (not just in intent) — the audit doesn't check.
- **Frontend/React code wasn't code-reviewed** beyond the envelope-system doc's necessarily narrow slice (fence-tag parsing, generated-registry drift). Given the GUI is "the primary mode," this is adjacent to the interactive-experience gap above but distinct — it's about code quality/correctness, not usage evidence.

## 7. Anything else notable

- **The `internal/mcpserver` per-session subprocess-callback mechanism is a directly reusable precedent for the new control-plane's namespace design.** I found this independently while verifying whether an external MCP server surface already exists (it turns out Nanite already runs `nanite mcp --session-id ... --tool-allowlist ...` as a scoped server for workflow-runner subprocess callbacks). It already demonstrates exactly the pattern the vision doc's "namespace separation matters from day one" corollary calls for — a tool-allowlist-scoped server instance, tested (`TestToolAllowlist_DiscoveryIsRestricted`). Whoever builds the MCP control-plane surface should look at this code before designing from scratch; the scoping mechanism it needs already exists in the codebase, just aimed at a different caller today.
- **The `tool_result_cache.was_truncated=1` on literally every row (100% of 1,117 all-time rows, including a 2,051-byte row) is a small but concrete signal worth fixing before it misleads someone building on the pointer mechanic.** Either the documented 64 KiB gate isn't actually the trigger condition in the running code, or the table structurally only ever receives pre-truncated rows — either way, anyone reading this table's data to reason about "how much content actually gets truncated" today would draw a wrong conclusion. Low priority, but cheap to resolve and worth doing in the same pass as the CLAUDE.md doc-drift fixes the audit already flagged.
- **The reproducible divide-by-zero panic in `DevToolsTransport.callGrep`** (`internal/mcp/dev_tools.go:821`, confirmed still present by the audit's own direct citation) is a real, live bug discovered through actual agent use (Curator's fallback exploration triggered it), not a hypothetical. It's small, it's exactly located, and it's the kind of thing that's easy to lose in a 23-document audit's volume — worth a one-line fix independent of anything else in this plan.
- **The audit's own methodology is worth naming as a strength to preserve going forward, not just a one-time artifact.** "Implement or fix, then immediately dogfood a live session, let what breaks become the next ticket" is explicitly named in the vision doc as the primary development methodology, and the evidence bears this out completely — nearly every real bug in this entire corpus was found this way, not through the agent's own pre-PR test suite (Copilot's automated review caught more bugs than the implementing agent's own testing in at least 13 documented instances). This isn't a gap to close; it's the thing actually working, and the release-vision plan should protect time for it rather than treating "get to v1" as a reason to stop dogfooding as hard.
