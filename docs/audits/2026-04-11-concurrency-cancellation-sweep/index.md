# Concurrency cancellation mini-sweep — 2026-04-11

**Scope:** mini-sweep. Walk every production goroutine spawn site in the Nanite tree and assess its cancellation / teardown story: does the body select on `ctx.Done()`, does the parent hold a handle to stop it, does the parent `Close`/`Shutdown`/`Stop` wait before returning, is the goroutine request-scoped or daemon-scoped or fire-and-forget, and if fire-and-forget is that actually acceptable here or a latent leak. Paired with a per-package audit of every `Close()` / `Shutdown()` / `Stop()` method to verify they actually cancel, wait, and return in a sound order. Closes the cross-cutting **"Concurrency teardown"** theme from `INDEX.md`. Excludes `vendor/`, generated files, and `_test.go`.

**Spawn-site inventory reused:** `docs/audits/2026-04-11-panic-recovery-sweep/goroutine-map.md` — 93 production `go` spawn sites already enumerated with file:line anchors. This sweep walks the same 93 sites to assess cancellation/teardown rather than re-enumerating them. Where a site's severity is driven purely by its panic story, the panic-recovery sweep owns it; where a site has a lifecycle problem, this sweep owns it. Cross-refs are mutual.

## Methodology

Commands run from repo root:

```
rg -n --type go '\bctx\.Done\(\)|<-ctx\.Done|\bcontext\.Cancel|WithCancel|WithTimeout|WithDeadline|context\.WithoutCancel|context\.Background' -g '!vendor/' -g '!*_test.go'
rg -n --type go 'func \([a-z]+\s\*?[A-Za-z]+\)\s+(Close|Shutdown|Stop|Cancel)\(' -g '!vendor/' -g '!*_test.go'
rg -n --type go 'sync\.WaitGroup|\.Wait\(\)' -g '!vendor/' -g '!*_test.go'
```

**Supplementary reads:** `cmd/nanite/main.go` (lines 250–475), `internal/service/container.go` (`Shutdown`), `internal/service/chat.go` (`HandleMessage`, `Shutdown`), `internal/service/chat_generate.go` (ctx propagation), `internal/service/chat_tool_executor.go` (tool batch wg), `internal/service/delegation.go`, `internal/service/events_composite.go`, `internal/service/stream.go`, `internal/service/a2a/subscribe.go`, `internal/plugin/host.go` (`EmitEvent`, `Shutdown`, `UnloadPlugin`), `internal/plugin/triggers.go` (`Dispatch`, `sendWithRetry`), `internal/plugin/subprocess/manager.go` + `transport.go`, `internal/plugin/catalog.go`, `internal/mcp/manager.go` (`Close`), `internal/mcp/stdio_transport.go` (`start`/`call`/`Close`), `internal/mcp/http_transport.go`, `internal/worker/manager.go` (`SpawnFull`, `Shutdown`, `heartbeatLoop`, deferred delete), `internal/workflow/executor.go` + `handlers.go`, `internal/coordination/badger.go` (`gcLoop`, `Close`), `internal/memory/extraction.go`, `internal/sandbox/proxy.go` (`Start`, `Stop`, `handleConnect` copy goroutines), `pkg/provider/pty.go` (`streamCLI`, `killProcess`), plus the 14 `pkg/provider/*.go` SSE readers.

No tooling runs — this is a grep- and read-driven sweep, not a `-race` sweep. Tooling is explicitly deferred to queued item 35 (`whole-repo-tooling-and-tests-sweep`).

## Headline

**Nanite has no uniform goroutine lifecycle discipline.** Of the 93 production goroutine spawns catalogued by the panic-recovery sweep, **the parent holds a mechanical handle on roughly 13** (workflow executor's per-level `sync.WaitGroup`, workflow `ParallelStep.Execute`'s wg, chat tool executor's concurrent batch wg, plugin `Host.EmitEvent`'s hook wg, worker heartbeat loop's stop channel, subprocess manager's `waitCh` + `healthCancel`, sandbox proxy's serve-wg, Badger `stopGC` channel, a2a pubsub's `ctx.Done` unsubscribe waiter). **The other ~80 are either fire-and-forget, daemon-ticker-without-stop-signal, or spawned-and-forgotten.** The three `Shutdown` methods that claim to be graceful shutdowns — `container.Shutdown`, `chatServiceImpl.Shutdown`, `worker.Manager.Shutdown` — do not uniformly cancel, do not uniformly wait, and have no WaitGroup to wait on. The two composite `Close`/`Shutdown` methods that *do* acquire a lock serialize **across inner Close calls** (`internal/plugin/host.go:1170` `Host.Shutdown` — known, cross-ref plugin-system-plan-eval#01; and `internal/mcp/manager.go:451` `Manager.Close` — new finding with the same shape).

There is no `ctx.Done()`-gated `for select` loop around the chat generation goroutines at all: `HandleMessage` / `RetryLastMessage` / `SendAgentMessage` / `DelegateTask` spawn `generateResponse` on a `context.WithoutCancel(ctx)`-derived context so that the HTTP handler's request cancellation doesn't bleed into the background generation. That is correct — but the goroutine is then orphaned. Nothing links it to process shutdown. On `container.Shutdown()`, `generateResponse` goroutines continue running against a context whose only cancellation is the 5-minute internal timeout. On `os.Exit(0)` after the signal handler returns, those goroutines are torn down abruptly with their half-written messages, half-drained streams, and half-sent plugin events.

## Overall severity

**High (systemic).** Cancellation teardown is the sibling of panic recovery: this sweep's counterpart finding. Where panic-recovery is "any unhandled panic crashes the host", concurrency teardown is "graceful shutdown is not actually graceful." The two sweeps together cover the entire "What happens when things go wrong?" surface. The three highest-blast-radius gaps are:

1. **`chatServiceImpl.Shutdown()` (`internal/service/chat.go:288`) claims graceful shutdown and does not wait for any generateResponse goroutine.** It calls `processTracker.KillAll()` and returns. This is a **claimed-vs-actual** mismatch — the name promises graceful chat shutdown, the implementation is "kill CLIs and hope." Combined with `HandleMessage` using `context.WithoutCancel(ctx)` at `chat.go:165`/`:209`/`:240`, in-flight chat responses have **no cancellation source at all** beyond the 5-minute WithTimeout in `generateResponse`. On SIGTERM, the signal handler runs `container.Shutdown()` (which calls this Shutdown), then `os.Exit(0)` at `cmd/nanite/main.go:274`. The generateResponse goroutines die mid-stream with no cleanup — assistant messages half-persisted, tool executions mid-flight, plugin events mid-emission. **Gap severity: High.**

2. **`worker.Manager.Shutdown()` (`internal/worker/manager.go:314`) cancels worker contexts but does not wait for SpawnFull's caller goroutine to return.** Cancel propagates via `w.cancel()`, `w.SetStatus(StatusCancelled)`, but `SpawnFull` is a blocking call whose *caller* is a separate goroutine (typically `delegation.go:264`'s sub-worker fan-out) that must observe the cancellation on its own. There is no WaitGroup. The 30-second-sleep "deferred delete" goroutine at `manager.go:179` holds no cancellation — it sleeps against wallclock and then calls `m.workers.Delete`. On process shutdown, this goroutine is leaked (and `time.Sleep` is not cancellable without a timer). **Gap severity: Medium.**

3. **`mcp.Manager.Close()` (`internal/mcp/manager.go:451`) holds `m.mu.Lock()` across each transport's `Close()` call.** This is line-for-line the same pattern as `plugin-system-plan-eval` finding 01 (`Host.Shutdown` holding `h.mu.Lock()` across `p.Unload()`). `StdioTransport.Close` at `stdio_transport.go:185` acquires `t.mu.Lock()`, so the cross-lock-during-Close is strictly intra-transport here, not cross-into-Manager. But the *shape* of the bug is the same, and if any future transport's `Close` calls back into the Manager (to record a status, emit an event, refresh tool list, etc.) the deadlock reappears — independently implemented, same class. **Gap severity: Medium.** Flagged as a pattern-adjacent finding, not as a re-flag of plugin-system-plan-eval#01.

## Summary of gaps

Headline-level groupings. Full per-package detail in `lifecycle-map.md`.

- **Chat generation goroutines are completely orphaned from shutdown.** `service/chat.go:165/209/240/delegation.go:123` — four `go s.generateResponse(bgCtx, ...)` sites. `bgCtx := context.WithoutCancel(ctx)` intentionally severs the request-ctx link. No parent-side wg. `chatServiceImpl.Shutdown()` does not wait. The only cancellation is the internal 5-minute `WithTimeout` inside `generateResponse`. Owner: **nobody.**
- **Plugin `Host.EmitEvent` is the rare good citizen.** `internal/plugin/host.go:1087-1100` — spawns one goroutine per hook, uses `var wg sync.WaitGroup`, `wg.Wait()` before returning. Hook body runs with `context.WithTimeout(h.ctx, 5*time.Second)`, and `h.ctx` is cancelled by `Host.Shutdown` at `:1181`. Per-hook panic still crashes host (panic-recovery sweep concern), but lifecycle shape is correct.
- **`Host.Shutdown` itself is broken by prior audit finding — holds `h.mu.Lock()` across `p.Unload()` loop (`host.go:1171-1179`)**, cross-ref plugin-system-plan-eval#01. Not re-flagged. In addition, `h.ctxCancel()` fires *after* the unload loop — so any in-flight EmitEvent goroutines spawned by the plugins during unload will still be running against a live `h.ctx` when `Unload` returns. Order is cancel-after-unload, should be cancel-then-unload-then-wait. Noted as a "claim-vs-actual" subtlety on top of the existing plugin #01 cross-ref.
- **`TriggerDispatcher.Dispatch` (`internal/plugin/triggers.go:44-82`) is spawned by `host.go:1105` as `go h.triggers.Dispatch(event)` — fire-and-forget at the parent.** Inside, each matching rule spawns `go td.sendWithRetry(...)` at `triggers.go:80`. `sendWithRetry` does a proper `td.host.ctx.Done()` check in its backoff select, so it does observe host shutdown. But the dispatch-level goroutine has no cancellation and no wg — the event is "lost" if the host shuts down mid-dispatch, and a single event under load can fan out to unbounded connectors without any spawn-rate limit.
- **Plugin subprocess `Transport.read` fixed the leak-on-timeout.** `internal/plugin/subprocess/transport.go:107-139` — the spawned reader blocks on `ReadBytes('\n')`. On timeout or `ctx.Done`, `t.Close()` is called which closes the underlying reader and unblocks `ReadBytes`. **This resolves plugin-system-plan-eval finding 03 at the single-Close level.** Cross-referenced, not re-flagged.
- **MCP stdio transport did NOT fix the same leak (`mcp-client-transport` finding 01).** `internal/mcp/stdio_transport.go:108-133` spawns the reader identically, but on timeout only sets `t.started = false` without closing stdin, killing the subprocess, or closing stdout. The reader goroutine stays blocked on `ReadBytes` against a now-abandoned pipe. Cross-ref mcp-client-transport#01, not re-flagged.
- **`mcp.Manager.Close()` (`manager.go:451-460`) holds the write lock across transport Close calls.** New finding — same pattern as plugin-system-plan-eval #01. Explicitly gap-listed in per-package detail below.
- **Four background daemon goroutines in `cmd/nanite/main.go:431/442/454/466` have no stop signal.** Tickers fire forever, bodies call container methods, exit only on process termination. `container.Shutdown()` does not cancel them — there is no channel, no context, no reference to them. On SIGTERM: signal handler fires → `container.Shutdown()` → `os.Exit(0)` → daemons are SIGKILLed mid-flush. At minimum the `Tasks.Snapshot` ticker and the `Workers.ReapStale` ticker hold references to state that gets accessed during shutdown — shutdown ordering is not enforced.
- **Signal handler goroutine in `cmd/nanite/main.go:268-275` terminates cleanly.** But it does not defer `os.Exit(0)` behind a max-timeout — a hung `container.Shutdown()` wedges the host indefinitely. Given that `chatServiceImpl.Shutdown` is quick but `mcp.Manager.Close` holds a lock and iterates transports (each with a `stdin.Close() + cmd.Process.Kill() + cmd.Wait()` that can block on a wedged subprocess), the cumulative shutdown can hang.
- **`worker.Manager.Shutdown` cancels without waiting.** `manager.go:314-324` — `workers.Range`, `cancel()`, `SetStatus(StatusCancelled)`. No WaitGroup. No wait for `SpawnFull` to return. Any concurrent `SpawnFull` blocked on its `DelegateTask` call has been cancelled but the goroutine is not awaited. Its `cleanup()` function still runs, releases the semaphore, and deletes the worker. Fine on exit-path, bad on reload-path: there is no "drain and restart" shape available.
- **`worker.Manager.SpawnFull` leaks a 30-second sleep goroutine per worker (`manager.go:179-182`).** Not a panic-recovery concern, but a shutdown concern: this goroutine holds no context, no stop channel, and survives process shutdown attempts. On SIGTERM, it is abandoned mid-sleep. Under churn (many workers spawned/completed within a short window), there can be N of these pending deletes accumulated, all invisible to `Shutdown`.
- **`BadgerStore.Close()` (`internal/coordination/badger.go:103-106`) signals `stopGC` then calls `db.Close()` without waiting for `gcLoop` to observe the stop and exit.** If `RunValueLogGC` is mid-call when `db.Close` runs, the call may return an error or panic depending on Badger v4 internals. Minor teardown race.
- **`sandbox.Proxy.Stop()` (`internal/sandbox/proxy.go:61-70`) waits for `Serve` but not for in-flight CONNECT tunnel goroutines.** `handleConnect` spawns two `io.Copy` goroutines with a local `copyWg` (`proxy.go:120-130`). After `handleConnect` returns, the hijacked connection is detached from the http.Server, and the copy goroutines are not tracked by `p.wg`. On `Stop`, `http.Server.Shutdown` only drains non-hijacked requests — hijacked CONNECTs live on. Proxy shutdown returns while tunnel goroutines may still be running.
- **Sandbox proxy CONNECT copy goroutines observe no `ctx.Done()`.** They terminate only when one side of the TCP pipe closes. If a sandboxed process is slow to release its end (or the remote endpoint is hung), these goroutines linger for the full kernel-level timeout — no Nanite-side cap.
- **`pkg/provider/pty.go:126`'s PTY reader only checks `ctx.Done()` in the no-scanner-data branch.** `scanner.Scan()` is a blocking read on the PTY master; if the CLI never outputs anything, cancellation doesn't propagate through the scanner loop. Redemption: `cmd = exec.CommandContext(ctx, ...)` at `pty.go:105` causes stdlib to kill the process on ctx cancel, which closes the PTY and unblocks Scan. So cancellation DOES flow — indirectly, via process death, not via the select. Not a leak, but not a "the body observes cancellation" either. Worth cataloging for future refactors.
- **PTY goroutine + killProcess has a latent double-`cmd.Wait()` risk.** `pty.go:172` (main body) and `pty.go:196` (killProcess nested goroutine) both call `cmd.Wait()`. Control flow ensures only one path runs per invocation (the main body returns early on ctx.Done before reaching :172), but this is subtle — future edits could introduce a double-wait without catching it at review time.
- **`CatalogFetcher.Fetch` (`internal/plugin/catalog.go:86-129`) has an unbounded goroutine fan-out with no per-source worker pool.** Observed by the panic-recovery sweep as a "noticed" entry; re-surfaces here because the `Fetch` goroutines also observe no `ctx.Done()` — they run `cf.fetchSource(ctx, s)` which does, but if the caller cancels ctx, the unused goroutines that haven't started yet still run to completion because `Fetch` uses `for range` over `<-results` which blocks until every goroutine posts. There is no "early return on ctx.Done" in the collection loop. Cross-ref queued scope #45 (`plugin-catalog-fetcher-concurrency`).
- **`StreamManager` has no Close/Shutdown.** `internal/service/stream.go` — holds six `sync.Map`s of active streams, SSE connections, presence clients, and throttle state. On shutdown, active SSE goroutines reading from the streams are abandoned, the presence client channels are never closed, and the `activePresence` / `cliThrottle` maps are left with stale state. Fine for an exiting process, but not fine for a restart-in-place or a hot-reload path. Claimed-vs-actual: there is no claim, just an absence — the reader expected a Close method and found none.
- **`internal/coordination/badger.go:33` `gcLoop` is a long-lived daemon goroutine that's launched from `NewBadgerStore`'s constructor, not tracked by a WaitGroup or sync.Once-wrapped Close.** `Close()` does signal via `close(s.stopGC)` but does NOT wait for the loop to observe it. Teardown ordering: `close(stopGC) → db.Close()`. On tick boundary, the loop can be mid-`RunValueLogGC(0.5)` when `db.Close()` runs. Racy.

## New gaps cataloged by this sweep

These are the cancellation / teardown gaps being written down for the first time. As a mini-sweep, this deliverable is the map, not per-finding folders — the orchestrator decides whether any of these get promoted to standalone findings or folded into the cross-cutting theme entry.

1. **`chatServiceImpl.Shutdown` does not wait for generateResponse goroutines (`internal/service/chat.go:288`).** Four spawn sites (`chat.go:166/210/241`, `delegation.go:123`) use `context.WithoutCancel(ctx)` then `go s.generateResponse(bgCtx, ...)`. No wg. No tracking. `Shutdown` only calls `processTracker.KillAll`. The 5-minute internal timeout is the only cancellation source. On SIGTERM, the signal handler calls `container.Shutdown()` then `os.Exit(0)` — in-flight chat responses die mid-persist, mid-stream, mid-event-emission.

2. **`worker.Manager.Shutdown` cancels without waiting (`internal/worker/manager.go:314`).** `workers.Range → w.cancel() → SetStatus(StatusCancelled)`. No wg. Concurrent `SpawnFull` calls still blocked on `DelegateTask` when Shutdown returns. The claim "cancels all active workers" is accurate; the implication of "shutdown" (wait for completion) is not.

3. **`worker.Manager.SpawnFull` deferred-delete leak (`internal/worker/manager.go:179`).** `go func() { time.Sleep(30*time.Second); m.workers.Delete(workerID) }()` — one goroutine per worker, no context, no stop channel, no cancellation. Under high worker churn the count accumulates. On shutdown, `time.Sleep` is uncancellable and the goroutine is abandoned. Separate concern from the panic sweep's "trivial body" note — the lifecycle shape is broken.

4. **`mcp.Manager.Close` mutex-across-inner-Close (`internal/mcp/manager.go:451`).** Holds `m.mu.Lock()` across every transport's `Close()`. Same pattern as `plugin-system-plan-eval` #01 but independently implemented in a different package. Currently latent (no transport's Close recurses into Manager) — becomes a real deadlock if any future transport records status, emits an event, or refreshes tool list from inside Close.

5. **`Host.Shutdown` cancel-after-unload ordering (`internal/plugin/host.go:1171-1181`).** On top of the known plugin #01 mutex-across-Unload bug: the ordering is `Unload loop → h.ctxCancel()`, which means EmitEvent goroutines spawned by plugin Unload handlers still see a live `h.ctx` for their 5-second WithTimeout. Correct order: cancel first, unload second, wait third. Sub-issue of plugin #01, not a separate flag.

6. **Background daemon tickers in `cmd/nanite/main.go` have no stop signal (`:431/:442/:454/:466`).** Four tickers, four `for range ticker.C` loops, zero cancellation paths. `startBackgroundWorkers` returns without handing back a `stop` channel or cancel func. `container.Shutdown` has no way to signal them. On SIGTERM they are SIGKILLed by `os.Exit(0)` mid-tick.

7. **Signal handler has no max-shutdown-timeout (`cmd/nanite/main.go:268-275`).** Synchronous `container.Shutdown()` call followed by `os.Exit(0)`. If any sub-shutdown hangs (mcp stdio `cmd.Wait()` on a wedged subprocess, plugin Unload calling into a hung plugin, etc.), the process hangs forever with no forced-exit timer.

8. **`BadgerStore.Close` does not wait for `gcLoop` exit (`internal/coordination/badger.go:103-106`).** `close(stopGC)` fires, but `s.db.Close()` runs immediately without waiting for the loop to observe the close. If a `RunValueLogGC` is in flight, behavior depends on Badger v4 internals — likely returns an error, possibly worse. Minor but cataloged.

9. **`sandbox.Proxy.Stop` does not wait for CONNECT tunnel goroutines (`internal/sandbox/proxy.go:61-70`).** `p.wg` only tracks the Serve goroutine. `handleConnect` uses a local `copyWg` that goes out of scope when the handler returns, so the hijacked-connection copy goroutines are fully detached from `p.wg`. On Stop, tunnel goroutines continue running until the TCP pipes close on their own.

10. **Sandbox proxy CONNECT copy goroutines observe no `ctx.Done()` (`proxy.go:122-130`).** They block on `io.Copy` until one side closes. No max-lifetime, no cancellation. A wedged remote server holds them until TCP keepalive times out — minutes to hours depending on OS tunables.

11. **StreamManager has no Close / Shutdown method (`internal/service/stream.go`).** Six `sync.Map`s of live state. On process shutdown, nothing closes presence client channels, nothing drains active streams, nothing flushes `activePresence`. Fine on process exit; breaks any in-process restart or hot-reload path.

12. **PTY reader cancellation is indirect (`pkg/provider/pty.go:126-161`).** `scanner.Scan()` blocks without checking `ctx.Done()`; the select-with-default at `:135-141` only runs AFTER a scan returns, which doesn't happen if the CLI is silent. Cancellation works because `exec.CommandContext(ctx, ...)` at `:105` kills the process on ctx cancel, which EOFs the PTY. That's an indirect, implicit contract — the PTY body doesn't observe the cancellation, the process death does. Worth a note for any future refactor that changes how `cmd` is constructed.

13. **PTY `killProcess` nested `cmd.Wait()` is latent double-wait (`pkg/provider/pty.go:196`).** The main body at `:172` and the killProcess goroutine at `:196` both call `cmd.Wait()`. Current control flow ensures only one runs per invocation. Subtle and fragile — a future edit that removes the early return would introduce a double-wait panic.

14. **`CatalogFetcher.Fetch` cannot be cancelled mid-fetch (`internal/plugin/catalog.go:86-129`).** Per-source goroutines observe ctx indirectly via `fetchSource`, but the collector loop `for i := 0; i < enabledCount; i++ { catalogs = append(catalogs, <-results) }` blocks on the channel — it does not select on `ctx.Done()`. If the caller cancels, `Fetch` does not return until every source goroutine posts a result. Cross-ref queued scope #45 for the full fan-out-bounding audit.

15. **`TriggerDispatcher.Dispatch` is spawn-unbounded per event (`internal/plugin/triggers.go:44-82`).** Per event, fan-out is `len(rules)` → each matching rule is a spawned `sendWithRetry` goroutine. No pool, no rate limit. `sendWithRetry` itself observes `td.host.ctx.Done()` for retry cancellation, which is correct. But the dispatch-level goroutine (spawned from `host.go:1105`) holds no cancellation signal — the event is never "given up on" at the dispatch layer.

16. **`Memory.Extractor` extraction goroutines observe no shutdown (`internal/memory/extraction.go:105/136`).** The hook's `Handle` discards its `_ context.Context` and spawns `go h.extractor.extractPerTurn(sessionID, content)`. Inside, `extractPerTurn` creates `context.Background()` with a 15-second `WithTimeout`. No link to process shutdown. On SIGTERM, extractor calls die mid-utility-LLM-call. This is the canonical "fire-and-forget without owner" shape.

## Noticed but out of scope

Observations made during the sweep that are not cancellation/teardown gaps but are worth spawning as queue entries or folding into other scopes:

- **`internal/plugin/host.go:1043-1052` comment admits the event-hook deregister-on-unload path is broken.** `EventHook` interface doesn't expose a plugin ID, so `UnloadPlugin` copies the hooks slice in-place with a no-op filter. The code comment says "tracked for future cleanup." A plugin's event hooks persist after the plugin unloads, until the process restarts. Candidate queue entry: already tracked as BLG-20260410-004 in `.nanite/agents/backend.md` Beta Known Issues — not re-flagged.
- **`internal/service/chat.go:165` comment documents `context.WithoutCancel` as intentional** ("the HTTP request context is cancelled when the handler returns (202 Accepted), but generateResponse runs in the background and must not be tied to the request lifecycle"). The intent is correct — the *implementation* of providing a separate shutdown ctx is missing. The comment should point at a `s.generateCtx` field that does get cancelled on Shutdown, which does not exist.
- **`internal/plugin/triggers.go:153` uses `td.host.ctx` directly** — the host's lifetime context — for per-call WithTimeout. On `Host.Shutdown → h.ctxCancel()`, this is wrong order: Shutdown holds `h.mu.Lock()` across Unload, so cancel fires after Unload. Same root cause as plugin #01, but the effect here is that trigger sends never observe the cancel while plugins are being unloaded.
- **`internal/plugin/subprocess/manager.go:292` `attemptRestart` uses `time.Sleep(backoff)`** — an uncancellable sleep. If the manager is `Stop`ped mid-backoff, it waits the full backoff before the stopped check re-runs. Not a severe gap but a "Stop is slow" contract detail.
- **`internal/plugin/subprocess/manager.go:176` healthLoop bound to `context.WithCancel(context.Background())`, not `host.ctx`.** Health check lifetime is decoupled from the host's shutdown context — acceptable because the subprocess manager owns it, but a hot-reload path where the host is being rebuilt but plugins are kept alive would desync here.
- **`internal/sandbox/proxy.go` has no max-concurrent-CONNECT limit.** Malicious or buggy sandboxed process can open thousands of tunnels, each spawning 2 goroutines. No cap. Observability hole. Candidate queue entry: `sandbox-proxy-fan-out` mini-follow-up.
- **Every `pkg/provider/*_test.go` spawn site excluded** — but the production readers use `httptest.NewServer` in tests, which shuts down cleanly. The prod readers don't have matching cleanup. Covered by panic sweep for the panic dimension.
- **`internal/contextbroker` has no goroutines and is not in this scope**, but its consumers (`AssembleContext` called by generateResponse) inherit generateResponse's orphaned ctx. The broker itself is sound; its caller's lifecycle weakness flows through.
- **`internal/service/events_composite.go`'s 20 naked emit-goroutines** are panic-sweep territory for panic risk, and this sweep's territory for fire-and-forget concerns. Each emit is spawned from a handler goroutine, runs against no shared wg, and has no link to shutdown. On `container.Shutdown`, any in-flight emits are dropped mid-call.
- **`internal/mcp/manager.go:99` `RemoveServer` only closes the transport it's removing.** There is no broadcast to existing tool-client consumers that the server has gone away — callers holding a `*provider.ToolDefinition` that references the removed server will get `unknown MCP server: <name>` on next call. Fine for exit-path; tool-broker cache coherency is a separate audit.
- **Graceful shutdown observability is absent.** No shutdown-phase OTel spans, no "Shutdown start" / "Shutdown end" events, no structured logs per subsystem. Debugging a hung shutdown requires attaching a debugger. Rolls into the `observability` queued scope.

## Cross-cutting observations — theme update proposal

The existing `INDEX.md` "Concurrency teardown" theme has three bullets: `UnloadPlugin deadlock`, `worker shutdown races (fixed)`, and a cross-reference to the "No panic recovery" theme. It was the sibling theme to panic-recovery and is now the natural owner of this sweep's findings.

Proposed expansion:

> **Concurrency teardown.** Nanite has no uniform goroutine lifecycle discipline. Of ~93 production goroutine spawn sites (see `2026-04-11-panic-recovery-sweep/goroutine-map.md`), only ~13 have a parent-side handle (WaitGroup, stop channel, cancel func that's actually awaited). The remaining ~80 are fire-and-forget, daemon-ticker-without-stop-signal, or spawned-and-forgotten. Three Shutdown methods claim graceful behavior they don't deliver: `(*Container).Shutdown` (calls sub-shutdowns sequentially with no max-timeout), `(*chatServiceImpl).Shutdown` (only kills CLI processes, does not wait for in-flight generateResponse goroutines), `(*worker.Manager).Shutdown` (cancels without waiting). Two `Close`/`Shutdown` methods hold a lock across inner `Close` calls, same shape as `plugin-system-plan-eval` #01: `(*plugin.Host).Shutdown` (the original) and `(*mcp.Manager).Close` (independently implemented, same pattern). The chat generation path uses `context.WithoutCancel(ctx)` to intentionally sever request-ctx from background goroutines — correct intent, but no replacement shutdown-ctx exists, so the goroutines are orphaned from shutdown entirely. The only sound subsystem lifecycle in the tree is `internal/plugin/subprocess/Manager.Stop` (cancel → wait → force-kill-on-timeout → re-wait). **Concrete refactor proposal** from this sweep: a `internal/lifecycle` primitive that owns a shutdown context + a tracked-goroutine pool (`lifecycle.Go(label, fn)` + `lifecycle.Shutdown(maxWait)` with sub-shutdowns called in reverse-init order, a max-total-timeout, and per-subsystem OTel spans). Every `Shutdown`/`Close`/`Stop` method should be expressible as "cancel context; wait on tracked goroutines; force-exit on timeout." Adopt via a golangci-lint custom rule that forbids bare `go ` in specific packages — same enforcement knob as the `internal/safego` proposal from the panic-recovery sweep. The two primitives (`safego` for panic safety, `lifecycle` for teardown) are orthogonal and compose: a typical spawn becomes `lifecycle.Go("chat.generate", safego.Wrap(fn))`.

Same proposed rewrite path as the panic-recovery sweep, different concern dimension. Together they propose replacing every `go func() { ... }()` in the tree with a structured spawn primitive that wraps (recover, span, cancel, wait).
