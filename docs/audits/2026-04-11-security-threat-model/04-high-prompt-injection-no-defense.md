# [High] No prompt injection defense — scope_guard is dead code, no user message sanitization exists

**Scope:** Chat engine — trust boundary #2 (User messages in chat), #3 (Tool arguments)
**Topic:** Security
**Date:** 2026-04-11

## Problem

User messages flow into the LLM provider with no sanitization, filtering, or prompt injection detection. The only designed defense (`scope_guard.go`) is confirmed dead code. The `FilterUserMessage` plugin filter point exists but no plugin implements it. User-controlled text can influence tool arguments generated by the LLM, creating an indirect prompt injection vector for all tool execution.

## Evidence

### scope_guard is dead code (cross-ref confirmation)

Already confirmed Critical in `chat-engine` audit: `NewScopeGuard` and `NewEventReactionPipeline` have zero non-test callers. `chat_generate.go` calls `prov.StreamChatWithTools` directly with no wrap. Even if wired, `DefaultEventReactionConfig()` at `pkg/provider/event_pipeline.go:L33-L35` sets:

```go
EnableScopeGuard:      true,
AllowedScopes:         []string{"*"}, // Allow all by default
ScopeViolationMode:    "log",
```

`AllowedScopes: ["*"]` passes through `isAllowedOperation` at `pkg/provider/scope_guard.go:L160-L168`:

```go
func (sg *ScopeGuard) isAllowedOperation(operation string) bool {
	for _, pattern := range sg.allowedPatterns {
		if pattern == "*" {
			return true
		}
	}
	return sg.isAllowedByPatterns(operation)
}
```

So even if wired, it would allow everything. And `ScopeViolationMode: "log"` means violations are logged, never blocked.

### No user message validation

`internal/service/chat_generate.go:L192-L199` shows the only touch-point for user message content before it reaches the LLM:

```go
if s.pluginHost != nil && userContent != "" {
    if filtered, err := s.pluginHost.ApplyFilter(pluginpkg.FilterUserMessage, userContent, fctx); err != nil {
        log.Printf("chat-service: system_prompt filter error: %v", err)
    } else if fs, ok := filtered.(string); ok {
        userContent = fs
    }
}
```

`FilterUserMessage` is a plugin filter point. No built-in plugin registers a filter for it. The filter chain is empty — `ApplyFilter` returns the input unchanged.

There is no:
- Input length validation on user messages
- Character set validation
- Prompt injection detection (marker words, instruction injection patterns)
- Content type validation (e.g., rejecting binary data in text messages)

### Tool arguments are LLM-generated from user-influenced context

`chat_generate.go:L240+` enters the tool-use loop where the LLM generates tool_use events with arguments. Those arguments are influenced by user message content. The tool execution path (`ToolService.Execute`) processes these without validating that the arguments are consistent with what a non-adversarial LLM would produce. Already covered by `toolbroker` finding (tool arguments passed through unvalidated), but the root cause is the lack of upstream prompt injection defense.

## Impact

1. **Direct prompt injection**: A user can instruct the LLM to execute tools it shouldn't (read sensitive files, run commands). The `nativeToolGuide` injected at `chat_generate.go:L178` includes allowed directory paths (`/Users/chrispian/Projects-apps`), which the LLM is instructed to respect — but this is a soft instruction, not an enforcement mechanism. A sufficiently crafted prompt can override it.

2. **Indirect prompt injection**: Content fetched by `web_fetch` or returned by MCP tools may contain injected instructions. These appear in the conversation context and influence subsequent LLM tool calls. No scanning of tool results for injection attempts occurs.

3. **Cross-session injection**: If a user pastes malicious content that gets stored in memory extraction (`internal/memory/extraction.go`), it persists and may influence future sessions via the context broker's memory source.

## Recommendation

1. **Short-term**: Wire `EventReactionPipeline` into the chat generate path. Change default `AllowedScopes` from `["*"]` to the session's working directory. Change `ScopeViolationMode` from `"log"` to `"kill"`.

2. **Medium-term**: Implement a built-in `FilterUserMessage` plugin (or core filter) that:
   - Enforces a maximum message length
   - Detects common prompt injection patterns (instruction override markers, role impersonation)
   - Scans tool results for embedded instructions before they re-enter the conversation

3. **Long-term**: Implement a proper defense-in-depth layer:
   - Tool argument validation at the tool execution boundary (not just tool broker permission checks)
   - Output filtering on tool results before they re-enter the LLM context
   - A "trusted context" / "untrusted context" separation in the system prompt assembly
