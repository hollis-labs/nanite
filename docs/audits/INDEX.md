### 2026-04-11 — `context-management` (Go, deep-review + claimed-vs-actual)
- **Counts:** 2 Critical, 2 High, 3 Medium, 0 Low, 1 Info
- **Folder:** `docs/audits/2026-04-11-context-management/`
- **Claimed-vs-actual verdict:** **Slot system, hot-swap, auto-compaction, and /compact are all stubs.** Only `PruneAfterTurn` and `EnforceTokenBudget` work end-to-end. The slot system (`ContextWindow`, `ContextSlot` types in `internal/chat/context_window.go`) is a data structure with no production wiring — `AssembleSlots` is never called from any code path. Hot-swap does not exist as a feature — no function, API, or command implements it. Auto-compaction (`chat_generate.go`'s `shouldAutoCompact` check) has the conditional but the branch was never reached in a code trace — the trigger threshold is never exceeded because `PruneAfterTurn` already reduces context below the threshold. `/compact` command exists as an API handler but is a minimal stub (calls `PruneMessages` which is `PruneAfterTurn`'s inner function, not the designed "summarize + replace" compaction).
- **Headline:** Two claimed-complete features are Critical stubs: (1) Slot system is unwired — the `ContextWindow` type, `AssembleSlots`, and `ContextSlot` structs compile but have zero production callers. Context assembly uses `AssembleContext` (flat list) not `AssembleSlots` (slot-based). (2) `/compact` API handler calls `PruneMessages` (drop oldest), not a summarize-and-replace compaction. Hot-swap (High) does not exist in any form. Auto-compaction (High) never fires because `PruneAfterTurn` preempts its threshold.

### 2026-04-11 — `memory-ranking` (Go, deep-review)
- **Counts:** 1 Critical, 2 High, 4 Medium, 1 Low, 1 Info
- **Folder:** `docs/audits/2026-04-11-memory-ranking/`
- **Headline:** **Embeddings are never generated** (Critical). The Conduit `EmbedHandler` is registered and the queue infrastructure exists, but when nanite calls `conduit.StoreRevision()`, the revision is stored without triggering an embed job because `StoreRevision` does not enqueue an embed task — it relies on a separate `EmbedRevision` call that is never made from nanite's memory extraction path. This confirms and deepens the `contextbroker` finding 01 (similarity ranking always fails): the failure is not just at the query side (missing `EmbedQuery: true`) but at the storage side (revisions are never embedded). The entire similarity-based recall path is dead. **Recall options missing query field** (High) — `SimilarRevisions` receives empty `RecallOpts.Query` from the broker because the broker doesn't populate it. **No hybrid ranking fallback** (High) — when similarity fails (always, currently), there is no BM25 or keyword fallback; recall returns an empty set. Plus: extraction fire-and-forget goroutines with no ctx (Medium), no PII scrubbing in memory extraction (Medium), no BM25 keyword recall exists (Medium), relevance scoring ignores Conduit-side score (Medium).
- **Cross-audit update:** `contextbroker` finding 01 (similarity ranking always fails) is now understood as a two-sided failure: query side (broker doesn't set EmbedQuery) AND storage side (embeddings never generated). Both must be fixed for similarity recall to work.

## Cross-cutting themes

Patterns that appeared in multiple audits — likely targets for refactoring even before any individual finding is fixed:

- **Symlink handling.** Installer follows symlinks (installer 02); scaffold creates symlinks without validation (installer 04); sandbox dir resolution is unsafe (sandbox 01); dev-tools `isAllowed` falls back to unresolved abs path on `EvalSymlinks` error (dev-tools 02). **Concrete refactor proposed by dev-tools auditor: a shared `internal/pathsafe.ResolveUnder(root, userPath)` helper** would close the symlink class across sandbox, installer, and dev tools in one primitive.
- **Marker / parser injection.** Managed section first-match parser (installer 03); seatbelt profile string interpolation (sandbox 01). Both are "untrusted string interpolated into a structured format without escaping" — same root cause, different format.
- **Concurrency teardown.** Nanite has no uniform goroutine lifecycle discipline. Of ~93 production goroutine spawn sites (see `2026-04-11-panic-recovery-sweep/goroutine-map.md`), only ~13 have a parent-side handle (WaitGroup, stop channel, cancel func that's actually awaited). Three `Shutdown` methods claim graceful behavior they don't deliver: `(*Container).Shutdown` (sub-shutdowns sequential, no max-timeout), `(*chatServiceImpl).Shutdown` (kills CLI processes only, does NOT wait for in-flight `generateResponse` goroutines — which use `context.WithoutCancel` with no replacement shutdown-ctx), `(*worker.Manager).Shutdown` (cancels without waiting). Two `Close`/`Shutdown` methods hold a lock across inner Close calls (same shape as `plugin-system-plan-eval` #01): `(*plugin.Host).Shutdown` (the original) and `(*mcp.Manager).Close` (independently re-implemented, same pattern — latent deadlock on any future recursive Close). Four background daemon tickers (`cmd/nanite/main.go:431/442/454/466`) have no stop channel. `BadgerStore.Close` closes `stopGC` without waiting for `gcLoop`. Worker shutdown races from 2026-04-10 remain fixed. The only sound subsystem lifecycle in the tree is `plugin/subprocess/Manager.Stop` (cancel → wait → force-kill-on-timeout → re-wait) — the reference implementation. Audits that found instances: plugin-system-plan-eval #01 (Host.Shutdown), plugin-system-plan-eval #03 (subprocess transport fixed), mcp-client-transport #01 (stdio timeout leak), concurrency-cancellation-sweep 2026-04-11 (authoritative repo-wide map). **Concrete refactor proposal**: a `internal/lifecycle` primitive that owns a shutdown context + tracked-goroutine pool (`lifecycle.Go(label, fn)` + `lifecycle.Shutdown(maxWait)` with sub-shutdowns in reverse-init order, max-total-timeout, per-subsystem OTel spans). Every `Shutdown`/`Close`/`Stop` method becomes "cancel context; wait on tracked goroutines; force-exit on timeout." Orthogonal to the `internal/safego` panic-recovery primitive — they compose: a typical spawn becomes `lifecycle.Go("chat.generate", safego.Wrap(fn))`. Both enforceable via the same golangci-lint custom rule forbidding bare `go ` in specific packages.
- **No panic recovery anywhere except HTTP middleware.** Exactly one `recover()` call exists in production code (`internal/server/server.go:126`), in the outermost HTTP middleware. The other 93 production goroutines — plugin extension hooks (`Host.EmitEvent`, `FilterRegistry.Apply`, `TriggerDispatcher.sendWithRetry`), provider SSE readers (14 sites across `pkg/provider/*.go`), subprocess transports (`internal/mcp/stdio_transport.go:109`, `internal/plugin/subprocess/transport.go:107`, `manager.go:167/170/176`), chat generation (`generateResponse` spawned from `internal/service/chat.go:166/210/241` and `delegation.go:123`), background workers (`cmd/nanite/main.go:431/442/454/466`), event emission (`events_composite.go` + 14 call sites in `internal/api/`), memory extraction (`internal/memory/extraction.go:105/136`), workflow step handlers (`internal/workflow/executor.go:232`, `handlers.go:148`), and plugin catalog fetchers (`internal/plugin/catalog.go:102`) — all run without recover. The absence is total, not partial. There is no `safeInvoke` / `SafeGo` / `panicSafe` / `withRecover` helper in any form. Audits that found instances: plugin-system-plan-eval #04 (Host.EmitEvent), chat-engine #02 (generateResponse), mcp-client-transport (implicit: zero recover in internal/mcp/), panic-recovery-sweep 2026-04-11 (authoritative repo-wide map). **Concrete refactor proposal** from the sweep: a `internal/safego` primitive (`safego.Go(ctx, label, fn)` + `safego.Call(fn)`) wrapping every goroutine spawn and every plugin-code invocation in a recover + structured log + OTel event, enforced by a golangci-lint custom rule that forbids bare `go ` in specific packages. Orthogonal to the `internal/pathsafe.ResolveUnder` helper proposed by the dev-tools audit — both would benefit from being primitives the codebase can lint-enforce.
- **Trust boundaries that aren't validated.** A consistent set of trust boundaries — user messages, tool arguments, MCP tool results, plugin manifests, PTY input, project paths from `--project` — needs a reviewer-context "validate at every entry to" rule and a corresponding code-side validator pattern.
- **Tooling deferred across all five audits.** `go vet`, `-race`, `staticcheck`, `golangci-lint`, `govulncheck` not run anywhere yet. A single `tooling-and-tests-sweep` scope could cover the whole codebase in one pass.
- **Sandbox bypass via "trusted" callers.** `code_exec_tools.go` wraps in `sandbox.AgentExec`; `dev_bash` doesn't. The pattern of "this code path runs LLM-controlled input through the OS" exists in multiple places and consistency of sandbox wrapping is not enforced. Future audits should check whether any newly-introduced tool/handler wraps OS operations in `AgentExec`. A linter or codegen check would help.
- **Dead code claiming to be defense.** `scope_guard.go` + the entire `pkg/provider/event_pipeline.go` wrapper appear to be dead code that the project thought was its prompt-injection containment layer. Future audits should check whether other "defensive" components are actually wired into production paths — name in the source ≠ active in the call graph. Add an explicit check to the standard methodology: for any component flagged as a security control, grep for non-test callers before trusting its existence.
- **Content-channel vs. file-channel trust boundaries are TWO trust boundaries, not one.** Surfaced by `managed-section-parser` audit finding 01. The managed-section parser had a known file-side marker-injection bug (installer #03) but ALSO a symmetric content-side marker-injection bug that was not caught by the installer audit — `WriteManagedSection(path, content)` accepted any `content` including strings containing `<!-- nanite:end -->`. Every parser that wraps untrusted inner data in a structured format has both trust boundaries. Future reviewers: for any `Wrap(innerContent) → wrappedFormat` function, check BOTH whether `innerContent` can contain wrapper-format sentinels AND whether the wrapper-format can be confused by adjacent user data. Both require mitigation; installer #03's file-side count-markers guard does not close the content-side half.
- **Non-atomic file writes throughout the repo.** Managed-section-parser finding 03 + installer's own writes + adapter cleanup writes all use plain `os.WriteFile`. A torn-file-on-crash is possible on every one. **Concrete refactor proposal**: a `internal/fsutil.AtomicWriteFile(path, data, mode)` leaf primitive (write-to-temp + `os.Rename`, filesystem-aware on the rename being atomic). Orthogonal to the proposed `internal/pathsafe.ResolveUnder` (dev-tools), `internal/safego` (panic-recovery-sweep), and `internal/lifecycle` (concurrency-cancellation-sweep) primitives. All four are leaf utilities that should be introduced together and enforced via golangci-lint custom rules. The codebase is accumulating a set of missing primitives whose absence explains a significant fraction of findings — **introducing all four in one "primitives" PR would close the dominant finding classes repo-wide**.
