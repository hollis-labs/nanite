# CW-20260516-0061 — The 300s hang: findings

**Status:** Diagnosed. Root cause identified. No fix landed — the correct fix
is not a clean, bounded change and is recommended as a separate task (see
§5). This report is the deliverable.

**Investigated:** 2026-05-17, against `main` @ `f0cd92b`.

---

## 1. Summary

A subagent run (sync `task_execute` / `subagent_spawn`, and async
`subagent_spawn`) that hits a **silently stalled provider stream** consumes
the entire run-level timeout — 300s by default — before terminating, instead
of fast-failing.

The hang is **not** triggered by a provider error that surfaces promptly: that
path already fast-fails. It is triggered exclusively by a provider streaming
connection that goes **silent mid-response** — TCP open, no bytes, no error.
The only thing that ever interrupts that silence is the run-level context
deadline at exactly 300s.

This is consistent with the c242 evidence in the task comment:
`subagent_runs.completed_at == created_at + 300s exactly`, error =
`subagent: child chat loop emitted error event / Streaming error from
provider`, after "the child agent emitted only an opening line."

## 2. Root cause

The hang is the sum of four facts, none of which is individually a bug:

1. **`generateResponse` has no wall-clock deadline of its own.** The former
   5-minute deadline was deliberately removed in **CW-20260512-0006**
   (`internal/service/chat_generate.go:128-142`) because it killed legitimate
   long-running agent work. Cancellation now flows *only* through `ctx`.

2. **For a subagent, that `ctx` is the run-level timeout.**
   `subagent.Service.execute` (`internal/subagent/service.go:672`) wraps the
   runner ctx with `context.WithTimeout(ctx, run.TimeoutSeconds * time.Second)`
   — default `DefaultTimeoutSeconds = 300` (`service.go:23`).

3. **The provider stream consumption loop has no inactivity timeout.**
   `chat_generate.go:1269` is a bare `for evt := range provCh`. When the
   provider streaming connection stalls mid-response (no bytes, no error),
   `provCh` produces nothing and the loop blocks. The only wakeup is `ctx`
   cancellation — i.e. the 300s deadline from fact 2.

4. **`drainCapture` has no inactivity timeout either.**
   `internal/service/subagent_runner.go:114` is a bare `for evt := range ch`
   with no `select` on a timer or ctx. It cannot fast-fail on its own; it is
   entirely at the mercy of when `ch` produces an event or closes.
   `ch` is closed by `generateResponse`'s `defer close(ch)`
   (`chat_generate.go:179`) — which only runs once `generateResponse` returns,
   which (fact 1) only happens on `ctx` cancellation.

**Chain:** provider stalls → `provCh` silent → stream loop blocks → at 300s the
run ctx deadline fires → the provider adapter's ctx-aware read aborts and
surfaces as a stream `error` event → `chat_generate.go:1374-1375` emits
`"Streaming error from provider"` → `generateResponse` returns →
`defer close(ch)` → `drainCapture` returns `errStreamFailure` →
`execute` finalizes the row with `completed_at ≈ created_at + 300s`.

The reported error string is real, but it is a *symptom of the ctx-cancelled
read at 300s*, not an error the provider sent early.

## 3. Why a real provider error already fast-fails (not the bug)

When the provider emits an actual error event promptly, the stream loop's
`case "error"` (`chat_generate.go:1328`) fires, emits the error event onto
`ch` (lines 1374-1375), and returns. `drainCapture`'s `case "error",
"structured_error"` (`subagent_runner.go:134`) returns `errStreamFailure`
immediately — it does **not** wait for the channel to close.

This is verified by the regression test
`TestDrainCapture_FastFailsOnErrorEvent`
(`internal/service/subagent_runner_stall_test.go`): an `error` event on an
*open* channel returns immediately.

The bug is exclusively the **silent stall** — no error, no data — for which no
bound shorter than 300s exists. Verified by
`TestDrainCapture_NoIdleTimeout_OnSilentStall` in the same file: an opening
delta followed by silence blocks `drainCapture` indefinitely.

## 4. Symptom mapping

| Session | Mode | Observed | Mechanism |
|---|---|---|---|
| c209 | sync `task_execute` | calling turn hangs 300s, `[generation interrupted]` | `Spawn` runs `executeWithSlot` **inline** (`service.go:413`); the caller's turn is blocked on the Go call stack inside `execute` for the full 300s |
| c242 | async `subagent_spawn` | run wedges 300s; `completed_at == created_at + 300s` | calling turn returns immediately; the background `execute` goroutine burns 300s before finalizing |

The **subagent reaper** (`internal/subagent/reaper.go`) does **not** mitigate
either case: it flips timed-out DB rows to `failed`, but (a) it does not
cancel the in-flight runner goroutine, and (b) a sync caller is blocked on the
call stack, not polling the row — so the reaped row never unblocks it. The
reaper is crash/leak cleanup, not a hang shortener.

## 5. Recommended fix (separate task — not landed here)

### Rejected: idle timeout in `drainCapture`
`drainCapture` sees only high-level events (`delta` / `tool_call` /
`tool_result`). A legitimately long tool call — the task body's own smoke uses
`dev_bash` running `sleep 400` — produces a long gap between `tool_call` and
`tool_result` with no intermediate events. An idle timeout there would kill
legitimate long work: exactly the regression CW-20260512-0006 removed the
wall-clock deadline to avoid. **Wrong layer.** Same objection rules out simply
lowering `timeout_seconds`.

### Recommended: provider-stream inactivity timeout
Add an inactivity timeout to the **provider stream consumption loop**
(`chat_generate.go` around line 1269): a `time.Timer` reset on every `provCh`
event; on fire, treat it as a mid-stream provider error and reuse the existing
`case "error"` abort path (lines 1374-1379).

This is the correct layer because it bounds *time between bytes within a
single open provider stream*. It does **not** false-fire on long local tool
work: tool execution happens *between* provider streams, not during one — the
provider stream for the tool-use turn has already ended (`stream_end`) before
the tool runs. Arm the timer only while a provider stream is open
(`stream_start` → `stream_end`).

Implementation notes for the follow-up task:
- Make the threshold configurable in `internal/config/appconfig.go`
  (alongside `IdleTimeoutSeconds`); choose a **generous** default — on the
  order of 90-120s of zero provider activity — to stay clear of legitimate
  long time-to-first-token on thinking models and large-context prompts.
- This loop is shared by **all** sessions, not just subagents — treat it as a
  core-chat-loop change with the corresponding review bar.
- Optional hardening: have `Cancel` / the reaper actively cancel the in-flight
  runner's context so a reaped row also unblocks the runner goroutine
  promptly, not just the DB row.

### Scope note
The fix touches the core chat streaming loop in a 3000-line file, affects every
session, and the threshold is a judgment call with real false-positive risk.
Per this task's diagnose-first guidance it is **not** a clean, bounded change
to land unilaterally — it warrants its own task with provider-layer review.
