# Glossary

Canonical definitions for terms used throughout Nanite's engineering docs and code. This file exists specifically because this codebase has a documented history of naming collisions (the same word meaning two unrelated things in two subsystems) causing real bugs and real confusion — for humans and for agents working on the codebase. When in doubt about what a term means here, this file wins over inference from context or memory of an older doc.

If you're an agent about to introduce new vocabulary, check this file first. Generic words (`status`, `scope`, `run`, `slot`) are fine to reuse across subsystems — the failure mode this file exists to prevent is an *unqualified* reuse that reads as one thing but means another. **Prefer namespacing over inventing a new word.** `Turn.Cancel` vs. `Run.Cancel`, and `Team Slot` vs. Context Broker slot, are each two real, coexisting meanings that stay unambiguous only because the owner is always spelled out — never written bare where both are in play. Reach for a genuinely different word only when the two concepts are close enough in *meaning*, not just in name, that even a namespaced form would still mislead — and add a disambiguation entry here either way.

---

**Agent** — a composed identity: a `role` (persona/system prompt) bound to a `scope` (project/data-source reference) plus tool/skill/permission grants, resolved through a cascading override (role → agent → task, closest wins). Not a flat, standalone definition — see `architecture/01-agent-construction.md`. Distinct from a *Claude Code subagent* (the Task/Agent tool mechanism used to run sessions like this one) and from the unrelated `.nanite/config.yaml`/`~/.nanite/roles/` developer-persona-boot convention used for working *on* this codebase — neither of those participates in Nanite's own runtime agent system.

**Role** — the reusable persona/behavior template an Agent is built from: name, system prompt, and optional defaults. Many Agents (different scopes) can share one Role.

**Scope** — a reference from an Agent composition to something that already exists independently (a project, eventually a data source or dataset) — not a new facet catalog of its own. Answers "where/what does this agent apply to," not "who is it."

**Team** — a saved, named, reusable organizational shape: Team Slots (below), authority, routing, and a phase/gate sequence, persisted in the `teams` table (`internal/store/teams.go`). The same `Role` → `Agent` pattern one level up, applied to *groups* rather than individuals — see `architecture/15-teams.md`. Deliberately **not** inserted into the existing `role → agent → task` cascade (see **Agent**, above); a Team Slot sits beside that cascade and resolves *into* it. A caller launches "against" a saved Team by name with invocation-time overrides, the same "closest wins" cascade shape Agent Construction already uses — no new persistent Team definition is required per launch.

**Team Slot** — one organizational role within a Team (e.g. "architect," "engineer," "reviewer"), decoded from `teams.slots_json` into a `TeamSlotDefinition` (`internal/store/teams.go`). **Always spelled out as "Team Slot" — never a bare `Slot`/`slot`.** `internal/context/slot.go` already defines an established, unrelated, load-bearing "slot" concept: `SlotOrder`, the Context Broker's own prompt-assembly ordering (one of six invariants documented in `internal/context/INVARIANTS.md`, "universal slot at position 0"). A Team Slot is an organizational role that resolves to a concrete `(agent_id, session_id)` tuple at TeamRun launch; a Context Broker slot is a named position (system/agent/rules/conversation/etc.) in the assembled LLM turn payload. Same word, two unrelated meanings, in two already-load-bearing subsystems — **"slot" alone is ambiguous in this codebase going forward; always qualify which one you mean** ("Team Slot" vs. "Context Broker slot"/`SlotOrder`).

**TeamRun** — a Team's launched execution instance. Not a new run engine or a new persistence path: a Team's phase/gate sequence compiles, at launch, into an ordinary `WorkflowDefinition`, and TeamRun *is* the resulting `WorkflowRun` (`workflow_runs`/`workflow_run_steps`) — one run engine, reusing `durable_agent_instances`' event-log machinery, the same framing `WorkflowLauncher` already uses elsewhere. See `architecture/15-teams.md`, Decision 2.

**Consumer** — the ownership/tenancy tag on an Agent (`agents.consumer_id`). Identifies which external system an agent belongs to (e.g. Loom owns Curator) without giving that system its own isolated database instance. Distinct from **Instance** (below).

**Instance** — a fully separate, isolated Nanite data directory/database (formerly and confusingly called "workspace" at the filesystem level, via `NANITE_WORKSPACE`). Full isolation, not a tenancy tag — a different tool for a different job than Consumer. Currently only ever has one value in practice; the in-app `workspaces` table (an unrelated, UI session-grouping concept that shared the same word) has been retired.

**Runtime kind** — the typed field (`agents.runtime_kind`: `cli` | `api`) that decides whether an agent runs as a CLI-based subprocess or via a direct HTTP provider call. Replaces four scattered string-prefix-matching call sites that used to make this decision independently.

**Protocol / Transport** — the typed field pair (`agent_profiles.protocol`/`.transport`) that selects which wire protocol/transport pairing a CLI-based-subprocess agent's process actually launches through, once `runtime_kind` has already routed it into the CLI runtime. Orthogonal to **Runtime kind**, not a replacement for it — an ACP-configured agent (`protocol='acp'`) still carries `runtime_kind='cli'` unchanged. `Protocol` values: empty (native — this provider's existing wire format), `claude-stream-json`, `codex-app-server`, `opencode-native`, or `acp`; `transport` (`stdio`/`tcp`) only applies when `protocol='acp'`. See `architecture/17-acp.md` and `TASKS/agent-host-acp/11-nanite-per-agent-protocol-transport-config.md`.

**CLI-based subprocess** (never "PTY") — a long-lived (Claude, via `StreamingStdio` — NDJSON over stdin/stdout pipes) or per-turn (Codex, OpenCode) subprocess Nanite spawns and manages. **There is no real pseudo-terminal anywhere in the current runtime.** "PTY" is a naming fossil surviving in a few provider-name strings and function names (`shouldUsePTY`, `pty-*` provider aliases) that are being scrubbed. If you see "PTY" in an older doc or comment, mentally substitute "CLI-based subprocess."

**Harness** — the shared turn-loop mechanics (`generateResponse`) every launched agent runs through regardless of entry point: context assembly, the provider round-trip, the tool-use loop, termination, persistence. One shared execution path — chat, subagent dispatch, and durable-agent wake all converge on it via a `CallerType`-tagged dispatcher.

**Turn** vs. **Run** — two levels of the harness's tool-settling loop, both real, both namespaced rather than merged: a **Turn** is one model invocation + stream + tool-call production + return control (`ls.iteration` in `chat_loop_state.go`); a **Run** is repeated Turns + tool settlement + continuation policy + completion (`generateResponse` as a whole). No separate name for the inner unit existed before this split — `chat_loop_state.go`'s own vocabulary (`MaxTurns`, `TerminationMaxTurns`) named the *outer* loop "Turn," which is now understood to be a Run. See `architecture/22-turn-vs-run.md`. **A second, unrelated "Run" also exists in this codebase and is not this entry:** `WorkflowRun`/`TeamRun`/`LoopRun` name *persisted, multi-step orchestration instances* (see **TeamRun** and **LoopRun**, this file) — a different altitude than the harness's in-process tool-settling loop. Same word, two coexisting meanings, same discipline as **Team Slot** vs. Context Broker slot (below): never used bare where ambiguous, always qualified by which one is meant.

**Turn.Cancel** vs. **Run.Cancel** vs. **Session.Stop** vs. **`interrupt.requested`/`interrupt.acknowledged`** vs. ACP's **`session/cancel`** — related-but-distinct operations spanning three layers; easy to conflate (this codebase's own architecture review did, once). **Run.Cancel** (currently named `CancelActiveGeneration`, `internal/service/chat.go`, still under its old name `Turn.Cancel` in code/comments — the rename to `Run.Cancel` is recommended but not yet executed, see `architecture/22-turn-vs-run.md`) stops Nanite from listening to/displaying the *current Run's* stream; for a CLI-hosted agent it deliberately does not touch the underlying process — the agent may still be useful for the next Run. **Turn.Cancel** (finer-grained: cancel just the current model call) is real vocabulary now that the Turn/Run split exists, but is not yet built — no current mechanism cancels at Turn granularity. **Session.Stop** (`internal/runtime/agent/manager.go`) terminates the *whole runtime process*, called only from explicit session-termination flows (reboot, cleanup, recovery), never from per-Run cancellation. **`interrupt.requested`/`interrupt.acknowledged`** (`go-runtime-events`) is the host-layer event pair `Session.Stop` emits around its own work — not something a caller invokes directly. ACP's **`session/cancel`** method, despite its name, is spec'd as Run-scoped (cancels the in-flight prompt; the session survives) — it must map onto Run.Cancel, never onto Session.Stop, wherever the ACP client abstraction implements it. See `architecture/16-agent-host.md`, `17-acp.md`, `19-api-cli-runtime-parity.md`, `22-turn-vs-run.md`.

**Steering** — the layer that decides what an agent does moment to moment. Consolidating onto **Reflexes** as the single primitive (see below) — the older five-layer system (agent broker, strategy planner, tool broker, skill broker, plus reflexes) is being retired down to just reflexes plus the plain tool/skill catalogs underneath.

**Reflexes** (`internal/agent/reflexes`) — the one real steering primitive going forward. A DB-backed, non-LLM predicate/event/interval rule engine: it watches session-state signals and, when a trigger fires, injects a reminder, nudges a tool choice, sends a message, adds a schedule, dispatches to another agent (`dispatch_to_agent`), or halts a session. The model never decides whether a reflex fires. Historically confused with **promptrouter** (below, retired) — the promptrouter package was literally named `internal/reflex` until it was renamed specifically to stop the collision; promptrouter's own phrase-matching job was later migrated onto this package's `dispatch_to_agent` predicates (`TASKS/phase-4/03-migrate-promptrouter-to-reflexes.md`), so the two-systems confusion this note used to warn about no longer has two live sides.

**Harness-reactive self-tools** (`internal/selftools`) — a sibling mechanism to Reflexes, not a Reflex action kind: a small, purpose-built `nanite_*`-namespace self-tool whose own call *is* the trigger (no predicate/event/interval to evaluate), where the harness decides whether/how to react — render a card, call an internal API, call an external API, invoke a callback, some combination, or nothing. See `docs/engineering/architecture/11-harness-reactive-self-tools.md`. Do not call this "event" or "notify" — both already mean something else in this codebase (see those entries below).

**Self-tool reaction** (`internal/selftools/reactions`) — the harness-side engine resolving a harness-reactive self-tool's DB-backed category/kind into an effect (`render_card`, `internal_api_call`, `external_api_call`, `callback`). Deliberately not named "action" — that word is already claimed by **Reflexes**' own `action_kind`/`AppliedAction`/`Executor.Apply` vocabulary (below); reusing it here would reintroduce the exact collision this glossary exists to prevent.

**promptrouter** — **retired** (`TASKS/phase-4/03-migrate-promptrouter-to-reflexes.md`; `internal/promptrouter` no longer exists). Was a deterministic phrase-match router, formerly (confusingly) named `internal/reflex`. Its phrase-matching job was absorbed into **Reflexes** (above) as `dispatch_to_agent` trigger/action rows (`internal/agent/reflexes/seeds.go`) rather than staying a separate system. Kept here as a glossary entry (not deleted) so the term still resolves for anyone reading an older doc, commit message, or CW ticket that names it.

**Cards** (formerly "the envelope system," as a subsystem name) — the structured, interactive UI-card system agents use to present rich content to a user (tables, approvals, diffs, forms) instead of raw prose. **Envelope** stays scoped narrowly to the wire/transport shape (the JSON wrapper a Card rides inside); **Card** is the rendered UI system built on top of it. A Card may internally be composed of smaller elements — that's a legitimate place for composition vocabulary later, without colliding with the system-level name.

**Envelope** — the wire-protocol wrapper (`kind`, `version`, `type`, `data`) a Card rides inside on its way from backend to frontend. Transport shape only — not the name of the UI system itself (see Cards).

**A2A** (Agent2Agent) — the real, external, Linux Foundation open protocol (a2a-protocol.org) for cross-vendor/cross-framework agent interop — for callers with *zero* Nanite-specific knowledge. Distinct from and not a duplicate of MCP (below): MCP requires the caller to already know Nanite-specific tool names; A2A doesn't. Also distinct from Nanite's own internal agent-to-agent messaging (`agent_messages`, briefly and confusingly also once called "a2a" before an April rename — see `internal/messaging` below).

**MCP** — the single external door for Nanite-aware external consumers (e.g. Loom). Chosen for industry standardization (one auth model, one discovery contract), not to avoid engineering cost.

**`internal/messaging`** (`agent_messages` table) — Nanite's real, actively-used internal messaging primitive: tuple-addressed `(session_id, agent_id) → (session_id, agent_id)` messages, used for subagent replies, notifications, and human-agent communication. Not A2A (see above) despite an old, now-corrected naming collision.

**Consumer** vs. **Instance** — see above; don't conflate. Consumer = who owns this agent (shared DB, lightweight tag). Instance = a fully separate database/data directory (full isolation, single-operator dev/test tool, not a tenancy mechanism).

**Recovery** (`internal/recovery/*`, being consolidated into this namespace) — four genuinely distinct mechanisms answering different "what went wrong" questions: the **Recovery Broker** (in-process crash while the daemon is alive), the **Orphan/Runtime Reaper** (reconciling stale process state after a daemon restart), the **Recovery Pack** (replaying trailing context into a freshly cold-booted session), and **interrupted-turn detection** (a cheap, read-only frontend signal). Not redundant with each other — each covers a different failure shape.

**Compaction** — the escalating, budget-driven pipeline that shrinks an over-budget conversation (drop enrichment → dedupe tool results → summarize oldest span → strip tool blocks). Distinct from a **Handoff** (below).

**Glass-4 handoff** — the agent-self-authored continuity snapshot (`session_intent`, recent decisions, an anchor for the next step) written before compaction and re-injected after. Being made universal (every session, not just ones classified "long-running" — that classifier is being cut alongside this change).

**Snapshot (filesystem)** (`libs/go-agent-wrapper`'s `snapshot` package: `FilesystemSnapshotProvider`, `ShadowGit`) — the undo/audit primitive for the on-disk filesystem content an agent's granted paths hold: capture a project tree before/after a model step, diff two captures, preview and selectively restore specific paths. Lives in the host — `libs/go-agent-wrapper`, a sibling repo to this one, not Nanite itself — see `docs/engineering/architecture/18-filesystem-snapshots.md`. Two other things are also reachable by the bare word "snapshot" in this codebase, and this entry is neither of them: (1) **`checkpoint`** (`agentkit/agentruntime/checkpoint`; Tether's "resume a logical agent from its checkpoint") is a provider-session *resume hint* — native-resume vs. fresh-boot vs. unsupported — with zero filesystem awareness; this feature deliberately never reuses that word, and "checkpoint" must never be used for filesystem state. (2) **Glass-4 handoff**'s own definition (above) uses the plain word "snapshot" loosely for its agent-self-authored *continuity* artifact (`session_intent`, recent decisions) — a conversation/session-timeline concept, not a filesystem one. The two timelines are deliberately never coupled at the data layer: Nanite's session-state machinery has zero filesystem awareness today, and this feature is designed to keep it that way — a UI is free to *correlate* the two ("restore files touched after this point in the conversation") without the underlying data model doing so. Going forward, an unqualified "snapshot" in a filesystem-state context means this entry.

**Scratchpad** — an agent's own working-notes tool. Its value is the *act* of an agent externalizing its reasoning, not the content persisting afterward — being usually-empty is expected, not a defect. Not a continuity mechanism (that's Glass-4's job) — don't conflate the two.

**Session handoff** (`handoff_request`/`_approve`/`_reject`, `session_handoffs`/`session_agents`) — rebinding which agent is a session's primary agent. Pure routing/authorization, carries no memory content. Distinct from **Glass-4 handoff** (above) despite sharing the word "handoff" — see `architecture/13-memory-and-knowledge-tools.md` §2 for the full disambiguation.

**Plugin** — code outside `internal/` that extends Nanite: either a compiled-in **builtin** (a Go struct in the binary) or a separate **subprocess** (JSON-RPC over stdio). Both describe what they register via a `plugin.yaml` manifest read by one shared host-side registration path, so builtin and subprocess plugins wire in identically.

**Filters / Hooks** — the plugin extension points already reaching deep into the turn loop (`FilterUserMessage`, `FilterSystemPrompt`, `FilterContextWindow`, `FilterToolResult`, `FilterAssistantResponse`, `FilterEnvelopeData`) and reflexes (`FilterReflexState`, `FilterReflexAction`), plus lifecycle events (session archived, agent switched, artifact created, etc.). Functionally Nanite's middleware-equivalent for the chat-turn domain, just named differently than the HTTP layer's actual `net/http` middleware chain.

**Middleware** — currently exists only at the HTTP-transport layer (`internal/server/server.go`'s real, standard `net/http` chain: recover → logging → CORS → auth → caller-identity → body-limit). Not currently plugin-extensible. Not a separate concept from Filters/Hooks — same underlying pattern (composable interceptors around a core operation), applied to a different layer.

**Boot-profile catalog** — retired as a standalone system (its job was solved more cleanly by the Agent construction model). Two pieces carried forward as first-class mechanisms: the `cmd`/`http` dynamic-context-resolver capability, and the mandatory post-compaction re-read of a project's real `CLAUDE.md`/`AGENTS.md`.

**Tether** — a sibling app in the operator's portfolio that originated both the boot-profile-catalog pattern (`bootgen`) and an earlier, pre-standardization A2A-host experiment. Cross-app portability with Tether is deliberately opt-in, not a structural default of Nanite's own operation.

**"Workspace"** — historically ambiguous, now resolved: the in-app UI-grouping concept (a `workspaces` table) is retired. The filesystem-level multi-database concept is renamed **Instance** (see above) and scoped narrowly to dev/test isolation.

**Goal** — a first-class, persisted target state (`goals` table) with its own lifecycle (`draft` → `defined` → `active` → `blocked`/`satisfied`/`failed`/`cancelled`/`superseded`), independent of any one execution. A Goal can exist before a Loop launches against it and can outlive a single `LoopRun` (survives a REPLAN, an abandon-and-restart, or decomposition into subgoals via `parent_goal_id`). See `architecture/21-loops.md`, Decision 2.

**Loop** (`internal/loop`) — a goal-driven control layer that orchestrates a sequence of ordinary `WorkflowRun`s toward a **Goal**'s target state, evaluating each iteration (reusing `agentworkflow`'s `Verify`) and deciding what happens next (`CONTINUE`/`RETRY`/`REPLAN`/`REARCHITECT`/`WAIT`/`ESCALATE`/`COMPLETE`/`FAIL`) via a deterministic-first continuation policy. Not a second workflow engine — `agentworkflow` stays DAG-only, no cycles; see `architecture/21-loops.md`. **Two other things are also reachable by the bare word "loop" in this codebase, and this entry is neither of them:** (1) the harness's own per-turn tool-call loop (`reason → act → observe → reason`, guarded against runaway repetition by `internal/loopdetect`) — an existing mechanism *within* one agent turn, not this control layer; (2) legacy `internal/workflow.LoopStep` — a narrow, deterministic-only (no LLM) "repeat a step until a gate passes or max iterations" primitive in the older generic YAML pipeline runner, a different mechanism for a different audience, not retired or replaced by this entry. Going forward, an unqualified "Loop" in an agentic/goal-driven context means this entry.

**LoopRun** — a Loop's launched execution instance, persisted in `loop_runs`. Deliberately **not** a `WorkflowRun` the way **TeamRun** is (contrast above) — a Loop's plan can change shape between iterations (REPLAN/REARCHITECT), which `agentworkflow`'s static DAG can't represent. `LoopRun` instead orchestrates a *sequence* of `WorkflowRun`s, each an ordinary, unmodified execution. A Workflow may contain a Loop via `StepKindLoop`, reusing `StepKindGate`/`StepKindFlex`'s existing pause/`Resume` plumbing (`RunStatusWaitingOnLoop`, a distinct status from `waiting_on_gate`/`waiting_on_flex` for the same reason those two are distinct from each other).

**Skill** — an authored, Agent-Skills-spec-compatible package (`SKILL.md` plus optional `scripts/`, `references/`, `assets/`), installed explicitly and indexed in Nanite as one **Skill catalog** row plus its vendored bytes in the **Skill vendor store** (both below). General, agent-independent capability content — not a per-agent behavior/SOP. Distinct from a **Procedure** (role-specific SOPs, `agent_procedures`) — the boundary is settled in `architecture/13-memory-and-knowledge-tools.md` §4a and unchanged by the Skills redesign (`architecture/20-skills.md`, `TASKS/skills/`). **A "Skill" in this codebase is not a bare *Claude Code Skill* file in isolation** — it's Nanite's DB-indexed, vendored wrapper around one: the filesystem package is the portable, spec-compliant artifact an operator authors or imports; Nanite's own row/vendored-copy pair is what makes that artifact addressable, versioned, enabled/disabled, and grantable inside this system. Also distinct from the pre-redesign meaning of `skills` table rows created by `mcp.Manager.AutoDiscover` (one row per visible tool, `category="auto-discovered"`) — that mechanism is cut in full (`TASKS/skills/01`); a Skill going forward means exactly the authored-package meaning in this entry, never a tool wrapper.

**Skill catalog** — the `skills` table/index (`internal/store/skills.go`): one global row per installed Skill package, purely an index (vendored-store address/content hash, version, source tier, enablement, declared dependencies) — it never holds `SKILL.md` body text, script contents, or asset bytes (see **Skill vendor store**, below, for where those actually live). Not itself a per-agent concept — a catalog row exists independent of any agent being granted access to it; see **Skill attachment** for that distinction.

**Skill attachment** — `agent_known_skills`: the per-agent grant/telemetry table recording that a given agent has been granted a Skill (plus activation telemetry — `pinned`/`activation_count`/`last_used_at`/`ttl_seconds`/`reason` — and, from `TASKS/skills/02` onward, grant-state columns `approved_content_hash`/`granted_at`/`granted_by`/`capabilities_granted`). Distinct from mere **Skill catalog** presence: a Skill can exist in the catalog with zero agents attached to it. `docs/engineering/architecture/13-memory-and-knowledge-tools.md` §4a cites this exact table (paired with the Skill catalog) as "a genuine catalog+attachment split — the reference pattern" a sibling Procedures redesign should mirror. Confirmed live: a real REST CRUD API (`internal/api/agent_capabilities.go`, `GET/POST/PUT/DELETE /api/agents/{id}/known-skills...`) and two frontend surfaces (the Agent Builder Wizard's submit-time seeding loop, the standalone Agent Capabilities Panel) read/write this table today — not dead, only ever dead for prompt assembly (`TASKS/phase-0/17`). The now-dropped `agent_skills` table (a separate, FK-enforced agent↔skill join table, confirmed zero rows workspace-wide) is not this entry and no longer exists (`TASKS/skills/02`) — `ListAgentSkills`/`AssignSkillToAgent`/`RemoveSkillFromAgent` (`internal/store/skills.go`) are rewired onto this table instead, keyed by the Skill's slug.

**Skill vendor store** (`internal/skillvendor`) — the content-addressed, filesystem-rooted store holding installed skill packages' actual bytes (`SKILL.md` body plus optional `scripts/`, `references/`, `assets/` subdirectories). Address format `skl-vendor-<sha256-prefix[:16]>` — deliberately a different prefix family from `internal/contextbroker`'s stash-artifact `art-stash-<hash>` addresses (see that entry's neighbor, `DeterministicArtifactID`) so the two content-addressed systems are never confused when debugging; they solve unrelated problems (oversized slot-content caching vs. vendoring an operator-authored package) and happen to share only the underlying hash-the-bytes technique. An address is a hash of the *whole tree* (every relative path + its file's bytes, sorted for determinism), not a single string, so a skill package's tree shape is as load-bearing to its identity as its content. Immutable once written — there is no "update this address" operation, only a fresh write (which always produces a different address if the content differs) or a full `Delete` (uninstall). Config root: `config.AppConfig.Skills.VendorStorageDir` (mirrors `Artifacts.StorageDir`'s existing load/default/override convention). This is the "vendored store" `docs/engineering/architecture/20-skills.md`'s "The model" section describes: the `skills` index table (row shape defined by `TASKS/skills/02`'s **Skill catalog** work, and its per-agent **Skill attachment** counterpart in `agent_known_skills`) holds only the pointer (address + hash) into this store — never `SKILL.md` body text, script contents, or asset bytes directly. Materialization (`TASKS/skills/06`) always reads this store live, every time a skill is used, rather than trusting a value cached in the DB at install time — see `13-memory-and-knowledge-tools.md` §4a for the sibling Skill/Procedure catalog+attachment split this store's index row participates in.

**Skill Resolver** (`internal/skill/resolver.go`, `TASKS/skills/06`) — the parameter-binding and nested-dependency-address-lookup half of `20-skills.md`'s Materialization pipeline: *"Skill Resolver → Skill Materializer → Policy/Sandbox → Materialized Skill."* Two building blocks, both real, both narrow by design: `ResolveSkillParameters` takes a skill's declared `Parameters` (task 04's `[]ParameterSpec`) plus a caller's invocation-time static arguments and produces the flat parameter-value map a **Skill Materializer** (below) will splice into the skill's final rendered output; `ResolveDependencyAddresses` takes a skill's `DeclaredDependencies` (the **Skill catalog** column) and resolves each declared dependency slug, one level only, to its own installed **Skill catalog** row and **Skill vendor store** address. **Not a second resolver-provider system**: a parameter's dynamic value comes from an existing `agent_context_resolvers` row — looked up by that row's `slot_name` matching the parameter's `ParameterSpec.ResolverSlot` (a semantic correlation between two differently-named, differently-tagged Go fields, never a literal name match) — and is resolved through the exact same `internal/runtime/agent.ResolveContextBlocks` function every other dynamic-context consumer in this codebase already calls. The Skill Resolver *wraps* `agent_context_resolvers`; it is not a replacement for it and implements no cmd/http execution logic of its own. Precedence: a caller-supplied static argument always overrides a `ResolverSlot` dynamic binding when both are present for the same parameter. Failure semantics mirror `ResolveContextBlocks`'s own all-or-nothing contract — one matching resolver row's failure aborts the whole `ResolveSkillParameters` call, with no partial-success mode layered on top. Same "Team Slot"-style disambiguation discipline as elsewhere in this file: the **Skill Resolver** (this entry — binds parameters and looks up dependency addresses, a pure function of already-parsed input) is distinct from the still-unbuilt **Skill Materializer** (`TASKS/skills/07`/`08` — composition semantics for `inline`/`fork`, plus script/marker execution under the policy/sandbox gate) the pipeline's own name places immediately after it; this entry's functions never compose, execute, or render anything themselves. Also distinct from install-time cycle/recursion-limit detection against the full installed-dependency graph, which `20-skills.md`'s own text places on the Skill Resolver conceptually but which task `07`'s Installer-pipeline extension actually implements — `ResolveDependencyAddresses` here is the single-call building block that graph-level logic runs on top of, not a graph walker itself.

**Skill Materializer** — the second half of `20-skills.md`'s Materialization pipeline, immediately after the **Skill Resolver** (above): takes a Resolver-produced parameter map plus a resolved dependency address and produces a skill's final materialized output. Two distinct provider families land under this one name, each its own task, each its own file — not one monolithic implementation: **composition** (`internal/skill/compose.go`, `TASKS/skills/07`) gives the `Context: "inline"|"fork"` frontmatter field its real semantics — `inline` recursively materializes a resolved dependency (its own parameters resolved, its own further dependencies handled the same way) and splices the result into the parent's output; `fork` instead delegates that already-materialized nested content to a real subagent turn (`internal/subagent.Service.Spawn`/`.Status`, `ModeSync` — the exact same live, mid-conversation mechanism the `subagent_spawn` self-tool rides, not a new spawning mechanism) and folds back only that invocation's terminal, persisted `Run.ResultJSON`, never its full transcript. Which mode applies to a given dependency is read from *that dependency's own* `Context` field (re-parsed from its vendored `SKILL.md` at materialization time, per the vendor store's own "always reads live" contract) — `Context` is a per-package, self-declared "how do I want to be composed when someone else includes me" attribute, not a per-declaring-parent annotation. **Inline deterministic execution and `scripts/` execution** (`internal/skill/exec.go`, `TASKS/skills/08`) is a separate provider covering the rebuilt, code-fence-aware `` !`cmd` `` marker and package-shipped script files, gated by `TASKS/skills/09`'s policy/sandbox layer — composition and script/marker execution are deliberately kept as separate concerns/files per `20-skills.md`'s own framing, sharing only the "Skill Materializer" name for the pipeline stage they both occupy. A `ProvenanceChain` (`internal/skill/compose.go`) tracks the root-skill → nested-skill segment of `20-skills.md`'s full provenance chain (*"user → agent → root skill → nested skill → script/materializer → requested capability"*) — the user/agent segment is the caller's own context, and the script/materializer → requested capability segment is task 08/09's concern for whatever executes *within* a materialized body, not composition's own job. Cycle/recursion-limit detection against the composition graph is **not** part of the Skill Materializer at all — per `20-skills.md`'s explicit instruction, that check runs once, at install/sync time, in `internal/skillinstall` (`checkDependencyGraph`, `DefaultMaxDependencyDepth = 5`, task 07's other half), against the graph of already-installed skills' own `DeclaredDependencies` — never discovered live during a materialization pass. `internal/skill/compose.go`'s own `maxCompositionDepth` constant mirrors that same limit purely as a defensive runtime backstop, not the primary enforcement.

**Skill capability gate** (`internal/skill/gate.go`'s `Gate`, `TASKS/skills/09`) — the "Policy/Sandbox" stage of `20-skills.md`'s Materialization pipeline (*"Skill Resolver → Skill Materializer → Policy/Sandbox → Materialized Skill"*), and the sole implementation of `exec.go`'s (`TASKS/skills/08`) `GatedExecutor` interface in production — every `` !`cmd` `` marker and `scripts/` file execution `ResolveInlineMarkers`/`ExecuteScript` performs routes through exactly this gate, never `sandbox.Apply` directly. **Not** the still-dormant `go-agent-wrapper` `policy.Engine`/`policy.Store` mechanism `architecture/16-agent-host.md` documents for CLI tool-call interception — that mechanism has `wrapper.Config.Policy` unset everywhere in Nanite today, so this gate is narrow, direct enforcement at its own call site instead, not a consumer of that dormant pipeline (see `TASKS/skills/09`'s own Context section, and `TASKS/plugin-system/06`'s independent, same-reasoning capability-enforcement-at-rpc-proxy-layer sibling). Looks up the invoking agent's `agent_known_skills` grant row (**Skill attachment**, above) keyed by `(agent_id, skill_slug)`, refuses outright (no ambient capability) when no grant row exists or the row has never been approved (`ApprovedContentHash` empty), refuses with a distinct re-approval-required error when the grant's `ApprovedContentHash` no longer matches the **Skill catalog** row's current `ContentHash` (a re-install since approval), and otherwise composes a `go-sandbox` `sandbox.Profile` from the grant's `capabilities_granted` JSON (this gate's own typed `Capabilities` shape — `FS`/`Network`/`SubprocessSpawn`, each mapped directly onto a real, enforceable `sandbox.Profile` field, deliberately omitting an "environment-secret-access" capability the library has no field to back) and calls `sandbox.Apply` for real. Independent of that grantable vocabulary, every execution's inherited environment is unconditionally stripped of secret-shaped variable names (`Gate.run`'s `filterSecretEnv`, mirroring `internal/sandbox`'s own `filterSecrets` pattern as a local copy) before `sandbox.Apply` is ever called — a floor no grant can widen back open, added post-landing to close a real secret-exfiltration bug a fresh review found (`TASKS/skills/09`'s "Fix required"/"Fix applied" sections). Decisions are logged (never returned through `GatedExecutor`'s fixed signature) in a `GateDecision` shape that loosely mirrors `go-agent-wrapper/policy.Decision`'s `Mode` taxonomy (observe/nudge/rewrite/block/approval) for future-compatibility only — no code is shared with that dormant package.
