# Agent Host

## The problem this names, not invents

Nanite, Tether, and Torque each launch CLI agents (Claude, Codex, OpenCode) almost identically — spawn a subprocess, own its stdio, stage a boot directory, apply an OS sandbox, compose env, and turn whatever comes back over the wire into something a product can react to. This doc doesn't propose building that layer. It names the boundary that layer must have, audits the closest existing candidate against it, and — per operator alignment on this review — treats adopting that candidate as the working direction.

**Implementation status**: this is no longer a proposal awaiting a planner — `TASKS/agent-host-acp/` is executing it now (Phase 1-2, the host migration itself, substantially landed; Phase 3-5, ACP client work, in progress). That folder's `README.md` is the authoritative, current tracker; it also corrected several claims in this doc's original audit against the live code during its own planning pass — where the two disagree, the task folder wins. The sections below are left as the original review's reasoning and evidence, with corrections noted inline rather than silently rewritten, so the "why" stays legible even as the "current state" moves past it.

## The boundary

A host owns: process spawn/supervision, stdio ownership (parsing whatever wire protocol flows over it), boot-dir/workspace staging and file planting (`CLAUDE.md`/`AGENTS.md`/`.mcp.json`/provider settings/hooks), OS-level sandbox application, filesystem snapshot mechanics for the sandbox's own granted paths (capture/diff/preview/restore — see [18-filesystem-snapshots.md](18-filesystem-snapshots.md)), env composition, the protocol adapter (bytes on the wire ↔ a normalized event stream, commands back down), realtime activity normalization (one event vocabulary regardless of provider), cooperative-cancellation signaling, and process-tree cleanup. This forms a safety/recovery ladder with a different mechanism at each rung — prompt/reflex hint → permission enforcement → sandbox restriction → cooperative cancel → process kill → filesystem restore — each answering a different failure mode, not a redundant stack.

A host does not own: why the agent is running, session/task/team semantics, persistence schema, lifecycle policy (when to fire the first turn, when to stop, whether to attach a supervisor), permission/gate business rules, chat/harness turn-loop mechanics, or product identity (agent roles, skills content). This is the same line this codebase already draws elsewhere — "abstract the intent, not the capability away" and "prefer composition over a feature-specific mechanism" ([00-overview.md](00-overview.md)) — applied to the launch layer instead of the tool/memory layer.

The same split applies one level down, inside enforcement mechanics: **the host owns the interception mechanism (observe a command/tool-call, ask a policy engine, apply the verdict); the product owns the actual policy (which rule fired, what it means, who's allowed to do what).** `go-agent-wrapper`'s `policy/` package already draws this line correctly in code, not just in principle — `policy.Engine.Decide` is the mechanism the host runs at every interception point, but `policy.Store` (the rule backing: YAML, SQLite, a central admin service, whatever an app wants) is explicitly "app-provided... the wrapper does not own storage." Worth stating as an explicit rule here rather than leaving it implicit: if a future change ever moved actual business rules (e.g., "engineers cannot merge without review") into the host itself rather than into an app-supplied `Store`, that would violate this boundary the same way a lifecycle-policy leak would.

## What already exists

This isn't greenfield. The portfolio already has four tiers:

- **Primitive**: `go-providers` (`CLIAdapter`: `Name`/`BuildArgs`/`ParseLine`/`Detect`, concrete Claude/Codex/OpenCode adapters — file names still carry a `pty_*` naming fossil mid-scrub, same pattern flagged in [02-agent-launching.md](02-agent-launching.md)), `go-sandbox` (`Profile`+`Apply`, macOS `sandbox-exec` / Linux `bwrap`), `go-runner` (spawn+sandbox+parse composition, emits only raw process-lifecycle events — deliberately opaque to app vocabulary).
- **Composition**: `agentkit` (the 2026-05-26 consolidation of `go-agent-context`/`go-agent-launch`/`go-agent-sessions`/`go-agent-runtime`/`go-agent-broker`) — `agentlaunch`'s `LaunchPlan → CompiledLaunch → PreparedLaunch` pipeline and bootdir materialization, `agentsessions`' `Session` (`Wait`/`Stop`/`SendInput`/`Resize`/`Health`) over PTY/streaming-stdio/jsonrpc-stdio/serve-http backends, `agentcontext`'s typed slot-resolver boot-prompt assembly. **Nanite already depends on this directly** — `internal/runtime/agent/*.go` imports `agentkit/agentsessions`, `agentkit/agentlaunch`, `agentkit/agentcontext`, `agentkit/agentruntime/runtimekind` at v0.3.0, as does `internal/recovery/broker`. So does Tether, Torque, agent-mux, clockwork-manifold, and Hadron.
- **Normalization**: `go-runtime-events` — a portfolio-wide typed vocabulary (`session.ready/idle/processing/heartbeat`, `turn.started/completed/failed`, `agent.delta/tool_use/tool_result/permission_requested/permission_resolved`, `interrupt.requested/acknowledged`, `policy.nudge/rewrite/block/approval_requested`, `plant.started/completed`, `sandbox.applied`, `process.started/exited`, `stdin.write`, `stdout.raw/line`, `stderr.raw/line`). This is, verbatim, the provider-independent activity model this review was asked to validate as a gap — it shipped 2026-05-26 and nothing today consumes it end-to-end inside an app.
- **Host-shaped**: `go-agent-wrapper` (`v0.1.0` tag from 2026-05-26, plus one further untagged commit on HEAD — "Strengthen headless wrapper core" — that a first pass of this review missed by reading the CHANGELOG instead of the live tree; corrected below) — composes all three tiers above into exactly the boundary stated above: `adapters.Adapter` (`Name`/`Describe`/`Resolve`, optional `RuntimeAdapter` for the agentkit-driven path), `plant.Planter` (files, `.mcp.json`, per-provider settings, hooks, a recovery prompt), `sandbox`, `policy`, `filters`, `activity` (bridges `llmtypes.StreamEvent` → `runtimeevents.Event`), and `wrapper.Wrapper` (`Run`/`SendInput`/`Stop`, per-session monotonic `TurnID` tracking, `interrupt.requested → session.Stop → interrupt.acknowledged`). Ships `adapters/claude`, `adapters/codex`, **and `adapters/opencode`** — three genuinely different runtime shapes (streaming-stdio, jsonrpc-stdio, http-sse) already proven under one `Adapter` contract, which is stronger evidence the abstraction is right than two similar shapes would have been. Its own README states the boundary almost word-for-word: "without prescribing prompt design, workflow logic, turn semantics, or agent cognition."

## Where Nanite actually stands

**As of the original review** (below), Nanite did not import `go-agent-wrapper` — `internal/runtime/agent` was a bespoke consumer of `agentkit` directly, with its own versions of most of what the wrapper offers:

- `agent.Mode` (`LongLived`/`OneShot`/`Resume`/`Subagent`/`Background`) — lifecycle policy. Correctly product-owned per the boundary above; not something a host should absorb, and this stays exactly where it is post-migration too.
- `Layout` (`bootdir.go`) — functionally overlapped `go-agent-wrapper`'s `plant.Planter`.
- `buildSandboxProfile` (`sandbox_profile.go`) — composed `go-sandbox.Profile` directly, same primitive `go-agent-wrapper/sandbox` wraps, just not through it.

**Current state**: this is now substantially migrated. `go-agent-wrapper v0.3.0` is a real Nanite dependency (`TASKS/agent-host-acp/03`); `Layout`'s bootdir planting now routes through `go-agent-wrapper`'s `Planter` (`04`); `buildSandboxProfile` routes through its `sandbox.Applier` (`05`, after an escalation found `sandbox.Applier` is a post-spawn attach mechanism, not a pre-spawn seam — resolved by folding into `06`'s scope); and `internal/runtime/agent`'s `Session` is now a thin wrapper around `*wrapper.Wrapper` for lifecycle (`06`, reviewed PASS) — `Session.Stop`, `SendInput`, and `Wait` all delegate to it directly (`internal/runtime/agent/manager.go`). `agent.Mode` and its lifecycle-decision call sites stay exactly where they were, as intended.

Tether and Torque have not adopted `go-agent-wrapper` — both still import `agentkit` directly. Sequencing their adoption is explicitly out of scope for `TASKS/agent-host-acp/` (Nanite's own tracker); see "What's genuinely still open" below.

## Audit findings on `go-agent-wrapper`

Evidence gathered during the original review, with each item's actual resolution noted:

- **Boundary fit is strong** and independently convergent with this doc's first-principles boundary. Confirmed correct in practice by the migration.
- **Version currency gap — resolved, and it turned out cheaper than estimated.** The original finding: `go-agent-wrapper`'s `go.mod` pinned `agentkit v0.1.0` while every real consumer ran `v0.3.0`/`v0.2.0`. **`TASKS/agent-host-acp/01`'s own investigation found the bump requires zero code changes** — `agentsessions` (the only agentkit subpackage `go-agent-wrapper` imports) is byte-identical across those tags; the renamed symbols this doc originally cited (`RenderFrontEnd`→`MissingPolicy`) live in `agentlaunch`, which `go-agent-wrapper` never imports. A pure version bump, not a compat pass. Landed.
- **Adapter coverage gap — resolved before this doc was even finalized.** Claude, Codex, and OpenCode were already covered by the time this section was corrected mid-review (the "first pass missed the live tree" note above). The only real gap was an ACP adapter — see [17-acp.md](17-acp.md) and Phase 3-4 below.
- **`Descriptor.Runtime` conflates protocol and transport — split, landed.** `TASKS/agent-host-acp/02` implemented the `Protocol`/`Transport` split described below. Internal to the host descriptor; no `agents.runtime_kind`/DB change, as this doc originally specified.
- **Real-interrupt ceiling — corrected, and narrower than even the corrected version first stated.** This doc originally claimed Claude's Agent SDK (`Query.interrupt()`) and Codex's `app-server` (`turn/interrupt`) both expose native interrupt mechanisms already reachable through the stack. **That was wrong in an important way**: those are real SDK-documented surfaces, but neither is actually called by `agentkit/agentsessions`, `go-agent-wrapper`, or Nanite's prior bespoke code — both providers get stdin-close + SIGTERM/SIGKILL only, at the process level. **Only OpenCode's `Stop()` calls a real native abort endpoint** (`/global/dispose`, `/session/{id}/abort`) — confirmed directly against the live code in `TASKS/agent-host-acp/README.md`. This is a carried-forward, known limitation (Nanite's own `internal/service/agent_deps.go` already had a TODO on it independently), not a regression, and not something the host migration itself was expected to fix — the host's job is to correctly *call* `Stop()` (which it now does, see below), not to grant an interrupt capability the underlying provider process doesn't expose.
- **`Session.Stop()` now genuinely works.** `internal/runtime/agent/manager.go`'s `Session.Stop(ctx)` calls `wr.Stop(ctx)` — go-agent-wrapper's real implementation: `interrupt.requested` → the underlying agentkit session's Stop (stdin close, grace period, SIGTERM/SIGKILL escalation) → `interrupt.acknowledged`. This is real, deterministic termination, landed via `TASKS/agent-host-acp/06`. See [19-api-cli-runtime-parity.md](19-api-cli-runtime-parity.md) for the distinct, easily-conflated concept of cancelling one in-flight turn without stopping the session.
- **Zero production mileage — no longer true.** `Wrapper.Run`'s dispatch path is now live in Nanite via the `06` migration (reviewed PASS, two non-blocking findings addressed). Real session-volume validation is `TASKS/agent-host-acp/07`'s job (dogfeed/validate).

## What's genuinely still open

- Whether `go-agent-wrapper` becomes the single host for Nanite+Tether+Torque together (matching the draw that motivated building it), and in what order across the three apps, is still open — `TASKS/agent-host-acp/` explicitly scopes this out as Nanite-only; Tether/Torque adoption is a separate, not-yet-made portfolio call.
- ACP client abstraction and native/bridge adapters (Phases 3-4 of `TASKS/agent-host-acp/`) — in progress; the bridge-library pick (`12`) is deliberately escalation-gated, not resolved here.
- Whether an in-process fs/terminal server is actually needed for any ACP-driven agent (`TASKS/agent-host-acp/16`'s audit) — open, by design; building one (if needed) is new scope for a later pass, not something silently absorbed into this batch.

## What's cut

Attach/detach to a CLI process launched outside a Hollis app (e.g., a bare `claude` run from a terminal) — no code anywhere in the portfolio supports discovering or attaching to such a process, and it's explicit, low-priority scope for the apps that launch their own agents 99% of the time. Not in scope for this doc or its planner.
