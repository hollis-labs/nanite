# Agent Host

## The problem this names, not invents

Nanite, Tether, and Torque each launch CLI agents (Claude, Codex, OpenCode) almost identically — spawn a subprocess, own its stdio, stage a boot directory, apply an OS sandbox, compose env, and turn whatever comes back over the wire into something a product can react to. This doc doesn't propose building that layer. It names the boundary that layer must have, audits the closest existing candidate against it, and — per operator alignment on this review — treats adopting that candidate as the working direction. The migration's shape (order, blast radius) is left to planning; the destination isn't a genuine toss-up.

## The boundary

A host owns: process spawn/supervision, stdio ownership (parsing whatever wire protocol flows over it), boot-dir/workspace staging and file planting (`CLAUDE.md`/`AGENTS.md`/`.mcp.json`/provider settings/hooks), OS-level sandbox application, env composition, the protocol adapter (bytes on the wire ↔ a normalized event stream, commands back down), realtime activity normalization (one event vocabulary regardless of provider), cooperative-cancellation signaling, and process-tree cleanup.

A host does not own: why the agent is running, session/task/team semantics, persistence schema, lifecycle policy (when to fire the first turn, when to stop, whether to attach a supervisor), permission/gate business rules, chat/harness turn-loop mechanics, or product identity (agent roles, skills content). This is the same line this codebase already draws elsewhere — "abstract the intent, not the capability away" and "prefer composition over a feature-specific mechanism" ([00-overview.md](00-overview.md)) — applied to the launch layer instead of the tool/memory layer.

The same split applies one level down, inside enforcement mechanics: **the host owns the interception mechanism (observe a command/tool-call, ask a policy engine, apply the verdict); the product owns the actual policy (which rule fired, what it means, who's allowed to do what).** `go-agent-wrapper`'s `policy/` package already draws this line correctly in code, not just in principle — `policy.Engine.Decide` is the mechanism the host runs at every interception point, but `policy.Store` (the rule backing: YAML, SQLite, a central admin service, whatever an app wants) is explicitly "app-provided... the wrapper does not own storage." Worth stating as an explicit rule here rather than leaving it implicit: if a future change ever moved actual business rules (e.g., "engineers cannot merge without review") into the host itself rather than into an app-supplied `Store`, that would violate this boundary the same way a lifecycle-policy leak would.

## What already exists

This isn't greenfield. The portfolio already has four tiers:

- **Primitive**: `go-providers` (`CLIAdapter`: `Name`/`BuildArgs`/`ParseLine`/`Detect`, concrete Claude/Codex/OpenCode adapters — file names still carry a `pty_*` naming fossil mid-scrub, same pattern flagged in [02-agent-launching.md](02-agent-launching.md)), `go-sandbox` (`Profile`+`Apply`, macOS `sandbox-exec` / Linux `bwrap`), `go-runner` (spawn+sandbox+parse composition, emits only raw process-lifecycle events — deliberately opaque to app vocabulary).
- **Composition**: `agentkit` (the 2026-05-26 consolidation of `go-agent-context`/`go-agent-launch`/`go-agent-sessions`/`go-agent-runtime`/`go-agent-broker`) — `agentlaunch`'s `LaunchPlan → CompiledLaunch → PreparedLaunch` pipeline and bootdir materialization, `agentsessions`' `Session` (`Wait`/`Stop`/`SendInput`/`Resize`/`Health`) over PTY/streaming-stdio/jsonrpc-stdio/serve-http backends, `agentcontext`'s typed slot-resolver boot-prompt assembly. **Nanite already depends on this directly** — `internal/runtime/agent/*.go` imports `agentkit/agentsessions`, `agentkit/agentlaunch`, `agentkit/agentcontext`, `agentkit/agentruntime/runtimekind` at v0.3.0, as does `internal/recovery/broker`. So does Tether, Torque, agent-mux, clockwork-manifold, and Hadron.
- **Normalization**: `go-runtime-events` — a portfolio-wide typed vocabulary (`session.ready/idle/processing/heartbeat`, `turn.started/completed/failed`, `agent.delta/tool_use/tool_result/permission_requested/permission_resolved`, `interrupt.requested/acknowledged`, `policy.nudge/rewrite/block/approval_requested`, `plant.started/completed`, `sandbox.applied`, `process.started/exited`, `stdin.write`, `stdout.raw/line`, `stderr.raw/line`). This is, verbatim, the provider-independent activity model this review was asked to validate as a gap — it shipped 2026-05-26 and nothing today consumes it end-to-end inside an app.
- **Host-shaped**: `go-agent-wrapper` (`v0.1.0` tag from 2026-05-26, plus one further untagged commit on HEAD — "Strengthen headless wrapper core" — that a first pass of this review missed by reading the CHANGELOG instead of the live tree; corrected below) — composes all three tiers above into exactly the boundary stated above: `adapters.Adapter` (`Name`/`Describe`/`Resolve`, optional `RuntimeAdapter` for the agentkit-driven path), `plant.Planter` (files, `.mcp.json`, per-provider settings, hooks, a recovery prompt), `sandbox`, `policy`, `filters`, `activity` (bridges `llmtypes.StreamEvent` → `runtimeevents.Event`), and `wrapper.Wrapper` (`Run`/`SendInput`/`Stop`, per-session monotonic `TurnID` tracking, `interrupt.requested → session.Stop → interrupt.acknowledged`). Ships `adapters/claude`, `adapters/codex`, **and `adapters/opencode`** — three genuinely different runtime shapes (streaming-stdio, jsonrpc-stdio, http-sse) already proven under one `Adapter` contract, which is stronger evidence the abstraction is right than two similar shapes would have been. Its own README states the boundary almost word-for-word: "without prescribing prompt design, workflow logic, turn semantics, or agent cognition."

## Where Nanite actually stands

Nanite does **not** import `go-agent-wrapper`. `internal/runtime/agent` is a bespoke consumer of `agentkit` directly, and it has already built its own versions of most of what the wrapper offers:

- `agent.Mode` (`LongLived`/`OneShot`/`Resume`/`Subagent`/`Background`) — lifecycle policy. Correctly product-owned per the boundary above; not something a host should absorb.
- `Layout` (`bootdir.go`: `Setup`/`Populate`/`RegenerateSystemPromptSlot`/`AmendEnv`/`SpawnWorkdir`/`BootPrompt`/`BootMode`, implemented per-provider in `bootdir_claude.go`/`bootdir_codex.go`/`bootdir_opencode.go`) — functionally overlaps `go-agent-wrapper`'s `plant.Planter`.
- `buildSandboxProfile` (`sandbox_profile.go`) — composes `go-sandbox.Profile` directly, same primitive `go-agent-wrapper/sandbox` wraps, just not through it.

Tether and Torque are in the same position — both import `agentkit` directly; neither imports `go-agent-wrapper`. The "~99% identical launch pipeline" this review set out to validate is real, but it's duplicated one layer *below* where `go-agent-wrapper` sits — at the agentkit-consumption layer, across at least six apps. `go-agent-wrapper` was built to collapse exactly that duplication and has zero adopters to date.

## Audit findings on `go-agent-wrapper`

Evidence gathered during this review. Boundary fit is strong enough, and the alternative (retrofitting Tether/Torque onto Nanite-shaped bespoke code) weak enough, that **adopting `go-agent-wrapper` as the shared host is the working direction**, not a genuine toss-up left to the planner. What follows is the concrete gap list a migration has to close — narrower than a first read suggests:

- **Boundary fit is strong** and independently convergent with this doc's first-principles boundary.
- **Version currency gap, and it's bounded, not sprawling.** Its `go.mod` pins `agentkit v0.1.0`; every real consumer (Nanite, Torque) already runs `v0.3.0`, and Tether runs `v0.2.0` — both releases landed the same day `go-agent-wrapper` shipped (2026-05-26), then nothing moved for three months (matches the operator's own account of the gap). The other four libs it depends on (`go-providers`, `go-sandbox`, `go-llm-types`, `go-runtime-events`/`go-harness-filters`) are already at their latest tags — only `agentkit` (2 releases behind, with renamed public symbols — `RenderFrontEnd`→`MissingPolicy` etc., see `agentkit/CHANGELOG.md`) and `go-runner` (1 minor behind, `v0.5.0` vs. latest `v0.6.0` — a gap shared by every app in the portfolio, not `go-agent-wrapper`-specific) need bumping. A compat pass, not a rewrite.
- **Adapter coverage gap is smaller than a first read suggested**: Claude, Codex, and OpenCode are already covered (see above) — verified directly against the current adapter source, not the CHANGELOG. The only real gap is an ACP adapter — see [17-acp.md](17-acp.md).
- **`Descriptor.Runtime` conflates protocol and transport.** Confirmed in the actual code: the field is a bare string carrying values `"pty"`, `"streaming-stdio"`, `"jsonrpc-stdio"`, `"http-sse"` — mixing "what shape the wire protocol takes" (streaming NDJSON vs. JSON-RPC vs. plain PTY bytes) with "what medium carries it" (stdio vs. HTTP+SSE). That collapse was harmless while every existing runtime happened to imply a unique transport. ACP breaks that assumption — the same protocol (ACP) can run over stdio or TCP, and a given provider's *native* protocol (Codex's `app-server`, Claude's stream-json) is a separate axis from ACP entirely, not a value on the same enum. Before the ACP adapter lands, `Descriptor` should split into an explicit `Protocol` (`claude-stream-json` / `codex-app-server` / `opencode-native` / `acp`) and `Transport` (`stdio` / `tcp` / `http-sse` / `pty`) rather than one overloaded `Runtime` string. This is internal to the host descriptor — no `agents.runtime_kind`/DB change implied, see [17-acp.md](17-acp.md) for how this interacts with ACP specifically.
- **Real-interrupt ceiling is narrower than it first looked.** `Wrapper.Stop`'s `interrupt.requested`/`acknowledged` pair is a cooperative signal at the wrapper layer, and whether it does anything real depends on whether the underlying provider's own protocol exposes a genuine interrupt — which, per [17-acp.md](17-acp.md)'s revalidation, both Claude Code (Agent SDK `Query.interrupt()`) and Codex (`app-server`'s `turn/interrupt`) already do. The open question is whether `go-agent-wrapper`'s `Session.Stop()` for each runtime actually calls that native mechanism today, or just closes stdin/signals the process — that's a concrete thing to verify against the current code, not assume either way.
- **Zero production mileage**: no app runs it. `Wrapper.Run`'s dispatch path, the activity bridge, and TurnID tracking are unvalidated against real session volume or against `internal/recovery/broker`'s existing agentkit-based classifier/dispatch logic, which needs auditing first (see below).

## What's genuinely still open

- Migrating `Mode`/`Layout`/`buildSandboxProfile` onto `go-agent-wrapper`'s `Adapter`/`Planter`/`sandbox` seams is real work, but the direction is set — this isn't left as an adopt-vs-not fork for the planner.
- **`internal/recovery/broker`'s existing dependency on `agentkit` is the first thing a migration should audit** — it has real production mileage on recovery paths and is the piece most likely to break or need rework, ahead of anything else in `internal/runtime/agent`.
- Whether it becomes the single host for Nanite+Tether+Torque together (matching the draw that motivated building it), and in what order across the three apps, is still open — this doc doesn't sequence that; the planner does.
- The `Protocol`/`Transport` split above should land before or alongside the ACP adapter (17-acp.md) — both need a home in `adapters/`, additive work, not blocking adoption of what already exists.

## What's cut

Attach/detach to a CLI process launched outside a Hollis app (e.g., a bare `claude` run from a terminal) — no code anywhere in the portfolio supports discovering or attaching to such a process, and it's explicit, low-priority scope for the apps that launch their own agents 99% of the time. Not in scope for this doc or its planner.
