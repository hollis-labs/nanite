# API / CLI Agent Runtime Parity

## Where Nanite already stands

This is largely already true, not something to build. `generateResponse` (`internal/service/chat_generate.go`) is one shared turn loop for every agent regardless of `agents.runtime_kind` — the fork between CLI-hosted and direct-API execution is a single two-armed `if` (`driveBootSession` vs. `provider.StreamChat`), both producing the identical `<-chan llmtypes.StreamEvent` signature, consumed by one switch statement with no `runtime_kind` branching inside it. `driveBootSession`'s own doc comment calls itself "the long-lived-PTY counterpart to `provider.StreamChat`" — this parity was the explicit design intent when it was written, not a gap discovered now. Tool-call handling (`preCheckTools` → `executeToolBatch` → `postProcessToolResults`) runs unconditionally with no `runtime_kind` branch at all; the only CLI-specific code anywhere in that path is a UI presence side-channel (`BroadcastPresence` gated by `chat.IsCLIProvider`, for GUI activity indicators), not tool-execution logic. The plugin filter chain documented in [09-plugin-system.md](09-plugin-system.md) (`FilterUserMessage`→`FilterSystemPrompt`→`FilterContextWindow`→`FilterToolResult`→`FilterAssistantResponse`→`FilterEnvelopeData`) sits inside this same shared loop, so it already applies uniformly regardless of entry point.

The remaining work is smaller and more precise than "unify the runtimes": keep the vocabulary precise (two distinct event tiers, and two distinct cancel/stop scopes, below — both easy to conflate, both real once disentangled) as host-layer work (16-agent-host.md) lands on top of an already-unified harness, rather than re-solving something that's already solved.

## Two event vocabularies, at different altitudes — don't conflate them

The source material's "normalize at the Nanite runtime abstraction and normalized event vocabulary" reads as one thing to build. It's actually two, already distinct, at different layers:

- **`llmtypes.StreamEvent`** (go-llm-types) — the harness-layer vocabulary. Already shared between CLI and API paths today, in production, feeding `generateResponse`'s one switch statement. This is the parity the source material is largely asking for, and it already exists.
- **`runtimeevents.Event`** (go-runtime-events) — the host/observability-layer vocabulary documented in [16-agent-host.md](16-agent-host.md) (`session.ready/idle/processing`, `turn.started/completed/failed`, `interrupt.requested/acknowledged`, etc.).

**Current state, precisely**: since `TASKS/agent-host-acp/06` migrated CLI session lifecycle onto `go-agent-wrapper`, `wrapper.Wrapper.Run` now consumes the raw provider stream internally and re-emits a normalized `runtimeevents.Event` stream for every CLI-hosted session. Nanite's `runtimeEventSink` (`internal/runtime/agent/wrapper_sink.go`) is the consumer — but its job is a **reverse translation back down** to the older `llmtypes.StreamEvent`/`provider.EventsCallback` shape, specifically so `internal/service/agentEventBridge`'s existing SSE-emission code needs zero changes. So: the richer host vocabulary now genuinely flows *through* Nanite's CLI path today, but nothing yet exposes it *as itself* — it's collapsed straight back down to the narrower harness-layer shape it's translated from. That's a deliberate, correct migration shim, not a gap — but it does mean richer host-layer signals (e.g., `interrupt.requested`/`acknowledged`'s distinct request/ack pairing, or tool-call lifecycle states finer than `llmtypes.StreamEvent` models) aren't visible to any GUI or plugin yet. Surfacing them as their own feed (rather than always downgrading) is a real future option, not something this doc resolves.

These don't merge into one vocabulary and shouldn't be designed to. The API path has no equivalent host layer to add, because there's no subprocess for a host to supervise; its `llmtypes.StreamEvent` stream already *is* its full observable surface. Parity at the harness layer does not imply parity at the host layer, and it shouldn't — a host only has work to do where there's a process to host.

## Two genuinely different operations sharing confusable names: Turn.Cancel and Session.Stop

This needed a direct correction mid-review, and the correction is worth recording precisely, because "cancel" and "stop" and "interrupt" all get used across four different layers here, and it's easy — this review did it — to conflate two of them into a false "gap."

**`CancelActiveGeneration(sessionID)`** (`internal/service/chat.go`) is a **turn-scoped** operation: it cancels the `ctx` bound to the current turn's stream, which for CLI-hosted agents (`internal/service/chat_boot_drive.go`) does exactly one thing — `s.agentEventBridge.SetPerSessionRouter(sessionID, nil)`, unbinding Nanite's listener for that turn. It deliberately does not touch the underlying process. **This is correct, not a bug**: a long-lived CLI-hosted agent is a persistent process across many turns, and canceling *this turn's* display shouldn't kill a process the user may want to send another message to next. Call this concept `Turn.Cancel` going forward (a rename worth making to `CancelActiveGeneration`, alongside this doc, not as a code change this doc makes itself) — the name should carry its scope the same way `Session.Stop` already carries its own.

**`Session.Stop(ctx)`** (`internal/runtime/agent/manager.go`) is a **session-scoped** operation: it terminates the whole runtime — `wr.Stop(ctx)` (go-agent-wrapper) emits `interrupt.requested`, calls the underlying agentkit session's Stop (stdin close → grace period → SIGTERM/SIGKILL escalation), then emits `interrupt.acknowledged`. This is real, working, deterministic process termination, landed via `TASKS/agent-host-acp/06`. It is called from explicit session-termination flows (reboot, cleanup, recovery), not from per-turn cancellation.

**What's real and carries forward, correctly scoped this time**: the interrupt-*fidelity* limitation already in [17-acp.md](17-acp.md) and [16-agent-host.md](16-agent-host.md) — neither Claude's nor Codex's `Stop()` reaches a true cooperative mid-generation interrupt today (process-kill only); only OpenCode's does. That's a `Session.Stop()`-level, provider-dependent limitation, unrelated to whether `Turn.Cancel` is wired correctly (it is).

**Naming recommendation**: rename `CancelActiveGeneration` to make its scope explicit in the name. [22-turn-vs-run.md](22-turn-vs-run.md) resolves the exact target name — `Run.Cancel`, not the `Turn.Cancel` this doc originally proposed — once the Turn/Run split (below) gave "Turn" a narrower, correct meaning of its own. This is exactly the kind of thing worth a `GLOSSARY.md` entry disambiguating the related-but-distinct terms already live in this codebase: `Run.Cancel` (stop listening to the current Run, harness-layer), `Session.Stop` (terminate the whole runtime, host-layer), `interrupt.requested`/`acknowledged` (the host-layer event pair `Session.Stop` emits while it works), and ACP's `session/cancel` (a wire-protocol method name that, despite saying "session," is spec'd as Run-scoped — it should map to `Run.Cancel`, never to `Session.Stop`, when the ACP client abstraction implements it; see 17-acp.md).

## ACP and Snapshots — already covered, not re-litigated here

The source material's ACP section ("ACP is a swappable client implementation under the host/runtime abstraction... keep protocol and transport conceptually separate") and its Host-boundary line (which lists snapshots alongside process tree, stdio/protocol, sandbox, and cleanup) restate decisions already made in [16-agent-host.md](16-agent-host.md), [17-acp.md](17-acp.md), and [18-filesystem-snapshots.md](18-filesystem-snapshots.md). Nothing here supersedes those; this doc's contribution is scoping how the *harness* layer (already parity'd, across both runtimes) relates to the *host* layer (executing now under `TASKS/agent-host-acp/`, per [16-agent-host.md](16-agent-host.md)'s status note), not re-deciding ACP or snapshots.

## Turn vs. Run — resolved, see 22-turn-vs-run.md

Confirmed directly: Nanite's harness genuinely conflated "one model invocation" with "the full agentic loop until completion" — `internal/service/chat_loop_state.go`'s `MaxTurns`/`TerminationMaxTurns`/`ls.iteration` vocabulary named the *whole* iterating loop "Turn," with no separate name for a single model call. This was real, not hypothetical, and is now resolved as its own topic: [22-turn-vs-run.md](22-turn-vs-run.md) defines **Turn** (one model call) and **Run** (the composing loop), confirms the conflation's real cost (Agent Workflows built a second, duplicate loop to get Turn-level control rather than reuse), and settles the naming (`Run.Cancel`, not `Turn.Cancel` — see the naming recommendation above, updated accordingly). Both the API and CLI paths shared the same (conflated) loop structure before this resolution and will share the same fix after it — this was a parity-preserving change by construction, not a new divergence to manage.

## Backend wire interception — cut

No evidence found anywhere in the codebase or docs of existing raw-provider-API wire interception, or any stated intent to build it. Supported configuration injection (bootdir provider-config, `.mcp.json`, hooks) and documented protocol transformation (the CLI adapters' own `BuildArgs`/`ParseLine`) are what already exists and are sufficient — API runtimes already have full prompt/request control without needing to intercept their own wire format, and CLI harnesses expose adequate configuration surfaces already. Not a target. (This was a grep-depth check, not an exhaustive audit — recorded as "no evidence found," not "proven absent.")

## What's genuinely still open

- The `CancelActiveGeneration`→`Turn.Cancel` rename above is a recommendation, not executed by this doc — real implementation work for whoever picks it up next (the `GLOSSARY.md` disambiguation entry is already in place, ahead of the actual rename).
- Whether the host-layer `runtimeevents.Event` vocabulary ever gets surfaced as its own richer feed (rather than always reverse-translated back to `llmtypes.StreamEvent` for compatibility) — real future option, not resolved here.
- Provider-level interrupt fidelity (Claude/Codex process-kill-only vs. OpenCode's real native abort) — carried forward as a known, accepted limitation per [16-agent-host.md](16-agent-host.md)/[17-acp.md](17-acp.md); not this doc's to fix.
- Turn vs. Run (above) — resolved in [22-turn-vs-run.md](22-turn-vs-run.md); the actual harness refactor and `workflow_step_executor.go` consolidation it enables remain unbuilt.
