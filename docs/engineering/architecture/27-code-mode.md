# Code Mode

A follow-up architecture topic from the harness audit: sandboxed deterministic execution, not an agent mode — aggregate/transform high-volume tool data outside model context, returning only useful structured results. Proposed uses: MCP aggregation, durable periodic computation, workflow steps, reflex preprocessing, research normalization.

**Approved for implementation, 2026-08-21** — a follow-up research pass, dispatched after this doc's original "no current pressure" framing was questioned, found the real blocker isn't the non-agentic-wiring question below at all: it's that `tool_call()` doesn't work for *any* caller in production today (see "The actual gap," below). Fixing that, plus the workflow and reflex integration it unblocks, is real, scoped, sequenced work, tracked under `TASKS/code-mode/` (see that folder's `README.md` for the task breakdown).

## The actual gap: unwired in production, not just non-agentic

A dedicated research pass (2026-08-21) into why the non-agentic wiring below was "undecided" found something more load-bearing than a scoping question: **`PythonPermChecker`/`PythonDispatcher` — the fields that bridge the sandbox's `tool_call()` helper to the real permission engine and tool dispatcher — are struct fields on `SelfToolsTransport` (`internal/selftools/self_tools_transport.go:198-208`) that are never assigned outside test code.** Grepped `cmd/nanite/main.go` and `internal/service/container.go` in full: neither field is ever set in the production wiring path — only `self_tools_python_test.go:508-509` sets them. In `pumpToolCalls` (`self_tools_python.go:414-454`), a nil `perm` silently skips the permission check entirely, and a nil `dispatcher` returns `"no tool dispatcher configured"` for every `tool_call()`. So this doc's earlier claim (below) that the sandbox "bridges **directly to the real permission engine and tool dispatcher**" describes the code path's design correctly, but not the running system: right now, any script that calls `tool_call()` — whether invoked by an LLM turn, a workflow, or a reflex — either fails outright or silently bypasses permission checks. This is unconditional on caller type and predates the non-agentic-wiring question entirely.

The same research pass also closed out the non-agentic-wiring question itself, once the real blocker was found: it isn't an identity/context-threading gap. `agentworkflow.StepExecutor.ExecuteToolStep` (`interfaces.go:38`, impl `workflow_step_executor.go:102-115`) already calls any named tool generically via `e.tools.Execute(ctx, req.AgentID, req.Tool, req.Args)` and `ToolStepRequest` already carries `AgentID` (`types.go:177-178`) — no new `StepKind` is needed to reach `python_run` from a workflow step. The one real gap there: `mcp.WithSessionID`/`WithCallerProfile` are stamped into context only by the LLM-turn loop (`chat_tool_executor.go:354,369`), never by `ExecuteToolStep`, so a workflow-triggered call collapses onto the shared `"ptc-default"` pseudo-session — a small, well-scoped session-stamping fix, not new plumbing. Reflexes are similarly close: `Executor.Apply(ctx, reflex, state)` (`executor.go:44-138`) already has `state.SessionID` and `reflex.AgentID` available at exactly the point a new action kind's hook would fire (`engine.go:142,145-146`) — adding a `run_python_sandbox` action kind is a `HookFunc` + `Executor` field + `case` branch, the same shape as existing kinds (`Halt`/`Schedule`/`SendMessage`, `executor.go:12-27`).

## Confirmed: designed as the real mechanism, not a lesser cousin of it — but not fully wired live

`internal/selftools`'s `python_run` self-tool (`RunPythonSandbox`) *is* Code Mode, by design. It executes a script in an isolated, resource-capped (10s/256MB default, 60s/1GB ceiling), network-denied subprocess. The `tool_call(name, args)` helper available inside the sandbox is designed to bridge **directly to the real permission engine and tool dispatcher** — every call intended to go through full permission enforcement, no security hole opened by design. Critically: intermediate tool-call results never touch the LLM's context and never cost a model turn — only the script's final `result`/`stdout` re-enters the conversation. That's the follow-up topic's core claim precisely (work happens outside the main agent's context; only structured results return), not a weaker version of it dressed up as a match. **Correction (see "The actual gap," above): that bridge is not actually wired in production today** — `PythonPermChecker`/`PythonDispatcher` are never assigned outside test code, so the permission-enforcement half of this claim doesn't hold for the running system yet. `TASKS/code-mode/` fixes this.

It's available broadly, not gated to one role: per its own tool-definition doc comment, reach for it is governed by the calling agent profile's tool permissions and a dev-mode gate — "Chat, Planner, Worker, or a custom agent profile" can all call it.

## Not wired to non-agentic callers, either — until this batch lands

`python_run` is reachable today only as an LLM-invoked self-tool — an agent has to decide, mid-turn, to call it. Confirmed by grep: `internal/service/workflow_step_executor.go` and `internal/agent/reflexes/*.go` contain **zero** references to `internal/selftools`. So the follow-up topic's other proposed use cases — durable periodic computation, workflow steps, reflex preprocessing — running Code Mode without an LLM in the loop deciding to invoke it, aren't wired yet. See "The actual gap," above, for why this turned out to be a small, near-free addition once the production wiring bug is fixed, not a standalone architectural lift.

## What's genuinely still open

Everything named above (the production wiring fix, workflow session-stamping, and the `run_python_sandbox` reflex action kind) is now approved and tracked under `TASKS/code-mode/` — nothing about *whether* to build these remains open. Real implementation-time detail not resolved here: the exact `run_python_sandbox` reflex action config shape, and whether `ExecuteToolStep`'s session-stamping fix should mint a per-`WorkflowRun` synthetic session or reuse the run's own ID as the session ID (an implementation-time call for the planning pass in `TASKS/code-mode/README.md`, not decided by this doc).
