# CW-20260815-0026: Fix Silent Agent Resolution Fallback

## Problem
When users ran `nanite chat -agent worker`, the CLI would silently fall back to the Default agent if resolution failed, providing no error feedback. This was because:

1. The CLI passed the raw user input (e.g., "worker") to the API
2. The API stored it directly in the DB without validation
3. Later, `ResolveForSession` tried to load it by ID, failed, and silently fell back to "file-default"

## Root Cause
The `-agent` flag accepted both IDs and slugs, but:
- File-based agents like "worker" have ID format `file-{slug}` (e.g., `file-worker`)
- When "worker" was passed, it was stored as-is in the DB
- The `Get(ctx, "worker")` call in `ResolveForSession` failed because "worker" isn't a valid ID
- The code then fell back to the default agent without surfacing an error

## Solution
Modified `internal/api/harness_v1.go` line ~243 to:

1. **Resolve agent ID/slug to canonical ID before storing**
   - Try `Get(ctx, req.AgentID)` first (in case it's already an ID)
   - Fall back to `GetBySlug(ctx, req.AgentID)` if Get fails
   - Return 400 Bad Request if both fail

2. **Fail loudly on resolution failures**
   - Error message: `agent "{slug}" not found`
   - HTTP 400 instead of silently creating session with default agent

## Related Code Paths

### ResolveForSession (internal/service/agent.go:244-254)
The silent fallback logic at line 248-254 remains unchanged by design:

**Before fix:**
- Invalid agent ID stored → Get fails → silent fallback (BAD: hides CLI errors)

**After fix:**
- Only valid IDs stored at session creation → Get should succeed
- Fallback remains for edge cases (agent deleted after session creation, DB corruption, etc.)
- This is now a legitimate error recovery path, not a bug-hiding mechanism

The fix moves validation to the entry point (session creation API) rather than at resolution time.
